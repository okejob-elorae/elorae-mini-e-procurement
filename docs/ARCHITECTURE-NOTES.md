# Architecture notes — landmines worth flagging

The detail behind the landmine index in `AGENTS.md`. Read the entry for whatever surface you are about to touch: each one records a mistake that already cost someone time, and several encode prod-measured findings. Split out of `AGENTS.md` on 2026-08-25 so 6k tokens of it stop riding along in every session; the text is unchanged. When a change makes an entry wrong, fix it here in the same session — and update the matching one-liner in `AGENTS.md` if the trigger itself moved.

- **Field sales (putus/konsi) is PER-VARIANT as of PR #144 (2026-07-17) — D15 SUPERSEDED.** `InventoryValue` is keyed `(itemId, variantSku)` and Jubelio-ingested variant items are stored entirely per-variant (real `variantSku` rows, no pooled row) — prod-confirmed. The PWA catalog exposes per-variant availability (`CatalogItem.variants[]`); a variant sheet picks variants; putus/konsi order lines carry the **real** `variantSku`; reserve/consume already keyed per line → per-variant `StockReservation`. **Min-qty aggregates per item**; **promos aggregate per item then pro-rate** across variant lines via shared `applyItemAggregatedPromos` (writer + preview → quote == recorded order). **Simple items (no `Item.variants`) stay item-level** (`variants: []`, inline stepper, cart `variantSku ""`, null/"" tolerant lookup). **Canvassing (van load/sale/reconcile) is ALSO per-variant (Track B, PR #146):** `VanStock`/van docs keyed per `variantSku`, backoffice load form picks per-variant (item block), PWA van sell groups by item + variant sheet, sale/reconcile stamp the variant label into `productName`; no schema migration; van stock has no reservation dimension. See `docs/BOUNDARY.md` D15. Caveat: a variant item restocked via ERP GRN/production writes a `null` pooled row the per-variant sale won't see (Jubelio feeds them per-variant, so rare). **A strict `""`-keyed lookup forks a phantom row** — `calculateMovingAverage`'s strict `""` key did exactly that on the canvassing reconcile path (caught and fixed pre-merge; see `docs/EPIC-STATUS.md` sub-8), and the same strict lookup in `reconciliation-runner.ts` was fixed on `PR #311` and now reads through the shared `findExistingInventoryValueRow`, but NINE other strict-spelled sites are still live and unfixed (see `docs/FOLLOWUPS.md` § Inventory for the current swept list). Note the inverse also holds: variantless `InventoryValue` rows key on `null`, while simple-item carts and `VanStock` deliberately key `""` — so an id may legitimately arrive as either, and every lookup must be OR-tolerant (`OR: [{ variantSku: null }, { variantSku: "" }]`) rather than "corrected" to one spelling.
- **Putus stock now leaves at DELIVERY, not at approve (PR #229, merged 2026-08-09).** Approve is paperwork: it no longer consumes stock and no longer writes `SalesHistory`. A putus order ships in parts through `FieldSalesDelivery`/`FieldSalesDeliveryLine` (`recordFieldSalesDelivery` in `apps/web/lib/field-sales/delivery/writer.ts`), each delivery consuming its own slice via `consumeFieldSalesOrderPartial` and writing its own `SalesHistory` rows keyed by the delivery `docNo` (an order number would collide on the second delivery of the same variant). `FieldSalesOrder.deliveryStatus` (PENDING/PARTIAL/DELIVERED/CLOSED) plus `FieldSalesOrderLine.deliveredQty`/`cancelledQty` track progress; `closeFieldSalesOrderRemainder` cancels every still-open line at once, releases the leftover reservation and stamps `closedAt`/`closedById`/`closeReason`. **`FieldSalesDelivery.docNo` is NOT always `DLV/`-prefixed** — the backfill migration gave every pre-existing approved putus order one full delivery carrying the ORDER number, so never pattern-match the prefix. Order/line discounts are pro-rated per delivery and the closing delivery absorbs every remainder, including residue stranded on a line that finished in an earlier delivery, so the deliveries sum back to the order total exactly. Konsi never delivers (transfer is still recorded at approve). *(Superseded for konsi — konsi stock now moves at delivery-shipment completion, one transfer per shipment; see the konsi delivery-completion entry at the end of this file.)*
- **Every nota tagihan carries exactly one `TaxInvoice` row (PR #239, merged 2026-08-13).** `TaxInvoice` is a satellite table 1:1 with `FieldSalesDelivery` (`deliveryId @unique`, no columns added to the delivery), created inside `recordFieldSalesDelivery`'s existing serializable transaction and backfilled for every pre-existing delivery — so `PENDING` has exactly one spelling and the queue is keyed on the nota being ISSUED, never on anyone printing it. Statuses are `PENDING`/`CREATED` (needs a faktur number)/`NOT_REQUIRED` (needs a reason), and every transition is reversible and writes its `AuditLog` row (with `changes` + `reason`) **in the same transaction as the update** — the row itself is last-write-wins, so the audit trail is the only surviving record of a superseded faktur number. Finance works the queue at `/backoffice/finance/faktur-pajak` gated on `tax_invoices:view`/`tax_invoices:manage`. First print of a nota tagihan stamps `notaPrintedAt` through an atomic compare-and-swap (`updateMany … where notaPrintedAt: null`) and fans out a `TAX_INVOICE_PENDING` notification only when the affected count is 1; reprints still audit but never re-notify. Writers in `apps/web/lib/tax-invoices/`, print action in `apps/web/app/actions/field-sales-deliveries.ts`. **The migration declares NO foreign key** (`relationMode = "prisma"`), so a `TaxInvoice` can outlive its delivery — the queue query skips orphans rather than letting one dangling row blank the whole page. *(Widened since: a `TaxInvoice` — like a `Receivable` — may now hang off a `KonsiSellThrough` report instead, so it is 1:1 with EITHER a delivery or a report, never both; every nota tagihan still carries exactly one. See the receivable-source entry at the end of this file.)*
- **An approving admin can ADD never-sent products to a konsi transfer (PR #242, merged 2026-08-13).** `listKonsiSuggestions` (`apps/web/lib/field-sales/queries.ts`) lists goods never sent to this store — exclusion is **item-level** (`sentItemIds`, any variant ever on a non-rejected, not fully cancelled konsi line kills the whole item, matching the writer's `ALREADY_SENT` check) while each surviving item expands to **one row per real `InventoryValue` variant**, because availability and the writer's `addedLines` are both per-variant; a `null`/`""` dual row dedupes to one suggestion at the **minimum** available (the writer reserves against a single findFirst row, so summing would offer more than it can honor). The panel (`KonsiSuggestionsCard`) stages additions client-side and `approveFieldSalesOrderAction` applies them **inside the approve transaction** — validated (unknown item, no inventory row, bad qty, duplicate, already-sent, not-konsi) before any write, priced by the same konsi gross-up as the salesman's own lines, and stamped `FieldSalesOrderLine.addedById` so the detail page can badge them. An already-APPROVED order **refuses** a payload carrying additions rather than returning its idempotent `ok` (it would report a success that created nothing). **No new permission — reuses `field_sales_orders:approve`, so nothing to seed on prod.** The client's "barang baru" wording is deliberately NOT implemented: only the never-sent criterion ships, because whether "baru" means newly-created, newly-in-season or never-sent is still an open client question (design doc D5).
- **A field salesman can raise a store retur request from the PWA (PR #245, merged 2026-08-24).** `createFieldReturn` (`apps/web/lib/field-sales/retur/writer.ts`) records what a store is sending back: lines (item + variant + qty + reason), a required photo of the store's paper nota retur, and how the goods travel (`SELF_CARRY` or `EXPEDITION` with a carrier name AND a resi — both are enforced server-side). Submitted online-only through `POST /pwa/api/retur`, which uploads the photo to R2 and then runs the writer; the multipart route validates every line's SHAPE before the upload so a malformed payload cannot strand an orphan object. **Status stops at `PENDING_WAREHOUSE_RECEIVING`** — a raised retur moves NO stock and writes no `StockAdjustment`; receiving, mismatch resolution and stock restore now ship in the warehouse-receiving half — see the next entry. Backoffice register at `/backoffice/field-returns`. **It takes its own `DocType.FIELDRET` (prefix `FRET/`), NOT `RET`** — `RET` is the vendor-return sequence used by `apps/web/app/actions/vendor-returns.ts`, and sharing it would interleave two registers on one counter and let a Settings prefix edit silently renumber vendor returns. There is **no foreign key** on `FieldReturnLine` (`relationMode = "prisma"`) while `item` is a REQUIRED Prisma relation, so the writer verifies every `itemId` exists inside the transaction (`ITEM_NOT_FOUND`) — an unchecked id would write a row whose detail page throws "Inconsistent query result" forever with no UI repair path. `deleteItem` counts `FieldReturnLine` before allowing a delete, which matters because the retur picker deliberately surfaces INACTIVE items. **Nothing to seed on prod** — no new permission (the register reuses an existing gate) and `generateDocNumber` creates the missing `DocNumberConfig` row on first use.
- **Warehouse receiving closes the other half of the field retur feature (PR #246, merged 2026-08-25).** The warehouse counts what physically arrived on a `PENDING_WAREHOUSE_RECEIVING` retur, splitting each line into sellable and rejected; any line whose count disagrees with the salesman's claim lands the retur in `MISMATCH_PENDING_RESOLUTION`, settled by an append-only `FieldReturnResolution` naming who bears it (`SALESMAN_BEARS`/`WRITE_OFF`/`ACCEPT_SURPLUS`/`INVESTIGATE`). Approving restores `sellableQty` to `InventoryValue` via a POSITIVE `StockAdjustment` sourced `FIELD_RETURN`, and routes `rejectedQty` to `RejectedGoodsLedger`. **`FieldReturnStatus` is now five members** (`PENDING_WAREHOUSE_RECEIVING`/`MISMATCH_PENDING_RESOLUTION`/`PENDING_APPROVAL`/`APPROVED`/`CANCELLED`) with **four separate `Record<FieldReturnStatus, …>` maps** across the backoffice clients — same landmine shape as the `DocType` maps documented in `AGENTS.md` § Code conventions: `apps/web` type-check never runs locally, so a missing member surfaces only in the Docker build during deploy, after migrations have already applied. **`INVESTIGATE` deliberately settles nothing** — it records that someone will look and holds the retur in `MISMATCH_PENDING_RESOLUTION` indefinitely, by design. Resolutions stay amendable until approval, and an amendment recomputes the parent status in BOTH directions — amending a settled line back to `INVESTIGATE` pulls the retur back out of `PENDING_APPROVAL`. **Variance direction is enforced in the writer, not the UI**: only `SALESMAN_BEARS`/`WRITE_OFF` settle a shortage, only `ACCEPT_SURPLUS` settles an over-line, `INVESTIGATE` is valid both ways — a whole-branch review finding, since a user holding `field_returns:manage` but not `field_returns:writeoff` could otherwise call the action directly with `ACCEPT_SURPLUS` on a shortage and absorb the loss with nobody bearing it (every export of a `"use server"` module is an independently callable endpoint). **Zero is a valid count on every line, including all-zero** — the client's lost-sack case, when an expedition loses the whole shipment; never add a positive-quantity validation anywhere in this flow. Restored stock comes back at the **current average cost** (`newAvgCost` = existing `avgCost`) because a retur carries no cost information and blending at zero would destroy the average for everything already in stock. `RejectedGoodsLedger.variantSku` and the create-`InventoryValue` branch both normalise to `null`, never `""`, and the inventory lookup is OR-tolerant (`OR: [{ variantSku: null }, { variantSku: "" }]`) matching `apps/web/lib/canvassing/reconcile-writer.ts`. **`apps/web/lib/field-sales/retur/variance.ts` is deliberately import-free** (`lineVariance`/`isSettled`/`allDiscrepantLinesSettled`/`isValidResolutionDirection`) because a `"use client"` component imports it and any import drags the `@elorae/db` barrel (Prisma + the mariadb driver) into the browser bundle — do not add an import to it. **Liability is recorded in UNITS, never money** — this slice ends approved with stock restored and nothing valued; the value calculation is a deliberate later slice. **The surplus path (`ACCEPT_SURPLUS`, and surplus blocking approval) is our invention, not a client requirement** — the client's story only ever describes shortages. **Post-merge seed: ✅ DONE 2026-08-25** — ran `packages/db/prisma/seed-field-return-permissions.sql` on prod (`field_returns:manage` + `field_returns:writeoff`, both linked to ADMIN; verified 0 → 2 rows, and re-running the file left it at 2, so it is idempotent as written). Do not re-run it blindly. The deploy pipeline migrates but never seeds; see the admin-wildcard entry in this file for why this doesn't unblock ADMIN but does let the permissions be granted to non-admin roles.
- **A field retur is now valued in money, not just units (PR #248, merged 2026-08-25).** Every `FieldReturnLine` gained `creditedQty`/`unitPrice`/`lineValue`/`priceSource`(`DELIVERY`\|`MANUAL`)/`priceDeliveryLineId`/`priceNote`, and `FieldReturn` gained `totalValue`/`valuationStatus`(`PENDING`\|`VALUED`) — additive migration, no backfill needed since every pre-existing row is simply unvalued. Valuation happens **once, at `approveFieldReturn`**, never before: `creditedQtyForLine` (units-only, from the prior slice) times a per-unit price resolved from `listPriceCandidates` — every `FieldSalesDeliveryLine` that ever shipped this exact item+variant to this store, priced off `lineTotal` (already net of its pro-rated discounts) rather than gross `unitPrice`. One matching price on every delivery auto-resolves (`AUTO`); disagreeing deliveries or zero deliveries leave the line unpriced (`AMBIGUOUS`/`UNPRICEABLE`) and `totalValue` **null, never a partial sum** — a partial total is a number that looks complete and would be trusted downstream. `setLinePriceAction` (`apps/web/app/actions/field-returns.ts`) lets an admin resolve what auto-resolve couldn't, pre-approval only (an `updateMany` compare-and-swap against `PRICEABLE_STATUSES` guards a concurrent approve, returning `ALREADY_APPROVED` rather than silently writing nothing); its `deliveryLineId` branch **re-verifies the candidate against this line's own store+item+variant** before trusting it — skipping that would let an admin point a line at any delivery anywhere and inflate the retur's value. An admin's choice that later stops resolving (a dangling `priceDeliveryLineId`, a wiped manual price) is **preserved, not silently cleared**, on an already-APPROVED retur — it is a recorded decision, not an absence of one. **`unitPrice` is a rounded 2dp REFERENCE figure and deliberately does not multiply back to `lineValue`** (`lib/field-sales/retur/pricing-rules.ts`'s `effectiveUnitPrice` stays unrounded until the one multiply-and-round that produces `lineValue`) — the backoffice UI never renders `qty × unitPrice` as a sum for exactly this reason; `lineValue`/`totalValue` are the only authoritative figures shown. **`ACCEPT_SURPLUS` is the one path where our figure exceeds the store's own paper** (credited at the received qty, which is greater than claimed) — badged per-line and noted once at the valuation card header, so finance sees the explanation before they see the gap. `pricing-rules.ts` is deliberately import-free, same rule as `variance.ts` — but NOT for the same reason: no `"use client"` component imports `pricing-rules.ts` directly (only `pricing.ts`, `queries.ts` and `setLinePriceAction` do; `LinePriceControls.tsx`/`FieldReturnDetailClient.tsx` instead import `variance.ts` and take pre-computed values type-only from `queries.ts`). The rule is kept anyway as cheap insurance against a future client import ever dragging `@elorae/db` into the browser bundle. UI: a per-line "Penilaian Retur" card (credited qty, unit price reference, line value, provenance chip) plus `LinePriceControls.tsx` (picker for `AMBIGUOUS`, required-note manual entry for `UNPRICEABLE`, read-only + change button for `SET`, nothing for `AUTO`) rendered only pre-approval and only for `field_returns:manage`; the register gained a value column and an "incomplete" marker restricted to `APPROVED + PENDING` rows (every open retur reads `PENDING` by default, so gating on status too avoids flagging every un-approved retur as broken). **`APPLIED`/settlement wiring against the retur's value is deliberately out of scope** — this slice only computes and displays the number. **Nothing to seed on prod** — no new permission (reuses `field_returns:manage`), migration is additive only. **Whole-branch review fix wave (same branch, 2026-08-25):** the MANUAL branch of `setLinePriceAction` is now re-verified server-side too, not just the DELIVERY branch — it re-resolves the line's price via `resolveLinePrice` and refuses a manual price with a new `AUTO_PRICE_AVAILABLE` code whenever the line would already auto-resolve, since the UI withholding the manual control on an `AUTO` line is not a server guarantee (every `"use server"` export is independently callable). A manual price of exactly 0 is now refused both client- and server-side (`<= 0`, not `< 0`) — a Prisma `Decimal` of 0 is still truthy, so it would otherwise read as a complete zero valuation rather than "never priced". `approveFieldReturn` now stamps `creditedQty`/`lineValue` on EVERY line, even one whose admin price choice is being preserved-but-unresolved (only `priceSource`/`priceDeliveryLineId` stay guarded) — the old all-or-nothing guard around the whole update left `creditedQty` null forever on those lines. The detail page's valuation-card header now derives its post-approval state from `valuationStatus`/`lineValue`, the same signal the register's own badge uses, instead of `priceState` (which reads `SET` for a preserved-but-never-resolved choice and previously made the two surfaces disagree); the approve confirm dialog also now surfaces the still-unpriced line count before the operator commits. `classifyPriceCandidates` de-dupes on a rounded 2dp key, not the raw float, so two deliveries at the genuinely same price can no longer read as `AMBIGUOUS` purely from IEEE-754 noise. `totalValue` is rounded once more after summing already-rounded lines.

This entry is left as written at the time.)* Stock leaves main in one full transfer at APPROVE — the same shape the putus flow was corrected away from in PR #229, so main understates what is really available for the window between approve and whenever the goods actually leave the building. **This is an accepted risk, and only two things make it acceptable:** no client story anywhere describes a partial konsi shipment, unlike putus where the client explicitly asked for delivery-in-parts; and the transfer document is **one-to-many from the order** (`KonsiTransfer.orderId`, not a 1:1), which is the escape hatch — partial shipment can later be added by writing a second transfer against the same order, with no data-model rewrite. - **THREE tables can now answer "how much of this item exists"**: `InventoryValue` (main), `VanStock` (per-canvasser), `StoreStock` (per-consignment-store). `getStockAcrossLocations` (`apps/web/lib/inventory/stock-across-locations.ts`) is the ONLY place allowed to fold them — nothing else may hand-roll that union. It is deliberately **not** the source of available-for-sale, which stays `InventoryValue.qtyOnHand - reservedQty`, main-only: that is what keeps consignment and van stock out of marketplace availability *by construction* rather than by remembering a filter. **Never add an `available` field to it.**
- **The variant-key hazard now has a THIRD spelling.** `InventoryValue.variantSku` is nullable and variantless rows key on `null` (see the PR #144 entry above). `VanStock.variantSku` is **ALSO nullable** — a prior version of this doc (and a comment inside `stock-across-locations.ts` itself) claimed InventoryValue was the only nullable one of the three; both are wrong. Every writer that touches `VanStock` inserts `""`, but the column itself allows `null`. `StoreStock.variantSku` and `KonsiTransferLine.variantSku` are non-nullable `@default("")`, because MySQL treats NULLs as distinct values and a nullable column would make their `@@unique([storeId/transferId, itemId, variantSku])` unenforceable. Net: every read of `InventoryValue`/`VanStock` must stay OR-tolerant (`OR: [{ variantSku: null }, { variantSku: "" }]`), every write into `StoreStock`/`KonsiTransferLine` normalises `?? ""`, and `getStockAcrossLocations` normalises before summing across all three.
- **A konsi retur can drive `StoreStock` negative, deliberately.** The goods physically arrived at the warehouse and were counted — bookkeeping must never refuse to record that reality just because the ledger disagrees. A negative row is absorbed by the next transfer to that store, or — now that the store stocktake ships (PR #257) — by an admin counting that store's shelf and approving the count, which overwrites `StoreStock.qty` outright. Nothing schedules, prompts or reminds anyone to open that count, so the row stays wrong until someone actually counts it. It is surfaced by a pre-commit warning in the retur approve dialog and by a destructive badge plus a header count on the store detail card's stock section — deliberately NOT by an `AdminNotification`, because that bell is already capped at 50 rows with no cursor and no mark-all-read (see `docs/FOLLOWUPS.md` § Notifications).
- **A `KONSI → PUTUS` `termsType` edit is refused while the store holds any non-zero `StoreStock` row, negative included** (`apps/web/lib/stores/queries.ts` `updateStore`). Without that guard the retur decrement and the whole stock card would silently stop applying to a store that reads as PUTUS, stranding the row and permanently double-counting the units with no surface anywhere that would show it. Since konsi stock moved to delivery-shipment completion (PR #318) it is also refused while the store has a konsi order awaiting approval, or approved with qty neither delivered nor closed: that qty is on no `StoreStock` row yet, and completing it after the switch would land it on a PUTUS store's balance with the same no-correction-path outcome. Same `StoreHasConsignmentStockError`, same copy key, widened to name both causes.
- **The quantity a konsi retur decrements from `StoreStock` is the already-stamped `creditedQty`, reused and never recomputed.** It encodes claimed-vs-received per resolution type (see the field-retur valuation entry above), and deriving it a second way in the store-stock branch is exactly how two spellings of one rule drift apart — the writer's own comment warns against collapsing it to `Math.max(claimed, received)`.
- **`StoreStock` now has THREE writers, not two (PR #255, merged 2026-08-25).** *(Stale if read as a current count — later entries in this file added a fourth (store stocktake, PR #257) and a fifth (`receiveFieldReturn`, admin-origin field return); see those entries below for the running total, five as of the latest merged slice. This entry is left as written at the time.)* The konsi transfer (in, PR #253 above) and a konsi retur approve (out, entries above) were already writing it; an SPG sale at a KONSI store now decrements it too (`apps/web/lib/spg/sale-writer.ts`, inside the same serializable transaction as the sale, below the idempotency short-circuit so a replay is decrement-safe with no guard of its own). A sale at a PUTUS store moves no stock at all — the store already owns those goods outright, and the gate on `termsType` is load-bearing, not defensive. All three writers normalise `variantSku` to `""`, matching `StoreStock.variantSku`'s non-nullable `@default("")` (see the variant-key-hazard entry above). **Only the transfer blends `avgCost`**; both decrement paths (retur and SPG sale) leave it untouched — removing units at the current average doesn't change the average, and a newly-created negative row from an SPG sale carries `avgCost: 0` for the same reason a konsi retur's would: a decrement with no cost information of its own has no basis to invent one. **A negative row is deliberate on both decrement paths** — the sale already happened and the cash is in the till, so the writer never clamps or refuses; a drifted or negative row is now correctable — the store stocktake (PR #257, entry below) counts the shelf and overwrites `StoreStock.qty` with the counted figure — but only at a store where someone actually performs a count; nothing schedules, prompts or reminds one. The SPG sale catalog also now shows the store's on-counter `StoreStock` quantity per row as information only — the sellable set stays unrestricted and nothing gates, caps, or gets ordered by it (see `getSellableCatalogForSpg`'s doc comment). **This slice only stopped the overstatement from growing further — it did not repair what had already accumulated.** Every store an SPG was selling at before this shipped carried an inflated `StoreStock` row; that drift is now measurable and correctable wherever the stocktake actually counts the store's shelf, but nowhere is a count required or scheduled, so an uncounted store's drift stands exactly as it was.
- **A store stocktake is the first `StoreStock` writer that SETS the quantity rather than adjusting it, and still the only one (PR #257, merged 2026-08-25).** Never count that table's writers — the set keeps growing and one document can be two of them; the landmine index carries the live list. An admin (no SPG required) opens a count against a store, counts the shelf, and approves — approval writes the counted figure onto `StoreStock.qty` through `setStoreStock` (upserting a row for an item the store had none of) plus the stocktake document itself, and deliberately writes no `StockAdjustment`, no `InventoryValue`, no `SalesHistory` and no `AuditLog`. Where a store has an assigned SPG, that SPG may submit a count from the PWA (`/pwa/spg/stocktake`) for the admin to verify; a blank line means "not counted" and writes nothing for that row, and `isFullCount` records whether every line got one. **Approval writes no `avgCost`, on any path** — consistent with every `StoreStock` decrement writer: a count carries no cost information to invent one from, so a row created because the counter found an item the store had no prior `StoreStock` row for lands at `avgCost: 0`, exactly like a negative row an SPG sale creates. **`StockAdjustment` is structurally the wrong vehicle for any store-side movement** — it has no `storeId`, and its `prevQty`/`newQty` are main-warehouse figures; `VanReconcile` already agrees with this by construction, writing an adjustment only for its return-to-main leg, never for the van side. That reasoning still holds for `StockAdjustment`, but store-side stock is no longer audited by documents alone: approval now goes through `setStoreStock` (PR #311), which writes the counted absolute and appends a `StockLedgerEntry` at the store's location in the same transaction, typed `ADJUSTMENT` carrying the signed difference. A line whose count matches its expectation still writes no entry, which is correct — nothing moved. **`varianceQty` is `countedQty − expectedQty`, the OPPOSITE sign to `VanReconcileLine.varianceQty` (`expected − counted`)** — copying the van formula types every shortfall as a surplus, silently inverting which lines demand a cause rather than throwing. `expectedQty` is snapshotted from the store's live `StoreStock.qty` at the moment the count opens, so it already nets every transfer/sale/retur that happened before it — there is no separate sent/sold/returned computation. Approval requires a non-blank reason on any nonzero variance and a cause on a shortfall, but never holds a discrepant count for review — it always applies the count once those are supplied. **What "applies the count" means changed with the konsi sell-through report (PR #319): approval re-applies every store movement recorded after the count was saved.** The count is true at the moment it was saved, not at approval. `saveStocktakeCounts` stamps `StoreStocktake.countFinishedAt` whenever a save changes a count figure — a line's `countedQty`, or an added line — and a cause- or reason-only resave leaves it alone, because the backoffice resends every line when an admin only fills in a reason at verification time and re-stamping there would drop everything sold since the physical count. Approval then SETs each counted line to `countedQty` plus the sum of every `STORE` ledger row for that item::variant stamped after `countFinishedAt`, so a POS sale or a konsi delivery while the count waited for an admin is kept rather than erased, and the stocktake's own ledger row is the true shrinkage or surplus at the count moment. One kind of row is excluded from that sum: a `FieldReturn` store row whose retur was raised on or before `countFinishedAt`. Returns are excluded because a retur's ledger row lags the physical movement — its goods leave the shelf when it is raised, but its store row lands at approve (FIELD) or at receipt plus an approve-time delta (ADMIN) — so a count taken in between already saw those units gone, and re-applying the row would take them off twice. Both retur writers stamp the FieldReturn id as the row's `refId`, which is how approval resolves the retur. The store-to-store transfer lags the same way — goods leave one store before the transfer is approved — and is excluded on the same principle (PR number on merge): a `StoreTransfer` row whose transfer's `movedAt` (the instant the goods moved) is on or before `countFinishedAt` is skipped, both legs, since both stamp the transfer id as `refId`. Because the skip is per ledger row and only counted lines read the post-count sums, it only ever affects items the count counted. A transfer like that which still moves a counted item and is still PENDING refuses the approval (`TRANSFER_PENDING`, naming the transfers) rather than being silently skipped, because once the count is approved the transfer can never be approved. That refusal also runs for a count whose `countFinishedAt` is null, taking the approval's own instant as the count moment — the same `approvedAt` fallback the transfer's `COUNTED_SINCE_MOVE` guard reads, so the two guards agree on one instant per document; the exclusion itself still never runs for such a count. A retur raised after the count is still subtracted. `appliedQty` records the target actually set; `varianceQty` keeps its `counted − expected` meaning. A stocktake whose `countFinishedAt` is null — counted before the column existed — keeps the old behaviour and sets the bare counted figure. What it still cannot see is a sale between the moment a shelf was physically counted and the moment the sheet was saved: that lands before the stamp and still reads as a surplus (`docs/FOLLOWUPS.md`). The Inventory Extensions "all movements create audit trail entries" criterion used to stay PARTIAL here, waiting on a store-side movement ledger; that wait is over — `StockLedgerEntry` IS that ledger, keyed by location rather than split into a separate `StoreStockMovement` table, and every store-side writer now appends to it. The cost is symmetric: for that same window — between raise and receipt — the store ledger OVERSTATES what is really on the shelf, because the goods have already left but the ledger has not yet caught up. A stocktake opened in that window reports a shortfall that is really goods on a truck. - **`Receivable.paidAmount`/`outstandingAmount` are atomic-increment-only, never read-modify-write (AR ledger + payment recording).** Same rule and same reason as `InventoryValue.reservedQty` above: `recordPayment`/`voidPayment` (`apps/web/lib/finance/ar/`) touch both fields with `{ increment }`/`{ decrement }` inside the writer's own serializable transaction, deriving `status` from the RETURNED row rather than a pre-read value. A read-then-write here would let two concurrent payments against the same receivable each read the pre-payment balance and one clobber the other's update — the exact bug class the atomic rule exists to prevent.
- **A voided payment keeps BOTH its allocations and its original receipt journal — void never deletes either.** `voidPayment` posts a reversing `PAYMENT_VOID` journal (mirrored DR/CR lines) under its own `sourceType`, distinct from `PAYMENT_RECEIPT`'s, so both entries stand side by side in the GL — `@@unique([sourceType, sourceId])` is what lets the two coexist on the same `sourceId` (the payment id). `PaymentAllocation` rows are untouched too; they are the record of what the voided payment claimed to settle, not a working set to clean up. Reading only the receipt journal after a void makes cash look overstated — the reversal is the second half of the story.
- **Journal retry for the AR posting kinds gates on a `JOURNAL_PENDING` `AdminNotification` existing, never on a missing `Journal` row — and the backfill is what makes that load-bearing.** `isArJournalRetryable`/`findPostableArJournalDocIds` (`apps/web/lib/finance/ar/journal-pending.ts`, mirroring the van/supplier-payment siblings) only offer a retry for a document that has an actual failed-post notification. Absence of a `Journal` row is NOT evidence a retry is safe: the backfill migration created a `Receivable` for every pre-existing delivery with no revenue/COGS journal at all, because auto-posting did not exist when they were recorded. If the gate instead keyed on a missing-journal test, every one of those backfilled rows would offer a retry, and clicking it would post DR AR/CR Revenue for goods that may already have been returned, or COGS against inventory already relieved elsewhere, with nothing on the other side of the entry to balance against. The `JOURNAL_PENDING` notification is the only signal that a post was actually ATTEMPTED and failed for this specific document. The konsi sell-through kinds are the one exception, gated on the missing journal instead, because no pre-invoicing sell-through report can owe one — the invoicing entry below says why.
- **Editing a delivery's dates (`updateDeliveryDatesAction`) moves THREE rows in one transaction, not one — and now refuses outright once a payment has touched the receivable.** Inside the action's existing serializable, read-pair-guarded transaction: the matching `Receivable`'s `invoiceDate`/`dueDate` sync to the new values (`originalAmount` untouched), and BOTH posted journals (`FIELD_DELIVERY_REVENUE`/`FIELD_DELIVERY_COGS`) get re-dated to the new `invoiceDate` — leaving either alone strands the aging ledger on the stale due date or the GL in the wrong period. This is safe only because the system has no period-close mechanism; revisit if one is ever built (`docs/FOLLOWUPS.md`). **But re-dating a journal whose receivable already has `paidAmount > 0` is REFUSED, not performed** — a payment posts its own DR Cash/CR AR journal dated on `paidAt`, which is correct (the cash moved when it moved), so re-dating only the revenue journal splits the pair: invoice corrected into a later period while the receipt stays in the earlier one, leaving that earlier period holding a credit AR balance and revenue recognised after the cash that settled it. Fail-closed rather than a warning, because nothing recomputes a journal's date later and the resulting disagreement is silent and permanent. A voided payment restores `paidAmount` to 0 and correctly reopens the correction — void first, correct, re-record.

  **The guard's POSITION is what makes that refusal total, and it is load-bearing.** The `Receivable` read and the `paidAmount > 0` check sit BEFORE the delivery compare-and-swap `updateMany`, not after it. `runSerializable` is a plain `prisma.$transaction(cb)` (`apps/web/lib/db/tx-retry.ts`), which COMMITS on a normal return and rolls back only on a THROW — so `return { kind: "HAS_PAYMENTS" }` placed anywhere below a write commits that write while telling the caller the correction was refused. That shipped once on this branch and the failure was total: a nota with a payment applied, corrected from 2026-01-01 to 2026-02-01, committed the DELIVERY at the new date while the `Receivable` and both `FIELD_DELIVERY_*` journals kept the old one, wrote NO `AuditLog` row, and reported `RECEIVABLE_HAS_PAYMENTS` to the operator. The printed nota date, the aging/overdue date and the GL period then disagreed three ways permanently — the same call is refused on every retry, and the journal-retry gate never fires because the journals already exist, so nothing reconverges them. Rule for that callback, and for any `runSerializable` body: **every early-return arm must be write-free.** `NOT_FOUND` and `CONFLICT` qualify (the CAS matching zero rows wrote nothing, which is the point of the CAS); a guard that must abort AFTER a write has to throw, not return.
- **A receivable can be settled entirely in cash and still never reach `PAID` — the sen/exact-zero rule.** `FieldSalesDelivery.total` is NOT rounded to whole rupiah (unlike `VanSale.total`/`SpgSale.total`, which round via `roundToWholeRupiah` because sen aren't physical cash), so a nota tagihan can legitimately total e.g. `1_234_567.50`. `PAID` requires `outstandingAmount === 0` exactly — rounding `originalAmount` would make the AR figure disagree with the revenue journal (posted at the unrounded `delivery.total`), and declaring `PAID` below one rupiah would write off money with no journal behind it. So a cash-settled receivable can sit at `PARTIAL` with a `0.50` outstanding forever; `ReceivableStatus.WRITTEN_OFF` exists in the enum for exactly this case, but nothing in this slice sets it (`docs/FOLLOWUPS.md`).
- **`lib/finance/ar/aging.ts`'s `daysOverdue` floors on WIB calendar days, not UTC — and `getDate()`/`getFullYear()` etc. are NOT the fix.** WIB midnight is `17:00Z` the PREVIOUS day, so naively flooring the raw epoch difference to a UTC day files every receivable one day early (a due date exactly today reports 1 day overdue, day 30 reports 31 and jumps buckets, day 120 reports 121 and jumps to `D120_PLUS`). The fix is a hardcoded `+7h` shift before flooring, in a deliberately import-free file — NOT `date.getFullYear()/getMonth()/getDate()`, which read the HOST machine's timezone: that would pass on a WIB laptop and silently fail on prod's UTC server. Indonesia has never observed DST, so WIB is a fixed UTC+7 and the hardcoded offset is correct for every date, not an approximation that could later go stale.
- **The four AR journal builders (delivery + payment) MAY THROW, and must only ever be called through `postArJournalSafely`.** Each builder's `Math.abs(value) < 0.01` guard screens near-zero MAGNITUDE but not sign — a negative amount reaches `postJournal` and raises `JournalError("BAD_LINE")`, which `generateAutoJournal` does not catch (it only catches `UNBALANCED`), so the builder throws rather than returning `{ ok: false }`. None of `delivery.total`, `cogsAmount` or `payment.amount` is expected to go negative under current business rules, so this is accepted as-is rather than hardened — byte-for-byte the same gap as `sales-journal.ts`, the file this slice's builders were modelled on, so it is house behaviour, not a local defect. What makes it safe in practice: `postArJournalSafely` (`apps/web/lib/finance/ar/post-ar-journal-safely.ts`) wraps every production call site in try/catch and turns a throw into a `JOURNAL_PENDING` notification instead of a crash. A future call site that invokes a builder directly — bypassing the wrapper — reintroduces a live crash risk on a delivery or payment write path. The three konsi sell-through builders (`lib/konsi-sell-through/journal.ts`) carry the same magnitude-only guard and fall under the same rule; `approveSellThroughAction` and the report's retry reach them only through the wrapper.
- **`voidPayment` refuses a `WRITTEN_OFF` receivable, with the same `ALREADY_SETTLED` code `recordPayment` uses.** Without that guard the two writers are asymmetric — `recordPayment` respects a terminal status while `voidPayment` would silently erase it. Concretely: a 1000 receivable is paid 400 (`PARTIAL`, 600 outstanding), finance writes off the 600 remainder (`WRITTEN_OFF`, 0 outstanding), then someone voids the 400 — without the guard, the restore takes `outstandingAmount` back to 400 and the status rule forces `OUTSTANDING`, resurrecting a written-off receivable for 400 with nothing reversing the write-off in the GL. Costs almost nothing today, since `WRITTEN_OFF` is reachable only by hand SQL (this slice ships no write-off writer) — but it puts the decision where it belongs: someone must deliberately un-write-off before correcting the payment. The eventual write-off slice must define this interaction properly, including whether a void should reverse the write-off's own journal.
- **Credit-limit enforcement's create-time flag is advisory only; the approve-time check is authoritative, and the two are DESIGNED to disagree in both directions.** `createFieldSalesOrder` (`apps/web/lib/field-sales/writer.ts`) stamps `FieldSalesOrder.creditHoldAtCreate` + a snapshot the moment a putus order is raised, but nothing gates on it — the order is written and reserves stock regardless. The real gate is `approveFieldSalesOrder`'s live recomputation of `computeStoreCreditExposure` (`apps/web/lib/finance/ar/credit-exposure.ts`) at the moment of approve. A store can pay down between raise and approve (flagged-at-create, clean-at-approve — no reason required) or blow past its limit in the same window (clean-at-create, over-at-approve — refused without a reason a snapshot gate would have missed entirely, since a salesman raising several orders in one visit converts each approval into the next order's residual exposure). Any UI that reads the stored `creditHoldAtCreate` flag as *why* an admin is being asked to override is wrong — always render the live figures.
- **The credit-limit approve-time refusal is a THROW, never a `return` — same trap `updateDeliveryDatesAction` already documents above, and the fix required restructuring the pre-existing PUTUS approve loop.** `approveFieldSalesOrder`'s finalPrices loop used to call `tx.fieldSalesOrderLine.update` per line, inside the loop, before the order's final total was known. The credit gate had to be inserted so the per-line writes happen AFTER the gate, not before — compute every final price into memory first, evaluate exposure and throw `CreditLimitExceededError` if over limit with no reason, and only then write. `runSerializable` commits on a normal return and rolls back only on a throw, so any future edit to this function that reorders a write ahead of the credit check reintroduces exactly the bug class this restructuring exists to prevent.
- **Credit exposure is `receivableOutstanding` PLUS each `APPROVED` putus order's undelivered residual, floored at zero PER ORDER — a receivables-only reading silently lets every undelivered order through.** `Receivable` rows are created at DELIVERY, not at approve, so an approved-but-undelivered order (the normal state for a busy store — orders routinely sit approved-undelivered for days) is committed exposure invisible to the receivable ledger without the residual term. The floor is per-order deliberately: an over-delivered order must not lend negative headroom to a sibling order's shortfall (`computeStoreCreditExposure`, `apps/web/lib/finance/ar/credit-exposure.ts`).
- **Konsi orders are exempt from the credit-limit check by construction, not by omission — and konsi AR existing now does not by itself make them gateable.** A konsi order's lines are written at `unitPrice: 0`/`lineTotal: 0` at create (the gross-up happens at approve), so there is no order value to gate on; and a konsi ORDER generates no `Receivable` — goods at a KONSI store sit in `StoreStock`, our own virtual warehouse, and the store owes nothing until its sell-through is invoiced, which happens when a konsi sell-through report is approved (the invoicing entry at the end of this file). That receivable is summed into its store's exposure like any other — `computeStoreCreditExposure` filters on store and status, never on source — and the store detail page shows the figure where a credit limit is set, but no gate reads it for a konsi order, which never reaches the putus-only approve tail. Whether konsi orders should now be gated on that exposure is an open decision logged in `docs/FOLLOWUPS.md`; until it is taken, the exemption stands.
- **A new `AdminNotification` category is delivered to nobody until it is added to `admin-fanout.ts`'s `CATEGORY_PERMISSION` map — `CREDIT_LIMIT_HOLD` is the first category added since that map's own comment was written, and the failure mode is silent.** The map's comment already says "a category absent from this map is delivered to nobody, deliberately" — this is the first time that comment has actually been tested against a new category since it was written, and it worked as documented: forgetting the entry produces zero recipients with only a `console.warn`, no thrown error, no failed test unless one specifically asserts on delivery.
- **A collection submission moves no money — `Receivable.outstandingAmount` stays untouched until `verifyCollection` runs.** `submitCollection` (`apps/web/lib/finance/collections/submit-writer.ts`) only creates a `CollectionSubmission` row and fans out a `COLLECTION_PENDING_VERIFICATION` notification; reading `outstandingAmount` alone therefore overstates what is still collectable in the field, since the sum of `PENDING` submissions against that receivable is the other half of the picture. `computeStoreCreditExposure` (`apps/web/lib/finance/ar/credit-exposure.ts`) deliberately does not read `CollectionSubmission` at all, so a store that has paid in the field but not yet been verified stays blocked from ordering — the credit gate trusts only money that has actually posted, never a collector's unverified claim to have it. Don't "fix" this by netting pending submissions into exposure; that would relieve a limit against unconfirmed cash, exactly the trust boundary `verifyCollection` exists to enforce.
- **The over-collection guard nets `PENDING` submissions inside the transaction, not `outstandingAmount` alone.** `submitCollection` reads every `PENDING` `CollectionSubmission` against the receivable via `tx` — not the top-level `prisma` singleton, and not read before `runSerializable` opens — and subtracts their sum from `outstandingAmount` before accepting a new claim. Skipping that netting lets two concurrent submissions each individually pass a naive per-line check against the same outstanding balance and together over-collect the invoice; the failure does not surface until the second submission reaches `verifyCollection`, by which point the first has already posted a real payment. `Serializable` isolation plus this in-transaction read is what forces the second submission to either see the first's committed row or hit a conflict and retry — a read taken outside the transaction reopens the exact race the in-tx read closes.
- **`verifyCollection` posts the payment BEFORE flipping the submission, using a deterministic idempotency key.** `apps/web/lib/finance/collections/verify-writer.ts` calls `recordPayment` with `idempotencyKey: \`collection-${submission.id}\`` first, then CAS-flips `CollectionSubmission.status` to `VERIFIED` in a second statement — deliberately not one enclosing `runSerializable`, because `recordPayment` opens its own transaction and nesting `prisma.$transaction` calls on the same client is unsafe. That ordering plus the deterministic key is what makes a crash between the two steps safely retryable: a retry calls `recordPayment` again, gets back the SAME payment instead of creating a second one, and the flip completes on the retry. Randomising the key, or flipping the submission first, strands a `VERIFIED` submission with no payment and no route back short of hand SQL.
- **`COLLECTION_PENDING_VERIFICATION` must be in `admin-fanout.ts`'s `CATEGORY_PERMISSION` map or the notification is delivered to nobody, silently — new instance of the trap the `CREDIT_LIMIT_HOLD` entry above already names.** It IS present as of this slice, mapped to `PERMISSIONS.PAYMENTS_MANAGE`, the same gate the payment-recording flow uses — so this entry is confirmation, not a bug report. The failure mode if it is ever removed or a sibling category is added without it stays exactly as documented above: zero recipients, only a `console.warn`, no thrown error, no failed test unless one specifically asserts on delivery.
- **`Receivable.collectorId` is a workflow column on a money table, not an assignment entity — there is no assignment status, and collection state is derived entirely from `CollectionSubmission` rows.** Assignment history lives only in `AuditLog` (written by `assign-writer.ts`'s `COLLECTOR_ASSIGN`/`COLLECTOR_UNASSIGN` actions); nothing tracks "assigned but never worked" as its own state. `listCollectionQueue` (`apps/web/lib/finance/collections/queries.ts`) filters on `Receivable.status: { in: ["OUTSTANDING", "PARTIAL"] }`, so an invoice settled through another channel — a direct backoffice payment, a write-off — resolves itself by dropping out of every collector's queue the moment its status changes, even though `collectorId` stays stamped on the row forever. Do not add a housekeeping writer to clear `collectorId` on settlement; nothing reads it as a signal of "still owed" independent of `status`, and clearing it would only destroy the record of who was assigned.
- **`AR_OVERDUE` is present in `admin-fanout.ts`'s `CATEGORY_PERMISSION` map, mapped to `PERMISSIONS.COLLECTIONS_MANAGE` — confirmation, not a bug report, of the same trap `CREDIT_LIMIT_HOLD` and `COLLECTION_PENDING_VERIFICATION` already document above.** Overdue notification is the third category added to this map since its own comment was written, and it held: forgetting the entry produces zero recipients with only a `console.warn`, no thrown error, no failed test unless one specifically asserts on delivery. Anyone adding a further AR-adjacent category should treat this as the third confirmed instance of a pattern, not a coincidence.
- **`runOverdueSweep` (`apps/web/lib/finance/ar/overdue-sweep.ts`) `await`s `fanOutAdminNotification` — the one deliberate exception to `void fanOutAdminNotification(...)` in this codebase.** Every interactive call site fires it unawaited because a user is already waiting on an already-committed transaction, and `fanOutAdminNotification`'s whole body sits inside one try/catch specifically so a floating `void` promise never becomes an unhandled rejection. A cron sweep has no such user, and hundreds of unawaited fan-outs firing in one tick — each an FCM call that firebase-admin retries for roughly a minute on network failure — would stampede Firebase rather than trickle. Never "correct" this particular `await` to `void`, and never copy the awaited shape into an interactive path where a real user is blocked on the response.
- **Overdue dedup keys on `AdminNotification.metadata.thresholdDays`, read back with NO `take` limit and NO `createdAt` floor — deliberately, unlike the `JOURNAL_PENDING` dedup's `take: 200` window.** `runOverdueSweep` folds every `category: "AR_OVERDUE"` row into a `Map<receivableId, highestThresholdDays>` before deciding what to announce this pass; `@@index([category, createdAt])` keeps that read indexed even unfiltered, and volume is bounded by construction to roughly one row per receivable per threshold. Copying the `alreadyFlagged` windowed pattern here would be a bug, not hardening: this is the ONLY record that a one-shot crossing already fired, so a row that ages out of a window gets re-announced forever, and a row written without `thresholdDays` in its metadata is invisible to the dedup map for the same reason.
- **Only the highest crossed threshold fires per sweep pass, and lower thresholds already skipped past are never revisited by design.** `runOverdueSweep` computes `crossed = thresholds.filter((t) => t <= days)` per receivable and only ever announces `crossed[crossed.length - 1]` if it exceeds the highest threshold previously recorded for that receivable. A receivable that first appears in the sweep already 45 days overdue against `[0, 7, 30, 60]` gets exactly one alert at `30`, never a backfill of the `0` and `7` alerts it silently walked past — the sweep only ever climbs forward from whatever it last announced.
- **`parseOverdueThresholds` (`apps/web/lib/finance/ar/overdue-thresholds.ts`) fails OPEN to `DEFAULT_OVERDUE_THRESHOLDS` on anything malformed, empty, or absent — the opposite of `readGlCutover` (`apps/web/lib/finance/sales/sweep.ts`), which fails CLOSED to `null` on the same shape of bad input.** The asymmetry is deliberate on both sides: an ambiguous GL cutover could trigger an unattended retroactive backfill into already-reported periods, so silence is the safe failure there. Here silence is the exact failure this feature exists to remove — an unparseable `ar.overdueThresholdDays` `SystemSetting` failing closed would mean no overdue alerts fire at all, invisibly, which is worse than falling back to `[0, 7, 30, 60]`.
- **`sendNotificationToUsers` (`apps/web/lib/notifications/recipients.ts`) carries no `VITEST` guard of its own, unlike `fanOutAdminNotification`.** Any new caller reaching it directly must guard itself or a spec run pushes real `NotificationQueue` rows and, via the `FIREBASE_ADMIN_*` credentials `vitest.config.ts` loads from `apps/web/.env`, real pushes to real phones. The overdue sweep's own `notifyCollectorOfOverdue` wrapper guards locally with `if (process.env.VITEST) return;` as its first statement, mirroring `fanOutAdminNotification`'s shape — deliberately local rather than pushed into the shared helper, because that helper also sits on the pre-existing PO-overdue cron path and this slice must not widen a shared function's contract.
- **Widening `PaymentMethod` to add `RETUR_OFFSET` also widens `CollectionSubmission.method`, since both columns share the one MySQL `ENUM` — guarded independently in the writer, not only at the action boundary.** `submitCollection` (`apps/web/lib/finance/collections/submit-writer.ts`) casts `input.method` through `unknown` and refuses anything but `"CASH"`/`"TRANSFER"` with `CollectionError("INVALID_METHOD")`, even though its own `SubmitCollectionInput.method` type already reads `"CASH" | "TRANSFER"` — the comment on that check spells out why the runtime guard exists anyway: a `"use server"` action is an independently callable endpoint reachable by a raw request that never went through TypeScript, and `CollectionSubmission.method` now legally accepts `RETUR_OFFSET` at the database level. `submitCollectionAction` (`apps/web/app/actions/collections.ts`) narrows the same way at the action boundary. Without the writer-level guard, a collector could submit a field claim typed `RETUR_OFFSET`, which `verifyCollection` would pass straight to `recordPayment`, posting a revenue-reversing journal (`DR SALES_REVENUE / CR AR`, via `debitRole`) against a receivable with no retur behind it and nothing ever marked `APPLIED`.
- **A retur offset is `PAYMENT_RECEIPT` with a different debit role, not a new `sourceType`.** `debitRole` in `apps/web/lib/finance/ar/payment-journal.ts` widens from `(method: "CASH" | "TRANSFER") => "CASH" | "BANK"` to `"CASH" | "TRANSFER" | "RETUR_OFFSET" => "CASH" | "BANK" | "SALES_REVENUE"` — a retur offset debits `SALES_REVENUE` instead of a cash/bank account, because the store settled with goods, not money, so the "receipt" is really a revenue counter-entry (the same shape a marketplace sales-return revenue leg already posts). Both `postPaymentReceiptJournal` and `postPaymentVoidJournal` call this one function, so the void reversal is automatically correct for free — it mirrors whatever the receipt debited. Minting a separate `sourceType` for the offset instead would fork the `JOURNAL_PENDING` retry plumbing and the `ArJournalKind` map for no gain, since `postArJournalSafely`'s retry gate already points at the right place under `PAYMENT_RECEIPT`. **Those two signatures are the state after the retur-offset widening, not the current one** — the store settlement approval slice widened `debitRole` again to five methods and five roles (`PROGRAM_DEDUCTION` → `TRADE_PROGRAM_EXPENSE`, `ADMIN_FEE` → `ADMIN_FEE_EXPENSE`, both `BEBAN`); read the `PaymentMethod`-widening entry near the end of this file for the full current cost, and the source for the current union.
- **Voiding a payment RE-PROJECTS the retur it drew from, rather than flipping a one-to-one link back — the `offsetPaymentId` release this entry used to describe is gone (branch `partial-retur-drawdown`).** `voidPayment` (`apps/web/lib/finance/ar/void-writer.ts`) reads the voided payment's `fieldReturnId` and, when it is non-null, calls `projectReturnOffset(fieldReturnId, tx)` inside its existing serializable transaction, after the allocation restores. Passing `tx` is load-bearing: `projectReturnOffset` opens its OWN `runSerializable` when handed no client, and nesting `prisma.$transaction` on the same client is unsafe — so the release has to ride the void's transaction and commit or roll back with it. Because the projection is a SET recomputed from the remaining POSTED payments, voiding one draw of several returns exactly that draw's value and leaves the rest applied, and voiding the last one returns the retur to `AVAILABLE` — arithmetic the old `updateMany` on `{ offsetPaymentId, offsetStatus: "APPLIED" }` could not express once a draw took only part of the value. Zero effect is still the normal case (the overwhelming majority of payments are cash and carry no `fieldReturnId` at all), not an error. **`Payment.fieldReturnId` is deliberately NOT nulled on void** — the link is history, exactly like the payment keeping its `PaymentAllocation` rows and its original `PAYMENT_RECEIPT` journal; the projection filters on `status: "POSTED"`, so a voided row stops counting without the trail from payment back to retur being erased. Without the release a single misallocation would strand the store's credit permanently. The already-voided early return (`{ voided: false }`, both on a missing payment and on a zero-row status-flip `updateMany`) stays above it, unchanged; per the `updateDeliveryDatesAction` landmine already in this file, every early return in that callback must stay write-free, since `runSerializable` commits on a normal return and rolls back only on a throw.
- **Re-applying a retur after its draw was voided WORKS now — the permanent refusal this entry used to describe was retired deliberately, and the UI gate built on it was deleted (branch `partial-retur-drawdown`).** The idempotency key moved from `returoffset-<returnId>` to `returoffset-<returnId>-<eventId>`, so a re-draw is a NEW event carrying a NEW key and simply posts a fresh payment; nothing collides with the voided row any more. `PaymentError("PAYMENT_VOIDED")` survives for a replay of the SAME event, which must still refuse rather than resurrect a voided draw, and the post-`recordPayment` status re-read stays for the narrow race where `recordPayment`'s own lookup resolves to a voided payment that landed between this writer's lookup and its call. The consequence worth knowing before touching this surface: **`hasVoidedOffsetAttempt` is GONE** — the derived field on `getFieldReturnById`, the per-row `payment.findUnique` on the old key that computed it, the `credit.voidedOffsetBody` no-action state it drove in `FieldReturnDetailClient.tsx`, and its exclusion from `isOffsettableNow` in `page.tsx`. Its entire premise was that the key could never succeed again for that retur; that premise is now false, so leaving the gate in place would have permanently bricked every retur that ever had a draw voided — the precise outcome it was written to explain rather than cause. Do not reintroduce a voided-attempt gate anywhere on this path.
- **Double-spend prevention for a retur draw is the in-transaction ceiling plus the per-event idempotency key — the CAS flip and the `@unique` column this entry used to name no longer exist (branch `partial-retur-drawdown`).** (1) **The ceiling inside `recordPayment`'s own serializable transaction** (`apps/web/lib/finance/ar/payment-writer.ts`): when the optional `fieldReturnId` is present, the transaction loads the retur, refuses `NOT_FOUND`/`WRONG_STORE`/`NOT_VALUED`, sums the POSTED payments already carrying that id, and throws `EXCEEDS_REMAINING` if this payment would take the total past the retur's frozen `totalValue` — then stamps `fieldReturnId` onto the row it creates in that same transaction, so the check and the fact it checks commit together or not at all. This is the only thing that holds under concurrency: two racing draws against one retur are serialised here, exactly the way `OVER_ALLOCATED` already guards receivables. Its `WRONG_STORE` arm is not decoration — the allocation loop's own `WRONG_STORE` compares each receivable to `input.storeId` and never looks at the retur's store, so without this one a payment could draw store A's retur credit while settling store B's invoices, with every other guard passing. (2) **The per-event idempotency key** `returoffset-<returnId>-<eventId>` makes one logical draw safely retryable after a crash between the payment committing and the projection landing: `recordPayment`'s own lookup returns the SAME payment rather than creating a second one, and the writer's key lookup runs FIRST, ahead of every guard that reads state a prior successful attempt already mutated. What is explicitly NOT part of this list: `FieldReturn.appliedValue`, which is a projection and never a guard (see the draw-down entry below), and the writer's `INSUFFICIENT_OUTSTANDING` check, still a plain un-transacted read that exists only to name the real problem — "this store's outstanding is smaller than what you are drawing" — instead of an allocation error the operator would rearrange numbers forever chasing. **Payment first, projection second**, for the same reason `verifyCollection`'s `collection-<submissionId>` pattern argues: projecting first would claim value against a payment that may never post, whereas a crash after the payment is recovered by re-running under the same `eventId`.
- **A `FieldReturn` that approves `valuationStatus: PENDING` can never be offset — this is terminal, not "not yet".** `setLinePriceAction` (`apps/web/app/actions/field-returns.ts`) refuses to write a line price once the retur's status has left the priceable set, returning `ALREADY_APPROVED` both from a pre-read (`PRICEABLE_STATUS_SET.has(...)`) and from the CAS `updateMany`'s own `status` filter — there is no post-approval repricing path anywhere in this codebase. So a retur whose lines weren't fully priced before approval is stuck at `valuationStatus: "PENDING"` / `totalValue: null` forever, and `applyReturnOffset`'s own guard (`ret.valuationStatus !== "VALUED" || ret.totalValue === null` → `NOT_VALUED`) will refuse it on every future call, not just the first. `FieldReturnDetailClient.tsx`'s credit card renders this honestly: `r.valuationStatus !== "VALUED" || r.totalValue === null` shows a `credit.neverOffsettable` message and offers no action, rather than an "Offset ke piutang" button that would always fail.
- **New retur-offset error codes land on `PaymentErrorCode`/`PaymentActionReason`, never on `FieldReturnErrorCode` — `ERROR_CODE_MAP` in `app/actions/field-returns.ts` is deliberately unaffected.** The five new codes (`RETURN_NOT_APPROVED`, `NOT_VALUED`, `ALREADY_APPLIED`, `INSUFFICIENT_OUTSTANDING`, `PAYMENT_VOIDED`) are money-path refusals raised by an AR writer (`retur-offset-writer.ts`), so they extend `PaymentErrorCode` in `apps/web/lib/finance/ar/errors.ts` and `PaymentActionReason` in `apps/web/app/actions/payments.ts` — confirmed both unions list all five. `ERROR_CODE_MAP` (`apps/web/app/actions/field-returns.ts`) stays a `Record<FieldReturnErrorCode, …>` with no new members, exactly as before this slice. This is deliberate, not an oversight: `INVALID_STATE` already means something else in the `FieldReturnErrorCode` family, and the instinct on seeing a new retur-adjacent error code is to add it to that map anyway — the third instance of exactly that instinct in this codebase, after the `DocType` and `FieldReturnStatus` map traps above. **Updated by the partial-draw-down branch:** the union gained a SIXTH member, `EXCEEDS_REMAINING` ("this draw exceeds what is left of the retur"), raised by `recordPayment`'s in-transaction ceiling and mapped in both `ERROR_CODE_MAP` and both locale files — and `ALREADY_APPLIED` became ORPHANED, still declared, mapped and translated but no longer thrown anywhere, since the CAS flip that raised it is gone. Do not delete it on that basis without checking the slice that reintroduces a terminal-state refusal first; do not read its presence as evidence the old flip survives either.
- **`computeStoreCreditExposure` does not subtract an available retur credit, by design — no `Receivable` has changed and no journal exists yet.** (`apps/web/lib/finance/ar/credit-exposure.ts`) reads only `Receivable.outstandingAmount` (for `OUTSTANDING`/`PARTIAL` rows) and each `APPROVED` putus order's undelivered residual; it does not touch `FieldReturn` or `offsetStatus` at all. This is the identical reasoning already applied to a `PENDING` `CollectionSubmission`, which credit exposure also ignores: an `AVAILABLE` retur credit is an unconfirmed-in-money-terms claim until `applyReturnOffset` actually runs, and subtracting it would lend a store headroom against an offset that may never be performed, making the approve-time credit gate disagree with the ledger it is supposed to be reading. The moment the offset is applied, `outstandingAmount` falls and exposure falls with it, through the existing arithmetic and with no change to this function.
- **`TaxInvoice.buyerNpwp`/`taxableAmount`/`ppnAmount` are snapshots taken once at `markTaxInvoiceCreated`, never live lookups.** `markTaxInvoiceCreated` (`apps/web/lib/tax-invoices/writer.ts`) copies the operator-entered NPWP and the already-computed taxable/PPN amounts straight onto the `TaxInvoice` row inside the same transaction that flips `status` to `CREATED`, and never re-reads `Store.npwp` or the `PPN_RATE_PERCENT` `SystemSetting` afterward. Editing a store's NPWP profile field, or changing the configured PPN rate in Settings, later must not — and does not — change what an already-filed faktur records; the row is the historical filing, not a live projection of current settings. A future "recompute on rate change" feature needs its own on-demand recompute path rather than mutating these columns after the fact.
- **`markTaxInvoiceSentToStore`'s `data` object is a bare `{ reason }`, deliberately leaving `invoiceNo`/`buyerNpwp`/`taxableAmount`/`ppnAmount`/`markedAt`/`markedById` untouched.** `TransitionData` (`writer.ts`) is a `Partial<{...}>`, and `transition()`'s CAS `updateMany` writes only the keys present in `data` — so a handover transition that must not touch the CREATED faktur's identity or amounts simply omits them, rather than every caller re-stating every field on every call. Copying `markTaxInvoiceCreated`'s full data block into `markTaxInvoiceSentToStore` would silently reassign `markedAt`/`markedById` (authorship) and blank or overwrite the invoice number, NPWP and amounts of every faktur ever marked sent. `reason` is optional here (`input.reason?.trim() || null`), unlike `markTaxInvoiceNotRequired`/`revertTaxInvoiceToPending`, because sending an already-created faktur to its store is the expected happy path, not something that needs justifying.
- **The NPWP requirement is enforced in `markTaxInvoiceCreated` (the writer), never the mark-created dialog.** `markTaxInvoiceCreated` trims and rejects an empty `buyerNpwp` with `TaxInvoiceError("INVALID_REQUEST")` before ever calling `transition()`, independent of whatever the dialog's own form validation does — because every `"use server"` export is independently callable, and a dialog withholding a submit button is not a database guarantee. Same reasoning already established for the FIELD-origin retur photo requirement and for the collector-assignment/overdue-notification slices' own writer-level gates: the UI is a convenience, the writer is the contract.
- **Adding a `TaxInvoiceStatus` member touches the writer's hand-written `Status`/`from`/`to` unions, `FakturPajakPageClient`'s hand-written `totalCount` sum, and `page.tsx`'s `STATUS_VALUES` array — none of the three is a `Record` a missing-member type error would catch.** `writer.ts`'s `type Status = "PENDING" | "CREATED" | "SENT_TO_STORE" | "NOT_REQUIRED"` and every transition's `from`/`to` arrays are typed against it by hand, not derived from the Prisma `TaxInvoiceStatus` enum, so a widened enum with an unhandled new state simply compiles and leaves that state unreachable through any transition. `FakturPajakPageClient.tsx`'s `totalCount = props.counts.PENDING + props.counts.CREATED + props.counts.SENT_TO_STORE + props.counts.NOT_REQUIRED` (confirmed still hand-written arithmetic in the merged code, not a `Record`) under-reports the "All" tab's count the same way on a widened enum — silently, not a compile error. `counts` itself (`Record<TaxInvoiceStatusFilter, number>` in `queries.ts`) IS a `Record` and would catch a missing member at compile time; `totalCount` sitting right next to it does not, which is exactly how it survived Task 6's own review requirement to include all four buckets without anyone noticing the gap. The third silent site is `STATUS_VALUES` in `apps/web/app/backoffice/finance/faktur-pajak/page.tsx` — a plain `TaxInvoiceStatusFilter[]` array literal, not a `Record`, so a widened union with a missing entry still compiles. `parseStatus` tests membership against that array, so a URL naming the absent status returns `undefined` rather than the status, and the page silently renders the unfiltered "All" tab: no compile error, no thrown exception, just a filter that quietly does nothing.
- **`apps/web/lib/tax-invoices/status-display.ts` is deliberately import-free, even of the type-only `TaxInvoiceStatusFilter` from `./queries`.** It declares its own structurally-identical `TaxInvoiceStatusValue` union instead, because `queries.ts` imports `@elorae/db`, and `FakturPajakPageClient.tsx`, `DeliveriesCard.tsx`, and (branch `amplop-digital`) `AmplopList.tsx` are all `"use client"` components that must never drag Prisma/mariadb into the browser bundle — even a type-only re-export through a value module carries that risk. The two unions (`TaxInvoiceStatusValue` here, `TaxInvoiceStatusFilter` in `queries.ts`) are structurally identical today but must be kept in sync by hand on every future status addition; this file is the site a widening will hit first, precisely because it duplicates rather than imports. The module also exports `toTaxInvoiceStatusValue`, a narrowing helper (falls back to `null` on an unrecognised value) — its server callers (`amplop`'s `page.tsx`) must resolve through this rather than casting a raw Prisma `string | null` straight to `TaxInvoiceStatusValue`, or a future status addition renders a raw, unmapped key path instead of the "no faktur" state.
- **Two tables now read as "a delivery," and they are not interchangeable — `DeliveryShipment` is the logistics event, `FieldSalesDelivery` stays the accounting event (branch `delivery-shipment-tracking`).** `DeliveryShipment`/`DeliveryShipmentLine` (`apps/web/lib/delivery/shipment-writer.ts`) own the pre-invoicing lifecycle — `PACKED → IN_TRANSIT → DELIVERED`/`PARTIALLY_DELIVERED`, or `CANCELLED` — and sit entirely IN FRONT of `recordFieldSalesDelivery`, never inside its transaction. *(The accounting writer is PUTUS-only: a konsi completion never calls it and instead issues a `KonsiTransfer` for the delivered qty — see the konsi delivery-completion entry at the end of this file.)* Completion then calls that writer with the **delivered** quantities, never the planned ones, and that substitution is the entire mechanism behind partial-refuse "returning to warehouse stock": a line the store refused is simply never handed to the accounting writer, so no stock is consumed, no nota tagihan line is issued and no receivable is raised for it — there is no compensating return document anywhere, and none is needed. A shipment line carries `plannedQty` and only stamps `deliveredQty` at completion, so reading `plannedQty` as what shipped, or reaching for `FieldSalesDelivery` to answer "where is this order right now", each gets the wrong table. **Both documents draw `docNo` from the SAME `DocType.DELIVERY` (`DLV/`) counter** (`generateDocNumber("DELIVERY", tx)` in both writers) — a deliberate no-new-`DocType` decision, but it is exactly the interleaved-register shape the `FIELDRET`-vs-`RET` entry elsewhere in this file argues against, so a shipment and the accounting delivery it produces get adjacent-but-different `DLV/` numbers out of one sequence; see `docs/FOLLOWUPS.md` before assuming a `DLV/` number identifies either one.
- **A konsi shipment completes without moving any stock, and the rule it contradicts is documented rather than resolved.** *(SUPERSEDED — resolved the way this entry prescribed, by reopening the approve-time transfer decision rather than patching the completion path: a konsi completion now moves the delivered qty main → `StoreStock` in one transaction. See the konsi delivery-completion entry at the end of this file. This entry is left as written at the time.)* `completeDeliveryShipment` branches on `shipment.order.orderType === "KONSI"` and skips `recordFieldSalesDelivery` entirely, returning `deliveryId: ""` — correctly, because `approveFieldSalesOrder` already moved those units into `StoreStock` via `KonsiTransfer` at approve (see the konsi-approve entry above), so consuming again at completion would double-decrement main. But the epic this slice implements states "stock moves at completion" as its own rule, and for konsi that rule is simply false; the two decisions were never reconciled. Do NOT add a stock-consuming call for konsi lines to make the rule true — that means reopening the at-approve transfer decision on its own terms (its escape hatch is that `KonsiTransfer.orderId` is one-to-many, so a second transfer can be written against the same order), not patching the completion path. The knock-on: a konsi shipment reaches `DELIVERED` with no `FieldSalesDelivery`, no `Receivable` and no journal, which is correct today only because konsi sell-through AR does not exist yet.
- **`completeDeliveryShipment`'s `MISSING_PROOF` is the FIRST hard-blocking proof gate in this codebase, and the surrounding house pattern is the opposite.** Every other GPS/photo check in the app warns and records rather than refusing — `StoreVisit.checkinOutOfRadius` stamps the distance and shows an amber banner, and check-in proceeds regardless (see the radius entry in `docs/EPIC-STATUS.md` sub-10). Completion refuses outright without a proof photo, enforced in the writer before any read, because a delivery marked complete without proof is unauditable after the fact while a check-in without proof is merely weaker evidence. Do not "harmonise" the two in either direction: softening this gate removes the only thing that makes the POD claim worth anything, and copying it onto check-in would block a salesman standing in a store with bad GPS.
- **`completeDeliveryShipment` posts NO journals — the caller does, and a new caller does not get them for free.** The writer is deliberately pure-DB, matching `recordFieldSalesDelivery`'s own convention (which also posts nothing); `completeShipmentAction` (`apps/web/app/actions/delivery-shipments.ts`) calls `postArJournalSafely` for `field_delivery_revenue` and `field_delivery_cogs` AFTER the writer returns, guarded on `result.deliveryId` being non-empty so a konsi completion posts nothing. That guard is load-bearing and the placement mirrors `recordDeliveryAction` exactly. A script, a test, or a second action that calls the writer directly produces a `FieldSalesDelivery` and a `Receivable` with no revenue/COGS journal and no `JOURNAL_PENDING` notification either — invisible to both the GL and the journal-retry gate, which keys on that notification existing (see the AR journal-retry entry above). It also throws TWO error classes: its own `DeliveryShipmentError` plus `recordFieldSalesDelivery`'s `DeliveryError`, which share code strings like `"NOT_FOUND"`/`"INVALID_STATE"` but are distinct classes. `mapError` in the action now tests BOTH and falls back to a logged `"UNEXPECTED"` rather than rethrowing, so nothing escapes as a digest-masked server-action crash — which means a new reason code is invisible rather than loud: `ShipmentActionResult`'s reason union is `DeliveryShipmentErrorCode | DeliveryErrorCode | "FORBIDDEN" | "INVALID_REQUEST" | "UNEXPECTED"`, the dialogs render it as `t(\`err.${reason}\` as any)`, and that `as any` means a code with no key in `en.json`/`id.json` shows the raw key string to the operator with no compile error. Add the key in BOTH locales whenever you widen either error enum.
- **Completion is TWO transactions, and the `shipment-<id>` idempotency key plus the `IN_TRANSIT` CAS are what make the gap between them survivable.** *(PUTUS only — a konsi completion is a single transaction with its CAS first; see the konsi delivery-completion entry at the end of this file.)* `recordFieldSalesDelivery` runs in its own serializable transaction first (stock, delivery, nota, receivable), and only then does a second `runSerializable` flip the shipment to `DELIVERED`/`PARTIALLY_DELIVERED` and stamp the proof. A crash in between would otherwise leave a shipment stuck `IN_TRANSIT` whose goods have already been consumed and invoiced, with a retry double-shipping them. Two things prevent that: the deterministic `idempotencyKey: \`shipment-${input.shipmentId}\`` means the retry's call to `recordFieldSalesDelivery` returns the SAME delivery instead of creating a second one, and the status write is a guarded `updateMany` on `{ id, status: "IN_TRANSIT" }` that throws `INVALID_STATE` on zero rows rather than blindly overwriting a terminal shipment. Regressing either — a random key, or a plain `update` on the id alone — restores a wedge with no repair path short of hand SQL. Note the second transaction's per-line writes are driven by `input.lines`, which is why that payload must be an exact one-to-one picture of the shipment — see the next entry.
- **`completeDeliveryShipment` demands the payload name EVERY shipment line EXACTLY once (`LINE_MISMATCH`), and `createDeliveryShipment`'s "remaining" is NOT `qty − deliveredQty − cancelledQty`.** Two separate quantity-integrity rules, both easy to undo by reading one side only. (1) On completion, a DUPLICATE `shipmentLineId` would pass the per-entry `OVER_PLANNED` check twice while `recordFieldSalesDelivery` aggregates by `orderLineId` internally and consumes/invoices the SUM; an OMITTED line would leave its `deliveredQty` null forever while `anyShort` — computed over `input.lines`, not `shipment.lines` — still reads "nothing short" and moves the shipment to `DELIVERED`, a terminal status that can then be neither completed nor cancelled. Both are refused up front with `LINE_MISMATCH`; relaxing either half is not a validation nicety, it desyncs the shipment from the accounting record with no repair path, because this call is terminal. (2) On creation, the remaining figure additionally subtracts `plannedQty` already claimed by OTHER `PACKED`/`IN_TRANSIT` shipments on the same order line, because `orderLine.deliveredQty` only moves at COMPLETION — without it two shipments packed back to back each see the full outstanding figure, both pass, and the second to complete dies inside `recordFieldSalesDelivery` on `OVER_DELIVER` after the goods have physically left. `PACKED`/`IN_TRANSIT` is the exact status set holding an unconsumed claim: the two delivered states have already moved `deliveredQty` (counting them would double-subtract) and `CANCELLED` holds nothing. **`CreateShipmentDialog`'s qty prefill still uses the plain `outstanding` figure and is deliberately NOT kept in sync** — the server guard is the enforcement, so a prefill above the true remaining is refused with a mapped `OVER_PLANNED` rather than silently accepted; anyone "fixing" the prefill must not move the guard into the client.
- **Carrier/resi entry is decoupled from the ship transition on purpose, and the ship guard deliberately does not re-check the resi.** `updateShipmentTracking` accepts a correction any number of times while the shipment is still `PACKED` (its own `updateMany` is `PACKED`-gated, so once `IN_TRANSIT` the resi is frozen); only `shipDeliveryShipment` requires one, throwing `MISSING_RESI` from a read before its CAS. That CAS's `where` checks `status: "PACKED"` but NOT `resiNumber`, so a concurrent `updateShipmentTracking` clearing the resi between the read and the write could let a ship transition complete with an effectively-empty resi — a known, accepted race (two admin actions on one shipment within milliseconds on a backoffice desktop flow), whose worst case is cancelling and recreating the shipment since tracking can no longer be corrected once `IN_TRANSIT`. Recorded in `docs/FOLLOWUPS.md`; do not "fix" it by folding resi entry back into the ship action, which is the decoupling the feature exists to provide.
- **`deliveries:ship` and `deliveries:pod` are two permissions on one screen, and a UI gate must check the SAME one its server action enforces.** `DELIVERIES_SHIP` covers create/pack/track/ship/cancel (admin + expedition desk); `DELIVERIES_POD` covers only the actor who completes a shipment against proof, so a role can legitimately hold one and not the other — RBAC role→permission grants are hand-run SQL that is never committed, so nothing in-repo rules that combination out. - **`deliveries:ship` and `deliveries:pod` are seeded by a file nothing runs automatically, and for two slices there was no such file at all.** `packages/db/prisma/seed-deliveries-permissions.sql` now exists (written in the salesman-carry review pass: it inserts both `Permission` rows, grants both to ADMIN, and grants `deliveries:pod` + `pwa:access` to the non-system `SALESMAN` role, which is what makes `listCarrierCandidates` non-empty). Three consequences, all live until the SQL runs: no non-admin role can be granted either permission on prod until that SQL is hand-run; `listCarrierCandidates` returns an EMPTY list on any database where the rows are absent, because it filters users by a role holding `deliveries:pod` AND `pwa:access`, so the carrier combobox is simply blank and no salesman-carry shipment can be shipped at all; and any spec touching this surface against the shared `:3308` bed fails on a real assertion rather than passing falsely — which is exactly what happened to `carrier-queries.test.ts`, whose positive test asserted the `deliveries:pod` row already existed, died in its own setup, and never reached `listCarrierCandidates()` while the file read as two passing tests. Such a spec must SELF-SEED the row with a `connectOrCreate` permission ref (the shape `lib/finance/collections/assign-writer.test.ts` uses) rather than assert one exists, so it is correct on a freshly seeded bed and on prod-shaped data alike; a `Permission` row is shared reference data and must never be torn down. ADMIN is unaffected either way — the wildcard is granted in code (`isSystem` → `['*']`), which is exactly why the gap survived two slices unnoticed, and it is also why seeding the two rows is only half the job: `listCarrierCandidates` filters `roleDefinition: { isSystem: false, … }`, so granting both codes to ADMIN alone leaves the combobox just as empty. The seed has to create or extend a NON-system role holding `deliveries:pod` + `pwa:access`, exactly as `packages/db/prisma/seed-collections-permissions.sql` does for COLLECTOR. This predates the salesman-carry work; it is restated here because that work is the first thing that becomes *unusable*, not merely ungrantable, when the rows are missing.
- **`completeDeliveryShipment`'s `invoiceDate`/`dueDate` have TWO sources, branched on `method`, and the `SALESMAN_CARRY` branch deliberately ignores the caller (branch `salesman-carry-pod`).** For `EXPEDITION` nothing changed: the backoffice `CompleteShipmentDialog` supplies both dates and the writer refuses `MISSING_DATES` without them. For `SALESMAN_CARRY` the writer reads them off the shipment row, where an admin committed them earlier through `updateShipmentTracking` at pack/ship time, and whatever the PWA sends is discarded — because the salesman is standing in the store holding a printed nota bearing those dates, so the accounting record must match the paper rather than whatever the phone decides at completion time. `shipDeliveryShipment` therefore refuses to move a `SALESMAN_CARRY` shipment to `IN_TRANSIT` without both dates (`MISSING_DATES`) and without a carrier (`MISSING_CARRIER`), symmetric with the expedition path's `MISSING_RESI`; the same date check is then repeated inside `completeDeliveryShipment` as defence in depth, since every write path here is independently callable and the alternative to refusing is writing `undefined` into `recordFieldSalesDelivery`. Both params are now OPTIONAL in the input type and still mandatory at runtime for `EXPEDITION` — the type no longer tells you which are required, the `method` branch does. A future third method gets its own explicit branch: neither existing source is the default, and the `else` arm is the expedition arm, not a fallback. One consequence of that split is that `updateShipmentTrackingAction` is the LAST place a reversed `dueDate < invoiceDate` pair can be caught at all, and it originally only validated each date's FORMAT: `updateShipmentTracking` is `PACKED`-gated so the pair freezes at `IN_TRANSIT`, the `SALESMAN_CARRY` completion path reads the dates off the row without revalidating them, and `recordFieldSalesDelivery`'s own ordering guard then rejects them — in the field, on the salesman's phone, with cancel-and-recreate as the only escape after the goods have moved. It now applies `completeShipmentAction`'s ordering check, conditional on BOTH dates being present since they are optional on that action (a carrier can be saved without touching the dates). `ShipmentTrackingDialog`'s `handleShip` pre-checks the same thing against the raw `YYYY-MM-DD` strings, where a plain string comparison is exactly a chronological one. *(All of the date handling above is PUTUS-only now: a konsi order raises no invoice, so `shipDeliveryShipment`'s `MISSING_DATES` and both completion-side date requirements skip it on either method, both backoffice dialogs hide the date inputs for it, and `completeShipmentAction` takes the dates as optional, refusing only a present-but-malformed one with `INVALID_REQUEST` — see the konsi delivery-completion entry at the end of this file.)*
- **The salesman-carry GPS gate is a HARD refusal built out of the check-in flow's soft-warn machinery, and the two disagree on purpose.** It reuses `evaluateCheckinRadius`/`resolveEffectiveRadius`/`parseRadiusSetting` from `lib/pwa/checkin-radius`, the `checkin.radiusMeters` `SystemSetting` and the per-store `Store.checkinRadiusMeters` override — deliberately NOT a delivery-specific radius, so widening one widens store check-in with it, and an ops change made for one flow silently moves the other. Three of its refusals need reading carefully. (1) `evaluateCheckinRadius` returns `distanceMeters: null` paired with `outOfRadius: false` when the store has no coordinates; the check-in flow reads that as a pass (it only ever warns), this gate raises `STORE_NOT_GEOCODED`. The interpretation lives in the caller, and the shared helper was left untouched precisely so neither flow owns the other's semantics — which is why this gate must not be written as `if (outOfRadius)` alone, and why the explicit `store.lat === null` check upstream is kept even though it covers the same case: a future change to the helper's null conditions then cannot silently open the gate. Compare `=== null`, never falsiness — a legitimate 0-metre distance is falsy. (2) A missing `Store` row is `NOT_FOUND`, not `STORE_NOT_GEOCODED`: under `relationMode = "prisma"` there is no FK behind `FieldSalesOrder.storeId`, so a dangling id is genuinely reachable, and reporting it as a geocoding gap sends ops to enter coordinates for a store that does not exist. That conflation was written first and caught in review. (3) The accepted coordinates plus the computed distance are written by the SAME CAS-guarded `updateMany` that flips the status, never as a second write — the audit trail and the status it justifies land together or not at all.
- **That same gate shipped BYPASSABLE, and the shape of the hole is the reason `Number.isFinite` is load-bearing there.** `input.gps.lat`/`lng` are declared `number`, and the first implementation trusted the declaration — but this is a `"use server"`-reachable writer, so the payload is network input. `{ lat: null, lng: null }` sails through: `null - null` coerces to `0` inside the haversine, which returns a distance of `0`, which passes both `distanceMeters === null` and `outOfRadius`, and the delivery completes carrying a fabricated "0 metres from the store" proof record — the strongest possible audit claim, manufactured by omitting the data. `NaN` and a missing field do the same, since `NaN === null` and `NaN > radius` are both false; note the failure mode is the gate OPENING, not throwing. The fix validates `Number.isFinite` on both coordinates plus `|lat| <= 90`/`|lng| <= 180` before any distance is computed, matching the stance the `deliveredQty` check twelve lines above already takes on its own declared type and the range the check-in action's zod schema enforces. It must be `Number.isFinite`, not the global `isFinite`, which coerces its argument — `isFinite(null)` is `true` and would leave the guard a decoration. The general rule: a writer that already refuses to trust one declared type on this path has no grounds to trust another.
- **`mapError` now exists in two copies that must be updated together.** The original is a private (non-exported) sync helper in `apps/web/app/actions/delivery-shipments.ts`; `apps/web/app/pwa/deliveries/actions.ts` carries a byte-faithful duplicate. This is not laziness and not fixable by exporting: a `"use server"` module may only export async functions, verified repo-wide with zero counterexamples across ~55 such files, so a sync helper in one of them can never be shared by import. Both copies test `DeliveryShipmentError` then `DeliveryError` and fall back to a logged `"UNEXPECTED"`, and both feed the same `ShipmentActionReason` union. Widening either error enum therefore means three edits, not one: both `mapError` bodies (if the new code needs anything beyond the generic `error.code` passthrough) and the `err.*` key in both locales. Skip one copy and the backoffice and PWA surfaces report the same failure differently, with no compile error either way.
- **The salesman-carry anti-fraud property is ONE line in `completeDeliveryShipment` (`NOT_CARRIER`), and it shipped missing — the three things that look like they enforce it do not.** The feature's acceptance criterion is that the GPS and photo evidence is tied to the salesman the shipment was assigned to. Three checks surround that and none of them are it: `shipDeliveryShipment`'s `MISSING_CARRIER` only asserts `carriedById` is non-null at ship time; `listMyDeliveries` only SCOPES the PWA queue by it, which hides a shipment from a list without protecting the URL; and `completePodAction` only checks the `deliveries:pod` PERMISSION, which is held by every salesman. Net effect before the fix: any `deliveries:pod` holder could open another salesman's `/pwa/deliveries/<id>` URL and complete it — consuming stock, creating a `FieldSalesDelivery` + `Receivable`, posting both AR journals and stamping their own id as `deliveredById` — while the real carrier's queue silently lost the row. The GPS gate is not a substitute and must never be read as one: it checks LOCATION, not identity, it is trivially spoofed from a browser, and it passes for anyone standing at the right store. The enforcement is `if (shipment.carriedById !== input.deliveredById) throw NOT_CARRIER` at the TOP of the `SALESMAN_CARRY` branch, ahead of the date and GPS checks, because it is the cheapest check and a refused completion should not have reasoned about location or quantities at all. `!==` against the nullable column is deliberate — a null `carriedById` cannot equal a session user id, so an unassigned shipment is refused here too. `apps/web/app/pwa/deliveries/[shipmentId]/page.tsx` repeats the comparison and calls `notFound()`, which is the fail-fast/UX half ONLY: `getShipmentAction` admits either delivery permission by design (the backoffice register needs that), so it hands any shipment to any POD holder, and every `"use server"` export is independently callable regardless of what a page renders.
- **`carriedById` carries no existence check in the writer, unlike `packedById`, and it freezes the moment the shipment ships.** `updateShipmentTracking` writes it through the same `PACKED`-gated `updateMany` that handles carrier and resi, so once a shipment reaches `IN_TRANSIT` the carrier is as frozen as the resi — and since `listMyDeliveries` keys the PWA queue on `carriedById` + `status: "IN_TRANSIT"`, assigning the wrong salesman means the right one never sees the shipment and cancel-and-recreate is the only escape hatch (recorded in `docs/FOLLOWUPS.md`). The missing existence check is a narrower risk than the `relationMode = "prisma"` required-relation trap documented above, for two reasons that both have to hold: `DeliveryShipment.carriedBy` is an OPTIONAL relation, so a dangling id reads back as `null` instead of throwing `Inconsistent query result` forever, and the only path that sets it is an admin-facing `SearchableCombobox` populated from `listCarrierCandidates()` rather than raw untrusted input. The cost of a bogus id today is therefore a shipment in nobody's queue and an unattributable carry, not a permanently unreadable row. Add the check inside the writer the moment anything else — a bulk assign, an import, a PWA-side self-claim — can write that column.
- **A new method-conditional guard does not make the guard sitting next to it conditional.** `ShipmentTrackingDialog`'s `handleShip` gained a `method === "SALESMAN_CARRY"` pre-check for carrier + both dates, added *before* a pre-existing unconditional `if (!resiNumber)` — and since a resi is an expedition-only concept that is never populated for a salesman-carry shipment, every salesman-carry ship attempt through the UI failed on the older check even with the carrier and dates correctly filled: the feature's own primary path could not ship at all. The fix scoped the existing check to `method === "EXPEDITION"`, which is also exactly what `shipDeliveryShipment` does server-side, so client and writer now agree branch for branch. Two things to carry forward: when adding a branch to a shared handler, read every check already in it rather than only the one you are adding beside; and a brief saying "add X before Y without touching Y" constrains the regression risk to Y's own path, it does not license leaving the new path broken. One narrow race stays parked — clicking Ship before `getShipmentAction`'s `useEffect` resolves leaves `method === ""`, both method-gated checks skip, and the server refuses instead; it needs a click faster than the dialog's own data load.
- **`signatureUrl`/`signatureR2Key`/`signedByName` mean "a photo of the signed nota, and who signed it" — NOT a drawn signature (branch `delivery-pod-nota-photo`).** The columns were added, unused, in the `salesman-carry-pod` slice anticipating a canvas signature pad that never got built; this slice closed the card's "digital signature capture" acceptance criterion a different way instead — the salesman already walks away with a physical wet-signature nota, so the digital artefact of record is a required, camera-only (`capture="environment"`) photo of that nota plus a typed receiver name, not a finger-drawn scribble (which would prove "a finger moved on a screen," not who received the goods — nobody holds a specimen signature for any store rep to compare against). Whoever next reaches for these three columns to build an actual signature pad is reusing fields that are already load-bearing for something else; read the spec (`docs/superpowers/specs/2026-09-05-delivery-pod-nota-photo-design.md`, if still present) before repurposing them. The completion gate added for this — `MISSING_NOTA_PHOTO`/`MISSING_SIGNED_BY` — sits LAST in the `SALESMAN_CARRY` branch, after the GPS checks, deliberately: there is no query-cost argument for ordering it earlier (unlike the GPS-finiteness check, which IS ordered before the store lookup to save two queries on a malformed payload), so it was placed where it changed the fewest existing tests and matches the sheet's own capture order (GPS resolves on mount, before either photo is taken). For a konsi order there is no nota — the paper photographed into these columns is the signed Surat Keluar, and the PWA sheet relabels that field accordingly; the gate itself is unchanged.
- **The nota-photo key is bound to the shipment and to being distinct from the goods-photo key — a caller can otherwise pass the SAME uploaded key for both proofs (branch `delivery-pod-nota-photo`, final-review catch).** `completeDeliveryShipment` refuses `signatureR2Key === proofPhotoR2Key` and refuses any `signatureR2Key` that doesn't start with `delivery-pod-proofs/<shipmentId>/` — without both, one photo could satisfy the entire evidence requirement (the goods photo AND the "signed nota" photo would be the identical file), because every `"use server"` export is independently callable and nothing upstream of the writer can be trusted to have sent two distinct uploads. One residual, parked gap: the equality check compares the TRIMMED `signatureR2Key` against `proofPhotoR2Key` UNTRIMMED (that field has never been trimmed anywhere in this file, before or after this slice) — a hand-crafted call padding one key with whitespace could theoretically slip past the equality check while the shipment-prefix check still independently refuses it. Real but vanishingly narrow; closing it fully means trimming `proofPhotoR2Key` too, which touches the earlier-shipped slice's own code outside this one's declared scope.
- **The goods-photo and nota-photo R2 keys are DETERMINISTIC and IDENTICAL in shape across every caller — literal `clientId` values `"goods"`/`"nota"`, no random suffix, no per-attempt uniqueness (branches `delivery-pod-nota-photo` and `delivery-pod-offline-queue`).** This was NOT the original design — an early version of the offline-completion-queue slice used a random-uuid-prefixed `clientId` on the live online path and a different literal (`"offline-goods"`/`"offline-nota"`) in the queued-completion flush path, so a photo captured online-then-interrupted and a photo captured while offline would land under two different keys for the same shipment, orphaning whichever attempt didn't win. Both paths were unified onto the same literal convention specifically so a retried upload (online retry, or a queued row flushed after several failed attempts) always overwrites the SAME R2 object rather than accumulating orphans — this is deliberate idempotency, not an oversight, and it is why `uploadToR2` never needs its own dedup logic. If a future change reintroduces per-attempt uniqueness on either path without the other, the two paths silently diverge again.
- **The salesman-carry client-side pre-check reuses the SAME `evaluateCheckinRadius`/`resolveEffectiveRadius`/`parseRadiusSetting` helpers the server-side gate uses — it does not, and must never, reimplement the haversine formula by hand (branch `delivery-pod-offline-queue`, fix-round catch).** An early version of the PWA sheet's offline pre-check hand-rolled its own haversine + radius comparison to decide, client-side, whether to refuse a completion before ever queuing it — and it silently dropped the server's `Math.round(...)` step before comparing against the radius, creating a real false-negative band (at the default 100m radius, a raw distance of 100.3m failed the client's raw comparison but would have PASSED the server's rounded one), which could strand a salesman who was genuinely close enough. The fix deleted the hand-rolled math entirely and imports the real shared helper (confirmed pure, no Prisma/mariadb import, safe for a client bundle) instead. Any future client-side mirror of a server check in this feature area should default to importing the real logic, not approximating it — this is the second time in this exact feature that "the pre-check doesn't quite match the writer" surfaced as a real bug (the first being the R2-key drift above).
- **A malformed-payload request now returns `NOT_FOUND`/`INVALID_STATE` instead of `NO_LINES`/`MISSING_PROOF`/`INVALID_QTY` when the shipment does not exist or is not `IN_TRANSIT` — a real, deliberate priority change with its own regression tests (branch `delivery-pod-offline-queue`).** Closing the offline-queue feature's foundation bug (a same-actor retry against an already-completed shipment used to throw `INVALID_STATE` instead of returning the idempotent success `recordFieldSalesDelivery` already supported) required moving the shipment fetch and the new replay guard to the TOP of `completeDeliveryShipment`, ahead of the pre-existing cheap payload-shape checks (`NO_LINES`/`MISSING_PROOF`/`INVALID_QTY`) — the replay guard's own test sends an empty/malformed payload against an already-`DELIVERED` shipment, and the old check order would throw `NO_LINES` before ever reaching the shipment row. The side effect: a malformed payload against a shipment that does not exist, or exists but isn't `IN_TRANSIT`, now costs one extra query and returns a different code than it used to. Nothing that shipped before this change depended on the old priority (verified — no test exercised that exact combination either way), and two regression tests now pin the NEW order down explicitly so a future edit can't silently flip it back without a test noticing.
- **The idempotent-replay guard on `completeDeliveryShipment` is scoped to the SAME `deliveredById` only — a different actor against an already-completed shipment still throws `INVALID_STATE` (branch `delivery-pod-offline-queue`).** `if (status IN (DELIVERED, PARTIALLY_DELIVERED) AND deliveredById === input.deliveredById) return {ok:true, deliveryId}` sits immediately after the `NOT_FOUND` check, ahead of everything else — this is what makes a lost-response retry (the classic offline failure mode: the server committed, the client never saw the response) safe to replay from the SAME device/session, without reopening the `NOT_CARRIER` anti-fraud hole a prior slice on this same feature had to close (any `deliveries:pod` holder completing a DIFFERENT salesman's already-finished shipment must still refuse, not silently succeed). Widening this to "any actor" without a real reason to reopen that question is exactly the mistake `NOT_CARRIER` exists to prevent.
- **The offline-completion queue's sync classifier treats `FORBIDDEN`/`UNEXPECTED` as `"retry"`, the OPPOSITE of every other classifier in this codebase (branch `delivery-pod-offline-queue`).** `classify.ts` (orders) and `photo-classify.ts` (visit photos) both treat an auth/permission failure as terminal, because a human is watching those flows and can re-authenticate by hand. This queue runs unattended in the background (fired from `online`/`visibilitychange`/mount, no user watching a specific attempt) — a session that expired mid-queue must wait for the next login and the next automatic flush, not have its evidence silently discarded. The queue still needs a floor: `MAX_RETRY_ATTEMPTS = 20` flips a row that has retried this many times to `"failed"` and fires an admin notification regardless of the underlying reason (covers a PERMANENTLY revoked permission, which looks identical to an expired session from the classifier's perspective but will never resolve on its own). `reportStuckDeliveryCompletionAction`'s own permission gate was deliberately loosened to "authenticated" only (not `deliveries:pod` specifically) for the same reason — the scenario the ceiling exists for is precisely a salesman whose `deliveries:pod` was revoked, and gating the rescue notification on the very permission that got revoked would silently swallow it. The notification itself is retried separately from the completion (a `notified` flag + a post-flush-loop pass that re-attempts ONLY the report, never the upload or the writer call) because the report is most likely to fail in exactly the connectivity conditions that tripped the ceiling in the first place.
- **`appliedValue` is a PROJECTION of the payment ledger, never a reservation — reserve-then-post was designed, examined and rejected, and it cannot be made safe (branch `partial-retur-drawdown`).** The obvious shape for a partial draw is to CAS-reserve `FieldReturn.appliedValue` upward and then post the payment against the reservation. It does not work, and the reasoning is written down here so nobody re-proposes it: a crash between the reservation and the post inflates `appliedValue` against a payment that never existed, and nothing on the row distinguishes that stale reservation from a legitimate in-flight one. Any automatic self-heal that recomputes `appliedValue` from the ledger — the only way to clear the stale case without a human — therefore also erases a LIVE reservation, at which point two racing draws each wipe the other's claim and both post: over-draw, the exact failure the ordering existed to prevent. There is no ordering of a reserve and a post on two different rows that closes both holes at once. So the guarantee moved into `recordPayment`'s transaction (entry above) and `appliedValue` became a pure projection: `projectReturnOffset` (`apps/web/lib/finance/ar/retur-offset-writer.ts`) sums the POSTED payments carrying that `fieldReturnId` and writes the result with a plain SET, deriving `offsetStatus` from the same number (`APPLIED` once the sum reaches `totalValue`, `AVAILABLE` below it). Being a SET rather than an increment is what makes it idempotent — safe to redo on a replay, after a crash, or after a void, with no double-count and no drift to reconcile. Two rules follow. **Never hand-increment or hand-decrement that column**, from a writer, a script or hand-run SQL: the payments are the ledger of record and the column is only ever their echo. And **`projectReturnOffset`'s read and write must be atomic with each other**, not merely individually safe — two draws committing back to back can each aggregate before the other's write lands, and the first one's write then lands LAST and overwrites the second's correct larger sum with its own stale one, leaving the retur permanently under-reporting `appliedValue`, stuck `AVAILABLE`, with nothing scheduled to correct it. Hence the function's two calling modes: given no client it opens its own `runSerializable`; given a caller's client (only `voidPayment` today) it runs the body directly against that client, because nesting `prisma.$transaction` on the same client is unsafe. Adding a third caller means picking the right mode deliberately, not copying whichever call site you read first.
- **The retur draw's idempotency key is per-EVENT and the CALLER owns it — `returoffset-<returnId>-<eventId>` (branch `partial-retur-drawdown`).** One retur can back several payments now, so a key derived from the retur id alone would make the second draw look like a replay of the first. `applyReturnOffset` therefore takes a required `eventId` and never mints one itself, which puts the whole crash-safety property in the caller's hands: **the id must be stable across retries of one logical draw, and fresh for a genuinely new one.** Both failure directions are silent. A fresh id per attempt turns a retried request into a SECOND draw against the same retur — the double-draw the key exists to prevent, refused only once the ceiling is reached and not before. A reused id hands back the EARLIER payment with `alreadyApplied: true` and draws nothing, so an operator sees success while the second draw never happened. The rejected alternative — deriving the key from a draw sequence off `appliedValue` — is actively unsafe for the first reason: a retry after a partially committed draw reads a different `appliedValue`, computes a different key, and posts a second payment. Concretely: `OffsetToPiutangSheet.tsx` mints a UUID with `useState` (not `useMemo` — React guarantees `useMemo` only as a performance optimisation, so a discarded cache could silently mint a second id mid-flow) and reseeds it in the same `useLayoutEffect` that seeds the allocation inputs, once per sheet open; a settlement caller will pass the deduction row's id, which already exists before the draw is attempted. `applyReturnOffsetAction` rejects an empty or non-string `eventId` with `INVALID_REQUEST`, because a `"use server"` export is independently callable and a missing id would otherwise collapse every draw on a retur onto one key.
- **A partially drawn retur stays `AVAILABLE`, so every surface showing its value must show `totalValue - appliedValue` (branch `partial-retur-drawdown`).** `listOffsettableReturns` filters on `offsetStatus: "AVAILABLE"` and keeps returning a half-drawn retur, which is correct — it still has value — so `offsetStatus` alone no longer tells you how much. All SEVEN read surfaces carry the subtraction: `listOffsettableReturns`, `getStoreAvailableCredit` and — added by the amplop digital slice — `getStoreAvailableCreditMap` (all three in `retur-offset-queries.ts`), `suggestOffsetAllocations` (a pre-fill, walked to the REMAINING value — a suggestion that exceeds what can be drawn is a suggestion that always fails), `listFieldReturns` + `getFieldReturnById` (`apps/web/lib/field-sales/retur/queries.ts`), the latter two exposing a `remainingValue` that is `null` exactly when `totalValue` is, and — added by the settlement-document slice, the unpaged counter-side-picker twin of `listOffsettableReturns` — `listAllOffsettableReturns` (also in `retur-offset-queries.ts`). An EIGHTH surface left on `totalValue` overstates the store's credit and invites a draw `recordPayment` will refuse with `EXCEEDS_REMAINING`. Two shape changes ride along: `getFieldReturnById` now returns `offsetPayments: { id, docNo }[]` (POSTED only, oldest first) instead of the single `offsetPayment`, since a retur can carry several draws; and `getPayment` reads the reversed relation as `fieldReturn` while still returning it under the old `returOffsetFor` name, so the payment detail page was untouched. Also note the writer's own arithmetic moved with it: `ALLOCATION_MISMATCH` now means "allocations do not sum to the requested DRAW", and `INSUFFICIENT_OUTSTANDING` compares the store's outstanding against the DRAW — `EXCEEDS_REMAINING` is the separate, new code for "the draw exceeds what is left", and overloading either older code with that meaning tells the operator to do the wrong thing.
- **The amplop digital's store set keys on the ORDER's salesman (`delivery.order.salesmanId`) for a delivery-backed receivable, NEVER on `delivery.deliveredById` (branch `amplop-digital`).** Two columns could plausibly be read as "the delivering salesman" and picking the wrong one is silent in both directions. `FieldSalesDelivery.deliveredById` is whoever RECORDED the delivery, and since the delivery-shipment work an expedition delivery is completed by a backoffice user holding `deliveries:pod` — frequently an admin who has never visited the store. `FieldSalesOrder.salesmanId` is the person who raised the order and owns the store relationship. An amplop is a ROUTE package — what am I carrying to this store today — so it keys on the order's salesman: `listAmplop` (`apps/web/lib/finance/collections/amplop-queries.ts`) selects on `OR: [{ collectorId: userId }, { delivery: { order: { salesmanId: userId } } }, { sellThrough: { salesmanId: userId } }]`, a union of "stores where I am the assigned collector", "stores where I raised the order" and — since receivables gained a second source — "stores whose sell-through report names me". Keying on `deliveredById` instead would file a store into that admin's amplop and silently drop it from the salesman's — the exact opposite of the feature's purpose, and visible to nobody, because both sides look like a plausibly populated screen. A spec pins the distinction directly (an admin who is `deliveredById` on a delivery must NOT see that store), so a future change to the union has to defeat a test rather than merely slip through review. The decision is reversible if the client asks for it, but reverse it deliberately: `deliveredById` is not a synonym here, it is a different person. The third arm follows the same principle for a receivable backed by a `KonsiSellThrough` report, which has no order: the owner is the report's own `salesmanId`, the same field `resolveReceivableSource` returns as the source's `salesmanId` and the one `submitSettlement`'s ownership check compares against. It is nullable, and approval stamps it whenever the report bills anything (the invoicing entry at the end of this file), so a null one belongs to a report that created no receivable; a null one still matches no amplop and passes no ownership check, and a receivable left in that state would be reachable only through its assigned collector. That is deliberate: guessing an owner from some other column would recreate exactly the `deliveredById` mistake this entry is about.
- **The amplop (`/pwa/pelunasan`) and the collection queue (`/pwa/collections`) overlap on purpose and must not be merged (branch `amplop-digital`).** They answer different questions and are scoped differently, which is why two PWA home entries can list the same receivable. `/pwa/collections` is a WORK QUEUE: a flat list scoped strictly to `Receivable.collectorId`, ordered by due date, every row actionable through the collection submit. The amplop is a READ-ONLY route package: grouped by store, wider store set (it also covers stores where nobody assigned a collector but the user raised the order), and it shows documents the queue never does — the faktur status, the store's available retur credit, and any `PENDING` `CollectionSubmission` already standing against a row so the salesman does not chase money a colleague has already claimed. Three rejected alternatives, so nobody re-proposes them: making the amplop the collections landing (it changes a shipped money-path screen and widens who reaches it), folding it into `/pwa` (the home shell is shared with SPG and van roles, most of whom cannot act on a finance block), and giving the amplop a tap-through into the collection submit (the acting surface is the settlement entry two slices later, so that wiring would have to be unpicked). The cost is real and lives in the copy: the two home CTAs must keep saying different things — one is what you are carrying to a store, the other is what you owe a collection on — and "Amplop Digital" is deliberately left untranslated in the English locale because it is the business's own name for the physical envelope, not a phrase to localise.
- **`getStoreAvailableCreditMap` exists because the amplop is an N+1 otherwise, and it shares `offsettableReturnWhere` with `getStoreAvailableCredit` so the two cannot drift (branch `amplop-digital`).** `getStoreAvailableCredit(storeId)` takes one store; calling it once per store on a screen that grows with the salesman's round is a query per store. The batched sibling takes an id list and returns a `Map`, and it is built on the SAME private `offsettableReturnWhere()` helper — the point is not brevity, it is that "available" (`status: APPROVED`, `valuationStatus: VALUED`, `offsetStatus: AVAILABLE`) is defined in exactly one place, so a future change to what counts as offsettable cannot land on one function and miss the other. It sums REMAINING value for the reason the entry above spells out; reading `totalValue` here would overstate every store carrying a partially drawn retur. One shape detail worth keeping: every requested id is pre-seeded to `0` before the rows are folded in, so a caller never has to distinguish "this store has no credit" from "I did not ask about this store" — `creditMap.get(storeId) ?? 0` is then belt-and-braces rather than the actual defaulting mechanism, and a future caller that iterates the map instead of looking ids up still sees the full requested set.
- **`collections:amplop` has no `Permission` row until `packages/db/prisma/seed-amplop-permission.sql` is hand-run, and this repo seeds no permission row from any migration or deploy step (branch `amplop-digital`).** Same shape as the `deliveries:ship`/`deliveries:pod` entry above, restated because the failure mode is silent and environment-specific rather than a build break. Until the SQL runs, `hasPermission(..., PERMISSIONS.COLLECTIONS_AMPLOP)` is false for every non-admin, so the `/pwa/pelunasan` page guard redirects to `/pwa` and the home CTA simply never renders — the screen is not broken, it is absent, with no error anywhere to notice. The seed grants THREE roles, not two: SALESMAN (reaches the amplop through the order-salesman arm) and COLLECTOR (created by `seed-collections-permissions.sql`, holding `pwa:access` + `collections:collect` — this is the role `listCollectorCandidates()` actually offers for `Receivable.collectorId`, so it is the role the collector-id arm of the store-set union exists for; the seed shipped without this grant for a while, leaving every real collector unable to see the screen and the collectorId arm dead code in practice), and ADMIN, which is convention-mirroring only (`seed.ts` assigns ADMIN every `Permission` row) and buys ADMIN nothing functionally: `pwaAccessGuard` redirects any wildcard holder to `/backoffice` BEFORE the permission check ever runs (`isSystem` → `['*']`), so an ADMIN account is **blocked** from this screen with or without the seed, not passing on the wildcard. That is exactly why an admin smoke test cannot detect a missing seed either way — post-seed verification on production must be done on a SALESMAN or COLLECTOR account. The seed is idempotent (`WHERE NOT EXISTS` on both the `Permission` row and each `RolePermission` grant), grants all three roles, and bumps `permissionsVersion` on each so already-logged-in users pick the grant up without re-login. It also carries its own caveat: it targets the non-system `SALESMAN`/`COLLECTOR` roles by name, and on a database where either role does not exist that role's grant silently no-ops — check before assuming the run worked. **A spec touching this permission must SELF-SEED the row with `connectOrCreate` rather than assert it exists.** Asserting is what made `carrier-queries.test.ts` die in its own setup and then read as two passing tests over zero real coverage; a `Permission` row is shared reference data on the `:3308` bed and must never be torn down.
- **Both settlement over-claim guards are DERIVED projections netted INSIDE the transaction, and the invoice half was missing from the design (branch `feat/settlement-document`).** `submitSettlement` (`apps/web/lib/finance/ar-settlement/submit-writer.ts`) exists to stop two salesmen standing at the same store on the same day from both spending the same money. A retur's remaining headroom is `totalValue − appliedValue − Σ(RETUR_OFFSET deduction amounts on OTHER PENDING settlements for that retur)`; an invoice's is `outstandingAmount − Σ(StoreSettlementInvoice.amount on OTHER PENDING settlements for that receivable)`. Both aggregates run through the `tx` client inside the same `runSerializable` call — not the top-level `prisma` singleton, and not a read taken before the transaction opened, which is precisely the shape `submitCollection`'s over-collection guard already carries an entry for above. A stale read lets two submissions each pass individually and together over-claim; `Serializable` isolation plus the in-transaction read is what forces the second to either see the first's committed rows or lose a serialization conflict and retry. **The invoice half (`INVOICE_OVERCLAIMED`) was NOT in the design spec** — it only surfaced in review, and without it two salesmen could each select the same receivable for its full outstanding, both collect cash at the counter, and the loser be refused at the approval slice after the money changed hands, which is exactly the failure the retur reserve was built to prevent. Neither claim is stored: there is no `claimedValue` column and no release path, because a settlement that stops being `PENDING` stops contributing to either sum by construction — the same reasoning that makes `appliedValue` a projection of the payment ledger rather than a reservation. And it is a **claim, not a lock**: the backoffice retur-offset sheet still posts a real payment immediately against the same retur, and `recordPayment` still accepts a direct payment against the same receivable, so the reserve narrows a wide race rather than closing it. The authoritative ceilings stay `EXCEEDS_REMAINING` and `OVER_ALLOCATED` inside `recordPayment`.
- **Three obligations the settlement APPROVAL slice inherits from the derived-claim design — read all three before building approval (branch `feat/settlement-document`).** Every one follows from claims being projections of `status = "PENDING"` rows rather than stored reservations, and all three were found in review rather than planned. **(1) Approval MUST decrement `Receivable.outstandingAmount`** (atomically, per the AR entry above). An APPROVED settlement's `StoreSettlementInvoice` rows stop counting in the `INVOICE_OVERCLAIMED` aggregate the instant the status flips, so if approval does not move the underlying figure, the same slice of the same invoice becomes claimable all over again by the next settlement — the guard silently unwinds itself, and the symptom is an over-collected invoice with every individual check having passed. The retur side has the same requirement via `appliedValue`. **(2) Approval must flip the status and post the retur draw such that the two can never disagree.** `applyReturnOffset` is deliberately not one transaction with anything else, so a status flip committed before the payment posts and `appliedValue` advances leaves that retur's headroom overstated by exactly the approved amount for the width of that window: the deduction has already stopped contributing to the PENDING sum and the draw has not yet landed in `appliedValue`. Make the draw durable first, or hold both under one transaction — never flip status first. **(3) The claim aggregates need no self-exclusion TODAY, and only because there is no edit path.** Neither carries `settlementId: { not: … }`, which is safe purely because the settlement row does not exist yet when they run (creation is the last step) and a replay returns from the idempotency guard long before them. The moment any slice adds edit, or resubmit-with-changes on a `REJECTED` settlement — which the design explicitly plans, since a rejected settlement is editable and keeps its document number — both aggregates must gain an explicit self-exclusion or the document refuses itself against its own rows with `RETUR_OVERCLAIMED`/`INVOICE_OVERCLAIMED`. **STATUS as of the approval slice (`feat/settlement-approval`): (1) and (2) are discharged and must not be undone** — approval moves AR only through `recordPayment`'s atomic decrement, and the status flip is the last write of the sequence rather than either alternative this entry offered (holding both under one transaction turned out to be impossible, since `recordPayment` and `applyReturnOffset` each self-transact; see the resumable-sequence entry near the end of this file). **(3) is still live**, satisfied only vacuously: approval introduced no edit path, so it binds whoever builds one.
- **The settlement's `draftId` is the document's identity BEFORE the document exists, and it is caller-stable on purpose (branch `feat/settlement-document`).** `StoreSettlement` has no `DRAFT` status, so at the moment a salesman photographs a kuitansi there is no `settlementId` to bind an evidence key to. The client mints one UUID per opening of the form and it does double duty: every proof object lands at `settlement-proofs/<draftId>/<slot>.<ext>` (`<slot>` is `program-<n>` or `adminfee`, deterministic per deduction), and the same id is submitted as `StoreSettlement.idempotencyKey`. That buys both properties at once — a retried upload overwrites the same object instead of orphaning one, and a double-tap or a retry after a lost response resolves to the settlement already created instead of raising a second. The writer refuses any `proofR2Key` not starting with this submission's own prefix (`INVALID_PROOF_KEY`) or reused across two deductions in one document (`DUPLICATE_PROOF_KEY`), which is the delivery-POD lesson restated: without both checks one uploaded photo satisfies every proof requirement at once. **Mint it with `useState(() => crypto.randomUUID())`, never `useMemo`** — React documents `useMemo` as a performance optimisation it may discard, and a re-minted id both strands the already-uploaded evidence under a prefix that no longer matches and turns the retry into a duplicate document. `SettlementForm` also deliberately does NOT rotate the id after a successful submit, unlike `SubmitCollectionSheet`, because this screen never renders its form again (`success` is never cleared) and rotating would only leave `rows` holding proof keys under a stale prefix. Both the upload route and `submitStoreSettlementAction` enforce the exact UUID shape: the id is interpolated straight into an R2 object key and there is no row to check ownership against, so a short or guessable id would let a caller overwrite another salesman's evidence before they submit. The replay itself is scoped to the SAME salesman at the SAME store — a `draftId` collision from a different actor is refused with `DRAFT_ID_CONFLICT` rather than handed someone else's real settlement id and docNo back as a reported success, following `completeDeliveryShipment`'s replay guard above. An empty-string `draftId` is rejected before the idempotency lookup runs at all, because it is a valid-looking global unique key a stale client build could send for every submission.
- **The settlement admin fee is charged on the NETTED base, and the calc module is import-free so the preview cannot disagree with the writer (branch `feat/settlement-document`).** `adminFeeBase = Σ selected invoice amounts − returTotal − programTotal`, then `adminFee = roundCents(base × percent / 100)` and `expected = base − adminFee`: the store's handling fee applies to what it actually hands over, not to the gross invoice. Exactly one `ADMIN_FEE` deduction is permitted (`DUPLICATE_ADMIN_FEE`) because applying a percentage more than once to the same base is ambiguous, and the row persists the computed rupiah `amount` — the schema's `amount` column is non-nullable — with the `percent` kept alongside it rather than instead of it. `lib/finance/ar-settlement/calc.ts` imports nothing but `roundCents` from the `@elorae/db/pricing` subpath and declares its own deduction-type union, because the `"use client"` `SettlementForm` imports it directly for the live preview; anything reaching the `@elorae/db` barrel would drag Prisma and the mariadb driver into the browser bundle — the same policy as `lib/field-sales/retur/variance.ts` and `lib/tax-invoices/status-display.ts`. The screen sharing the module rather than recomputing is the whole point: `expected` is still recomputed server-side at submit and never trusted from the client, and a screen carrying its own arithmetic would recreate the preview-vs-writer mismatch this file already records twice on the pricing path. Variance is `actual − expected` and ANY non-zero variance sets `isFlagged` here — the configurable tolerance belongs to the approval queue, so exactly one place ever hardcodes a threshold.
- **The settlement deliberately has NO exhaustive `Record<SettlementErrorCode, …>` anywhere, which moves the cost rather than removing it (branch `feat/settlement-document`).** `submitStoreSettlementAction` passes `e.code` straight through into `SettlementActionReason` — no translation map at the action boundary, the same shape as `toCollectionResult` in `app/actions/collections.ts` — specifically to avoid a fourth instance of this repo's most-repeated landmine (the two `DocType` maps, the four `FieldReturnStatus` maps, `ERROR_CODE_MAP`). The consequence is that a new code fails SILENTLY at the other end instead of loudly at build time: `REASON_KEY` in `SettlementForm` is a `Partial<Record<…>>` read as `REASON_KEY[reason] ?? "errGeneric"`, so a code added to the union with no entry there and no `en.json`/`id.json` key shows the salesman a generic failure, with no compile error and no runtime error. The codes intentionally left out of that map are the tamper/bug ones a salesman cannot act on (`INVALID_PROOF_KEY`, `SALESMAN_NOT_FOUND`, `WRONG_STORE`, `RECEIVABLE_NOT_FOUND`, …) — the whole-branch review fix wave added three more of exactly this kind (`STORE_NOT_FOUND`, `NOT_ASSIGNED`, `INPUT_TOO_LARGE`, growing the union from 23 to 26 members) and deliberately left all three unmapped for the same reason: none is reachable through the screen's own scoping, only through a raw request. Adding an operator-fixable code means adding the `REASON_KEY` entry AND both locale keys by hand. **The approval slice grew the union to 34 members and added TWO more surfaces to that hand-maintenance, both with the same silent failure (branch `feat/settlement-approval`).** `approveSettlementAction`/`rejectSettlementAction` pass `e.code` through the same way, discriminating `SettlementError` from `recordPayment`'s `PaymentError` on `instanceof` (never on the code string — `WRONG_STORE` is genuinely shared), so the finance queue needs a `financeStoreSettlements.err.<CODE>` key in BOTH locales; its `errorMessage()` helper falls back to `err.UNEXPECTED` via `t.has()` rather than a hand-maintained code list, so a miss degrades to a generic message rather than a raw key path, but it is still a miss. And if the new code is one the queue's read-only checklist can PREVIEW, it must also join the `SettlementCheckReason` `Extract<>` union in `lib/finance/ar-settlement/checks.ts` — that `Extract` is deliberately welded to `errors.ts`, so a rename there breaks here loudly, which is the one place on this path that does fail at build time.
- **The settlement gates on its own `settlements:submit` permission now, not `collections:collect` — a whole-branch review fix wave, branch `feat/settlement-document`.** The screen, `submitStoreSettlementAction`'s guard and the proof upload route originally reused `collections:collect`, which per `seed-collections-permissions.sql` goes to ADMIN and COLLECTOR only (SALESMAN holds just `pwa:access`, granted by `seed.ts`) — while `AmplopList`'s Settle button rendered unconditionally regardless of any permission. The result: a salesman opened the amplop (gated on the separate `collections:amplop`, which SALESMAN does hold), saw a full-width Settle button on every store card, tapped it, and was silently redirected to `/pwa` with no message — on the exact feature this repo's own spec frames as "the document a salesman fills in at a counter." Fixed by introducing `settlements:submit` (`packages/db/prisma/seed-settlements-permission.sql`, modelled on `seed-amplop-permission.sql`, granting SALESMAN + COLLECTOR + ADMIN-by-convention, hand-run on prod post-merge — see the amplop entry above for why the ADMIN grant is inert) and gating the button on the SAME permission the next screen enforces (`AmplopDigitalPage` now computes `canSubmitSettlement` server-side and passes it down) — the exact "gate the control on what the action enforces" shape this repo's delivery-shipment entries already name twice. `collections:collect` still gates the unrelated collections/setoran flow; it was never meant to double as the settlement gate.
- **The writer now re-derives the receivable's ownership instead of trusting the screen's own scoping — same fix wave.** `listAmplop` already scopes what a screen shows via `OR: [{ collectorId }, { delivery: { order: { salesmanId } } }]`, but `submitSettlement` never re-checked it: any `input.salesmanId` could claim any receivable at the right store, as long as it was `OUTSTANDING`/`PARTIAL`. A raw request naming a receivable that belongs to a DIFFERENT salesman or collector at a shared store passed every existing guard and would stamp a PENDING settlement over money the caller has no relationship to. The only release path is a `collections:manage` holder noticing it in the finance approval queue and rejecting it by hand — nothing chases a PENDING settlement — so the guard is the real defence, not a first line of one. Fixed with a `NOT_ASSIGNED` guard mirroring `submitCollection`'s `NOT_ASSIGNED_COLLECTOR` in `lib/finance/collections/submit-writer.ts` — widened the receivable `select` to include `collectorId` and `delivery.order.salesmanId`, refuse when input.salesmanId matches neither. *(Since receivables gained a second source, the salesman half compares against `resolveReceivableSource`'s `salesmanId` — the order's salesman for a delivery-backed receivable, the report's own for a sell-through one — and a report with no salesman resolves to `null`, which matches no caller, so only its collector can claim it. See the receivable-source entry at the end of this file.)* A parallel `STORE_NOT_FOUND` check was added alongside the existing `SALESMAN_NOT_FOUND` one, for the identical `relationMode = "prisma"` reason: `StoreSettlement.store` is a required, FK-less relation, and a receivable pointing at a deleted store would otherwise commit a row that throws `Inconsistent query result` on every later read through it.
- **Both claim aggregates now filter on `storeId` too, not just `status` — same fix wave, and a pure lock-contention fix with no semantic change.** Under SERIALIZABLE every plain SELECT takes a shared-mode lock, and `@@index([status, createdAt])` leads on `status` alone, so `where: { …, settlement: { status: "PENDING" } }` S-locked the WHOLE PENDING range across every store, and step 6's insert (defaulting to PENDING) lands in that same range. Two salesmen submitting for completely unrelated stores could deadlock each other, retry, and past the retry ceiling (or a transaction timeout, whose `P2028` is not retryable) surface a bare `UNEXPECTED` while holding a store's cash — exactly the failure mode end-of-day submission clustering would trigger. Adding `storeId: input.storeId` to both the `storeSettlementInvoice` and `storeSettlementDeduction` aggregates changes no semantics (the receivable/retur are already proven to belong to that store by the guards above) and moves the optimizer onto `@@index([storeId, status])`, making contention per-store instead of global.
- **`proofUrl` on a `PROGRAM`/`ADMIN_FEE` deduction is now DERIVED from the audited `proofR2Key`, never accepted as a second independent field — same fix wave.** `uploadToR2` already returns `${PUBLIC_URL}/${key}`, so the URL is fully reconstructable; a new `urlFromKey` export on `lib/r2.ts` (the inverse of the existing `keyFromUrl`) does that reconstruction in the writer. Before this, a raw caller could pair a validly-scoped, validly-prefixed `proofR2Key` with an arbitrary `proofUrl`, and a downstream screen (the finance approval queue, or the BKM print route) would render the attacker's URL while the audited key pointed at real evidence. `RETUR_OFFSET` rows are untouched by this — see `docs/FOLLOWUPS.md` for why that gap is deliberately left open for now.
- **`submitSettlement`'s inputs are now bounded — same fix wave.** A `"use server"` export is independently callable by a raw request that never went through the client's own limits (the note `Textarea`'s `maxLength`, one photo per deduction row). Unbounded, a caller could hit a `Decimal(15,2)` range error on a bare `1e20` amount, a MySQL 1406 truncation on an oversized note, or run 10,000 sequential per-line aggregates inside one serializable transaction — all surfacing as a bare `UNEXPECTED` instead of a named, cheap-to-reject code. `MAX_LINES` (200), `MAX_NOTE_LENGTH` (1000), `MAX_PROOF_KEY_LENGTH` (191, the real MySQL `VARCHAR(191)` ceiling — 300 was never it), `MAX_PROOF_URL_LENGTH` (191, checked against the DERIVED url `urlFromKey` produces, since that url is always longer than the key it comes from) and `MAX_AMOUNT` (999,999,999.99, comfortably inside the `Decimal(15,2)` range) all throw the shared `INPUT_TOO_LARGE` code except the amount ceiling, which reuses `INVALID_AMOUNT` since it is conceptually the same failure as a non-positive amount. Both length checks run for EVERY deduction type, `RETUR_OFFSET` included — a whole-branch review found they originally sat after the loop's own `if (type === "RETUR_OFFSET") continue`, so a `RETUR_OFFSET` deduction's caller-supplied `proofUrl` (the create block persists it verbatim whenever no `proofR2Key` accompanies it) skipped both checks entirely and could die at insert with a MySQL 1406 data-truncation error instead of this named code.
- **Settlement approval is a RESUMABLE SEQUENCE, not a transaction, and the status flip is deliberately the LAST write (branch `feat/settlement-approval`).** `approveSettlement` (`apps/web/lib/finance/ar-settlement/approve-writer.ts`) posts up to four kinds of component against the settlement's own invoices — every retur draw, then the trade-program deduction, then the admin fee, then the cash — and only once all of them have committed does it CAS-flip the document to `APPROVED`. It cannot be one transaction: `recordPayment` and `applyReturnOffset` each open their own `prisma.$transaction`, and nesting those on the same client is unsafe. What makes a crash mid-approval safe instead is that **every component carries a DETERMINISTIC idempotency key** — `settlement-<settlementId>-<PAYMENT_METHOD>` for cash/program/fee (keyed on the METHOD, not the deduction type, because there is no `CASH` deduction type for a method to be derived from), and `returoffset-<returnId>-<deductionRowId>` for a retur draw, which reproduces the key `applyReturnOffset` mints internally rather than inventing a `settlement-` spelling of its own. Re-approving therefore finds what already posted, posts the remainder and flips. A settlement reading `APPROVED` means every component committed; a settlement stranded `PENDING` means some may have, which is why the queue screen renders each component as Posted / Voided / Not posted yet. **The flip is last for a second reason beyond resumability, and this is the obligation slice 3 handed forward:** the submit writer's retur and invoice claims are DERIVED from `PENDING` settlements, so a settlement that stops being `PENDING` stops reserving anything. Flipping ahead of the components would leave every other document's headroom overstated by exactly this settlement's amount for the width of that window — the same reasoning that makes `appliedValue` a projection rather than a reservation. The two remaining inherited obligations are satisfied the same structural way: AR moves only through `recordPayment`'s atomic `decrement` (nothing here hand-rolls it), and the self-exclusion obligation is still vacuous because approval added no edit path — it binds whoever adds one. The flip's own `runSerializable` has exactly one early return, the `flipped.count === 0` arm, and it is write-free, per the `updateDeliveryDatesAction` rule already in this file: `runSerializable` COMMITS on a normal return, so an early `return` placed after a write commits that write while reporting a refusal. `approveSettlement` posts **no journals** — `approveSettlementAction` loops `postArJournalSafely("ar_payment", …)` over EVERY id in the returned `paymentIds`, not just the first, since one approval posts one payment per retur deduction row plus up to three more (trade-program, admin fee, cash) — `RETUR_OFFSET` is one of the four component KINDS, not a fourth singleton beside the draws; `Journal @@unique([sourceType, sourceId])` absorbs the repeat on an `alreadyApproved` replay.
- **A resumed retur component must RE-ENTER `applyReturnOffset`, never be skipped on the strength of its payment already existing — this cost a full review round and the failure is permanent and silent (branch `feat/settlement-approval`).** The component loop's resume skip is correct for the cash/program/fee components, because `recordPayment` projects nothing onto any other row: once its payment exists there is nothing left to do. It is WRONG for a retur draw. `applyReturnOffset`'s replay branch exists precisely to re-run `projectReturnOffset`, which is what writes `FieldReturn.appliedValue` and `offsetStatus`; a run that committed the payment and then died before the projection landed leaves the credit drawn with `appliedValue` stale at 0 and `offsetStatus` still `AVAILABLE`. Skip the re-entry and nothing ever repairs that — the resumed approval sees the payment, skips, and flips the document to `APPROVED`. **This needs no process kill to reach:** `projectReturnOffset` opens its own `runSerializable`, and a P2034 serialization failure after `withRetry` exhausts its attempts is enough. The consequence is not local, which is what makes it worth an entry rather than a comment: a stale `appliedValue` overstates that retur's headroom at SUBMIT time for every later settlement, so a salesman files a document the submit guard accepts and the approval writer then refuses. That is this file's own "`totalValue − appliedValue` is the spendable credit" landmine arriving from a direction the index does not name. The loop is therefore split by kind, with the `COMPONENT_VOIDED` refusal hoisted ABOVE the split so it applies to both, and the retur arm calls `applyReturnOffset` unconditionally (it is idempotent, refuses a voided replay on its own terms, and re-projects). On that replay path the allocations passed are `[]` on purpose: the writer returns from its replay branch before it reads them, and if the payment had somehow vanished between the lookup and the call, an empty list fails closed on `ALLOCATION_MISMATCH` rather than silently posting a short draw. Do not "optimise" the retur arm back into the skip.
- **Approval's server-side re-validation must be scoped to what THIS settlement still owes, or a resume is impossible and the document is stuck forever (branch `feat/settlement-approval`).** The obvious specification is to re-check that every selected receivable is still `OUTSTANDING`/`PARTIAL`. Implemented literally that passes spec compliance and fails correctness on the same line: the check runs on every attempt, resumes included, so a receivable that THIS settlement's own already-posted component paid off blocks the retry with `NOT_OUTSTANDING`. A crash between the last component and the CAS flip then leaves money moved, the document `PENDING` forever, and no path out but hand SQL. The fix is not to drop the check — it is to split it. **Existence and store ownership stay unconditional** (`RECEIVABLE_NOT_FOUND`, `WRONG_STORE`), because neither can be caused by this settlement's own writes. **Collectibility moved below `computeComponentHeadroom` and is exempted on TWO terms, both carried on `HeadroomRow` alongside the capped allocation figure.** `settlementAllocated > 0` — a component of THIS settlement already allocated against that receivable — and `agreedRemaining <= 0` — this settlement's whole agreed share of the invoice is spent. Either way the closed status is explained by this document rather than surprising. **`agreedRemaining` alone was NOT enough, and shipping it alone was half a fix**: it is derived from the agreed figure only, so whenever `StoreSettlementInvoice.amount` exceeds the live balance at approval time — a verified `CollectionSubmission` paying the invoice down between submit and approval is enough, since those two writers deliberately do not net each other — one component closes the RECEIVABLE while leaving part of the agreed share unspent, `agreedRemaining` stays positive against a now-`PAID` row, and the resume throws `NOT_OUTSTANDING` permanently. It needs no process death either: the flip's own `runSerializable` exhausting `withRetry` on a P2034 opens the window. The tell that such a refusal is spurious is that `min(live, agreedRemaining)` is 0 for that row, so `allocateOldestFirst` never allocates to it and `recordPayment` is never called against it — the check refuses over a receivable it would not touch. **Do NOT collapse the two terms into "skip whenever the effective headroom is zero"**: `outstandingAmount` is that same `min()`, so the collapsed rule also skips a receivable some OTHER channel closed before approval ever ran, which is the genuine refusal this check exists for, and re-reports it one block down as `COMPONENT_EXCEEDS_HEADROOM`. Only the AGREED side of the minimum may excuse a closed status. **Ordering that the review did not name and that a later edit will get wrong:** the collectibility check must run BEFORE the `totalOwed > totalHeadroom` comparison, because a receivable closed by some OTHER channel also leaves zero headroom — the other order reports `COMPONENT_EXCEEDS_HEADROOM` for it, pointing the operator at the invoice selection instead of at the real cause, and silently kills the fresh-approval refusal. Both pre-flights (invoice headroom and retur credit) count only components that have NOT already posted, for the same reason. The finance screen's checklist re-runs all of this read-only through `lib/finance/ar-settlement/checks.ts`, and its specs pin the scoping in BOTH directions — drop the posted-key term from `buildHeadroomCheck` and a resumable settlement renders headroom FAIL with Approve permanently disabled, leaving finance able only to reject a document with real payments behind it.

- **The stock ledger sits BESIDE the balance tables rather than replacing them, and each of the three obvious alternatives was ruled out for a concrete reason (branch `PR #311`).** `StockLedgerEntry` is one location-keyed movement table — `locationType`/`locationId` (`""` for MAIN, the store id for STORE, the user id for VAN), a signed `qty`, the post-move `balanceQty` **at that location**, and a `[refType, refId]` back-reference to the document that moved it. `InventoryValue`, `StoreStock` and `VanStock` all stay, unchanged, and remain the read path for current stock. **Converging them into one location-keyed balance table** was rejected on three counts: it contradicts the client's explicit decision that `VanStock` is not rewritten, it has nowhere to put `reservedQty` (a main-only concept with no store or van analogue), and it rewrites every stock read in the repo. **Deriving balances from the ledger** (event sourcing) was rejected because `reservedQty`, `avgCost` and the atomic guards all live in `InventoryValue` and are raced by concurrent webhook workers across processes — in particular the guarded `UPDATE … WHERE (qtyOnHand - reservedQty) >= n` stops being expressible at all once the balance is a fold over events rather than a column. There is deliberately **no Prisma relation on `itemId`**: under `relationMode = "prisma"` there is no database FK, and a required relation with a dangling id throws `Inconsistent query result` forever with no repair path — a ledger is history and must outlive the row it describes.
- **History was NOT backfilled from `StockMovement`, and reconstructing it later would bake today's drift in permanently (branch `PR #311`).** `StockMovement` stores a running balance per row, but only seven paths ever appended to it — GRN, opname, production, vendor returns, reconciliation, the UMKM opening-stock manifest (`apps/web/lib/reconciliation/umkm-opening-stock.ts`) and manual adjustment — every field-sales path (konsi transfer out, van load out, field-retur restore in, reservation consume) wrote `InventoryValue` and a `StockAdjustment` and no `StockMovement` at all. So its running balance already disagrees with `InventoryValue.qtyOnHand` on any item that has been through konsi, van or field retur, by an unmeasured amount. A reconstructed ledger built from it would therefore be *wrong and authoritative-looking* — strictly worse than no history, because the new table's whole value is that its balances can be trusted. Cutover instead wrote **one `OPENING` entry per LEDGER KEY**, so every location's series starts from a figure that matches the balance table it was read from, and pre-cutover movements are simply absent rather than fabricated. Per KEY, not per balance ROW, and that distinction was a review fix rather than the original shape: the ledger stores exactly one spelling of "no variant" (`""`), while `InventoryValue` and `VanStock` both legitimately hold a `null`-spelled and a `""`-spelled row for the same item — MySQL does not enforce `@@unique` across NULLs — so a per-row insert put two entries at one ledger key, dedup-guarded on the normalised key, which either double-counts the opening balance or drops one row's units depending on how MariaDB evaluates the self-referencing `NOT EXISTS`. Both outcomes are permanent: the ledger is append-only and the migration is one-shot and re-run-guarded. The MAIN and VAN inserts therefore `GROUP BY` the normalised key and `SUM`, with `refId` naming `MIN(id)` as a REPRESENTATIVE of a possibly-folded bucket rather than its sole source; `StoreStock` stays per-row because its `variantSku` is `NOT NULL` under a real unique key. The non-zero test moved to `HAVING SUM(...) <> 0` deliberately — the opening balance of a ledger key is the SUM over its bucket, so a bucket of `+5` and `−5` genuinely holds nothing and must get no entry, while a zero row beside a non-zero one must still get one carrying the full sum; filtering rows out first answers both of those wrong. `StockMovement` was untouched by that branch and its drift was never repaired. It has since stopped being written at all, which FREEZES the drift rather than fixing it — every archived running balance stays exactly as wrong as it was on the day the writes stopped, and the ledger still holds nothing from before its own cutover, so neither table can be used to repair the other.
- **Delta movers and set movers are different shapes on purpose, and only the set movers may read before they write (branch `PR #311`).** `moveMainStock`/`moveStoreStock`/`moveVanStock` take a signed `qtyDelta` and apply it as an atomic `increment`, taking `balanceQty` from the update's own return value — they may pre-read to RESOLVE which row to write (`moveMainStock` does exactly that when the caller has not pinned an `inventoryValueId`), but the balance itself must never come from a read — a read-then-write on the quantity loses to the concurrent webhook workers, and that race is the entire reason the atomic-increment rule exists. `setMainStock`/`setStoreStock` take an absolute `nextQty`, because the opname snapshot and the store stocktake approval both replace the figure rather than adjusting it; a physical count is authoritative by definition, so last-writer-wins is the correct semantics and a pre-read is legitimate. They append an `ADJUSTMENT` entry whose `qty` is `counted − previous`, which the delta form cannot express. Two consequences worth stating: a set that changes nothing short-circuits and writes NO entry, while NO delta mover has such a short-circuit (it may still need to write `avgCost`/`totalValue` when the quantity does not move), so a no-op Jubelio stock webhook does write a `qty: 0` MAIN row. `moveStoreStock` and `moveVanStock` lack the short-circuit just as `moveMainStock` does, but that is not currently observable on the store side: both konsi-retur writers skip a zero line at the CALL SITE before they ever reach a mover, so the all-zero "lost sack" receive — explicitly valid on every line — produces no entry rather than a `qty: 0` one. Treat the guard as the call site's, not the mover's, and do not claim a store-side zero row exists. Now that the ledger has a read surface, the zero rows that ARE written are visible to an operator, and both the store detail card and the movement view render them on purpose rather than filtering on `qty !== 0`: the ledger is the record of what happened, and a processed document that moved nothing is a real event rather than noise. And cost was folded INTO both mover families rather than left as a follow-up `.update` at each call site, because five legitimate direct balance writes would have made the write guard either unenforceable or so exception-riddled that it hid the real offenders.
- **Every migrated site that moves `qtyOnHand` by a DELTA now does so atomically while writing `totalValue` as an absolute derived from a pre-read, so under a concurrent interleave the two can be mutually INCONSISTENT where they were previously consistently stale (branch `PR #311`).** This is a real change in the failure mode, uniform across the delta-moving sites by design and not a defect in any one writer. It does not apply to the set-mover sites (opname — both its FG/accessories lines and its fabric aggregate — and the store stocktake), which write BOTH columns as absolutes and so stay consistently stale in the old way. The FG/accessories half reached that state late: it shipped on this branch routed through the DELTA mover, which is a different defect entirely (see the absolute-count entry below) and was fixed in the same review wave. Before, a costing path read the row, computed a new quantity AND a new `totalValue` from that snapshot, and wrote both absolutely: a concurrent writer's change was lost, but the two columns still agreed with each other. Now the quantity half is an atomic `increment` that composes correctly with a concurrent writer while `totalValue` is still an absolute computed from the pre-read snapshot — so the quantity can reflect both writers and the value only one. The trade was taken deliberately: the quantity is the figure the guards, the available-to-sell derivation and the ledger all depend on, and making it lossless is worth `totalValue` being reconcilable-after-the-fact rather than wrong-together. Do not "fix" it by reverting the quantity half to a read-modify-write. A proper fix computes the value delta and increments it too, which needs each call site's costing arithmetic restated as a delta and was out of scope here.
- **`moveMainStock` refuses a decrement that would cross zero, atomically, and main is the ONLY location guarded that way (branch `PR #311`).** Routing the delta sites through an atomic `increment` quietly removed a floor that used to hold by accident: each of them pre-reads the row, computes a non-negativity guard from that read, and previously followed it with an ABSOLUTE write of the guarded figure — so a concurrent interleave lost an update but could not produce a negative balance. With an atomic decrement against a base that may have moved, the delta-moving sites could drive `qtyOnHand` below zero — `app/actions/inventory.ts`, `production.ts` twice, `costing.ts`'s `reverseInventoryValue` (the vendor-return path) and its `reverseMovingAverage` (the GRN-decline path), `reconciliation/umkm-opening-stock.ts`, and `inventory/reconciliation-runner.ts` — none of them inside `runSerializable`, and only `reverseInventoryValue` carrying a guard of its own (its pre-read `Insufficient stock` throw); `reverseMovingAverage` and `reconciliation-runner.ts` have none at all and depend entirely on the mover's floor. Two corrections to the list this entry first carried, both worth knowing because they change WHICH code the floor protects: `inventory/opname-approve.ts` is NOT on it, because a later commit in the same wave moved the FG/accessories opname onto `setMainStock` (see the absolute-count entry below) and `setMainStock` has NO floor — a physical count is authoritative, and a set landing negative means the counter wrote a negative number, not that a race occurred; and the unguarded `costing.ts` path is `reverseMovingAverage`, not `reverseInventoryValue`, which the first version of this entry had the wrong way round. The fix is in ONE place rather than eight: the floor is a condition in the UPDATE's own `where` (`qtyOnHand: { gte: -qtyDelta }`) on both of `moveMainStock`'s paths, so the refusal is atomic with the decrement, and a miss throws the greppable `MainStockNegativeError` naming the item, the delta and the live quantity. Never clamp it and never swallow it — `available = qtyOnHand − reservedQty` is derived at read time and feeds `loadVan`, `reserveKonsiFieldSalesOrder` and the Jubelio stock push, and a negative main row has no repair path short of an opname. `moveStoreStock` and `moveVanStock` are deliberately NOT guarded: a store balance goes negative on purpose (an SPG sale at a konsi store can outrun its ledger) with a stocktake as the documented correction, and main has no such routine correction.
- **An absolute physical count goes through a SET mover; routing it through the delta mover is wrong twice over, and the second way is permanent (branch `PR #311`).** The FG/accessories opname shipped on this branch computing `counted − current` from its own pre-read and handing that to `moveMainStock`. Two defects, not one. The row then lands at `previousActual + delta`, which is NOT `countedQty` if anything moved between the read and the write — while the `StockAdjustment` row written beside it records `newQty: countedQty`, so the two disagree with nothing to reconcile them, and a count's whole contract is that the counted figure is what ends up in the table. And `ledgerTypeForDelta` types the entry `IN` or `OUT`, where every other count in this system writes `ADJUSTMENT`; the ledger is append-only, so that spelling could never be corrected. `setMainStock` with the counted absolute fixes both. `SetCommon` gained an optional `unitCost` in the same change, recorded on the ledger entry only (a count does not reprice stock), so a set-mover entry carries the same unit cost the delta-mover entry it replaced did.
- **The reservation-versus-movement distinction is pinned by REVIEW only — no test asserts that a reservation writes no ledger entry (branch `PR #311`).** `packages/db/src/reservation-writer.ts` performs nine balance-adjacent writes: three move `qtyOnHand` (each paired with exactly one `appendStockLedger` call) and six touch only `reservedQty` or `StockReservation` (each with none). That split is the invariant the whole ledger rests on — if a reservation logged a movement, every reserved-then-released order would appear in the ledger as stock that came and went. The specs covering that file are typing tests plus DB round-trips that assert what IS written; none counts entries and asserts a zero, so the file would still pass if a future edit logged an entry per reservation. A DB-backed count assertion is the missing gate. The same file is also the one documented exception to the movers, for two reinforcing reasons. Its raw guarded `UPDATE`s are cross-process race guards — `WHERE qtyOnHand >= n` on the field-sales consume, `WHERE (qtyOnHand - reservedQty) >= n` on the konsi reserve — which cannot be Prisma calls at all; note that only ONE of the file's three raw statements moves a balance quantity, the second moving only `reservedQty` and the third updating `StockReservation`. And every `qtyOnHand` write in it, that one raw statement and the two plain `tx.inventoryValue.update`s alike, decrements `reservedQty` in the same statement — splitting that pair would strand stock reserved against nothing, permanently.
- **The ledger's read surface is exhaustive over a REGISTRY, tolerant of the COLUMN, and the registry itself is held by review rather than by the compiler — three separate guarantees that must not be collapsed into one.** `StockLedgerEntry` finally has a read side. A pure grouper and a query layer in `apps/web/lib/inventory/stock-ledger-card.ts` fold one item's rows into one section per (location, variant) across MAIN, STORE and VAN, resolving the polymorphic `locationId` through two batched lookups because `relationMode = "prisma"` leaves nothing to join on; `/backoffice/inventory/movements` renders them behind `inventory:view`, re-checked inside the action rather than trusted from the page's redirect, since every `"use server"` export is independently callable. The store detail card was repointed off its `KonsiTransferLine` + approved-`FieldReturnLine` joins onto the same TABLE, which is why it can finally explain an SPG sale or a stocktake correction instead of showing two of the five things that move `StoreStock` — **but not onto the same MODULE — and that is now HALF true rather than wholly true**: both readers import `LEDGER_ROW_SELECT`, `LEDGER_ORDER_BY` and `isCeilingReached` from `apps/web/lib/inventory/ledger-query.ts`, so the `select` block, the newest-first ordering and the fetch-ceiling test are one thing in one place. Everything above that primitive stays per-surface, deliberately and permanently: `store-stock-card.ts` keeps its own item-name lookup, its own href resolution and its own flat shaping, because the two readers answer different questions — item-scoped across every location and sectioned by (location, variant) on one side, store-scoped across every item and flat on the other, with batched lookups resolving different entities. Forcing the store card through the movement view's sectioning would distort a shipped screen to remove a duplication smaller than it looks. The drift that remains is real and narrower, and the `refType` filter this note once named as the HYPOTHETICAL example is now the actual one: the warehouse and movement-type filters ship on the movement view and the store card has neither. Logged in `docs/FOLLOWUPS.md` and deliberately NOT ticked closed — the open half is a per-behaviour question about which surfaces owe what, never an invitation to unify the two shapes. The typing then runs in layers on purpose, and confusing them breaks the screen in opposite directions. **The WRITE path does not type `refType` at all** — `AppendStockLedgerInput` and both mover input types declare it a bare `string`, so a writer can pass a value that belongs to no registry and it compiles with `tsc` silent, the label map never consulted, and both read surfaces rendering the bare identifier to an operator. `STOCK_LEDGER_REF_TYPES` in `packages/db/src/stock-ledger-ref.ts` is the union, and the `satisfies StockLedgerRefType` annotations dotted through the writers pin those EXISTING call sites only; nothing obliges a new one to carry one. The compiler enters exactly one step later, and only once someone independently adds the value to the registry: `LEDGER_REF_MESSAGE_KEY` in `apps/web/lib/inventory/ledger-ref-display.ts` is a `Record` over the union, so a new MEMBER fails to compile until it has a message key. The honest statement is therefore that registry membership is a convention enforced by review, and the compile error polices only its second half — do not restate it as a compiler guarantee standing between a new writer and a bare identifier on screen, because a rule that overstates its own enforcement buys false confidence and is worse than no rule. Even that half gets you as far as the KEY and no further: the locale files are not type-checked against the map, so the copy itself stays a manual edit in both `en.json` and `id.json`, caught by a test rather than by `tsc`. The COLUMN, meanwhile, is a free-form `String` that genuinely holds values outside the registry today — test fixtures on the shared dev database write `"TEST"` rows, and a writer can always land before its registry entry does — so a `Record` indexed on a raw value type-checks clean and returns `undefined` at runtime. Every read therefore goes through `ledgerRefMessageKey` (and, for the store card's badge variant, its own `isStockLedgerRefType` guard) and falls back to rendering the raw string, the same rule the grouper already applies to a `locationId` that resolves to no store or user: render what you have, never drop the row, never throw. History has to outlive its subject, and without a database FK the subject can genuinely disappear. The same asymmetry binds ENUMERATION and not only labelling, and that half is the one that looks safe while it is not: any surface that lists the registry members as a CLOSED SET — the options behind a filter, a set of grouping buckets, tabs, a validation allow-list — is exhaustive over the union and not over the column, so the moment it is used to NARROW, every row spelled outside the registry drops out silently and no option is left that would bring it back. The failure is invisible in exactly the state an operator starts in, because a control with everything selected sends no filter at all and shows those rows perfectly; it appears only once they narrow, which reads as the filter working. A registry-built control therefore needs an explicit out-of-registry class of its own, for the same reason the label map needs its raw-value fallback — and widening the registry is not that fix, since it is exhaustive over the union by construction and the column can always hold a value it does not know. Three boundaries are worth stating because they read as omissions. **At least THREE tables carry a `refType` column over three unrelated vocabularies — `StockLedgerEntry`, `StockMovement` and `RejectedGoodsLedger` — and they OVERLAP**, so membership in one is never evidence about another. The overlap IS the trap, because these vocabularies were long described here as distinguishable by spelling shape (the ledger's CamelCase against the others' SCREAMING_SNAKE) and that is simply false: at least one spelling is a valid member of more than one of them, written a few lines from a ledger append in every path that writes both tables. So feeding one table's values through another's resolver does not fail cleanly the way "nothing collides, everything falls back to the raw string" suggests — most values fall back, the colliding ones resolve, and the operator gets a half-translated column that reads as a missing locale key rather than as the table mix-up it is. That is exactly the shape the main stock card's repoint had to avoid, and did: it resolves the ledger's own vocabulary through `ledgerRefMessageKey` like every other ledger surface. The live direction of the trap is now the other one — reusing that resolver to label a `StockMovement` or `RejectedGoodsLedger` value looks safe-because-nothing-collides and is not. Do not enumerate which spellings collide — that list rots; treat the overlap as a class and never fold the sets together in either direction. **Second, `OpeningBalance` is written by the cutover MIGRATION and by no TypeScript writer at all**, including one `locationType: 'STORE'` row per non-zero `StoreStock` row — so it is both reachable at a store and the OLDEST row on that card, the first thing an operator scrolls to. Any claim about which `refType`s can appear at a location has to be derived from the writers AND the migration; deriving it from the TypeScript writers alone is precisely how a "closed set" ends up missing its most visible member. And third, the main stock card has since moved onto this same table, so the two-tables-different-coverage split is gone and every movement screen answers from the ledger. What separates them now is SCOPE, not source: the card filters `locationType: "MAIN"` and the movement view deliberately does not.
- **An empty filter array has to reach the query as "match nothing", and the `length > 0` guard that turns it into "match everything" reads as harmless defensive code at every review layer.** A `where` arm written `if (x !== undefined && x.length > 0)` makes `[]` and `undefined` indistinguishable to the database. `undefined` genuinely is "no filter" and nothing over the wire spells "match nothing" on its own, so the guard looks like it is merely skipping an empty term — while the inversion it produces is total: an operator who unticks every box is handed the ENTIRE unfiltered set, and nothing throws, warns or logs. Where the same guard also feeds a SEPARATE predicate behind an empty-state message, the damage is NOT that the screen contradicts itself: while both halves carry the bug they agree, both go unfiltered, every section is full and the empty-state copy never renders at all. The contradiction appears only in the HALF-FIXED state — one predicate made to fail closed while its sibling still fails open, so the table shows nothing while the count behind the copy still answers the unfiltered question. That state is not hypothetical; it is what this work shipped for one commit, and it is exactly what the structural sharing described next exists to make unreachable. `getItemMovementCard` is the worked example of the fix, in two parts. Each array argument has its own builder — `buildRefTypeCondition` and `buildLocationTypeCondition` — whose result is computed ONCE and assigned into both the main `where` and the `historyWhere` behind `hasAnyHistory`; that sharing is structural rather than a promise to keep two literals in sync, and two independent predicates answering the same question is precisely how `sections` and `hasAnyHistory` disagreed before it. And each builder returns `{ ... : { in: [] } }` for an empty selection, because an empty array is a SELECTION and only `undefined` is an absence. The two arms did not arrive there together: for one commit `refTypes` failed closed while `locationTypes` still failed open, two sibling arguments of one function disagreeing about the same input with nothing on either saying why, which is how it was caught. When one filter arm changes meaning, its siblings are the first place to look and not the last. The mirror-image decision — collapsing "everything ticked" back to `undefined` — is a real one too and fails quieter, and it is split across both layers here rather than living in one: it is correct ONLY when the control's full selection genuinely selects every row the column can hold. The movement view renders an out-of-registry class as one more option in the movement-type filter, so `refTypes` collapses to "no filter" only when that class is ticked as well — "every registered member ticked, unregistered EXCLUDED" differs from it by one checkbox, is a real `refType IN (registry)` filter, and must still travel as an explicit pair of arguments. `buildRefTypeCondition` encodes exactly that (the collapse branch tests the registry length AND the flag) and the page mirrors it in the `allRefTypesSelected` it computes before the call. Sending the rendered option list instead of collapsing would behave identically today and would start excluding rows the day the column holds a value the control does not render, which on a free-form column is a matter of when rather than if. That class travels as its own BOOLEAN and never as a sentinel string inside `refTypes`: a sentinel riding an `in`/`notIn` array leaks straight into the SQL list the moment anything downstream forgets to strip it, and a boolean cannot — the sentinel exists only inside the component's own selection state and is split back out immediately before the wire call, which is also what lets it ride "select all" and the control's empty-selection guard for free. The control keeps a policy of its own on top of all this and both layers stay: `MultiSelectFilter` refuses the toggle that would empty the selection, so the query layer's fail-closed behaviour is currently unreachable from that one screen. The refusal is a UX choice, since an empty grid is a dead end the operator has to undo; the `in: []` is a correctness floor for every OTHER caller — a second screen, a server-side default, a saved-filter feature — and neither substitutes for the other. Other optional-array filter arms elsewhere in `apps/web` still carry the `length > 0` shape and inherit none of this; importing a helper never inherits the choice either. Two further things about that shared query primitive (`apps/web/lib/inventory/ledger-query.ts`) read as tidy-up invitations and are not. `LEDGER_ROW_SELECT` is the INTERSECTION of what the two readers select, each spreading it and adding its own extras, rather than one block both over-select from — over-selecting is how a payload quietly grows. And `isCeilingReached` is `===` while `isSectionTruncated` in `stock-ledger-card.ts` is `>`: the first tests a FETCH ceiling, where `take` caps the row count so equality is the only comparison available and over-warning is the harmless direction, and the second tests a DISPLAY cap over a fully-known count, where at exactly the limit nothing is hidden and flagging it would lie to the operator. Be precise about what the extraction moved, because the loose reading invites exactly the fold it warns against: only `isCeilingReached` went into `ledger-query.ts`, and all three named helpers stayed where their callers and tests import them from — `isQueryTruncated` and `isSectionTruncated` in `stock-ledger-card.ts`, `isStoreMovementsTruncated` in `store-stock-card.ts`. What changed is that the two FETCH-ceiling helpers, `isQueryTruncated` and `isStoreMovementsTruncated`, are now thin wrappers over that one shared implementation; `isSectionTruncated` is not and never was, because it tests the display cap. Two of the three sharing one implementation is what makes folding in the third look like the obvious next step. It is still wrong.
- **The registry needs its own package subpath because a client component imports it, and the identical barrel leak landed in two files and took two separate fix rounds.** `@elorae/db`'s main barrel eagerly loads Prisma and the mariadb driver, so a `"use client"` file importing anything from it — a plain `const` array, or a `type` sitting beside a value import — risks dragging the driver into the browser bundle. `packages/db/package.json` therefore exposes `./stock-ledger-ref` as its own export, and both client-reachable consumers import from `@elorae/db/stock-ledger-ref`: `ledger-ref-display.ts`, which the movement page's client component imports, and the store detail card's `StoreStockCard.tsx`. The second one is the instructive half. It was written by copying the first while the first still imported from the barrel, so the fix that added the subpath export repaired only the file it was looking at, and the copy had to be found and fixed on its own afterwards — a reviewer reading either diff in isolation sees a correct file. The query layer itself (`stock-ledger-card.ts`) does import the barrel and always will; it is server-only, which is exactly why the movement action folds `QUERY_ENTRY_LIMIT` into its own return shape instead of re-exporting the constant for the client to import — a client importing even a number from that module would pull the whole import graph with it.
- **The `StockMovement` retirement finished by giving the ledger its own VALUE columns, and the price was a second cutover inside the first (PR #317, merged 2026-09-21).** The asymmetry that had held the old table alive was real: `StockMovement` carried `unitCost`, `totalCost`, `balanceQty`, `balanceValue` and a free-text `notes`, while `StockLedgerEntry` carried `unitCost` and `balanceQty` and none of the rest, so the ledger could answer "how many moved, and how many were there afterwards" at every instant and could never answer "what was it worth afterwards". Two readers were held on the old table by that alone — the main stock card, a screen, and `opnameNetDelta`, a general-ledger posting — and the assumption was that closing the gap needed `totalCost == qty × unitCost` demonstrated against real historical data. **It did not, and the reason is the thing to carry forward: `opnameNetDelta` runs at POSTING time for a NEW opname and never re-reads an already-posted one.** So once the opname writer stamps the SAME `totalCostAdj` onto the ledger row that it was already computing for its `StockMovement` row, the two agree BY CONSTRUCTION from that point on, no backfill and no equality proof required, and every journal posted before the change stays untouched. The same held for every other writer: each already had its `totalCost` and `balanceValue` in scope at its `stockMovement.create`, so carrying them into the ledger was passing an existing value, never deriving a new one. **`totalCost` and `balanceValue` are therefore NULLABLE with no backfill, and null means UNRECONSTRUCTIBLE rather than zero.** Every row the ledger already held carries null, and nothing can recover those values — the moving average at that instant is recorded nowhere else, and `qty × unitCost` is the wrong number anyway, since `unitCost` is what one movement cost rather than the running average the balance was valued at. Value history therefore starts at this migration while quantity history started at the ledger's own earlier cutover: a second cutover nested inside the first, and the only two dates a reader of these columns can reason from. **A real `0` is the opposite claim and an equally legitimate one**, which is why it cannot be collapsed into null in either direction: an item that has never been costed is genuinely worth nothing, so the fabric-aggregate opname path (`syncFabricAggregateQty` in `apps/web/lib/inventory/opname-snapshot.ts`) lands a real zero rather than leaving the columns undefined, at both of its branches and by two different means: the set-mover call passes an UNGUARDED `delta * avgCost`, which already evaluates to zero when the item has never been costed and is more truthful than a guard that would substitute null, and the row-provisioning `OPENING` append beside it passes a literal `0` because the row it just created sits at `avgCost: 0`. Stamping null there would make every opname on an as-yet-uncosted fabric item refuse to post, because **`opnameNetDelta` treats a null `totalCost` as a HARD ERROR and throws.** Summing an unknown as zero would post an inventory-variance journal short by exactly that row's value, with nothing on screen to flag it and an append-only ledger behind it; a loud failure at posting time is strictly better, since the only way a null reaches it is data that predates the columns. Never soften that throw into a `?? 0`. **The movers forward both values and compute neither.** `moveMainStock`/`moveStoreStock`/`moveVanStock`/`setMainStock`/`setStoreStock` accept them and pass them straight to `appendStockLedger`; the caller owns the cost basis, and a mover that invented one would disagree with the balance write sitting beside it. **The stock card's repoint cost two columns and gained a scope filter.** `getStockCard`/`getStockCardByType`/`getStockCardByCategory` in `apps/web/app/actions/stock-card.ts` now read `StockLedgerEntry`, scoped to `locationType: "MAIN"` — without that filter the ledger's store and van rows silently join the main warehouse's card without looking wrong on screen. Opening balance reads the stored `balanceQty` off the last row before the range rather than summing `qty`, and a null `balanceValue` renders an em-dash placeholder rather than `Rp 0`, with a standing note on the screen saying value history begins at this migration; the CSV export writes an empty cell for the same reason. The `notes` column is gone for good — `StockLedgerEntry` has none and nothing derives one — so the column renders permanently empty rather than being removed, keeping the print layout identical across every stock-card kind; do not "restore" it from `refDocNumber` or a refType label. The in/out split is taken from the SIGN of `qty`, never from the type: `StockLedgerType.ADJUSTMENT` is signed either way and `OPENING` is a balance snapshot whose `qty` equals its own `balanceQty`, so a type-driven split mislabels both. **`deleteItem`'s guard counts BOTH tables, for two different reasons, and dropping either is wrong differently.** `StockMovement.item` remains a REQUIRED Prisma relation with no database FK behind it, so an archived row pointing at a deleted item throws `Inconsistent query result` on every read that joins it, forever — stopping the writes froze the archive rather than emptying it, so that count is still the only thing standing in front of a permanent crash. `StockLedgerEntry` declares no relation to `Item` at all, deliberately, so its rows are safe to orphan and can never crash a read; its count refuses the other failure, silently stranding live stock history behind a deleted item. Each count looks individually droppable and neither is. **What this does NOT do.** It does not recover a single pre-migration value, and it never can. It does not repair `StockMovement`'s historical drift; it freezes it. It does not drop the table or the model — both are kept as a frozen archive, still read by that delete guard and by `getItemVariantOptions`'s three-way union, whose old-table half can now only fall further behind. And it leaves `packages/db/prisma/seed.ts` writing `StockMovement` rows with no ledger row beside them, which is the inverse of the production shape and is logged in `docs/FOLLOWUPS.md` rather than fixed here.
- **Store-to-store transfer moves stock at APPROVE, through both movers in one transaction, and deliberately does not check whether the source can afford it (PR #317, merged 2026-09-21).** `StoreTransfer`/`StoreTransferLine` (`apps/web/lib/stores/transfer/writer.ts`) close the last gap in inter-warehouse movement: main→store already existed as the konsi transfer and store→main as a field retur, but store→store had no document at all. It is a new pair of models rather than a widened `KonsiTransfer`, which has no source-store concept and is bound to a `FieldSalesOrder` this document has no reason to carry. **Creation moves nothing.** A `PENDING` transfer is paperwork; `approveStoreTransfer` is the only thing that calls `moveStoreStock`, once out of the source and once into the destination inside one serializable transaction, so cancelling is a pure status flip with no ledger entry and nothing to reverse — that is why `cancelStoreTransfer` is so much shorter than its neighbour, and it is not an oversight. **The cost basis is the source's `avgCost` re-read at APPROVE, never the create-time snapshot.** Each line still stores the source store's `StoreStock.avgCost` as `unitCost` when the document is staged (zero when the source holds no row yet) — that figure is the document's own record of what it was estimated at when raised, fine for a screen to show — but `approveStoreTransfer` re-reads the source's CURRENT `avgCost` inside its own transaction and hands that figure, not the snapshot, to both legs. This shipped the other way once and was wrong: the source can legitimately reprice between create and approve (an ordinary konsi transfer landing there is enough), and handing the stale snapshot to both legs while the source's own `balanceValue` is computed from its current average meant the source's row disagreed with its own arithmetic and the transfer moved value into or out of existence by the size of the reprice. Re-reading at approve for both legs is what keeps the source's row internally consistent and makes the destination receive exactly what the source gave up. The source leg omits `avgCost` entirely — removing units at the current average leaves the average unchanged, which is what every other store-side decrement in this repo does — while the destination leg BLENDS through `weightedAvgCost`, clamping a negative existing balance to zero for the blend only, since averaging a cost against units that are not physically there uses a negative weight and inflates the result. **An insufficient source balance is ALLOWED, and that is a decision rather than a gap.** `moveStoreStock` carries no floor guard because a store balance is permitted to go negative in this system with a stocktake as the correction path; `moveMainStock`'s `MainStockNegativeError` is main-only for the reasons in its own entry above. So there is no pre-check on the source, and adding one would make this writer the only store-side path that refuses what the others accept. **Both status flips are a CAS, and the CAS is the guard.** `updateMany` filtered on `status: "PENDING"` runs BEFORE any stock moves and throws on a non-1 match count, which is what makes a double approval impossible and what makes cancelling an APPROVED transfer structurally unreachable rather than merely refused — the `where` can only ever match a row still pending. Every failure path in both writers THROWS rather than returning, because `runSerializable` is a plain `prisma.$transaction` that commits on a normal return, so a `return { error }` placed after the CAS would commit the flip while reporting failure. **An APPROVED transfer has no reversal.** There is no un-approve and no compensating document; the correction is a second transfer the other way, raised and approved like any other. **The move time is recorded, and a count that already saw the move blocks the approval (PR number on merge).** Ops moves goods first and records the transfer afterwards, and stock moves only at approve, so a count taken in between records the move as a shortfall at the source and a surplus at the destination. `StoreTransfer.movedAt` is the instant the goods moved: a required WIB date and time on the create form, defaulting to now, never later than now (`MOVED_AT_IN_FUTURE`), read with an explicit `+07:00` and round-trip checked (`parseMovedAtInput`) so a UTC server cannot shift it. It is an instant rather than a day so that a count earlier on the move day stays before the move. Approve refuses `COUNTED_SINCE_MOVE`, naming the counts, when either store has an APPROVED count whose moment (`countFinishedAt ?? approvedAt`) is on or after it and which COUNTED one of the transfer's item::variant keys (a line with a `countedQty`), because applying the move now would record it twice. A partial count of other items, a count of another variant of the item, or a line left uncounted never saw the move and does not refuse. The check runs after the CAS, so a repeat approval still reports `INVALID_STATE`, and before any stock moves; it throws, rolling the CAS back with it. The only remedy is to cancel, and the move then stands as variance. The stocktake and sell-through guards key on the same column (their entries). Existing transfers were backfilled with `COALESCE(approvedAt, createdAt)`. A transfer still PENDING at deploy is therefore dated to its creation and may become unapprovable, which is correct if its goods moved when it was raised; otherwise cancel it and raise it again with the real move time. **The cancelling actor is recorded in `AuditLog`, not in columns.** `StoreTransfer` has no `cancelledById`/`cancelledAt` — unlike `StoreStocktake`, which has both plus a reason — and reusing `approvedById`/`approvedAt` would misrepresent the document as approved, so the writer writes an `AuditLog` row inside its own transaction instead, the same way `rejectCollection` covers the identical gap on `CollectionSubmission`. Anything that needs to show who cancelled reads that table. **All three actions re-check `stores:manage` themselves** and the read surfaces take `stores:view`; no new `Permission` row exists or is needed, which is deliberate in a repo whose deploy migrates but never seeds.
- **Konsi stock now moves at delivery-shipment COMPLETION, one `KonsiTransfer` per completed shipment — the approve-time transfer decision was reopened, not patched (PR #318).** Approve only RESERVES: `approveFieldSalesOrder`'s konsi branch still runs `reserveKonsiFieldSalesOrder` (the guarded `(qtyOnHand − reservedQty) >= n` raw UPDATE, so a short order is still refused with `InsufficientStockError`) and still prices the lines, but no longer calls `issueKonsiTransfer` — main `qtyOnHand` is unchanged, no `StoreStock` row moves and no ledger entry is written. The stock moves when a delivery shipment for the order completes: `completeDeliveryShipment`'s konsi branch calls `issueKonsiTransfer` with the DELIVERED quantities and the shipment's id, which lands on the new nullable `@unique` `KonsiTransfer.shipmentId` (no hand-authored FK behind it). **Why it was reopened.** The approve-time entry above was accepted on two conditions — no client story for partial konsi shipment, and the transfer staying one-to-many from the order — and told whoever found either broken to reopen rather than patch. The delivery epic's stock-on-completion story is that client story: it asks for konsi stock to reach the store's virtual warehouse when a delivery is marked complete, and for a failed or partial delivery to return the remaining qty to warehouse stock. This change takes the escape hatch that entry named — several transfers against one order, one per shipment — with no data-model rewrite beyond the link column. **Partial consume.** `issueKonsiTransfer` no longer flips the line's reservation to `CONSUMED` in one step. Per line it first runs one atomic `UPDATE StockReservation SET consumedQty = consumedQty + n WHERE fieldSalesLineId = ? AND state = 'RESERVED' AND consumedQty + n <= qty` — the idiom `consumeFieldSalesOrderPartial` uses — BEFORE any balance write for that line, throws `KonsiTransferReservationMismatchError` on zero rows, and flips the row to `CONSUMED` only once `consumedQty` reaches `qty`. `StockReservation` is not a balance table, so that raw statement needs no stock-balance-guard entry. Everything else in the function is unchanged: the pinned `findExistingInventoryValueRow` + `moveMainStock`, the `reservedQty` decrement on the same row id immediately after, the `StockAdjustment`, and the store leg's `weightedAvgCost` blend through `moveStoreStock`. **One transaction.** The konsi completion tail is a single `runSerializable`, in this order: the `IN_TRANSIT` status CAS `updateMany` carrying every POD field (first, so a concurrent second completion throws `INVALID_STATE` before any stock moves), the shipment lines' `deliveredQty`, `issueKonsiTransfer` for the lines with `deliveredQty > 0` (an all-zero completion writes no transfer), the order lines' `deliveredQty` increments, and the order's `deliveryStatus` through `nextDeliveryStatus`. That is stronger than the putus path's two-transaction tail, which is unchanged. It writes no `FieldSalesDelivery`, no `Receivable`, no `TaxInvoice` and no journal; `deliveryId` stays empty, which is what keeps `completeShipmentAction`'s journal posting off. `MISSING_DATES` is PUTUS-only at both ship and completion, since a konsi order raises no invoice. Every refusal the transfer raises leaves as a typed code, `instanceof`-mapped in one catch: `KonsiTransferReservationMismatchError` → `KONSI_NOT_RESERVED`, `MainStockNegativeError` (main's floor) → `DeliveryError` `INSUFFICIENT_STOCK`, `InventoryValueMissingError` → `NO_INVENTORY_ROW` — all terminal in the offline completion classifier, which would otherwise retry an unmapped `UNEXPECTED` to its ceiling. `issueKonsiTransfer` also refuses a non-positive or fractional draw itself rather than trusting its caller to filter. **Remainder.** A short or refused line stays outstanding and still reserved. The admin either packs another shipment for it — a second transfer against the same order at its completion — or runs Close remainder: `closeFieldSalesOrderRemainder` dropped its PUTUS-only refusal, and `releaseFieldSalesOrder` widened its source filter to `FIELD_SALES` and `FIELD_SALES_KONSI` both, because the konsi release would otherwise match nothing and strand the reservation. Releasing is what "remaining qty returned to warehouse stock" means here: those units never left main. Close remainder is REFUSED with `DeliveryError` `SHIPMENT_IN_FLIGHT` while the order has any shipment `PACKED` or `IN_TRANSIT` — putus as well as konsi — checked inside its transaction before any write: the release flips each line's WHOLE reservation (a partial release per reservation is not expressible), so an in-flight shipment would then complete against nothing — `KONSI_NOT_RESERVED` for konsi, `OVER_DELIVER` for putus — with its goods already on the truck, and netting the planned qty out instead would still let an admin close units that are physically travelling. The konsi shipments card disables the button with that reason. `createDeliveryShipment` likewise refuses any order that is not `APPROVED` (`INVALID_STATE`), since neither a putus nor a konsi shipment against one could ever complete. Cancelling a shipment reverses nothing, because nothing moved before completion. **The accepted window.** Between ship and completion main `qtyOnHand` still counts goods that have physically left — the same shape putus already has — while available-for-sale (`qtyOnHand − reservedQty`) stays correct throughout because the reservation covers them. In exchange the store's `StoreStock` no longer claims goods that are still on a truck, so a stocktake opened during transit no longer counts them as present. **Legacy orders, and why a legacy shipment fails closed structurally.** The migration tells the konsi orders that were `APPROVED` when it ran apart per LINE, by the line's `StockReservation`, into three historical populations: (a) transferred in full at approve — reservation `CONSUMED`; (b) approved before reservations existed — no reservation row at all; (c) approved after reservations existed but before the transfer document did — reservation still `RESERVED`, `reservedQty` still held on main. Only (a) and (b) are marked delivered to their full `qty` (and only lines with `cancelledQty = 0`, which every legacy line has, since close remainder refused konsi then). A (c) line is left an ordinary approved-and-reserved line — shippable or closable from the order detail page, either of which resolves its held reservation through the UI — so those orders now show as outstanding konsi work until an admin ships or closes them; marking them delivered would have stranded their `reservedQty` for good. The order becomes `DELIVERED` only when every one of its lines is fully delivered after that, so an order holding a (c) line keeps its status. Both UPDATEs are safe to re-run by construction — the line predicate never touches a live reservation, a closed line or an already-delivered one. Legacy transfers keep `shipmentId = null`. `getFieldSalesOrderById` surfaces only that null-linked transfer, as `legacyKonsiTransfer`, and it alone drives the order header's Surat Keluar button; a legacy order delivered in full shows a "delivered at approval under the previous flow" state on its shipments card instead of the empty one. Every later order prints a Surat Keluar per shipment from that card, at planned qty under the shipment's own docNo (the `DELIVERY` counter) — the `KONSITRF` number is minted at completion and never printed. `KONSI_NOT_RESERVED` means the line holds no `RESERVED` reservation with enough headroom; the partial-consume guard affects zero rows, throws, and the whole completion rolls back including the status CAS, so no double move is reachable. With packing refused on a non-`APPROVED` order and close remainder refused while a shipment is in flight — the two ways ordinary use used to create it — it is reachable only for a konsi shipment packed before this change, or for an order the PREVIOUS release approved after the migration ran: the deploy's `migrate` job runs before `deploy-web`, so for that window the old image still transfers at approve, consuming the reservation while leaving `deliveredQty` at 0. The remedy for the second is re-running the migration's two UPDATEs (see `docs/FOLLOWUPS.md`). It surfaces as the `DeliveryShipmentErrorCode` `KONSI_NOT_RESERVED` (copy in both locales, terminal in the offline completion classifier) rather than as an unhandled throw. The migration carries no `SIGNAL` for the case; the guard is the protection. **Assortment knock-on.** Approved but not yet delivered konsi qty (reserved or in transit) now sits on nobody's `StoreStock`, so both gap tests — `listAssortmentGaps` and the approve-time `currentAssortmentGapKeys` — add it back through ONE helper, `openKonsiQtyByKey` (`apps/web/lib/field-sales/konsi-open-qty.ts`), which takes the caller's client so the approve path reads inside its own transaction. `AssortmentGapRow.onHandQty` stays physical and the open qty travels separately as `inTransitQty` (the field name predates the wording: it covers packed and unpacked qty alike), summed only inside the gap test and shown as a muted "+N on order, not yet delivered" hint on both gap tables — never pre-added into `onHandQty`, which is the figure a store keeper checks against the shelf. **Other readers of konsi quantity.** `sentItemIds` counts an item once it appears on a non-rejected konsi line that is not fully cancelled, so a line closed with nothing delivered no longer marks the item sent; `getStoreSentItems` sums konsi `deliveredQty` rather than the approved `qty`; and `updateStore`'s KONSI → PUTUS guard refuses not only while `StoreStock` holds a non-zero row but also while the store has a konsi order awaiting approval or approved with qty neither delivered nor closed — completing such an order after the switch would land stock on a PUTUS store's `StoreStock`, where nothing can correct it.
- **A konsi sell-through report classifies what left a consignment store over one counting period, and moves no stock; approving it is what bills the store (PR #319).** `KonsiSellThrough`/`KonsiSellThroughLine` (`apps/web/lib/konsi-sell-through/`, new `DocType.SELLTHRU`, prefix `SLT/`) are the report half of consignment: what a KONSI store sold between two of its counts, verified before anything can bill it. **Anchored on a count.** An admin creates a report FROM an approved store stocktake with `isFullCount` true, at a KONSI store with `Store.sellThroughMethod` set, through a button on that stocktake's backoffice detail page; the stocktake becomes the report's closing count. `checkSellThroughPreconditions` (`writer.ts`) refuses, in this order, a missing, unapproved or partial stocktake, a missing or non-KONSI store, an unset method, a stocktake a live report already uses (`ALREADY_USED`, carrying that report's id so the detail page can link to it), a stocktake whose boundary precedes the store's earliest `STORE` ledger row (`BEFORE_LEDGER_CUTOVER` — a count approved before the ledger's cutover, or before the store's first recorded movement, closes a window with no history behind it), a stocktake that does not close after the previous approved report's closing count (`OUT_OF_ORDER`), a count taken while a retur was in flight (`RETUR_IN_FLIGHT`, below), a count taken while a store transfer that moved goods it counted was still pending (`TRANSFER_IN_FLIGHT`, below), and a store that already has a DRAFT. The order is what the eligibility check shows: `ALREADY_USED` first because it is the one the page turns into a link, then the refusals that make the count permanently unusable, then the ones that clear on their own. The eligibility check behind the button runs that same function read-only rather than a copy of it. Reports form one chain per store: `previousId` is the store's latest APPROVED report, `chainKey` (`${storeId}:${previousId ?? "root"}`) makes a second live successor of the same report a unique violation — which is what caps a store at one DRAFT under concurrent creates, the explicit `DRAFT_EXISTS` check being only the readable path — and `stocktakeKey` does the same for the closing count. Both keys are nulled on cancel, and that is the whole reason they exist instead of the plain `@unique` on `closingStocktakeId` the design first called for: a plain unique would make a cancel permanent and leave the count unusable for a corrected report. **The window.** Every `STORE` ledger row of the store lands in exactly one report: `(previous boundary, boundary]`, where a boundary is the max `createdAt` of that report's closing stocktake's own `StoreStocktake` rows, falling back to the stocktake's `approvedAt` only when the count changed nothing and so wrote no rows. Defining the boundary by the rows it must contain is what stops one approval's rows splitting across two reports; `approvedAt` is stamped separately in the stocktake writer after those rows, and leaning on that ordering would tie this invariant to another file's statement order. Neither is a commit time: a row's `createdAt` is fixed when its insert runs — Prisma 7 even builds `@default(now())` in the client, one `new Date()` per query — so a transaction still open when a boundary is read can later commit a row stamped at or before it (the race logged in `docs/FOLLOWUPS.md`). A database-side default would not close that gap. The next report closes that race one level deep — see **Carry-forward** below. The window query also carries an OR arm that pulls in the closing stocktake's rows whatever their date and a NOT arm that drops the previous closing stocktake's; both are dead under the one-open-stocktake-per-store rule and are not a safety net, since either one firing would double-count. **Openings.** A store's first report has no openings and no lower edge: its window starts at the ledger's cutover, and the cutover migration's `OpeningBalance` rows are classified as opening rather than movement. Every later report takes its openings from the previous APPROVED report's per-line `closingQty` — not from a scan for the last `balanceQty`, as the design first described — so each report opens exactly where the last one closed. **Derivation** (`deriveSellThroughLines`, `derive.ts`, import-free): per (item, variant), `KonsiTransfer` and the positive `StoreTransfer` leg are IN; `FieldReturn` and the negative `StoreTransfer` leg are OUT, for both retur origins, so an ADMIN return's receipt-time and approve-time decrements both count; `SpgSale` is POS-sold; and `StoreStocktake` is the GAP, `−Σ qty`, so a shortfall is positive — the opposite sign to `StoreStocktakeLine.varianceQty` — and every count in the window contributes, mid-period and partial ones included. Any other `refType` refuses the whole report with `UNKNOWN_REF_TYPE` — an out-of-registry value, but equally a registry member the switch does not name — because a movement the derivation cannot classify would otherwise drop out of a billed quantity. `closingQty = opening + in − out − posSold − gap` is ledger-derived; `countedQty` is the closing stocktake line's own figure, shown beside it. **Billing by method.** `SHELF_COUNT`: `billedQty = opening + in − out − closing`, clamped at 0 with `negativeSold` set when the raw figure is negative; POS rows are informational and no line ever holds. `SPG_POS`: `billedQty` starts at POS-sold, and every line with a non-zero gap HOLDS approval until an admin saves a resolution — a shortfall resolves as `BILL` (billed += gap) or `SHRINKAGE` (written off, reason required), a surplus as `BILL_POS` (billed stays at POS) or `REDUCE` (billed = POS + gap, floored at 0, reason required). The stocktake line's recorded cause prefills `suggestedResolution` (`UNRECORDED_SALE` → `BILL`, `SHRINKAGE` → `SHRINKAGE`), but only a saved `resolution` releases the hold. The method is snapshotted onto the report at creation, and the hold, the resolution rules and approve all read that snapshot rather than the store's current setting. `unitCost` snapshots the store's `StoreStock.avgCost` at creation (0 where the store holds no row) and is the cost basis of invoicing's COGS and shrinkage journals (the invoicing entry below). **Returns in flight.** A retur takes its goods off the shelf when it is raised, but `StoreStock` only drops later — at approve for a FIELD retur, at receipt plus an approve-time delta for an ADMIN one — so a count taken in between records the returned units as a shortfall — a phantom gap the report would bill. `RETUR_IN_FLIGHT` therefore refuses a closing count when any retur of the store, either origin, was raised on or before the count moment (`countFinishedAt`, or `approvedAt` for a count saved before that column existed) and is still `PENDING_WAREHOUSE_RECEIVING`, `MISMATCH_PENDING_RESOLUTION` or `PENDING_APPROVAL`, or was approved only after that moment; `detail` names the returns. Settling the retur later does not clean the count, which is why a late approval refuses as well as a pending status. `approvedAt` is the settle moment for both origins, which is conservative for an ADMIN retur whose clean receipt already decremented at `receivedAt`. The remedy is never to use that count: finish or cancel the returns, then close the period with a later count — the contaminated count's own rows then sit mid-period and net out against the later count's, because the gap sums every stocktake row in the window. **Transfers in flight (PR number on merge).** A store-to-store transfer has the same shape: its goods move before its approval moves stock. `TRANSFER_IN_FLIGHT` (`assertNoTransferInFlight`, run from the same two places as the retur check) refuses a closing count while a PENDING transfer touching the store — from it or to it — and moving an item::variant the count counted, has `movedAt` on or before the count moment; `detail` names the transfers. Stocktake approval already refuses that case while the count is open (`TRANSFER_PENDING`), so what reaches here is a transfer recorded after the count was approved (or a count approved before that refusal existed), which can then only be cancelled (`COUNTED_SINCE_MOVE`); cancelling it lets this same count close the period, with the move standing in it as variance. There is no approved-later arm, unlike returns. A transfer approved after the count has its rows inside the window, and stocktake approval skipped exactly those rows, so the report derives it as in/out with no gap. **Approve** re-checks, in order, that the store is still KONSI (`NOT_KONSI`), that no retur and no store transfer was in flight at the closing count (so a DRAFT created before either rule cannot slip through), that re-deriving the period inside its own transaction still yields every stored figure (`STALE`), and only then that no SPG_POS gap line is unresolved (`HELD`) — the re-derivation runs before the hold so an admin is never sent to resolve lines on a report that must be cancelled anyway. `STALE` catches any movement that reached the period after creation: a row stamped at or before the boundary by a transaction that committed after the report read it, or a late row landing in the previous report's period, whose carried figures are part of the comparison. Its remedy is cancel and recreate, never a refresh in place, so an approved report always shows the figures the admin reviewed. Approval then freezes the document and invoices it — the invoicing entry below. `updateStore` refuses a KONSI → PUTUS switch while the store has a DRAFT report (`StoreHasDraftSellThroughError`), since approve would then refuse it for good. **Carry-forward (PR number on merge).** A row stamped at or before an approved report's boundary, in a transaction that committed after that approval, belongs to no window. So each report re-derives its previous report's window with that report's own inputs (openings from its predecessor's stored `closingQty`, its boundary, its snapshotted method) through `computeLateMovements` (`late.ts`). It compares the result against the previous report's stored in/out/POS/gap MINUS the `lateInQty`/`lateOutQty`/`latePosSoldQty`/`lateGapQty` that report had itself carried, and adds the non-zero per-key differences into its own buckets before closing and billing. Those differences are stored in the same four columns, and `hasLateMovements` flags the line with a badge on the detail page, beside a note naming the previous report. A line carrying late figures is kept even when its totals net to zero, since dropping it would lose them and the next report would carry them again. The subtraction is load-bearing: without it, every report after one that carried late movements would re-bill them negated. Create and approve both run it inside their own transaction, so the late figures are part of approve's `STALE` comparison. The previous report's lines and invoice are never modified. Depth is one level: a row committing after two reports are approved is caught by neither (`docs/FOLLOWUPS.md`). **Permissions** reuse `stores:manage` for create, resolve, approve and cancel and `stores:view` for the list and detail pages — no `Permission` row, nothing to seed. **What it deliberately does not do.** No money at creation: a DRAFT has no `Receivable`, `TaxInvoice`, journal or nota — every one of those comes from approval, which became invoicing once receivables and fakturs gained a second source document (the receivable-source and invoicing entries below). No stock: the stocktakes already SET `StoreStock` — to the counted figure plus whatever moved after the count was saved — so the report only classifies what left, and approval calls no mover. No SPG batch-report screen: POS already is the SPG's per-sale record, and a second manual report of the same sales would double-count against a `StoreStock` that POS already decrements — the epic's literal wording was ruled out, not skipped. No scheduling: nothing opens a count, creates a report or reminds anyone, so a store nobody counts is never reported and never verified. No notification when a report holds. `SpgSale` is unchanged and keeps writing `SalesHistory`, which is the forecast's demand signal, not GL revenue.

- **Approving a konsi sell-through report invoices it: one approve with two modes, and a store's first report may instead be a no-invoice baseline (PR #322).** Migration `20260924200000_konsi_sell_through_invoicing` adds `invoiceDate`, `dueDate`, `total`, `baseline` and `baselineReason` to `KonsiSellThrough` and `unitPrice`/`lineTotal` to `KonsiSellThroughLine`. `approveSellThrough` (`apps/web/lib/konsi-sell-through/writer.ts`) keeps every re-check the report entry above lists, in the same order, and only then branches on `mode`. **INVOICE.** Every line is priced through `priceSellThroughLines` (`pricing.ts`, import-free beyond the `@elorae/db/pricing` subpath), the same function the DRAFT preview runs, so the screen cannot show a figure approve then disagrees with. Then, in order: a billed line with no price refuses `UNPRICED`, its `itemId::variantSku` keys in `detail`; an invoice date outside the period-end day through today refuses `INVALID_INVOICE_DATE` (`isInvoiceDateAllowed`, `invoice-dates.ts`), compared as WIB calendar days rather than instants, because the picker sends WIB midnight and an instant comparison would refuse the period-end day whenever the closing count finished later that day; a total above zero with no salesman refuses `SALESMAN_REQUIRED`; a salesman who is not a candidate refuses `SALESMAN_INVALID`. A zero-total INVOICE approval therefore creates no receivable and no faktur and needs no salesman, but its COGS and shrinkage journals still post wherever their cost is non-zero: a billed line whose item sells at 0 prices at 0, which is a price and not `UNPRICED`, so a zero total can still carry billed units and the cost they relieve. **Why a flagged price counts as no price.** `computeStorePrice`'s KONSI branch never reads the discount, and for a missing or out-of-range margin it returns the raw selling price with `flagged: true` rather than null; billing that figure would invoice below the store price with nothing on screen to say so. Nothing is written before the refusal, so the remedy is fixing the item's selling price or the store's margin and approving again — unlike `STALE`, no cancel. **Who owns the receivable.** `SALESMAN_CANDIDATE_WHERE` (`salesman-candidates.ts`): a user on a non-system role holding both `settlements:submit` and `pwa:access` — someone who can file the store settlement from the PWA, the same shape as `listCarrierCandidates`. The dialog's list and the writer's check read that one predicate. The dialog prefills the salesman on the store's most recent KONSI `FieldSalesOrder`, only while that user is still a candidate. That salesman is what puts the receivable into an amplop and lets its holder settle it (the amplop entry above). **BASELINE.** A store's first report only (`previousId` null, else `BASELINE_NOT_FIRST`), with a required reason (`BASELINE_REASON_REQUIRED`, capped like every other reason on the report). It stamps `baseline`/`baselineReason` and prices nothing: no receivable, faktur, journal or nota, and the next report opens from its closing figures as from any approved report. It exists because a first report has no lower edge — its window runs from the ledger's cutover — so a store invoiced by hand for part of that span would otherwise be billed for those units twice. It is first-report-only because every later report opens where an approved one closed, which leaves nothing for a later baseline to correct. The migration marked every report already `APPROVED` before invoicing existed as a baseline with the reason "Approved before invoicing existed.", so none of them can be mistaken for an invoice that was never raised. That makes the COLUMN wider than the MODE: a migrated baseline can sit anywhere in a chain, not only first, and its billed units were not necessarily billed by hand — some were simply approved before the ERP could invoice them. Because nothing posted a baseline's units out of inventory, the report page shows its cost not relieved from GL inventory — Σ (billed + shrinkage) × `unitCost` — as the figure for finance's manual journal. **Journals.** `approveSellThroughAction` posts them after the writer commits, never inside it, each through `postArJournalSafely` under its own kind (`konsi_sell_through_revenue`/`_cogs`/`_shrinkage`; builders in `lib/konsi-sell-through/journal.ts`): `KONSI_SELLTHRU_REVENUE` debits `AR` and credits `SALES_REVENUE` for the total, `KONSI_SELLTHRU_COGS` debits `COGS` and credits `INVENTORY` for Σ billed × `unitCost`, and `KONSI_SELLTHRU_SHRINKAGE` debits `INVENTORY_VARIANCE` and credits `INVENTORY` for Σ shrinkage × `unitCost`. All three are dated on the report's invoice date, never on when the post ran, so a retry across a month boundary books into the invoice's period. A kind with nothing to post counts as done, and a baseline or never-invoiced report posts nothing. None of the five roles is new, so the feature adds no Account Mapping step of its own. **Retry** lives on the report's own page, not the piutang detail, and its gate is the missing journal rather than a `JOURNAL_PENDING` flag: `sellThroughJournalGaps` (`journal.ts`) returns every kind whose amount is postable and that has no `Journal` row for its source type, the page shows the banner while that list is non-empty, and `retrySellThroughJournalsAction` posts exactly those kinds. A flag would be the wrong gate twice over — it never clears, so the banner would outlive a successful retry, and a crash between the approve commit and the posts writes none, so no retry would ever appear. A missing journal is a safe gate HERE, and only here, because every report approved before invoicing existed is a baseline and owes nothing; the delivery sibling cannot use it, since every backfilled delivery has a receivable and no journal by construction (the AR journal retry entry above). Each post still goes through `postArJournalSafely`, so a retry that fails again flags it again. It is gated on `stores:manage`, this module's own permission, the way the delivery journal retry is gated on its own module's permission rather than `journals:manage`. `postJournal` is idempotent on its source, so re-posting a kind that already posted creates nothing. **The nota.** `buildKonsiSellThroughNotaHtml` (`lib/print/konsi-sell-through-nota-html.ts`) is a full-document builder printed through `printHtmlInIframe`, money at 2dp through `print-theme`'s `money()`, listing billed lines only; `getSellThroughNotaAction` refuses `INVALID_STATE` for anything but an invoiced report with a total above zero. Its first print stamps `TaxInvoice.notaPrintedAt` through a CAS on `sellThroughId` and sends one `TAX_INVOICE_PENDING` notification, and a reprint writes only its audit row — the sell-through twin of the delivery nota's `recordNotaTagihanPrinted`, best-effort for the same reason: the paper is already printed. **What it deliberately does not do.** No reversal: an invoiced report cannot be un-invoiced, cancelled (cancel is DRAFT-only) or re-approved, and there is no credit note. No invoice-date correction — `updateDeliveryDatesAction` has no sell-through twin. No GL entry for a surplus: the count that SET the extra units into `StoreStock` posts nothing, and only shrinkage is journalled. No GL entry for a baseline beyond the figure the page shows. A line snapshotted at `avgCost` 0 relieves nothing from inventory. All of these are logged in `docs/FOLLOWUPS.md`.
