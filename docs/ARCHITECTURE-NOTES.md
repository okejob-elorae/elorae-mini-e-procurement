# Architecture notes — landmines worth flagging

The detail behind the landmine index in `CLAUDE.md`. Read the entry for whatever surface you are about to touch: each one records a mistake that already cost someone time, and several encode prod-measured findings. Split out of `CLAUDE.md` on 2026-08-25 so 6k tokens of it stop riding along in every session; the text is unchanged. When a change makes an entry wrong, fix it here in the same session — and update the matching one-liner in `CLAUDE.md` if the trigger itself moved.

- **Field sales (putus/konsi) is PER-VARIANT as of PR #144 (2026-07-17) — D15 SUPERSEDED.** `InventoryValue` is keyed `(itemId, variantSku)` and Jubelio-ingested variant items are stored entirely per-variant (real `variantSku` rows, no pooled row) — prod-confirmed. The PWA catalog exposes per-variant availability (`CatalogItem.variants[]`); a variant sheet picks variants; putus/konsi order lines carry the **real** `variantSku`; reserve/consume already keyed per line → per-variant `StockReservation`. **Min-qty aggregates per item**; **promos aggregate per item then pro-rate** across variant lines via shared `applyItemAggregatedPromos` (writer + preview → quote == recorded order). **Simple items (no `Item.variants`) stay item-level** (`variants: []`, inline stepper, cart `variantSku ""`, null/"" tolerant lookup). **Canvassing (van load/sale/reconcile) is ALSO per-variant (Track B, PR #146):** `VanStock`/van docs keyed per `variantSku`, backoffice load form picks per-variant (item block), PWA van sell groups by item + variant sheet, sale/reconcile stamp the variant label into `productName`; no schema migration; van stock has no reservation dimension. See `docs/BOUNDARY.md` D15. Caveat: a variant item restocked via ERP GRN/production writes a `null` pooled row the per-variant sale won't see (Jubelio feeds them per-variant, so rare). **A strict `""`-keyed lookup forks a phantom row** — `calculateMovingAverage`'s strict `""` key did exactly that on the canvassing reconcile path (caught and fixed pre-merge; see `docs/EPIC-STATUS.md` sub-8), and the same strict lookup is still live and unfixed in `reconciliation-runner.ts` (see `docs/FOLLOWUPS.md` § Inventory). Note the inverse also holds: variantless `InventoryValue` rows key on `null`, while simple-item carts and `VanStock` deliberately key `""` — so an id may legitimately arrive as either, and every lookup must be OR-tolerant (`OR: [{ variantSku: null }, { variantSku: "" }]`) rather than "corrected" to one spelling.
- **Putus stock now leaves at DELIVERY, not at approve (PR #229, merged 2026-08-09).** Approve is paperwork: it no longer consumes stock and no longer writes `SalesHistory`. A putus order ships in parts through `FieldSalesDelivery`/`FieldSalesDeliveryLine` (`recordFieldSalesDelivery` in `apps/web/lib/field-sales/delivery/writer.ts`), each delivery consuming its own slice via `consumeFieldSalesOrderPartial` and writing its own `SalesHistory` rows keyed by the delivery `docNo` (an order number would collide on the second delivery of the same variant). `FieldSalesOrder.deliveryStatus` (PENDING/PARTIAL/DELIVERED/CLOSED) plus `FieldSalesOrderLine.deliveredQty`/`cancelledQty` track progress; `closeFieldSalesOrderRemainder` cancels every still-open line at once, releases the leftover reservation and stamps `closedAt`/`closedById`/`closeReason`. **`FieldSalesDelivery.docNo` is NOT always `DLV/`-prefixed** — the backfill migration gave every pre-existing approved putus order one full delivery carrying the ORDER number, so never pattern-match the prefix. Order/line discounts are pro-rated per delivery and the closing delivery absorbs every remainder, including residue stranded on a line that finished in an earlier delivery, so the deliveries sum back to the order total exactly. Konsi never delivers (transfer is still recorded at approve).
- **Every nota tagihan carries exactly one `TaxInvoice` row (PR #239, merged 2026-08-13).** `TaxInvoice` is a satellite table 1:1 with `FieldSalesDelivery` (`deliveryId @unique`, no columns added to the delivery), created inside `recordFieldSalesDelivery`'s existing serializable transaction and backfilled for every pre-existing delivery — so `PENDING` has exactly one spelling and the queue is keyed on the nota being ISSUED, never on anyone printing it. Statuses are `PENDING`/`CREATED` (needs a faktur number)/`NOT_REQUIRED` (needs a reason), and every transition is reversible and writes its `AuditLog` row (with `changes` + `reason`) **in the same transaction as the update** — the row itself is last-write-wins, so the audit trail is the only surviving record of a superseded faktur number. Finance works the queue at `/backoffice/finance/faktur-pajak` gated on `tax_invoices:view`/`tax_invoices:manage`. First print of a nota tagihan stamps `notaPrintedAt` through an atomic compare-and-swap (`updateMany … where notaPrintedAt: null`) and fans out a `TAX_INVOICE_PENDING` notification only when the affected count is 1; reprints still audit but never re-notify. Writers in `apps/web/lib/tax-invoices/`, print action in `apps/web/app/actions/field-sales-deliveries.ts`. **The migration declares NO foreign key** (`relationMode = "prisma"`), so a `TaxInvoice` can outlive its delivery — the queue query skips orphans rather than letting one dangling row blank the whole page.
- **An approving admin can ADD never-sent products to a konsi transfer (PR #242, merged 2026-08-13).** `listKonsiSuggestions` (`apps/web/lib/field-sales/queries.ts`) lists goods never sent to this store — exclusion is **item-level** (`sentItemIds`, any variant ever sent kills the whole item, matching the writer's `ALREADY_SENT` check) while each surviving item expands to **one row per real `InventoryValue` variant**, because availability and the writer's `addedLines` are both per-variant; a `null`/`""` dual row dedupes to one suggestion at the **minimum** available (the writer reserves against a single findFirst row, so summing would offer more than it can honor). The panel (`KonsiSuggestionsCard`) stages additions client-side and `approveFieldSalesOrderAction` applies them **inside the approve transaction** — validated (unknown item, no inventory row, bad qty, duplicate, already-sent, not-konsi) before any write, priced by the same konsi gross-up as the salesman's own lines, and stamped `FieldSalesOrderLine.addedById` so the detail page can badge them. An already-APPROVED order **refuses** a payload carrying additions rather than returning its idempotent `ok` (it would report a success that created nothing). **No new permission — reuses `field_sales_orders:approve`, so nothing to seed on prod.** The client's "barang baru" wording is deliberately NOT implemented: only the never-sent criterion ships, because whether "baru" means newly-created, newly-in-season or never-sent is still an open client question (design doc D5).
- **A field salesman can raise a store retur request from the PWA (PR #245, merged 2026-08-24).** `createFieldReturn` (`apps/web/lib/field-sales/retur/writer.ts`) records what a store is sending back: lines (item + variant + qty + reason), a required photo of the store's paper nota retur, and how the goods travel (`SELF_CARRY` or `EXPEDITION` with a carrier name AND a resi — both are enforced server-side). Submitted online-only through `POST /pwa/api/retur`, which uploads the photo to R2 and then runs the writer; the multipart route validates every line's SHAPE before the upload so a malformed payload cannot strand an orphan object. **Status stops at `PENDING_WAREHOUSE_RECEIVING`** — a raised retur moves NO stock and writes no `StockAdjustment`; receiving, mismatch resolution and stock restore now ship in the warehouse-receiving half — see the next entry. Backoffice register at `/backoffice/field-returns`. **It takes its own `DocType.FIELDRET` (prefix `FRET/`), NOT `RET`** — `RET` is the vendor-return sequence used by `apps/web/app/actions/vendor-returns.ts`, and sharing it would interleave two registers on one counter and let a Settings prefix edit silently renumber vendor returns. There is **no foreign key** on `FieldReturnLine` (`relationMode = "prisma"`) while `item` is a REQUIRED Prisma relation, so the writer verifies every `itemId` exists inside the transaction (`ITEM_NOT_FOUND`) — an unchecked id would write a row whose detail page throws "Inconsistent query result" forever with no UI repair path. `deleteItem` counts `FieldReturnLine` before allowing a delete, which matters because the retur picker deliberately surfaces INACTIVE items. **Nothing to seed on prod** — no new permission (the register reuses an existing gate) and `generateDocNumber` creates the missing `DocNumberConfig` row on first use.
- **Warehouse receiving closes the other half of the field retur feature (PR #246, merged 2026-08-25).** The warehouse counts what physically arrived on a `PENDING_WAREHOUSE_RECEIVING` retur, splitting each line into sellable and rejected; any line whose count disagrees with the salesman's claim lands the retur in `MISMATCH_PENDING_RESOLUTION`, settled by an append-only `FieldReturnResolution` naming who bears it (`SALESMAN_BEARS`/`WRITE_OFF`/`ACCEPT_SURPLUS`/`INVESTIGATE`). Approving restores `sellableQty` to `InventoryValue` via a POSITIVE `StockAdjustment` sourced `FIELD_RETURN`, and routes `rejectedQty` to `RejectedGoodsLedger`. **`FieldReturnStatus` is now five members** (`PENDING_WAREHOUSE_RECEIVING`/`MISMATCH_PENDING_RESOLUTION`/`PENDING_APPROVAL`/`APPROVED`/`CANCELLED`) with **four separate `Record<FieldReturnStatus, …>` maps** across the backoffice clients — same landmine shape as the `DocType` maps documented in `CLAUDE.md` § Code conventions: `apps/web` type-check never runs locally, so a missing member surfaces only in the Docker build during deploy, after migrations have already applied. **`INVESTIGATE` deliberately settles nothing** — it records that someone will look and holds the retur in `MISMATCH_PENDING_RESOLUTION` indefinitely, by design. Resolutions stay amendable until approval, and an amendment recomputes the parent status in BOTH directions — amending a settled line back to `INVESTIGATE` pulls the retur back out of `PENDING_APPROVAL`. **Variance direction is enforced in the writer, not the UI**: only `SALESMAN_BEARS`/`WRITE_OFF` settle a shortage, only `ACCEPT_SURPLUS` settles an over-line, `INVESTIGATE` is valid both ways — a whole-branch review finding, since a user holding `field_returns:manage` but not `field_returns:writeoff` could otherwise call the action directly with `ACCEPT_SURPLUS` on a shortage and absorb the loss with nobody bearing it (every export of a `"use server"` module is an independently callable endpoint). **Zero is a valid count on every line, including all-zero** — the client's lost-sack case, when an expedition loses the whole shipment; never add a positive-quantity validation anywhere in this flow. Restored stock comes back at the **current average cost** (`newAvgCost` = existing `avgCost`) because a retur carries no cost information and blending at zero would destroy the average for everything already in stock. `RejectedGoodsLedger.variantSku` and the create-`InventoryValue` branch both normalise to `null`, never `""`, and the inventory lookup is OR-tolerant (`OR: [{ variantSku: null }, { variantSku: "" }]`) matching `apps/web/lib/canvassing/reconcile-writer.ts`. **`apps/web/lib/field-sales/retur/variance.ts` is deliberately import-free** (`lineVariance`/`isSettled`/`allDiscrepantLinesSettled`/`isValidResolutionDirection`) because a `"use client"` component imports it and any import drags the `@elorae/db` barrel (Prisma + the mariadb driver) into the browser bundle — do not add an import to it. **Liability is recorded in UNITS, never money** — this slice ends approved with stock restored and nothing valued; the value calculation is a deliberate later slice. **The surplus path (`ACCEPT_SURPLUS`, and surplus blocking approval) is our invention, not a client requirement** — the client's story only ever describes shortages. **Post-merge seed: ✅ DONE 2026-08-25** — ran `packages/db/prisma/seed-field-return-permissions.sql` on prod (`field_returns:manage` + `field_returns:writeoff`, both linked to ADMIN; verified 0 → 2 rows, and re-running the file left it at 2, so it is idempotent as written). Do not re-run it blindly. The deploy pipeline migrates but never seeds; see the admin-wildcard entry in this file for why this doesn't unblock ADMIN but does let the permissions be granted to non-admin roles.
- **A field retur is now valued in money, not just units (PR #248, merged 2026-08-25).** Every `FieldReturnLine` gained `creditedQty`/`unitPrice`/`lineValue`/`priceSource`(`DELIVERY`\|`MANUAL`)/`priceDeliveryLineId`/`priceNote`, and `FieldReturn` gained `totalValue`/`valuationStatus`(`PENDING`\|`VALUED`) — additive migration, no backfill needed since every pre-existing row is simply unvalued. Valuation happens **once, at `approveFieldReturn`**, never before: `creditedQtyForLine` (units-only, from the prior slice) times a per-unit price resolved from `listPriceCandidates` — every `FieldSalesDeliveryLine` that ever shipped this exact item+variant to this store, priced off `lineTotal` (already net of its pro-rated discounts) rather than gross `unitPrice`. One matching price on every delivery auto-resolves (`AUTO`); disagreeing deliveries or zero deliveries leave the line unpriced (`AMBIGUOUS`/`UNPRICEABLE`) and `totalValue` **null, never a partial sum** — a partial total is a number that looks complete and would be trusted downstream. `setLinePriceAction` (`apps/web/app/actions/field-returns.ts`) lets an admin resolve what auto-resolve couldn't, pre-approval only (an `updateMany` compare-and-swap against `PRICEABLE_STATUSES` guards a concurrent approve, returning `ALREADY_APPROVED` rather than silently writing nothing); its `deliveryLineId` branch **re-verifies the candidate against this line's own store+item+variant** before trusting it — skipping that would let an admin point a line at any delivery anywhere and inflate the retur's value. An admin's choice that later stops resolving (a dangling `priceDeliveryLineId`, a wiped manual price) is **preserved, not silently cleared**, on an already-APPROVED retur — it is a recorded decision, not an absence of one. **`unitPrice` is a rounded 2dp REFERENCE figure and deliberately does not multiply back to `lineValue`** (`lib/field-sales/retur/pricing-rules.ts`'s `effectiveUnitPrice` stays unrounded until the one multiply-and-round that produces `lineValue`) — the backoffice UI never renders `qty × unitPrice` as a sum for exactly this reason; `lineValue`/`totalValue` are the only authoritative figures shown. **`ACCEPT_SURPLUS` is the one path where our figure exceeds the store's own paper** (credited at the received qty, which is greater than claimed) — badged per-line and noted once at the valuation card header, so finance sees the explanation before they see the gap. `pricing-rules.ts` is deliberately import-free, same rule as `variance.ts` — but NOT for the same reason: no `"use client"` component imports `pricing-rules.ts` directly (only `pricing.ts`, `queries.ts` and `setLinePriceAction` do; `LinePriceControls.tsx`/`FieldReturnDetailClient.tsx` instead import `variance.ts` and take pre-computed values type-only from `queries.ts`). The rule is kept anyway as cheap insurance against a future client import ever dragging `@elorae/db` into the browser bundle. UI: a per-line "Penilaian Retur" card (credited qty, unit price reference, line value, provenance chip) plus `LinePriceControls.tsx` (picker for `AMBIGUOUS`, required-note manual entry for `UNPRICEABLE`, read-only + change button for `SET`, nothing for `AUTO`) rendered only pre-approval and only for `field_returns:manage`; the register gained a value column and an "incomplete" marker restricted to `APPROVED + PENDING` rows (every open retur reads `PENDING` by default, so gating on status too avoids flagging every un-approved retur as broken). **`APPLIED`/settlement wiring against the retur's value is deliberately out of scope** — this slice only computes and displays the number. **Nothing to seed on prod** — no new permission (reuses `field_returns:manage`), migration is additive only. **Whole-branch review fix wave (same branch, 2026-08-25):** the MANUAL branch of `setLinePriceAction` is now re-verified server-side too, not just the DELIVERY branch — it re-resolves the line's price via `resolveLinePrice` and refuses a manual price with a new `AUTO_PRICE_AVAILABLE` code whenever the line would already auto-resolve, since the UI withholding the manual control on an `AUTO` line is not a server guarantee (every `"use server"` export is independently callable). A manual price of exactly 0 is now refused both client- and server-side (`<= 0`, not `< 0`) — a Prisma `Decimal` of 0 is still truthy, so it would otherwise read as a complete zero valuation rather than "never priced". `approveFieldReturn` now stamps `creditedQty`/`lineValue` on EVERY line, even one whose admin price choice is being preserved-but-unresolved (only `priceSource`/`priceDeliveryLineId` stay guarded) — the old all-or-nothing guard around the whole update left `creditedQty` null forever on those lines. The detail page's valuation-card header now derives its post-approval state from `valuationStatus`/`lineValue`, the same signal the register's own badge uses, instead of `priceState` (which reads `SET` for a preserved-but-never-resolved choice and previously made the two surfaces disagree); the approve confirm dialog also now surfaces the still-unpriced line count before the operator commits. `classifyPriceCandidates` de-dupes on a rounded 2dp key, not the raw float, so two deliveries at the genuinely same price can no longer read as `AMBIGUOUS` purely from IEEE-754 noise. `totalValue` is rounded once more after summing already-rounded lines.
- **Approving a konsi order now physically moves stock (PR #253, merged 2026-08-25).** Stock leaves main in one full transfer at APPROVE — the same shape the putus flow was corrected away from in PR #229, so main understates what is really available for the window between approve and whenever the goods actually leave the building. **This is an accepted risk, and only two things make it acceptable:** no client story anywhere describes a partial konsi shipment, unlike putus where the client explicitly asked for delivery-in-parts; and the transfer document is **one-to-many from the order** (`KonsiTransfer.orderId`, not a 1:1), which is the escape hatch — partial shipment can later be added by writing a second transfer against the same order, with no data-model rewrite. If either condition stops holding — a client story for partial konsi shipment appears, or someone reworks the transfer to be 1:1 with the order — this decision must be reopened, not patched around.
- **THREE tables can now answer "how much of this item exists"**: `InventoryValue` (main), `VanStock` (per-canvasser), `StoreStock` (per-consignment-store). `getStockAcrossLocations` (`apps/web/lib/inventory/stock-across-locations.ts`) is the ONLY place allowed to fold them — nothing else may hand-roll that union. It is deliberately **not** the source of available-for-sale, which stays `InventoryValue.qtyOnHand - reservedQty`, main-only: that is what keeps consignment and van stock out of marketplace availability *by construction* rather than by remembering a filter. **Never add an `available` field to it.**
- **The variant-key hazard now has a THIRD spelling.** `InventoryValue.variantSku` is nullable and variantless rows key on `null` (see the PR #144 entry above). `VanStock.variantSku` is **ALSO nullable** — a prior version of this doc (and a comment inside `stock-across-locations.ts` itself) claimed InventoryValue was the only nullable one of the three; both are wrong. Every writer that touches `VanStock` inserts `""`, but the column itself allows `null`. `StoreStock.variantSku` and `KonsiTransferLine.variantSku` are non-nullable `@default("")`, because MySQL treats NULLs as distinct values and a nullable column would make their `@@unique([storeId/transferId, itemId, variantSku])` unenforceable. Net: every read of `InventoryValue`/`VanStock` must stay OR-tolerant (`OR: [{ variantSku: null }, { variantSku: "" }]`), every write into `StoreStock`/`KonsiTransferLine` normalises `?? ""`, and `getStockAcrossLocations` normalises before summing across all three.
- **A konsi retur can drive `StoreStock` negative, deliberately.** The goods physically arrived at the warehouse and were counted — bookkeeping must never refuse to record that reality just because the ledger disagrees. A negative row is absorbed by the next transfer to that store; **there is no manual correction path in this slice.** It is surfaced by a pre-commit warning in the retur approve dialog and by a destructive badge plus a header count on the store detail card's stock section — deliberately NOT by an `AdminNotification`, because that bell is already capped at 50 rows with no cursor and no mark-all-read (see `docs/FOLLOWUPS.md` § Notifications).
- **A `KONSI → PUTUS` `termsType` edit is refused while the store holds any non-zero `StoreStock` row, negative included** (`apps/web/lib/stores/queries.ts` `updateStore`). Without that guard the retur decrement and the whole stock card would silently stop applying to a store that reads as PUTUS, stranding the row and permanently double-counting the units with no surface anywhere that would show it.
- **The quantity a konsi retur decrements from `StoreStock` is the already-stamped `creditedQty`, reused and never recomputed.** It encodes claimed-vs-received per resolution type (see the field-retur valuation entry above), and deriving it a second way in the store-stock branch is exactly how two spellings of one rule drift apart — the writer's own comment warns against collapsing it to `Math.max(claimed, received)`.
- **`StoreStock` now has THREE writers, not two (PR #255, merged 2026-08-25).** The konsi transfer (in, PR #253 above) and a konsi retur approve (out, entries above) were already writing it; an SPG sale at a KONSI store now decrements it too (`apps/web/lib/spg/sale-writer.ts`, inside the same serializable transaction as the sale, below the idempotency short-circuit so a replay is decrement-safe with no guard of its own). A sale at a PUTUS store moves no stock at all — the store already owns those goods outright, and the gate on `termsType` is load-bearing, not defensive. All three writers normalise `variantSku` to `""`, matching `StoreStock.variantSku`'s non-nullable `@default("")` (see the variant-key-hazard entry above). **Only the transfer blends `avgCost`**; both decrement paths (retur and SPG sale) leave it untouched — removing units at the current average doesn't change the average, and a newly-created negative row from an SPG sale carries `avgCost: 0` for the same reason a konsi retur's would: a decrement with no cost information of its own has no basis to invent one. **A negative row is deliberate on both decrement paths** — the sale already happened and the cash is in the till, so the writer never clamps or refuses; there is still no manual correction path for a drifted or negative row until the stocktake slice ships. The SPG sale catalog also now shows the store's on-counter `StoreStock` quantity per row as information only — the sellable set stays unrestricted and nothing gates, caps, or gets ordered by it (see `getSellableCatalogForSpg`'s doc comment). **This slice only stops the overstatement from growing further — it does not repair what already accumulated.** Every store an SPG has been selling at before this shipped is carrying an inflated `StoreStock` row right now, and nothing here measures or corrects that historical drift; the stocktake slice is what will eventually count the shelf, quantify it, and zero it out.
- **`KONSITRF` (prefix `KTRF/`) is a new `DocType` member, so it required updating the same TWO `Record<DocType, …>` maps documented in `CLAUDE.md` § Code conventions** — `apps/web/lib/docNumber.ts` and `apps/web/app/actions/settings/doc-numbers.ts`. Missing either is a build-breaking type error that surfaces only in the Docker build during deploy, after migrations have already applied.
- **Nothing to seed on prod for this branch** — no new permission, and the migration is additive with no backfill.
- **VPS MariaDB is shared between local dev and the VPS-deployed web.** A local destructive query (delete, truncate, bad migration) hits the same data the client demo shows. Run migrations only via `pnpm -F @elorae/db migrate:deploy`; never `migrate dev --create-only` without thinking. **On prod, the deploy workflow's `migrate` job auto-applies pending migrations on every push to master, so no manual `migrate:deploy` post-merge. It does NOT seed** — RBAC/permission rows are seeded by hand (surgical SQL). Don't conflate the two. **`migrate` is gated on the image builds as of PR #240** (`needs: [pull, build-push-web, build-push-api]` + `always()` with per-build result checks): the builds are where `next build`/`tsc` type-check, and they used to RACE the migration as siblings — so a type error let the schema advance and then failed the build, leaving prod on the old image against the new schema (that is what happened on PR #229 → deploy `31293514640`). The `always()` is load-bearing, not decoration: both build jobs are `if:`-gated on the path filter and are legitimately SKIPPED on a single-service change, and a skipped job in `needs` cascade-skips its dependents — without it an api-only push would deploy nothing at all. Skipped is fine; failed is not. No automatic backups — set up daily `mariadb-dump` → R2 separately (TODO).
- **`Item` is dual-owner** (web for ERP forms; api for Jubelio catalog ingest). All api writes go through `@elorae/db/item-writer.ts` helpers, stamping `source = JUBELIO_INGEST`. See `docs/BOUNDARY.md §3.3`.
- **`StockAdjustment` is dual-owner** (web for ERP-driven adjustments; api for Jubelio stock webhooks). Api writes go through `@elorae/db/stock-writer.ts` `applyJubelioStockAdjustment`, stamping `source = JUBELIO_WEBHOOK` + `idempotencyKey`. See `docs/BOUNDARY.md §3.1`.
- **The "admin wildcard" is granted in CODE, not by a DB row.** `apps/web/lib/auth.ts:70` sets `permissions = ['*']` whenever the user's `RoleDefinition.isSystem` is true (ADMIN), and `hasPermission` short-circuits on `'*'`. There is no `*` Permission row, and ADMIN's explicit `RolePermission` links are irrelevant to access — on prod ADMIN is missing 5 of them (`journals:*`, `field_sales_orders:*`, `canvassing:manage`) with no effect whatsoever. So a post-merge permission seed does NOT unblock admin access, which already works; it makes the permission a real row so it can be granted to NON-admin roles and appear in role management. Seeding a new role with `isSystem = 1` would hand it full admin — the seeds correctly use `0`.
- **Hand-run SQL against prod needs `--skip-ssl`.** MariaDB 11.4's client requires TLS by default and the VPS server has none configured, so a bare `mariadb`/`mariadb-dump` fails with `error 2026: TLS/SSL error: SSL is required, but the server does not support it`. In a pipeline that failure is silent — `mariadb-dump ... | gzip` returns gzip's exit status, and produces a valid 123-byte empty archive. Always verify a dump with its size and a `Dump completed on` trailer. Also set `SET SESSION max_statement_time = <seconds>` before any aggregate over `SalesOrder`: a client-side timeout leaves the query running server-side, which wedged the prod tunnel twice on 2026-08-08.
- **Jubelio webhook signature is HMAC-SHA256 with header `Sign`** — not plain SHA256 with `webhook-signature`. Jubelio's docs *text* is wrong; their code example is correct. See `docs/BOUNDARY.md §9 Q1`.
- **Before using or adding ANY Jubelio endpoint, check the OpenAPI spec FIRST** (`reference/jubelio-openAPI.yaml`; memory `reference_jubelio_openapi`) — grep the path for its documented params/request/response schema. Don't guess or reverse-engineer from live probing. BUT the spec lags/misdescribes the live API (same class as the webhook-sig gotcha), so **verify the real shape live** before relying on it. Concrete gotcha found 2026-07-26 (salesorder `no→id` resolve): the spec's purpose-built `POST /wms/order/getOrderByNo/` is **pick-flow-scoped** — returns HTTP 200 with an *empty body* for completed/settled orders, so it's unusable for settlement backfill. The `q` search on `/sales/orders/completed|cancel|failed/` (what `findSalesOrderIdByNo` uses) is itself **undocumented** (spec lists only `page`/`pageSize`) and only covers those 3 status buckets → misses in-flight orders. The only lookup that resolved every status live is the (also undocumented) `GET /sales/orders/?q=<salesorder_no>` general list. Net: consult the spec, then confirm live.
- **Catalog ingest pulls from Jubelio** via `POST /jubelio/catalog/sync` (apps/api). Product push (ERP → Jubelio) is wired via the outbox — see sub-3 in `docs/EPIC-STATUS.md`.
- **Inbound webhook pipeline ships in BullMQ-backed queue.** `JubelioWebhookEvent` carries authoritative status (`RECEIVED → PROCESSING → PROCESSED / SKIPPED / DEAD`). Worker runs in apps/api process, concurrency 4 by default (`JUBELIO_WORKER_CONCURRENCY`). Sweeper rescues stuck rows every 10 min. Note: shared-state writers (e.g. `InventoryValue` aggregates) must use atomic Prisma `increment`/`decrement`, never read-modify-write — the worker is concurrent and the ERP-ship path races the ship-webhook across processes.
- **Outbound push pipeline ships in `JubelioOutbox` table + `outbox-poller` + `outbox-processor`.** Handlers in `apps/api/src/jubelio/outbox/handlers/`: `product_push`, `stock_push`, `salesorder_pick`, `salesorder_pack`, `salesorder_ship`. Already-in-state Jubelio responses are skipped (not retried). New push types add: handler file + payload builder + spec + router case.
- **Marketplace stock is reserve-at-ingest, consume-at-ship, release-on-cancel.** `StockReservation` ledger (one row per `salesorderDetailId`) + aggregate `InventoryValue.reservedQty`, driven by `reserveOrder`/`consumeOrder`/`releaseOrder` in `@elorae/db/reservation-writer.ts`. `available = qtyOnHand - reservedQty`, derived at read time — never stored. `consumeOrder` deducts `qtyOnHand` via a `StockAdjustment` stamped `source = FULFILLMENT_CONSUME`, and is idempotent so the Jubelio ship webhook and the ERP Ship button can both trigger it safely. Jubelio stock push sends `available`, not raw `qtyOnHand`. See `docs/BOUNDARY.md` D6.
- **PWA service worker gotchas** (cost hours 2026-07-06). (1) `apps/web/proxy.ts` IS the Next 16 middleware — `proxy.ts` is Next 16's rename of `middleware.ts` (compiles to `.next/server/middleware.js`, runs on every request); it is NOT dead code. Its allow-list gates `/pwa/*`; the Serwist SW script `/pwa/sw.js` is currently gated (307 → /login unauth) — a SW script behind auth is wrong (breaks update fetches). (2) The `/pwa` Serwist SW (`app/pwa/sw.ts` → `public/pwa/sw.js`) only exists in a **production build** (`next build --webpack`; disabled in dev, and Turbopack skips the plugin per PR #92) → offline behavior is testable **only on prod** (local `next start` over http has a NextAuth secure-cookie login quirk). (3) **Never commit next-pwa/serwist generated files** (`public/sw.js`, `public/workbox-*.js`, `public/pwa/sw.js`, gitignored) — a stale committed `workbox-<hash>.js` rides the Docker `COPY` into the build, poisons the SW precache manifest, then 404s at runtime → SW install fails → offline dinos (root cause of the #113 field-test failure; fixed #115). (4) Root `/` next-pwa SW (scope `/`, caches `/^https?.*/`) and the `/pwa` Serwist SW coexist.
