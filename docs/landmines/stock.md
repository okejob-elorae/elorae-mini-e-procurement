# Stock, inventory, reservations landmines

The full entries behind the **Stock, inventory, reservations** triggers in `AGENTS.md` § Landmine index, in the same order. Each one was written after someone paid for it. Read the entry for whatever surface you are about to touch before writing code; where an entry points on to `docs/ARCHITECTURE-NOTES.md`, `docs/EPIC-STATUS.md` or `docs/FOLLOWUPS.md`, follow it. When a change makes an entry wrong, fix it here in the same session — and update its trigger in `AGENTS.md` if the trigger itself moved.

- Looking up an `InventoryValue` row? The variant key may legitimately be `null` OR `""` — variantless rows key on `null`, while simple-item carts and `VanStock` deliberately key `""`. Always use the OR-tolerant lookup (`OR: [{ variantSku: null }, { variantSku: "" }]`); a lookup strict on either spelling misses rows and forks a phantom row. Never "fix" one spelling into the other.
- Matching variant SKUs in app code — a `Map`, a `Set`, an `===` between a catalog variant and an `InventoryValue`/ledger key? The `(itemId, variantSku)` unique index sits on `utf8mb4_unicode_ci` (the table's collation in the initial migration's DDL; measured on the `:3308` bed), so the DATABASE treats `ABC-01` and `abc-01` (and accent variants) as ONE key, and a Prisma lookup already matches them. An in-memory match that is case-sensitive silently disagrees: the Master Produk variant list showed the catalog variant at zero and the real stock as a separate "Not in catalog" row until it matched on `trim().toLowerCase()` (`matchKey` in `apps/web/lib/items/variant-rows.ts`), displaying the catalog's own spelling. The fold is close to the collation but not identical: lower-casing does not fold accents, and `trim()` folds LEADING whitespace the collation keeps distinct (it pads only trailing), so a fold can merge two keys the database stores as separate rows — acceptable for display, say so where it matters. The folded key is a MATCH key only: never write it and never loosen a write-side check with it — `isStockableVariantKey` (`apps/web/lib/items/variants.ts`) is deliberately case-sensitive because the konsi push writes the key it accepts into reservations, `StoreStock` and the ledger, and a folded spelling would put the same variant under two keys everywhere a JS map or the ledger compares strings. See `docs/ARCHITECTURE-NOTES.md` (PR #342).
- Editing the item form's variant table (`apps/web/components/forms/ItemForm.tsx`, `apps/web/lib/items/variant-grid.ts`)? The table's rows and their SKU/barcode values live in ONE state value (`GridState`: the rows on screen plus the last COMPLETE grid as a snapshot), recomputed in the same event as every attribute edit by the pure `resolveGridRows`; no effect drives the rows. Each row resolves a value carried from the SAME combination (identical attribute keys and values: what the user has in that row now) → saved match → a value carried by a rename or projection → blank, so a code typed over a saved one survives the next attribute edit, while a saved code still beats a value that only a rename or projection carried onto its combination. A BLANK value is never carried (`carryRowValues` keeps non-empty values only), so a saved code the user cleared comes back on the next attribute edit — that is the precedence working, not a lost edit. A saved match (`findSavedVariant`) needs the saved variant's attribute names to equal the combination's exactly (`sku`/`barcode` aside, trimmed and case-insensitive), so removing an attribute never hands a saved SKU to a combination it only partly describes; do not loosen it back to "every key the combination carries matches". A value is carried only onto its OWN combination: by value when the attribute keys are unchanged, by position when a key is renamed, and by a projection onto the shared keys when an attribute is added or removed — carried ONLY when that projection is one-to-one on both sides, otherwise blanked. A transient layout (a name cleared, two attributes sharing a name, an attribute with its last value removed) never becomes the snapshot, and the form refuses to submit while two attribute names collide case-insensitively (`findCollidingAttributeNames`, the same check `isGridComplete` uses). The carry SOURCE is the current rows when they still show the snapshot's grid, or when the change leaves the on-screen grid unchanged (so codes typed in a transient layout survive a change that keeps that layout); otherwise it is the snapshot, so a transient layout never carries into a different grid. Do not "simplify" that source choice to always carry from the snapshot — that drops codes typed in a transient layout, the last defect the PR fixed. Every earlier design broke a different way and each break looked fine in review: index-aligned arrays moved a saved SKU onto a different combination once a saved row was unticked and a size added; carrying with keys that included a named-but-valueless attribute blanked every SKU on the ordinary "type the name, then the value" path; two effects writing in one commit paired old values with new combinations. A SKU that lands on the wrong combination is worse than a blank one: the save catalogues the wrong variant, orphans the right one's stock, and pushes it to Jubelio for a mapped item. Keep the rules in `variant-grid.ts`, and test them by chaining the SAME exported functions the form calls, in the order a user types — a test-local copy of the algorithm proved nothing. See `docs/ARCHITECTURE-NOTES.md` (PR #344).
- Writing to `InventoryValue` / `reservedQty`? Atomic Prisma `increment`/`decrement` only, never read-modify-write — the webhook worker is concurrent and races the ERP ship path across processes. That rule still governs `reservedQty` and the DELTA movers; the SET movers (`setMainStock`/`setStoreStock`) are the documented exception, because a physical count is authoritative and they legitimately read the previous quantity before writing an absolute — reasoning in `docs/ARCHITECTURE-NOTES.md`. And a `qtyOnHand` write is no longer yours to make as a direct Prisma call, with ONE exception: `reservation-writer.ts` still moves it through a plain `tx.inventoryValue.update` twice and through a raw guarded `UPDATE` once, for the reasons in the `Writing reservedQty?` entry below.
- Moving stock anywhere? Go through the movers in `packages/db/src/stock-balance.ts` — `moveMainStock`/`moveStoreStock`/`moveVanStock` for a signed delta, `setMainStock`/`setStoreStock` for an absolute count — and never write a quantity onto `InventoryValue`/`StoreStock`/`VanStock` directly. Each mover moves the balance and appends a `StockLedgerEntry` in the SAME transaction, and `apps/web/lib/inventory/stock-balance-guard.test.ts` fails on a new direct write. The predecessor is the reason: `StockMovement` drifted precisely because a writer could move `InventoryValue` without appending to it, and konsi, van, retur and consume all did — so its stored running balance disagrees with `InventoryValue.qtyOnHand` on any item those paths ever touched. `StockMovement` has NO production writer left — the movers are the only way stock moves now, and the predecessor table is a FROZEN ARCHIVE of pre-retirement history that nothing appends to. Never add a write to it to "keep the two in step": there is nothing to keep in step, and the new row would be the only one of its kind. The table and the model are KEPT rather than dropped because its rows are still READ, by two surfaces needing coverage the ledger structurally cannot have — `deleteItem`'s guard and the stock card's variant picker, each its own entry below. Its historical running-balance drift against `InventoryValue.qtyOnHand` was never measured and never repaired, and stopping the writes FROZE that drift rather than fixing it, so treat an archived balance as indicative and never as a figure to reconcile against. See `docs/ARCHITECTURE-NOTES.md`.
- Reading or writing `StockLedgerEntry.totalCost`/`balanceValue`? NULL means UNRECONSTRUCTIBLE, never zero — and a real `0` is the opposite claim, also legitimate, so neither may stand in for the other. The columns were added with no backfill: every row the ledger already held carries null, and the moving average at that instant is recorded nowhere else, which makes this a SECOND cutover inside the first (quantity history begins at the ledger's own cutover, value history begins later). A reader must therefore render a placeholder rather than `Rp 0` — the main stock card does, behind a standing note saying exactly that, and its CSV export writes an empty cell rather than a zero. A stamped `0`, by contrast, says the movement was genuinely worthless, which is true of an item that has never been costed; that is why the fabric-aggregate opname path lands a real `0` instead of leaving the columns undefined — both by passing an unguarded `delta * avgCost` that already evaluates to zero, and by a literal `0` on the row-provisioning append beside it — since stamping null there would make every opname on an uncosted item refuse to post. That refusal is the mechanism, not a side effect: `opnameNetDelta` (`apps/web/lib/inventory/opname-journal.ts`) sums the ledger's `totalCost` over one opname's rows and THROWS on a null rather than folding it in as zero, because a silent zero posts an inventory-variance journal short by exactly that row's value with nothing on screen to flag it. Never soften that throw into a `?? 0`, and never omit the value columns from a writer whose rows an opname will sum. The movers FORWARD both values and compute neither — the caller owns the cost basis, so pass the same expression you already computed for your own balance write, never a re-derivation, or the ledger and the balance table end up disagreeing about one movement. See `docs/ARCHITECTURE-NOTES.md`.
- Deleting an `Item`, or tidying `deleteItem`'s blocker list? It counts BOTH `StockMovement` and `StockLedgerEntry`, and the two counts refuse two DIFFERENT failures — so dropping either is wrong for a different reason, and each deletion looks individually safe. The archive half: `StockMovement` has no writers left, but `StockMovement.item` is still a REQUIRED Prisma relation with no database FK behind it, so an archived row left pointing at a deleted item throws `Inconsistent query result` on every read that joins it, forever; stopping the writes froze that archive, it did not empty it, and this count is the only thing standing in front of it. The ledger half: `StockLedgerEntry` declares no relation to `Item` at all, deliberately, so ledger history outlives the item it describes and an orphaned row can never crash a read — which is precisely why it is useless as a crash guard, and why its count is there for the other reason, refusing to silently strand live stock history behind a deleted item. "The archive is dead, drop its count" and "the ledger cannot crash anything, drop its count" are both individually plausible and both wrong. See `docs/ARCHITECTURE-NOTES.md`.
- "Simplifying" `getItemVariantOptions` (`apps/web/app/actions/stock-card.ts`) back onto one table? It unions THREE sources on purpose — `Item.variants`, `StockLedgerEntry` and `StockMovement` — because the two movement tables have complementary blind spots and neither alone is a superset. The ledger misses any variant that sat at ZERO at cutover, since the backfill wrote an `OPENING` row only for non-zero balances; `StockMovement` misses every variant that only ever moved through a field-sales path, which never wrote it; and only the catalog can offer a variant that has never moved at all. Dropping any one of them silently makes a real variant unselectable in the stock card, the movement view and both adjustment forms. Their two variantless exclusions are also NOT interchangeable: the ledger's `variantSku` is `NOT NULL` defaulting to `""` so it takes `{ not: "" }`, `StockMovement`'s is nullable so it takes `{ not: null }`, and only one of the two wrong substitutions is a compile error. `StockMovement` stopped being written entirely when the retirement finished, so its half of this union is a FROZEN pre-retirement archive — it can only fall further behind, and it still cannot be dropped, because the ledger's zero-at-cutover blind spot is equally permanent and nothing will ever fill it. See `docs/FOLLOWUPS.md`.
- Reading an `InventoryValue` row before writing it? OR-tolerance on the READ is not enough — pass the row's id to the mover as `inventoryValueId` so the write provably lands on the row you read, instead of the mover re-resolving the same null/`""` bucket independently. Rows created through the ERP are spelled `null` (`apps/web/lib/items/mutations.ts`), so a strict `findUnique` on a normalised `""` key misses them, and pairing that strict read with an OR-tolerant write is what destroyed the moving average on every receipt of a variantless item: the read found nothing, `previousAvgCost` fell back to 0, and the write then SET `avgCost`/`totalValue` on the real `null` row from that zeroed base — 100 @ 10 then 100 @ 20 ends at 20, not 15. Worst defect on the ledger branch; four fix rounds. `findExistingInventoryValueRow` in `apps/web/lib/inventory/costing.ts` is the ONE spelling of that lookup **inside `apps/web`**, tie-break included — reuse it there, never write a second; the sole straggler is `lib/field-sales/writer.ts`'s `hasInventoryRow`, an existence check that pins no id, and it is a known exception rather than a precedent. The konsi transfer (`issueKonsiTransfer`) is the one `apps/web` writer that deliberately does NOT resolve through it: it draws a reservation down, so it acts on the row that reservation stored, through `packages/db`'s `resolveReservedInventory` (below) — a fresh lookup there would pick the lowest-id row of a dual bucket, not necessarily the one the reservation sits on. `packages/db` cannot import the helper (it sits above `apps/web`), so it carries its OWN copies, and there are more than two — four of them must all match the helper's shape, tie-break included, and move together with it: `stock-balance.ts`'s `moveMainStock` AND `setMainStock`, `sales-return-writer.ts`'s return-accept restore, and `stock-writer.ts`'s `applyJubelioStockAdjustment`. Two further `packages/db` lookups are deliberately NOT that shape and must not be "harmonised" into it — `reservation-writer.ts`'s `findReservationInventory` prefers an EXACT `""` row and only then falls back to the lowest-id `null` row, because a bare OR can decrement the sibling row and orphan `reservedQty` on an item carrying both spellings. It picks the row EVERY reserve in that file lands on, the Jubelio half and the field-sales half alike — never give either half its own lookup — and each reserve stores that row's id on the reservation (`StockReservation.inventoryValueId`). Every consume and release, and the konsi transfer's draw-down, then act on the STORED row through `resolveReservedInventory` (scoped by `itemId`, so a stored id that does not belong to the item is treated as missing), which is why a variantless row provisioned for the item after the reserve no longer pulls the consume onto it. It falls back to `findReservationInventory` only for a reservation whose column is null — every one made before the column existed, deliberately not backfilled, because stamping today's lookup onto a reservation on an already-forked item could pin the wrong row — or whose stored row is gone; those legacy reservations keep the old exposure until they resolve. A new reserve path must stamp `inventoryValueId`, and a new consume or release path must resolve through `resolveReservedInventory`, never a fresh lookup. The second exception, `item-price-writer.ts`, reads `avgCost` only, item-level with no variant input at all, so it pins no row and needs no tie-break. A missing `orderBy: { id: "asc" }` is the half that reads as cosmetic and is not — four spellings shipped on this branch without it, and because each pins its resolved id into the mover, two paths over one dual bucket can pin DIFFERENT rows and interleave two independent balances under a single ledger key. `moveMainStock`'s `createIfMissing` opens a variantless row spelled `null`, matching `items/mutations.ts` and every other writer that opens one — two specs pin it by name. Spelling it `""` was tried and reverted: it would buy `@@unique([itemId, variantSku])` as a fork guard, since MySQL enforces that constraint for `""` and treats NULLs as distinct, but the price is a second spelling for the same logical row — the phantom-`""` problem these OR-tolerant lookups exist to survive. The concurrent double-create it would have guarded is closed another way: when the first lookup finds no row, `moveMainStock` locks the `Item` row (`SELECT … FOR UPDATE`) and re-reads with `lockMainInventoryValueRow` (`packages/db/src/stock-row-lock.ts`, re-exported from `stock-writer.ts`), so a second first receipt waits for the first to commit and then finds its row. Every half of that is load-bearing. A `FOR UPDATE` on the absent `InventoryValue` row would take only gap locks, which do not exclude each other — hence the `Item` row. The re-read must itself be a LOCKING read: the transaction runs at REPEATABLE READ, so a plain re-read still sees the snapshot the first lookup fixed, finds no row, and forks anyway. And the lock is taken only on that miss, never on every call, because locking `Item` on every receipt lets two multi-line receipts naming the same items in a different order deadlock. See `docs/ARCHITECTURE-NOTES.md`.
- Writing `reservedQty`? A reservation is NOT a stock movement — only `qtyOnHand` is, and a write touching `reservedQty` alone gets no ledger entry, ever. `packages/db/src/reservation-writer.ts` is the single documented exception to the movers, for two reinforcing reasons. Its raw guarded `UPDATE`s are cross-process race guards — `WHERE qtyOnHand >= n` on the field-sales consume, `WHERE (qtyOnHand - reservedQty) >= n` on the konsi reserve — which cannot be expressed as Prisma calls at all. And every `qtyOnHand` write in that file, the one raw statement and the two plain `tx.inventoryValue.update`s alike, decrements `reservedQty` in the SAME statement; splitting that pair to route the quantity half through a mover strands stock reserved against nothing, permanently. It calls `appendStockLedger` by hand instead, once per `qtyOnHand` movement and never for a reservation. Nothing asserts that second half; it is pinned by review only. Every reserve in that file stores the row it reserved against on `StockReservation.inventoryValueId`, and every consume and release acts on that row through `resolveReservedInventory` rather than a fresh lookup (the fallback for an unpinned reservation is in the entry above). The one writer of `reservedQty` and `StockReservation` OUTSIDE that file is `issueKonsiTransfer` (`apps/web/lib/field-sales/konsi-transfer/writer.ts`): it moves `qtyOnHand` through `moveMainStock`, pinned to the row the line's reservation stored, then decrements `reservedQty` on that same row and draws the line's reservation down (`consumedQty`, flipping it `CONSUMED` once exhausted) in the same transaction — a documented exception with its own `ALLOWED` entry in the balance-write guard, not a precedent. See `docs/ARCHITECTURE-NOTES.md`.
- Wondering why a no-op wrote a ledger row? NO delta mover has a zero-delta short-circuit — `moveStoreStock` and `moveVanStock` no more than `moveMainStock` — while `setMainStock`/`setStoreStock` both do, and the asymmetry is deliberate: a DELTA mover may still legitimately need to write `avgCost`/`totalValue` when the quantity does not move, whereas a SET that changes nothing has nothing to record. The Jubelio stock webhook is a SET (`applyJubelioStockAdjustment` → `setMainStock`), so a no-op webhook writes NO ledger entry, exactly like an unchanged stocktake line — though it still creates its `StockAdjustment` row, a mismatch logged in `docs/FOLLOWUPS.md`. On the STORE side the missing short-circuit is currently not observable: both konsi-retur writers skip a zero line at the CALL SITE before reaching a mover, so the all-zero "lost sack" receive (valid on every line) produces no entry at all — the guard is the caller's, not the mover's, so never state it as a mover behaviour and never claim a store-side zero row exists. Those rows now reach a screen: the store detail card and the movement view both RENDER them rather than filtering them, because a processed document that moved nothing is a real event an operator is entitled to see. Do not harmonise the movers in either direction, and do not add a `qty !== 0` filter to a read surface to tidy them away. See `docs/ARCHITECTURE-NOTES.md`.
- Trusting the balance-write guard to have caught you? It greps for Prisma MODEL calls only and is blind to raw SQL — `reservation-writer.ts`'s own raw guarded `UPDATE`s are invisible to it, matched or not — there are three, of which TWO touch `InventoryValue` (one moves `qtyOnHand` and appends a ledger entry by hand, one moves only `reservedQty` and appends nothing) while the third updates `StockReservation`, which is not a balance table. A new `$executeRaw`/`$queryRaw` that touches `InventoryValue`/`StoreStock`/`VanStock` passes the suite whether or not it appends to the ledger, so it must append by hand at the call site AND be added to the guard's `ALLOWED` list deliberately, with its reasoning written down like every other entry there. Do not widen the regex to chase SQL text — that was considered and rejected as brittle and false-positive-prone.
- Creating a balance row at quantity 0 (a new ERP item, a synced catalog variant, a bootstrap before a lookup)? That is row PROVISIONING, not a movement: it writes no ledger entry, because an opening entry of zero carries no information. The guard exempts it BY PATH, not by shape — so a file that provisions rows has to join `ALLOWED`, and, once there, any real quantity change later added to that same file escapes the guard silently. Keep the provisioning create and the quantity move in different files where you can.
- Provisioning a variantless `InventoryValue` row for an item that may already hold one (the Jubelio catalog sync, a new import or item path)? Look for a row under EITHER spelling first and create nothing if one exists. The unique index treats NULLs as distinct, so `createMany({ skipDuplicates })` on `variantSku: ""` does NOT collide with an existing `null` row — it forks a second one. That fork still splits a LEGACY reservation — one made before reservations stored their row, so its `inventoryValueId` is null: its consume or release falls back to `findReservationInventory`, which prefers `""`, so a reservation made on the `null` row is consumed or released on the new `""` row — a consume drives its `qtyOnHand` negative, a release its `reservedQty` — while `reservedQty` stays stranded on the old row for good. A reservation that stored its row is immune: its consume and release act on that row whatever is provisioned after it. `ensureInventoryRows` in `apps/api/src/jubelio/catalog/catalog-sync.service.ts` guards this with an OR-tolerant `findFirst` (PR #395); that check is a read with no lock, so a concurrent create can still fork. Never "repair" a fork by normalising one spelling into the other.
- Supplying `balanceQty` to `appendStockLedger`? It comes from the balance write's own return value, never a follow-up read — a re-read races the concurrent webhook workers across processes, the same hazard the atomic-increment rule exists for. The two paths that do read back (`moveMainStock`/`setMainStock`'s pinned `inventoryValueId` branch, and `reservation-writer.ts`'s raw statement) are safe ONLY because `updateMany`/`$executeRaw` return an affected-row count rather than the row, and the row is already locked by the update that just succeeded inside the same transaction. Do not copy that read-back into a path whose write already returns the row.
- Decrementing main stock? `moveMainStock` REFUSES a delta that would take `qtyOnHand` below zero and throws `MainStockNegativeError` — the floor is a condition in the UPDATE's own `where`, not an advisory pre-check, because every caller's own guard is computed from a pre-read that the atomic decrement then races. Do not clamp it, do not catch-and-continue, and do not copy the guard onto `moveStoreStock`/`moveVanStock`: a STORE balance goes negative on purpose with a stocktake as the correction path, and main has no such correction. See `docs/ARCHITECTURE-NOTES.md`.
- Applying a physical COUNT — an opname line, a stocktake, a reconciliation to an external figure? Use `setMainStock`/`setStoreStock` with the counted absolute, never a `counted − current` delta through `moveMainStock` — the store stocktake's absolute is the count plus what moved after it was saved (its own entry below), still a SET. The delta form lands the row at `previousActual + delta` (which is not the counted figure if anything moved in between, while the `StockAdjustment` beside it records that it is) and types the ledger entry `IN`/`OUT` where every other count writes `ADJUSTMENT` — and the ledger is append-only, so that half can never be corrected. Shipped on this branch and caught in review. See `docs/ARCHITECTURE-NOTES.md`.
- Writing a migration that backfills the ledger, or any query that folds `InventoryValue`/`VanStock` by variant? Group on the NORMALISED key (`COALESCE(variantSku, '')`) and AGGREGATE — one item can hold both a `null`-spelled and a `""`-spelled row, and one output row per input row puts two records at one ledger key. The opening backfill does this with `GROUP BY` + `SUM` and a `HAVING SUM(...) <> 0` non-zero test (a bucket of `+5` and `−5` holds nothing; a zero row beside a non-zero one still owes an entry), and its `refId` is a REPRESENTATIVE `MIN(id)`, not the sole source. `StoreStock` needs none of this — its `variantSku` is `NOT NULL` under a real unique key. See `docs/ARCHITECTURE-NOTES.md`.
- Reading `qtyOnHand` as "what we can sell"? `available = qtyOnHand − reservedQty`, derived at read time and never stored. That is the ERP's OWN selling figure — the PWA catalog, the van load and the konsi reserve guard read it — and it is NOT what Jubelio receives. The stock push sends `end_qty = max(0, qtyOnHand − offlineReserved)`, subtracting only the field-sales holds (open `StockReservation` rows with `source <> 'JUBELIO'`), because Jubelio's `end_qty` is on-hand and Jubelio already nets its own marketplace orders as `order_qty`; subtracting `reservedQty` there takes every marketplace order off twice. The push said `available` until that was disproved live — never put it back. The whole contract (push, webhook, reconciliation, and which side is the source of truth) is in `docs/landmines/jubelio.md`.
- Touching field-sales order lines, van stock or the PWA catalog? All of it is PER-VARIANT (real `variantSku`); simple items stay item-level, min-qty aggregates per item, promos aggregate per item then pro-rate.
- Working on putus stock movement? Stock leaves at DELIVERY, not at approve — and `FieldSalesDelivery.docNo` is NOT always `DLV/`-prefixed, so never pattern-match the prefix.
- Working on konsi stock movement? Approve only RESERVES — main `qtyOnHand` is untouched and nothing reaches `StoreStock` until a delivery shipment COMPLETES, which moves main → `StoreStock` through `issueKonsiTransfer` as ONE `KonsiTransfer` per completed shipment (`KonsiTransfer.shipmentId`, `@unique`) for the DELIVERED qty only, drawing the line's reservation down partially, all inside one serializable transaction whose `IN_TRANSIT` status CAS runs first. A short line stays reserved until another shipment carries it or Close remainder releases it. Between ship and completion main `qtyOnHand` still counts the goods on the truck — accepted, exactly as for putus, because `reservedQty` keeps available-for-sale honest. Approve-time transfers from before this change carry `shipmentId = null`. The migration marked a then-`APPROVED` konsi line delivered in full only when it held no `RESERVED` reservation (consumed at approve, or never reserved) and no cancelled qty — a line still `RESERVED` from before the transfer document existed stays open, to be shipped or closed, and the migration's two UPDATEs are safe to re-run; a konsi completion that finds no `RESERVED` reservation with enough headroom refuses with `KONSI_NOT_RESERVED` and moves nothing. Because undelivered konsi qty sits on no `StoreStock`, `updateStore` refuses KONSI → PUTUS while the store has a konsi order awaiting approval or approved with qty neither delivered nor closed, not only while a `StoreStock` row is non-zero. Never move konsi stock back to approve, and never add a konsi stock writer that has no completed shipment behind it — the shipment is what carries the proof of delivery. The admin push to a konsi store is NOT such a writer: it creates and approves an ordinary konsi order, which only reserves, and its stock moves at that order's shipment completion like any other (its own entry in `docs/landmines/field-sales.md`). See `docs/ARCHITECTURE-NOTES.md`.
- Reading/writing `VanStock`, `StoreStock` or `KonsiTransferLine`? A THIRD variant-key spelling exists — `VanStock.variantSku` is nullable too (writers insert `""`, but `null` is legal), while `StoreStock`/`KonsiTransferLine` are non-nullable `@default("")`. Stay OR-tolerant on the nullable ones, normalise `?? ""` on write into the non-nullable ones. `StoreStock` has many writers and the set keeps growing, so never trust a COUNT of them — grep `moveStoreStock`/`setStoreStock` for the live one, and note that one document can be two writers. Today it spans the konsi transfer (in, at delivery-shipment completion — never at approve), a konsi retur approve (out), a KONSI-store SPG sale (out), a store stocktake approval, which SETS the quantity rather than adjusting it (to the count plus every movement stamped after it — its own entry below), the admin-return receipt-time decrement in `apps/web/lib/field-sales/retur/receive-writer.ts` (out), and BOTH legs of a store-to-store transfer (`apps/web/lib/stores/transfer/writer.ts`) — one store's decrement and another store's increment inside a single transaction, which is exactly how a sweep that counts documents undercounts balance writes. Every writer in that set is also a case in the konsi sell-through derivation's `refType` switch, which refuses a store movement it cannot classify — a new one belongs there too (its own entry in `docs/landmines/konsi-sell-through.md`). Blending `avgCost` tracks DIRECTION rather than document: an INCOMING leg carrying its own cost basis blends it in (the konsi transfer, and the store transfer's destination leg through `weightedAvgCost`), while everything else leaves the column alone — every decrement, the stocktake included, and the store transfer's own SOURCE leg — because removing units at the current average leaves that average unchanged. A decrement can go negative on purpose and a stocktake-created line lands at `avgCost: 0`, same as an SPG-sale-created negative row. A drifted or negative row is now correctable, but only at a store where someone actually opens and approves a count — the monthly count sweep opens one, at most once per month, only at an active KONSI store with a sell-through method (`docs/landmines/konsi-count-schedule.md`), and nothing schedules one anywhere else. **The konsi-retur decrement (out) is itself origin-dependent as of PR #258**: a FIELD-origin return still decrements the full `creditedQty` once, at approve; an ADMIN-origin return decrements `receivedQty` at RECEIPT (`receive-writer.ts`) and only the delta (`creditedQty − receivedQty`) at approve — reading either writer alone looks like the decrement was halved or doubled, but the total over the return's life is `creditedQty` either way for both origins. ADMIN decrements early so the store's ledger keeps the units until they physically arrive rather than vanishing into an in-transit void — the cost is that the ledger OVERSTATES during that transit window, so a stocktake opened in it reports a shortfall that is really goods on a truck — which is why a sell-through report refuses such a count as its closing count (`RETUR_IN_FLIGHT`, `docs/landmines/konsi-sell-through.md`); the store detail card shows the in-transit qty, the stocktake count screen deliberately does not, since `expectedQty` must stay the live ledger figure and never gain a second meaning. See `docs/ARCHITECTURE-NOTES.md`.
- Building on the store-to-store transfer (`apps/web/lib/stores/transfer/writer.ts`)? Stock moves at APPROVE and only at approve, so a PENDING transfer has moved nothing and cancelling one is a pure status flip with no ledger entry and nothing to reverse — never add a compensating move to the cancel path. Both legs go through `moveStoreStock` inside ONE serializable transaction, and the cost basis for BOTH legs is the source store's `avgCost` re-read fresh from `StoreStock` at APPROVE time, inside that same transaction — never `StoreTransferLine.unitCost`, which is only a create-time snapshot for the document's own display and must not be wired back into either leg's cost. Re-reading at approve (rather than trusting the snapshot) is what keeps the source's row internally consistent with its own `balanceValue` and stops value from appearing or vanishing when the source reprices between create and approve — an ordinary konsi transfer landing at the source in that window is enough to trigger it, and it shipped once, caught in review. An insufficient source balance is ALLOWED, deliberately rather than by omission: `moveStoreStock` carries no floor guard because a store balance is allowed to go negative in this system with a stocktake as the correction path, so never add a pre-check that refuses one and never copy `moveMainStock`'s floor across — main is the only guarded location, for the reasons in its own entry above. Both status flips are a CAS `updateMany` filtered on `PENDING` that runs BEFORE any stock moves, and that CAS is what makes a double approval and a cancel-after-approve structurally impossible rather than merely guarded against; every failure path in both writers must THROW rather than return, since `runSerializable` commits on a normal return. An APPROVED transfer has NO reversal path — the correction is a second transfer the other way, raised and approved like any other. `StoreTransfer.movedAt` (required) is the INSTANT the goods physically moved, entered on the create form as a WIB date and time; the action reads the `datetime-local` value with an explicit `+07:00` and round-trips it (`parseMovedAtInput`, `moved-at.ts`), because prod runs UTC, and a value that does not round-trip is `INVALID_REQUEST`. Every lag guard compares it as an instant against a count moment, the way returns key on their raise time, and every guard treats a count and a transfer as related only when the stocktake has a COUNTED line (`countedQty` not null) for one of the transfer's item::variant keys — both `variantSku` columns are non-nullable, so the keys match exactly. Never widen that to `itemId` alone or to uncounted lines: a count that did not count the item never saw the move. Approve refuses `COUNTED_SINCE_MOVE`, naming the counts, when either store — source or destination — has such an APPROVED stocktake whose count moment (`countFinishedAt ?? approvedAt`) is ≥ `movedAt`, because that count already absorbed the move as variance and moving the stock now would record it twice. The check runs after the CAS (so a repeat approval still reports `INVALID_STATE`) and before any stock moves, and it throws. Create refuses `MOVED_AT_IN_FUTURE` for a moment more than five minutes after the server's now (`MOVED_AT_FUTURE_TOLERANCE_MS`, `moved-at.ts`), so a browser clock running slightly fast cannot refuse the form's default of now. The operating rule this enforces: record and approve a transfer before a count of its items at either store is approved. A transfer recorded only after such a count — one taken after the move — was approved can only be cancelled; its move then stands as that count's variance, at the source a shortfall that a SHELF_COUNT report bills as sold (logged in `docs/FOLLOWUPS.md`). The refusal is whole-transfer by design, so cancelling also drops every line that count did not count: raise those lines again as a new transfer, and raise the whole transfer again with the real move time if the goods actually moved after the count. See `docs/ARCHITECTURE-NOTES.md`.
- Computing a store stocktake line's `varianceQty`? It is `countedQty − expectedQty`, the OPPOSITE sign to `VanReconcileLine.varianceQty` (`expected − counted`). Copying the van formula types every shortfall as a surplus and inverts which lines demand a cause. The konsi sell-through line's `gapQty` is the van's sign, not the stocktake's — `−Σ` of the window's `StoreStocktake` ledger qty, so a shortfall is POSITIVE — and it sums every count in the period, mid-period and partial ones included, not only the closing count.
- Touching store stocktake approval or `saveStocktakeCounts`? Approval SETs each counted line to `countedQty` PLUS every `STORE` ledger row for that item::variant stamped after `StoreStocktake.countFinishedAt`, so a sale or delivery while a count waits for an admin is carried rather than erased, and the stocktake's own ledger row is the shrinkage or surplus at the count moment — except that a `FieldReturn` row whose retur was RAISED on or before `countFinishedAt` is skipped, because a retur's store row lags its goods (they leave at raise; the row lands at approve for FIELD, at receipt plus an approve delta for ADMIN), so the count already saw them gone, while a retur raised after the count is still subtracted. A `StoreTransfer` row is skipped the same way when its transfer's `movedAt` ≤ `countFinishedAt` — BOTH legs, the source's −q and the destination's +q, which both stamp the transfer id as `refId`; the skip is per ledger row and only counted lines read the post-count sums, so it touches only items the count counted. Approval also refuses `TRANSFER_PENDING`, naming the transfers, while a PENDING transfer touching the store — from it or to it — has `movedAt` ≤ the count moment and moves an item::variant this count COUNTED, because once the count is approved that transfer can never be approved (`COUNTED_SINCE_MOVE`, the store-transfer entry above). For a count with a null `countFinishedAt` that refusal takes this approval's own instant as the count moment — the same `approvedAt` fallback `COUNTED_SINCE_MOVE` reads, so the two guards agree and a legacy count cannot approve first and strand the transfer — while the exclusion does not run for it at all. `appliedQty` is the target set, `varianceQty` keeps `counted − expected`. `countFinishedAt` moves only on a save that changes a count figure (a `countedQty` or an added line) — never stamp it on a cause- or reason-only resave, because the backoffice resends every line when an admin fills in a reason, and re-stamping there drops every sale since the physical count. A null `countFinishedAt` (a count saved before the column existed) sets the bare counted figure. A sale between physically counting a shelf and saving the sheet still lands before the stamp and reads as a surplus. See `docs/ARCHITECTURE-NOTES.md`.

That rule binds ENUMERATION as hard as it binds labelling, and the enumerating half is the one that looks safe: any surface that lists the registry members as a CLOSED SET — a filter's option list, a set of grouping buckets, tabs, a validation allow-list — is exhaustive over the union and not over the column, so the instant it is used to narrow, every real row spelled outside the registry drops out silently and no option remains to bring it back. The same fact that forces the raw-value fallback on the label map forces an explicit out-of-registry class on any such control, and it has now bitten twice in this area: the label map first, a registry-built filter second. Widening the registry is never the fix — it is exhaustive over the union BY CONSTRUCTION, and the column will always be able to hold a value it does not know. At least THREE tables carry a `refType` over three unrelated vocabularies — `StockLedgerEntry`, `StockMovement` and `RejectedGoodsLedger` — and they OVERLAP on at least one spelling, so membership is NEVER a safe way to tell them apart and the old "the other ones are SCREAMING_SNAKE" test is false. - Building a query filter arm out of an optional array — `if (arr !== undefined && arr.length > 0)`? That guard collapses "the caller selected NOTHING" into "no filter", so a control whose operator unticked every box is handed the ENTIRE unfiltered set, the exact inverse of the request, and nothing throws, warns or logs on the way there. The screen does NOT contradict itself while both halves carry the bug — where the same guard also feeds a separate count behind an empty-state message, the two agree, both go unfiltered, every section is full and the empty-state copy never renders at all. The contradiction belongs to the HALF-APPLIED fix: one predicate made to fail closed while its sibling still fails open, so the table shows nothing and the count behind the copy still answers the unfiltered question. That state is not hypothetical — it is what this work shipped for one commit — and making it unreachable is the whole point of the structural sharing below. `undefined` is the only honest spelling of "no filter"; an empty array is a SELECTION and belongs in the query as `in: []`, which matches nothing. `getItemMovementCard`'s two array arms are the worked example of the fix: each is a condition built ONCE by its own builder and applied BY REFERENCE to both the main `where` and the `historyWhere` behind `hasAnyHistory` — structural sharing, not a promise to keep two literals in sync — and each returns `{ … : { in: [] } }` for an empty selection. The collapse in the OTHER direction is a real decision too, and fails quieter: "everything ticked" may be sent as `undefined` only when the control's full selection genuinely selects every row the column can hold. The movement card's movement-type filter renders an out-of-registry class as one more option, so it collapses only when THAT is ticked as well — every registered member ticked with unregistered EXCLUDED differs by one checkbox, is a real `IN (registry)` filter, and must still travel; sending the rendered option list instead of collapsing behaves identically today and starts dropping rows the day the column holds a value the control does not render, which on a free-form column is a matter of when. The three already found in this repo fall out as the unfiltered set, a DATABASE-WIDE sweep, and a HARDCODED default list the caller never named; the last is the hardest to spot, since the rows that come back look like a filter that ran. `docs/FOLLOWUPS.md` carries the shape and the open sites. - Editing `generateDocNumber`'s reset `CASE`, adding a reset period, or loosening doc-number prefix validation? Three traps, and none of them fails a build — each one re-issues a number or refuses documents at runtime. **A reset period needs its own `WHEN` arm.** `generateDocNumber`'s atomic `UPDATE` (`apps/web/lib/docNumber.ts`) resolves the counter through a `CASE` with one `WHEN` arm per period, and a period with no arm falls through to `ELSE 1` — not a reset but a counter pinned at 1, so every number comes out `…/0001` and the second document of that type dies on its unique `docNo`. `NEVER` shipped exactly that way, offered on the settings page with no arm, until it got `WHEN resetPeriod = 'NEVER' THEN lastNumber + 1`; its numbers still render `PREFIX/YYYY/NNNN` with the year of issue, since only `MONTHLY` adds the month. A new period needs its own `WHEN` arm, its own render branch below the `UPDATE`, a place in `RESET_PERIODS` (`apps/web/lib/doc-numbers/validate.ts`) and a `documents.resetPeriods.<PERIOD>` label in both locales. **No two doc types may share a prefix.** `updateDocNumberConfig` refuses one with `DUPLICATE_PREFIX`, through `findPrefixConflict` in `apps/web/lib/doc-numbers/validate.ts`: it compares the NORMALISED prefix — trimmed, plus the trailing `/` the generator appends when it is missing — case-insensitively against every other doc type, and a type with no row yet counts at its `DEFAULT_CONFIGS` prefix, the one `generateDocNumber` will create it with. The reason is that some doc types write the same `@unique` column — PUTUS and KONSI both write `FieldSalesOrder.orderNo` — and the document columns use `utf8mb4_unicode_ci`, so `putus/` and `PUTUS/` are one unique value. Give KONSI the prefix `PUTUS/` for a while, revert it, and PUTUS later reaches a number KONSI already issued: the insert dies on P2002, and because `generateDocNumber` runs inside the caller's transaction the rollback takes the counter `UPDATE` with it, so the next attempt draws the same number and dies the same way — forever, since Settings cannot edit `lastNumber` to step past it. Never narrow the comparison to exact case or exact slash, and never scope it to the pairs known to share a column today — comparing every type is what keeps the next shared column safe. The page pre-checks against its loaded rows for instant feedback; the action is the enforcement. The action reads then writes outside a transaction, so two admins saving the same prefix at the same instant can both pass — accepted for an admin-only screen. **A MONTHLY↔YEARLY flip-flop can re-issue a number, and that is accepted.** The reset period stays editable on a counter that has already issued numbers, by owner decision. A type that issues YEARLY numbers, switches to MONTHLY (whose counter restarts at 1 whenever the month changes) and switches back within the same year continues the yearly format from the lower monthly counter, re-drawing a `PREFIX/YYYY/NNNN` it already issued. It fails loudly on P2002 — wedged the same way as a shared prefix — and is fixed by editing the config back. There is no guard and no confirm; do not add one without reopening that decision.
- Finding a catalog item with no `JubelioProductMapping` whose variants are mapped on ANOTHER item, or about to zero or deactivate one? It is a SUPERSEDED duplicate a catalog re-ingest left behind: Jubelio's stock webhook sets only the item the links moved to, so the old item's `InventoryValue` rows are governed by nothing, double-count on-hand, and erode when orders reserved against it consume after the move. That is where the last 62 negative rows of the 2026-09-29 erosion came from, beside 22,824 units counted twice across 24 items. Retire one ONLY through `retireSupersededItem` in `packages/db/src/superseded-items.ts`, run from `scripts/retire-superseded-items.mjs` (dry by default; a write needs `CONFIRM=1` plus the dry run's `EXPECT_SKUS`), never by hand: it locks every row first, refuses an item that is not catalog-ingested, has a variant whose mapped twin holds no stock row of its own, a variantless row, an open reservation or held `reservedQty`, store or van stock, or a pending return line, and writes each zeroing as a `SUPERSEDED_ITEM_RETIRE` adjustment plus ledger entry keyed per attempt. A retired row can still take stock through one path: `acceptReturnItem` keys a return line on its order's reservation — accepting a released line with no stock change, refusing a still-reserved one, restoring a consumed line onto the reservation's row while it is still mapped, else onto the one item its variant moved to, and refusing otherwise — but a line that names no order line at all falls back to the `itemId` the return ingest resolved with `inventoryValue.findFirst({ where: { variantSku } })`, no item filter and no ordering, which can be the superseded item's zeroed row. If that happens, re-run the script; see `docs/FOLLOWUPS.md` for the resolution fix. The item itself is kept inactive, never deleted: its sales history points at it. See `docs/ARCHITECTURE-NOTES.md`.
- Accepting a marketplace return, or adding any path that puts returned stock back? The ORDER'S RESERVATION decides it, never the return line's own `itemId` when the line names an order line — that `itemId` is resolved at ingest by variant SKU alone and can be a superseded duplicate. `acceptReturnItem` (`packages/db/src/sales-return-writer.ts`) looks the line's reservation up by `salesorderDetailId`: RELEASED → accept with no stock change (the goods never left, and no COGS was booked); RESERVED → refuse `order_not_settled` (a later consume would take off goods that came back); CONSUMED → restore, capped at the reserved qty, onto the reservation's row while it is still mapped, else the single other item the variant is mapped on, else refuse `no_governing_row`; a line naming an order line with no reservation → refuse `stock_not_traceable`; only a line naming no order line falls back to the ingest-resolved `itemId` (the residual path in the superseded-items entry above). Never add a path that accepts a CONSUMED line without stock: the sale's COGS is booked and the return's COGS reversal counts only lines with a stock adjustment, so revenue would reverse while the cost stayed. That is also why `ACCEPTED` with no `stockAdjustmentId` always means "never left ERP stock" — keep it that way, since the screen reads it. The reversal is priced at the restore row's current `avgCost`, not the cost stamped on the sale. See `docs/ARCHITECTURE-NOTES.md`.
