# Forecast landmines

The full entries behind the **Forecast** triggers in `AGENTS.md` § Landmine index, in the same order. Each one was written after someone paid for it. Read the entry for whatever surface you are about to touch before writing code; where an entry points on to `docs/ARCHITECTURE-NOTES.md` or `docs/FOLLOWUPS.md`, follow it. When a change makes an entry wrong, fix it in the same change.

- Changing which marketplace orders count as forecast demand? A synced `SalesOrder` counts ONLY when a settlement proves it (`buildMarketplaceDemand`, `apps/web/lib/forecast/marketplace-demand.ts`): its WIB month must be settled for its marketplace (`isMonthSettled` — the uploaded `Settlement` periods cover the month start through month end + `forecast.payoutDelayDays.<SHOPEE|TIKTOK>`, default 14), the sum of `netIncome` over its MATCHED lines must be above 0, and its match key (Shopee `salesorderNo`, TikTok/Tokopedia `channelOrderNo`) must belong to exactly one `SalesOrder`. Jubelio status is NOT read for counting — a settled order later marked RETURNED still counts, its returned units coming off through `returnedQty` — and an order in an unsettled month is left out and the month shown as provisional; there is no status-based fallback, by decision (#399). Only periods that reach into the month are considered: an older gap between settlements must not make every later month unsettled, which the first version did. Settlement lines prove finality only — quantity and revenue always come from `SalesOrderItem`, never `netIncome`, which is after fees. → `docs/ARCHITECTURE-NOTES.md`
- Feeding the same marketplace sales from two places? Excel imports (`SalesHistory` with an `importBatchId`) and synced orders describe the same sales, so `loadMarketplaceDemandInput` dedupes on the marketplace order number: an order whose `channelOrderNo`, or `salesorderNo` behind `SP-`, equals an imported `SalesHistory.orderId` of the same marketplace family is skipped. A new import parser must keep `orderId` as the bare marketplace order number, or every overlapping order counts twice.
- Adding a `SalesHistory` writer, or a konsi sale path? Konsi demand counts `billedQty − posSoldQty` per sell-through line (`buildKonsiDemand`) because every SPG POS sale already writes `SalesHistory` (OFFLINE) when it happens. A path that writes `SalesHistory` for units a sell-through report also bills, other than POS, double-counts them; one that bills POS-sold units without recording them in `posSoldQty` drops them.
- Bucketing forecast demand by month? Use `wibYearMonth` (+7h, never `getMonth()` — prod runs UTC), and keep the month in the grouping key: `salesHistoryToDemandRows` (`apps/web/lib/forecast/history-demand.ts`) once grouped by article alone, which put an item's whole history on the month of its first sale and flattened the series the base rate and seasonal indices read.
