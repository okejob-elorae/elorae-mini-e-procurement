# Jubelio integration landmines

The full entries behind the **Jubelio integration** triggers in `AGENTS.md` § Landmine index, in the same order. Each one was written after someone paid for it. Read the entry for whatever surface you are about to touch before writing code; where an entry points on to `docs/ARCHITECTURE-NOTES.md`, `docs/EPIC-STATUS.md` or `docs/FOLLOWUPS.md`, follow it. When a change makes an entry wrong, fix it here in the same session — and update its trigger in `AGENTS.md` if the trigger itself moved.

- Verifying a Jubelio webhook signature? HMAC-SHA256 in header `Sign` — their docs *text* is wrong, their code example is right.
- Reaching for any Jubelio endpoint? Grep `reference/jubelio-openAPI.yaml` FIRST, then confirm the shape LIVE — the spec both lags and misdescribes (the purpose-built order-by-no lookup returns 200-with-empty-body for settled orders).
- Adding an outbound push to Jubelio? It goes through the `JubelioOutbox` table, not a direct call — handler file + payload builder + spec + router case.
- Debugging a stuck inbound event? `JubelioWebhookEvent.status` is authoritative (`RECEIVED → PROCESSING → PROCESSED / SKIPPED / DEAD`); a sweeper rescues stuck rows every 10 min.
- Touching `outbox-poller.service.ts` or the processor's catch block? Two independent mechanisms kept a failed OUTBOUND row `PENDING` at `attempts: 1` forever instead of reaching `DEAD` — a retained BullMQ job holding the deterministic `jobId` (making `q.add` a silent no-op) and a failure that left the row `PROCESSING` (making every retry LOSE the status-guarded claim and take the guard's early-return arm, which completes the job successfully). Prod ran that way for months with zero DEAD rows and zero admin notifications. Reintroducing EITHER one restores the wedge; `lastEnqueuedAt` will keep advancing and hide it. The same `jobId` trap applies to the INBOUND webhook queue — both now go through `queue/finished-jobs.ts`'s `clearFinishedJob`, so a new queue that hand-rolls its own `add()` reintroduces it. See `docs/ARCHITECTURE-NOTES.md`.
- Detecting an "already in that state" reply from Jubelio? It is an HTTP 500 whose real reason is free-text Indonesian at `err.cause.code`, never a machine-readable code and never `err.code` — the invented `"ALREADY_IN_STATE"` marker the handlers used to test for was never set by anything. Use the shared `outbox/handlers/already-in-state.ts`; add observed phrasings to its marker list rather than loosening the match. See `docs/ARCHITECTURE-NOTES.md`.
- Building a WMS pick push? `POST /wms/sales/picklists/` takes the create-and-autocomplete body (`picklist_id: 0`, `picklist_no: "[auto]"`, `picker_id`, per-line `salesorder_detail_id` + `item_id`) — a bare `{ids}` is rejected with a `picklist_no` validation error, which is how every pick push silently failed on prod. Its neighbour `POST /wms/sales/packlist/mark-as-complete/` genuinely does take `{ids}`; the two are not symmetric. See `docs/ARCHITECTURE-NOTES.md`.
- Adding a Jubelio call whose response carries contact data (addresses, phones, emails)? Shaping it out of your service's return value does NOT stop it being retained — `JubelioHttpService` logs the RAW body into `JubelioApiCall.responseBody` before any mapping runs, and nothing prunes that table. Pass `redactResponseBody: true` on the request init — and note the catch block has TWO sinks, the DB row AND a `logger.error` to stdout, so a fix that covers only one still leaks to the container logs. See `docs/ARCHITECTURE-NOTES.md`.
- Sending a `location_id` to any Jubelio WMS endpoint? It is **`-1`** — the literal id of the only location, "Warehouse Elorae", confirmed live via `GET /jubelio/locations` 2026-09-02. A real id, not a typo: pick and ship both shipped hardcoding `1`, which does not exist here — pick pushes first failed Joi on the payload shape, then, once that was fixed, died on `location_picklist_header` FK violations (`code: "23503"`). Pack sends no `location_id` at all. Re-check the endpoint before changing it; do not "correct" the negative number. See `docs/ARCHITECTURE-NOTES.md`.
- Extending `ALREADY_IN_STATE_MARKERS` because a skip did not fire? Jubelio's body `code` is NOT a stable type — the same call returned free-text Indonesian one day and the bare SQLSTATE `"23505"` the next. Adding SQLSTATEs to the marker list would swallow real defects; the condition to detect is a repeated identical DB-constraint error, not a reason string. See `docs/FOLLOWUPS.md`.
- Reading `SalesOrder.fulfillmentStatus`/`pickedAt`/`packedAt` as proof Jubelio agrees? It is not — the local stamp and the outbox row are written in one transaction, but a push that later skips or dies never rolls them back, and nothing reconciles the two. See `docs/ARCHITECTURE-NOTES.md`.
- Deciding which marketplace a Jubelio order came from — editing `detectChannel` (`apps/api/src/jubelio/handlers/_shared/channel-detect.ts`), adding a marketplace, or writing a query or backfill that derives a channel? Key on the order-number prefix FIRST (`TT-` TikTok, `TP-` Tokopedia, `SP-` Shopee, case-sensitive) and fall back to `source_name` only when no known prefix is present. `source_name` alone is wrong for every TikTok Shop order: TikTok Shop absorbed Tokopedia and Jubelio sends those orders as `Shop | Tokopedia`, so its last token labels them all `TOKOPEDIA` — that shipped and mislabelled every TikTok order until the prefix rule and a backfill corrected it. It reads like the obvious simplification, and a TikTok order looks plausible under the wrong label, so nothing fails loudly. A new marketplace gets its prefix added to the `PREFIX` map, not a new `source_name` token only. Every caller must pass the order number (the sales-order webhook handler passes `salesorder_no`, the sales-return ingest `detail.salesorder_no`) — a caller that omits it silently falls back to the broken rule. Any SQL that matches the prefix must compare binary with `BINARY` on the column (`WHERE BINARY salesorderNo LIKE 'TT-%'`), because `salesorderNo`/`jubelioReturnNo` sit under the case-insensitive `utf8mb4_unicode_ci` default and a bare `LIKE 'TT-%'` also matches `tt-…`, which the runtime rule does not. Not `COLLATE utf8mb4_bin` on the literal: the prod `migrate` job applies SQL through the `mariadb` CLI as utf8mb3, which rejects that at parse time and blocks the deploy (see `docs/landmines/database-ops.md`). Settlement matching does not read `SalesOrder.channel` (it keys on the uploaded marketplace and `channelOrderNo`), so a settlement compare will not surface a channel mislabel. See `docs/ARCHITECTURE-NOTES.md`.
- Editing `upsertSalesOrder`'s item recreate in `apps/api/src/jubelio/handlers/salesorder.handler.ts`? Carry `cogs` across it. The handler replaces an order's `SalesOrderItem` rows on EVERY handle (`deleteMany` then `createMany`), and `SalesOrderItem.cogs` is written only by `consumeOrder` (`packages/db/src/reservation-writer.ts`), once, on the RESERVED → CONSUMED flip — nothing ever writes it again. So the existing `{ salesorderDetailId, cogs }` is read inside the handler's transaction BEFORE the delete and set back on each recreated item that had a non-null one; a detail id with no stored cost is recreated without one. Drop that read, move it after the delete, or rebuild the items from the payload alone, and every post-ship webhook, replayed event or settlement resync nulls the order's cost for good — the settlement line matched to it goes "profit pending" and no path restores it. Costs nulled by handles before this fix are NOT backfilled (logged in `docs/FOLLOWUPS.md`). Do not "fix" this by stamping `cogs` from the handler instead: the cost is the `qty * avgCost` the consume decremented `totalValue` by, and `avgCost` moves afterwards. The carry-over is not race-free: nothing serializes two handles of the same order (webhook queue concurrency 4, plus the separate resync worker), and the `findMany` is a REPEATABLE READ snapshot read while the `deleteMany` is a current read, so a first-time `consumeOrder` stamp that commits between the two is deleted unseen and never re-stamped — the open fix (lock the item rows `FOR UPDATE` before reading them) is logged in `docs/FOLLOWUPS.md`. See `docs/ARCHITECTURE-NOTES.md`.
- Pushing, applying or comparing a Jubelio stock quantity? `end_qty` is **ON-HAND**, never "available", and until cutover **Jubelio, not Elorae, is the source of truth for stock**. `GET /inventory/items/` returns three quantities per variant: `end_qty` (on-hand), `order_qty` (Jubelio's OWN open marketplace orders) and `available_qty = end_qty − order_qty`. A read-only probe of prod Jubelio against prod `InventoryValue.qtyOnHand` on 2026-09-27 settled it — Jubelio `end_qty` / Elorae `qtyOnHand` on four sampled variants: 128/128, 137/133, 125/124, 186/187. So Jubelio already subtracts marketplace commitments itself; the only commitments it cannot see are Elorae's field-sales holds — open `StockReservation` rows with `source <> 'JUBELIO'` (`FIELD_SALES` from putus order create, `FIELD_SALES_KONSI` from konsi approve and the admin konsi push). Their open quantity is `offlineReserved = SUM(qty − consumedQty)` over `state = 'RESERVED'` for the same `itemId` and variant (`""` for variantless — that column is non-nullable). The contract, through the helpers in `packages/db/src/jubelio-stock-contract.ts` (`offlineReservedQty`/`offlineReservedByKey`, their switch-aware `effectiveOfflineReservedQty`/`effectiveOfflineReservedByKey`, `jubelioEndQtyFor`, `eloraeOnHandFromJubelio`, `parseJubelioQty`, `isValidJubelioQty`) — never restate the arithmetic by hand: **(1) push** (`stock-push.handler.ts`) sends `end_qty = max(0, qtyOnHand − offlineReserved)`; **(2) the `stock` webhook** (`stock.handler.ts` → `applyJubelioStockAdjustment`) sets `qtyOnHand = end_qty + offlineReserved` as an ABSOLUTE, via `setMainStock` on the row it locked (`SELECT … FOR UPDATE`, the transaction's first statement), reading the holds after the lock; the raw `end_qty` is validated BEFORE any coercion by `parseJubelioQty` (a finite non-negative number or a plain decimal string), so `null`, `""` and anything else is logged and skipped rather than written — `Number(null)` and `Number("")` are both `0`, which is how a coerce-then-validate check would write a zero Jubelio never reported; **(3) reconciliation** compares Elorae's figure against Jubelio `end_qty` — `max(0, qtyOnHand − offlineReserved)` while pushes are enabled, raw `qtyOnHand` (can be negative) while they are off, via `comparableEloraeQty`; **(4) `MATCH_JUBELIO`** sets `qtyOnHand = end_qty + offlineReserved` as an ABSOLUTE through `setMainStock` on the locked row. **The `offlineReserved` term in (2)–(4) applies only while stock pushes are enabled** (the cutover switch, next entry): only a push nets the holds out of Jubelio's `end_qty`, so while pushes are off nothing has, and adding them back would overstate on-hand — the effective term is then `0`. Use the `effective*` helpers on those three paths, never the raw figure; the push itself only runs while enabled, so it always nets. **(3)'s floor at 0 is gated the same way** — it exists only to mirror what the push actually sends, so while pushes are off nothing floors Jubelio's own figure for the comparison to mirror, and a negative `qtyOnHand` compares raw and gets flagged rather than hidden by a floor that means something only on the push path. **A missing figure is never a zero.** The reconciliation snapshot pages through every item group of `GET /inventory/items/` (200 per page, until a short page, `totalCount`, a repeated page, or a 100-page ceiling — some Jubelio list endpoints ignore paging, see `categories.service.ts`) and reads `end_qty` ONLY, never `available_qty`; a mapped variant absent from every page, or with an invalid `end_qty`, is `null`, which the run records FLAGGED and never corrects or compares as 0 (the non-nullable column stores 0 with `variance = eloraeQty`). The manual `MATCH_JUBELIO` resolve re-reads ONE group live through `GET /jubelio/inventory/snapshot/group/:groupId` — the group id in the PATH, never a query string (the signed channel's landmine is in `docs/landmines/data-ownership-auth.md`) — which reads `GET /inventory/items/group/{id}`, the endpoint the stock webhook already trusts; it refuses, writing nothing, when that live figure is missing, null or invalid, and when Elorae's figure moved since the run (compared to 2dp, after the lock). **Never change the push to send `available`, and never subtract `reservedQty` anywhere on this path.** `reservedQty` includes the `JUBELIO` reservations — the very orders Jubelio already counts in `order_qty` — so subtracting it takes every marketplace commitment off twice, once here and once by Jubelio, and under-lists every item with open marketplace orders. That is exactly what the push did until `fix/jubelio-stock-contract` (`max(0, qtyOnHand − reservedQty)`, commented "push AVAILABLE"), because older docs said `end_qty` meant available and nobody had checked; and because the webhook writes `end_qty` back as on-hand, a push that Jubelio then echoed as a `stock` webhook would also have lowered Elorae's own on-hand by the reserved amount (whether a push echoes at all is unconfirmed). It was a latent contract bug whose prod impact is limited by how rarely a push runs. `available = qtyOnHand − reservedQty` stays correct for the ERP's own selling decisions (`docs/landmines/stock.md`) — it is simply not what `end_qty` means. By the same token never "fix" the webhook by dropping the add-back or by reading `available_qty`. **The add-back and the push are two halves of one contract:** `end_qty + offlineReserved` is on-hand only when Jubelio's `end_qty` was last set by a push that already netted those holds out. That is why the add-back is gated on the switch: while pushes are off it is `0`. While they are on, a field-sales hold created with no push after it is still subtracted by nothing and added back by the webhook, overstating on-hand, until the next push — so enabling the switch has to be followed immediately by a bulk push, and the automatic push (after cutover) is what closes the gap for good. **Direction until cutover:** `InventoryValue` is a MIRROR kept by the `stock` webhook and marketplace reserve/consume, so Jubelio → Elorae (the webhook, `MATCH_JUBELIO`) is the direction that must be correct today. Every Elorae → Jubelio push — the bulk "push all stock" on `/backoffice/jubelio/admin`, the per-item push on the item page, reconciliation `REASSERT_ELORAE` and the push after opname approval — overwrites the source of truth with a mirror that is not yet trustworthy: a negative-on-hand row pushes as `end_qty 0` and takes a live marketplace listing out of stock. Keep reconciliation at `FLAG_ONLY` (the prod setting), resolve a flag by `MATCH_JUBELIO`, and never use `REASSERT_ELORAE` before cutover. The cutover switch (next entry) now refuses every one of those pushes while it is off. **Prod stock is damaged and the push is NOT the proven cause:** on 2026-09-27, 308 `InventoryValue` rows held negative on-hand (−4,036 units in total) and 383 sat below `reservedQty`; the latest reconciliation run flagged 524 of 949 rows, 418 with Jubelio higher. Pushes are too rare to explain that. The leading hypothesis is an ordering race: a `stock` webhook's absolute set, whose `end_qty` already reflects a shipment, landing BEFORE the salesorder ship webhook's `consumeOrder` decrement, so the same units come off twice (`consumeOrder` has no floor). Unproven, and the priority investigation in `docs/FOLLOWUPS.md`. See `docs/ARCHITECTURE-NOTES.md`.
- Adding anything that pushes stock to Jubelio, or touching the cutover switch? Every Elorae → Jubelio stock write goes through a `stock_push` outbox row, and nothing calls `PUT /inventory/items/{id}/stock` outside `apps/api/src/jubelio/outbox/handlers/stock-push.handler.ts` — that handler is where the switch is enforced, so a direct call bypasses it. **The switch** is the `SystemSetting` key `JUBELIO_STOCK_PUSH_ENABLED` (`JUBELIO_STOCK_PUSH_ENABLED_KEY`, read only through `isJubelioStockPushEnabled` in `packages/db/src/jubelio-stock-contract.ts`). It fails CLOSED: only the exact string `"true"` enables pushing; an absent row, `"false"`, `"TRUE"`, `"1"` or anything else is off, and nothing seeds the row, so every environment starts off. **Enforcement:** `StockPushHandler` is the backstop. It reads the switch before anything else and skips with `stock_push_disabled` for EVERY `stock_push` row — the per-item and bulk buttons, the post-opname push (`pushFgStockAfterOpname`, which still enqueues and relies on this backstop), `REASSERT_ELORAE`, rows queued before the switch went off, and any future automatic push. The web refuses first where it can, so the operator sees why: `pushItemStockToJubelio` and `bulkPushAllStockToJubelio` return `push_disabled`, the manual `REASSERT_ELORAE` resolve and saving `REASSERT_ELORAE` as the configured direction both return `PUSH_DISABLED` (saving any other direction still succeeds, even with a stale `REASSERT_ELORAE` stored), and the reconciliation run degrades `REASSERT_ELORAE` to `FLAGGED` so it never enqueues. **Skipped rows are not replayed** when the switch goes back on — a `SKIPPED` row stays skipped unless an admin re-queues it from the outbox table. **The webhook direction is unaffected** — Jubelio → Elorae keeps applying — except that the field-sales add-back applies only while the switch is on (previous entry). **Turning it on** is the LAST cutover step, on `/backoffice/jubelio/admin` (admin wildcard only; the flip and an `AuditLog` row, `JUBELIO_STOCK_PUSH_TOGGLE` with before/after, commit in one transaction): only after the recount in `docs/FOLLOWUPS.md` and a clean reconciliation, and IMMEDIATELY followed by "Sync all stock" on the same page, so Jubelio receives figures net of the open field-sales holds the webhook now starts adding back. Never add a path that pushes stock without going through `stock_push`, and never add a second switch read that could disagree with this one. See `docs/ARCHITECTURE-NOTES.md`.
