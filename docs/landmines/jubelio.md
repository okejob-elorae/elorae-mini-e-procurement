# Jubelio integration landmines

The full entries behind the **Jubelio integration** triggers in `AGENTS.md` § Landmine index, in the same order. Each one was written after someone paid for it. Read the entry for whatever surface you are about to touch before writing code; where an entry points on to `docs/ARCHITECTURE-NOTES.md`, `docs/EPIC-STATUS.md` or `docs/FOLLOWUPS.md`, follow it. When a change makes an entry wrong, fix it here in the same session — and update its trigger in `AGENTS.md` if the trigger itself moved.

- Verifying a Jubelio webhook signature? HMAC-SHA256 in header `Sign` — their docs *text* is wrong, their code example is right.
- Reaching for any Jubelio endpoint? Grep `reference/jubelio-openAPI.yaml` FIRST, then confirm the shape LIVE — the spec both lags and misdescribes (the purpose-built order-by-no lookup returns 200-with-empty-body for settled orders).
- Adding an outbound push to Jubelio? It goes through the `JubelioOutbox` table, not a direct call — handler file + payload builder + spec + router case.
- Debugging a stuck inbound event? `JubelioWebhookEvent.status` is authoritative (`RECEIVED → PROCESSING → PROCESSED / SKIPPED / DEAD`); a sweeper rescues stuck rows every 10 min.
- Touching `outbox-poller.service.ts` or the processor's catch block? Two independent mechanisms kept a failed OUTBOUND row `PENDING` at `attempts: 1` forever instead of reaching `DEAD` — a retained BullMQ job holding the deterministic `jobId` (making `q.add` a silent no-op) and a failure that left the row `PROCESSING` (making every retry LOSE the status-guarded claim and take the guard's early-return arm, which completes the job successfully). Prod ran that way for months with zero DEAD rows and zero admin notifications. Reintroducing EITHER one restores the wedge; `lastEnqueuedAt` will keep advancing and hide it. The same `jobId` trap applies to the INBOUND webhook queue — both now go through `queue/finished-jobs.ts`'s `clearFinishedJob`, so a new queue that hand-rolls its own `add()` reintroduces it. See `docs/ARCHITECTURE-NOTES.md`.
- Detecting an "already in that state" reply from Jubelio? It is an HTTP 500 whose real reason is free-text Indonesian at `err.cause.code`, never a machine-readable code and never `err.code` — the invented `"ALREADY_IN_STATE"` marker the handlers used to test for was never set by anything. Use the shared `outbox/handlers/already-in-state.ts`; add observed phrasings to its marker list rather than loosening the match. See `docs/ARCHITECTURE-NOTES.md`.
- Building a WMS pick push? `POST /wms/sales/picklists/` takes the create-and-autocomplete body (`picklist_id: 0`, `picklist_no: "[auto]"`, `picker_id`, per-line `salesorder_detail_id` + `item_id`) — a bare `{ids}` is rejected with a `picklist_no` validation error, which is how every pick push silently failed on prod. Its neighbour `POST /wms/sales/packlist/mark-as-complete/` genuinely does take `{ids}`; the two are not symmetric. See `docs/ARCHITECTURE-NOTES.md`.
- Adding a Jubelio call whose response carries contact data (addresses, phones, emails)? Shaping it out of your service's return value does NOT stop it being retained — `JubelioHttpService` logs the RAW body into `JubelioApiCall.responseBody` before any mapping runs, and nothing prunes that table. Pass `redactResponseBody: true` on the request init — and note the catch block has TWO sinks, the DB row AND a `logger.error` to stdout, so a fix that covers only one still leaks to the container logs. See `docs/ARCHITECTURE-NOTES.md`.
- Sending a `location_id` to any Jubelio WMS endpoint? It is **`-1`** — the literal id of the only location, "Warehouse Elorae", confirmed live via `GET /jubelio/locations` 2026-09-02. A real id, not a typo: pick and ship both shipped hardcoding `1`, which does not exist here — pick pushes first failed Joi on the payload shape, then, once that was fixed, died on `location_picklist_header` FK violations (`code: "23503"`). Pack sends no `location_id` at all. Re-check the endpoint before changing it; do not "correct" the negative number. See `docs/ARCHITECTURE-NOTES.md`.
- Extending `ALREADY_IN_STATE_MARKERS` because a skip did not fire? Jubelio's body `code` is NOT a stable type — the same call returned free-text Indonesian one day and the bare SQLSTATE `"23505"` the next. Adding SQLSTATEs to the marker list would swallow real defects: a unique violation is not by itself proof the order is already in the target state. The repeat is settled without classifying the reason. `outbox/constraint-fingerprint.ts` fingerprints a `JubelioError` whose `cause.code` is a class-23 SQLSTATE as `<http status>:<code>`, the processor appends it to `lastError` as `[constraint <status>:<code>]`, and when the next attempt fails with the same fingerprint the processor marks the row `DEAD` and returns, exactly like the `NonRetryableError` arm: the job completes, BullMQ does not retry and `onJobFailed` never fires, so it is one DEAD and one alert instead of five attempts. The first such error still retries, and a different error on the next attempt retries as before. Keep that arm returning rather than throwing (a throw retries and leaves the alert to the last attempt), and keep it comparing against the PREVIOUS attempt's `lastError`, which the processor reads before it claims the row. It only sees errors a handler lets propagate as the original `JubelioError` with its parsed body on `cause`; a handler that wraps or replaces the error disables it. See `docs/ARCHITECTURE-NOTES.md`.
- Reading `SalesOrder.fulfillmentStatus`/`pickedAt`/`packedAt` as proof Jubelio agrees? It is not — the local stamp and the outbox row are written in one transaction, but a push that later skips or dies never rolls them back. `runFulfillmentPushDivergenceSweep` (`apps/web/lib/fulfillment/push-divergence-sweep.ts`, every 30 minutes) makes that divergence loud without fixing it: for each `PICKED` order it reads the latest `salesorder_pick` row, for each `PACKED` order the latest `salesorder_pack` row, and raises one `FULFILLMENT_PUSH_STUCK` admin notification per (order, outbox row) when that row is `DEAD`, `SKIPPED` for any reason other than `jubelio_already_in_state`, or still `PENDING`/`PROCESSING` an hour after it was created. It corrects neither side. It deliberately never compares `wmsStatus`, whose vocabulary from Jubelio is not reliably known, so a push Jubelio accepted and later reversed on its side stays invisible; an order with no outbox row is skipped; and the ship push is not covered, since a `SHIPPED` order is never swept. See `docs/ARCHITECTURE-NOTES.md`.
- Adding an outbox push that must land after another one (pick → pack → ship), or editing the pack or ship handler? The pushes are enqueued as independent `JubelioOutbox` rows, and with `WORKER_CONCURRENCY: 1` the retry backoff alone reorders them: a pick that fails transiently is re-queued 5 s later and the worker takes the pack meanwhile, so the pack reached Jubelio before the pick had. The first statement of the dependent handler is `assertPredecessorSettled` (`outbox/handlers/predecessor-push.ts`), which looks up the latest predecessor row for the same order created at or before this row (a re-enqueue made afterwards never gates it). `PENDING`/`PROCESSING` throws a plain `Error`, which burns one of this row's retries; `DEAD` throws `NonRetryableError`, so this row goes `DEAD` with its own alert; `DONE`, `SKIPPED` or no row at all proceeds. The pack handler gates on `salesorder_pick`, the ship handler on `salesorder_pack` (Ship requires `PACKED`, which only `markOrderPacked` sets, and it enqueues the pack row, so one always precedes a ship). A new dependent push calls it the same way, before any read or HTTP call. Do not gate on `SalesOrder.fulfillmentStatus` instead: the local stamp advances when the row is enqueued, not when Jubelio accepts it, so it says nothing about the predecessor having landed. The wait is bounded by the dependent row's own retry window (about 75 s of backoff), so a predecessor stuck longer than that sends the dependent row `DEAD` (logged in `docs/FOLLOWUPS.md`). See `docs/ARCHITECTURE-NOTES.md`.
- Deciding which marketplace a Jubelio order came from — editing `detectChannel` (`apps/api/src/jubelio/handlers/_shared/channel-detect.ts`), adding a marketplace, or writing a query or backfill that derives a channel? Key on the order-number prefix FIRST (`TT-` TikTok, `TP-` Tokopedia, `SP-` Shopee, case-sensitive) and fall back to `source_name` only when no known prefix is present. `source_name` alone is wrong for every TikTok Shop order: TikTok Shop absorbed Tokopedia and Jubelio sends those orders as `Shop | Tokopedia`, so its last token labels them all `TOKOPEDIA` — that shipped and mislabelled every TikTok order until the prefix rule and a backfill corrected it. It reads like the obvious simplification, and a TikTok order looks plausible under the wrong label, so nothing fails loudly. A new marketplace gets its prefix added to the `PREFIX` map, not a new `source_name` token only. Every caller must pass the order number (the sales-order webhook handler passes `salesorder_no`, the sales-return ingest `detail.salesorder_no`) — a caller that omits it silently falls back to the broken rule. Any SQL that matches the prefix must compare binary with `BINARY` on the column (`WHERE BINARY salesorderNo LIKE 'TT-%'`), because `salesorderNo`/`jubelioReturnNo` sit under the case-insensitive `utf8mb4_unicode_ci` default and a bare `LIKE 'TT-%'` also matches `tt-…`, which the runtime rule does not. Not `COLLATE utf8mb4_bin` on the literal: the prod `migrate` job applies SQL through the `mariadb` CLI as utf8mb3, which rejects that at parse time and blocks the deploy (see `docs/landmines/database-ops.md`). Settlement matching does not read `SalesOrder.channel` (it keys on the uploaded marketplace and `channelOrderNo`), so a settlement compare will not surface a channel mislabel. See `docs/ARCHITECTURE-NOTES.md`.
- Editing `upsertSalesOrder`'s item recreate in `apps/api/src/jubelio/handlers/salesorder.handler.ts`? Carry `cogs` across it. The handler replaces an order's `SalesOrderItem` rows on EVERY handle (`deleteMany` then `createMany`), and `SalesOrderItem.cogs` is written only by `consumeOrder` (`packages/db/src/reservation-writer.ts`), once, on the RESERVED → CONSUMED flip — nothing ever writes it again. So the existing `{ salesorderDetailId, cogs }` is read inside the handler's transaction BEFORE the delete and set back on each recreated item that had a non-null one; a detail id with no stored cost is recreated without one. Drop that read, move it after the delete, or rebuild the items from the payload alone, and every post-ship webhook, replayed event or settlement resync nulls the order's cost for good — the settlement line matched to it goes "profit pending" and no path restores it. Costs nulled by handles before this fix are NOT backfilled (logged in `docs/FOLLOWUPS.md`). Do not "fix" this by stamping `cogs` from the handler instead: the cost is the `qty * avgCost` the consume decremented `totalValue` by, and `avgCost` moves afterwards. The carry-over is not race-free: two handles of the same order run concurrently (webhook queue concurrency 4, plus the separate resync worker), and although their upsert transactions now serialise on the staleness guard's `SalesOrder` row lock, `consumeOrder` stamps after the handler's commit, outside that lock, and the `findMany` is a REPEATABLE READ snapshot read while the `deleteMany` is a current read, so a first-time `consumeOrder` stamp that commits between the two is deleted unseen and never re-stamped — the open fix (lock the item rows `FOR UPDATE` before reading them) is logged in `docs/FOLLOWUPS.md`. See `docs/ARCHITECTURE-NOTES.md`.
- Editing `upsertSalesOrder`'s order fields in `apps/api/src/jubelio/handlers/salesorder.handler.ts`? `trackingNumber` and `courier` are deliberately NOT in the fields shared by the upsert's create and update arms. The create arm writes the incoming value as received (NOT trimmed — `nonBlank` trims only to test for blank) or null when it is blank after trimming; the update arm spreads each key ONLY when the incoming value is non-blank, so Prisma leaves the stored column untouched when a payload carries no resi. Before this, a newer payload that simply omits the resi wiped one the order already had, and so could an older payload landing after a newer one. Moving either field back into the shared set reintroduces that silently — the spec in `salesorder.handler.spec.ts` pins it. The upsert now also opens with a staleness guard, and the two cover different failures, so keep both. The guard is a `SELECT lastModifiedJubelio … FOR UPDATE` on the order's `SalesOrder` row, compared through `isStalePayload`: a payload whose `last_modified` is strictly older than the stored value returns before anything is written, and the handler reports `SKIPPED` `stale_payload` with no state row, item recreate, reserve, consume or release, since a newer payload already drove those. Equal timestamps, or a missing one on either side, process as before — which is why the blank guard still matters: a newer resi-less payload, or one with no `last_modified`, still reaches the update. The locking read must stay the transaction's first read: it returns the latest COMMITTED row and makes a second handle of the same order wait for the first, while a plain read there would compare against the transaction's snapshot and let an older payload through. A resi Jubelio cancels without a replacement stays visible until a new one arrives, because a blank never clears it (PR #346).
- Deciding whether a Jubelio sales order is cancelled or returned? Never from `is_canceled` alone. Jubelio often reports a cancel through `internal_status: "CANCELED"` and leaves `is_canceled` false. `deriveStatus` always read both, but the salesorder handler released reservations on the flag alone, so `SalesOrder.status` said `CANCELLED` while 3,084 orders kept 3,298 units `RESERVED` until PR #375 fixed the handler and a one-off script released them (2026-09-29). **In apps/api**, every cancel decision goes through `isCanceledOrder` in `apps/api/src/jubelio/handlers/_shared/status-derive.ts` — the handler's release branch, its reserve guard, `lastIsCanceled` and `deriveStatus` itself — so there is one definition to keep right; never write a fresh `p.is_canceled` check beside it. A RETURNED order is finished too: `isReturnedOrder` (internal or wms status `RETURNED`) joins `isCanceledOrder` as `isFinished`, which the release branch and the reserve guard key on, so a returned order is released and never reserved — until PR #378 nothing released one, and 651 orders held 741 units `RESERVED`. The shipped branch runs first, so a finished order Jubelio also reports shipped still consumes; `lastIsCanceled` stays cancel-only. Narrowing the release branch back to cancel alone leaves every returned order holding `RESERVED`; narrowing the reserve guard lets a returned order that never reserved reserve fresh lines (`reserveOrder` skips lines already released, so it is the unreserved ones that leak). **In apps/web**, `SalesOrder.isCanceled` is the RAW flag and stays raw, so a query that means "not finished" filters on `status` too: the packer's four queries filtered on the flag alone and kept cancelled orders in the packer pool, and now exclude `CANCELLED` and `RETURNED` (`NOT_FINISHED` in `apps/web/lib/packer/queries.ts`). Readers that already gate on `status` are safe as they stand — `isAwaitingResi` admits only `NEW`/`PROCESSING` and the reconciliation report only `COMPLETED`/`SHIPPED`. Do not "fix" the column by writing the derived value into it instead — every historical row holds the raw flag and would stay wrong until Jubelio re-delivered it. See `docs/ARCHITECTURE-NOTES.md`.
- Deciding whether Jubelio shipped a sales order? Never from `wms_status: "SHIPPED"` alone. Jubelio has all but stopped sending it — measured on prod 2026-09-29, salesorder webhooks carrying it fell from 2,167 in July to 185 in August and 6 in September, while `internal_status: "SHIPPED"` (almost always with `wms_status: "READY_TO_SHIP"`) arrived on 16,102, 14,545 and 8,282. `is_shipped` was null on every one. `reportsShipped` read only the WMS field and the always-null flag besides the completion signals, so by September no order consumed at ship: of 1,080 orders at `internal_status: "SHIPPED"`, 1,013 still held about 1,135 units `RESERVED`, read `NEW` in the order list and stayed in the pick queue until they completed about 5.6 days later. `internal_status: "SHIPPED"` is a real ship, not a booking: 298 of 300 sampled completed orders passed through it, and Jubelio's own on-hand had already dropped by the in-transit qty — 50 flagged reconciliation rows were off by exactly that figure — with no `stock` webhook at the ship (0 of 90 lines), so a consume at ship does not race one. The residual risk: 53 other rows with in-transit orders already matched Jubelio, read as timing skew — where Jubelio's figure had in fact already taken the order off, a consume puts Elorae below it by that qty until the variant's next `stock` webhook. That risk is not new; the old path took the same units off at completion. `isShippedOrder` in `apps/api/src/jubelio/handlers/_shared/status-derive.ts` is the one definition (`wms_status` SHIPPED, `is_shipped`, or `internal_status` SHIPPED); `deriveStatus`'s SHIPPED arm and the handler's `reportsShipped` (which adds the completion signals) both call it, and `READY_TO_SHIP` alone reads `PROCESSING` — it is NOT a ship, so never add it to `isShippedOrder`. Never add a fresh ship check beside it. **In apps/web**, `SalesOrder.wmsStatus`/`internalStatus` are raw mirrors: decide shipped from the derived `status` or `fulfillmentStatus`, never from those columns. Consume at ship matches the ERP's own Ship button, which consumes in `markOrderShipped`; a return after ship restores through the consumed reservation (`acceptReturnItem`, `docs/landmines/stock.md`). A cancel after ship releases nothing, since the lines are already `CONSUMED`, and nothing reverses the order's sales journals once a GL cutover lets the sweep post them — the same outcome a `wms_status: "SHIPPED"` order always had, now reachable for nearly every shipped order. Measured on prod 2026-09-29 it has not happened: of 19,278 orders that reached `internal_status: "SHIPPED"`, 0 were later cancelled and 704 were returned, which go through the return accept. Measure it again before arming the cutover (open in `docs/FOLLOWUPS.md`). Fixed in PR #381. See `docs/ARCHITECTURE-NOTES.md`.
- Pushing, applying or comparing a Jubelio stock quantity? `end_qty` is **ON-HAND**, never "available", and until cutover **Jubelio, not Elorae, is the source of truth for stock**. `GET /inventory/items/` returns three quantities per variant: `end_qty` (on-hand), `order_qty` (Jubelio's OWN open marketplace orders) and `available_qty = end_qty − order_qty`. A read-only probe of prod Jubelio against prod `InventoryValue.qtyOnHand` on 2026-09-27 settled it — Jubelio `end_qty` / Elorae `qtyOnHand` on four sampled variants: 128/128, 137/133, 125/124, 186/187. So Jubelio already subtracts marketplace commitments itself; the only commitments it cannot see are Elorae's field-sales holds — open `StockReservation` rows with `source <> 'JUBELIO'` (`FIELD_SALES` from putus order create, `FIELD_SALES_KONSI` from konsi approve and the admin konsi push). Their open quantity is `offlineReserved = SUM(qty − consumedQty)` over `state = 'RESERVED'` for the same `itemId` and variant (`""` for variantless — that column is non-nullable). The contract, through the helpers in `packages/db/src/jubelio-stock-contract.ts` (`offlineReservedQty`/`offlineReservedByKey`, their switch-aware `effectiveOfflineReservedQty`/`effectiveOfflineReservedByKey`, `jubelioEndQtyFor`, `eloraeOnHandFromJubelio`, `parseJubelioQty`, `isValidJubelioQty`) — never restate the arithmetic by hand: **(1) push** (`stock-push.handler.ts`) sends `end_qty = max(0, qtyOnHand − offlineReserved)`; **(2) the `stock` webhook** (`stock.handler.ts` → `applyJubelioStockAdjustment`) sets `qtyOnHand = end_qty + offlineReserved` as an ABSOLUTE, via `setMainStock` on the row it locked (`SELECT … FOR UPDATE`, the transaction's first statement), reading the holds after the lock; the raw `end_qty` is validated BEFORE any coercion by `parseJubelioQty` (a finite non-negative number or a plain decimal string), so `null`, `""` and anything else is logged and skipped rather than written — `Number(null)` and `Number("")` are both `0`, which is how a coerce-then-validate check would write a zero Jubelio never reported; **(3) reconciliation** compares Elorae's figure against Jubelio `end_qty` — `max(0, qtyOnHand − offlineReserved)` while pushes are enabled, raw `qtyOnHand` (can be negative) while they are off, via `comparableEloraeQty`; **(4) `MATCH_JUBELIO`** sets `qtyOnHand = end_qty + offlineReserved` as an ABSOLUTE through `setMainStock` on the locked row. **The `offlineReserved` term in (2)–(4) applies only while stock pushes are enabled** (the cutover switch, next entry): only a push nets the holds out of Jubelio's `end_qty`, so while pushes are off nothing has, and adding them back would overstate on-hand — the effective term is then `0`. Use the `effective*` helpers on those three paths, never the raw figure; the push itself only runs while enabled, so it always nets. **(3)'s floor at 0 is gated the same way** — it exists only to mirror what the push actually sends, so while pushes are off nothing floors Jubelio's own figure for the comparison to mirror, and a negative `qtyOnHand` compares raw and gets flagged rather than hidden by a floor that means something only on the push path. **A missing figure is never a zero.** The reconciliation snapshot pages through every item group of `GET /inventory/items/` (200 per page, until a short page, `totalCount`, a repeated page, or a 100-page ceiling — some Jubelio list endpoints ignore paging, see `categories.service.ts`) and reads `end_qty` ONLY, never `available_qty`; a mapped variant absent from every page, or with an invalid `end_qty`, is `null`, which the run records FLAGGED and never corrects or compares as 0 (the row stores `jubelioQty` and `variance` as NULL; rows written before the nullable-figures migration still hold `jubelioQty 0` with `variance = eloraeQty`, since a stored 0 cannot be told apart from a real zero, so they were not backfilled). The manual `MATCH_JUBELIO` resolve re-reads ONE group live through `GET /jubelio/inventory/snapshot/group/:groupId` — the group id in the PATH, never a query string (the signed channel's landmine is in `docs/landmines/data-ownership-auth.md`) — which reads `GET /inventory/items/group/{id}`, the endpoint the stock webhook already trusts; it refuses, writing nothing, when that live figure is missing, null or invalid, and when Elorae's figure moved since the run (compared to 2dp, after the lock). **Never change the push to send `available`, and never subtract `reservedQty` anywhere on this path.** `reservedQty` includes the `JUBELIO` reservations — the very orders Jubelio already counts in `order_qty` — so subtracting it takes every marketplace commitment off twice, once here and once by Jubelio, and under-lists every item with open marketplace orders. That is exactly what the push did until PR #338 (`max(0, qtyOnHand − reservedQty)`, commented "push AVAILABLE"), because older docs said `end_qty` meant available and nobody had checked; and because the webhook writes `end_qty` back as on-hand, a push that Jubelio then echoed as a `stock` webhook would also have lowered Elorae's own on-hand by the reserved amount (whether a push echoes at all is unconfirmed). It was a latent contract bug whose prod impact is limited by how rarely a push runs. `available = qtyOnHand − reservedQty` stays correct for the ERP's own selling decisions (`docs/landmines/stock.md`) — it is simply not what `end_qty` means. By the same token never "fix" the webhook by dropping the add-back or by reading `available_qty`. **The add-back and the push are two halves of one contract:** `end_qty + offlineReserved` is on-hand only when Jubelio's `end_qty` was last set by a push that already netted those holds out. That is why the add-back is gated on the switch: while pushes are off it is `0`. While they are on, a field-sales hold created with no push after it is still subtracted by nothing and added back by the webhook, overstating on-hand, until the next push — so enabling the switch has to be followed immediately by a bulk push, and the automatic push (after cutover) is what closes the gap for good. **Direction until cutover:** `InventoryValue` is a MIRROR kept by the `stock` webhook and marketplace reserve/consume, so Jubelio → Elorae (the webhook, `MATCH_JUBELIO`) is the direction that must be correct today. Every Elorae → Jubelio push — the bulk "push all stock" on `/backoffice/jubelio/admin`, the per-item push on the item page, reconciliation `REASSERT_ELORAE` and the push after opname approval — overwrites the source of truth with a mirror that is not yet trustworthy: a negative-on-hand row pushes as `end_qty 0` and takes a live marketplace listing out of stock. Keep reconciliation at `FLAG_ONLY` (the prod setting), resolve a flag by `MATCH_JUBELIO`, and never use `REASSERT_ELORAE` before cutover. The cutover switch (next entry) now refuses every one of those pushes while it is off. **Prod stock is damaged and the push is NOT the proven cause:** on 2026-09-27, 307 `InventoryValue` rows held negative on-hand (−4,018 units in total) on 2026-09-29, 296 of them already negative when the ledger opened on 2026-09-16, so the damage predates the ledger. The once-suspected ordering race — a `stock` webhook's absolute set landing before `consumeOrder` takes the same units off again — is ruled out by the ledger (17 exact reversals in about 1,460 consumes). The rows stay negative because a `stock` webhook fires only when Jubelio's figure changes. What to do about them is the priority item in `docs/FOLLOWUPS.md`. See `docs/ARCHITECTURE-NOTES.md`.
- Resolving a reconciliation row with Match Jubelio, singly or in bulk, or adding another resolve path? The result's `MANUALLY_RESOLVED` mark is written INSIDE the stock transaction, as an `updateMany` conditional on `action: "FLAGGED"` whose zero count throws and rolls the stock write back as `ALREADY_RESOLVED` (`resolveOneResult` in `apps/web/lib/inventory/reconciliation-runner.ts`). Marking it after the commit — the shape before PR #376 — let a failed mark leave stock moved under a row that still reads FLAGGED, whose retry then refuses `STOCK_MOVED` until a new run, and let a concurrent resolve that came out as a no-op overwrite the winner's `resolutionDirection`. Every resolve goes through `resolveOneResult`. The bulk path caches each Jubelio item group for ONE call only — never across calls, since each write must follow its own live read. The REASSERT_ELORAE branch still marks outside any transaction; it is refused until cutover, and the fix is logged in `docs/FOLLOWUPS.md`. See `docs/ARCHITECTURE-NOTES.md`.
- Adding anything that pushes stock to Jubelio, or touching the cutover switch? Every Elorae → Jubelio stock write goes through a `stock_push` outbox row, and nothing calls `PUT /inventory/items/{id}/stock` outside `apps/api/src/jubelio/outbox/handlers/stock-push.handler.ts` — that handler is where the switch is enforced, so a direct call bypasses it. **The switch** is the `SystemSetting` key `JUBELIO_STOCK_PUSH_ENABLED` (`JUBELIO_STOCK_PUSH_ENABLED_KEY`, read only through `isJubelioStockPushEnabled` in `packages/db/src/jubelio-stock-contract.ts`). It fails CLOSED: only the exact string `"true"` enables pushing; an absent row, `"false"`, `"TRUE"`, `"1"` or anything else is off, and nothing seeds the row, so every environment starts off. **Enforcement:** `StockPushHandler` is the backstop. It reads the switch before anything else and skips with `stock_push_disabled` for EVERY `stock_push` row — the per-item and bulk buttons, the post-opname push (`pushFgStockAfterOpname`, which still enqueues and relies on this backstop), `REASSERT_ELORAE`, rows queued before the switch went off, and any future automatic push. The web refuses first where it can, so the operator sees why: `pushItemStockToJubelio` and `bulkPushAllStockToJubelio` return `push_disabled`, the manual `REASSERT_ELORAE` resolve and saving `REASSERT_ELORAE` as the configured direction both return `PUSH_DISABLED` (saving any other direction still succeeds, even with a stale `REASSERT_ELORAE` stored), and the reconciliation run degrades `REASSERT_ELORAE` to `FLAGGED` so it never enqueues. **Skipped rows are not replayed** when the switch goes back on — a `SKIPPED` row stays skipped unless an admin re-queues it from the outbox table. **The webhook direction is unaffected** — Jubelio → Elorae keeps applying — except that the field-sales add-back applies only while the switch is on (previous entry). **Turning it on** is the LAST cutover step, on `/backoffice/jubelio/admin` (admin wildcard only; the flip and an `AuditLog` row, `JUBELIO_STOCK_PUSH_TOGGLE` with before/after, commit in one transaction): only after the recount in `docs/FOLLOWUPS.md` and a clean reconciliation, and IMMEDIATELY followed by "Sync all stock" on the same page, so Jubelio receives figures net of the open field-sales holds the webhook now starts adding back. Never add a path that pushes stock without going through `stock_push`, and never add a second switch read that could disagree with this one. See `docs/ARCHITECTURE-NOTES.md`.
- Adding or changing a path that pushes a PRODUCT to Jubelio? Creating a product in Jubelio is always a deliberate act: the create-time push when an item is created through the form (`enqueueProductPushOnCreate`), a Master Produk import with its Jubelio box ticked, the item page's "Create in Jubelio" button (`createItemInJubelio`, gated on `items:edit` and `jubelioCreateEligibility`), or the Jubelio bulk migration (`enqueueBulkMigration` in `apps/web/app/actions/jubelio-bulk-migration.ts`, `settings:security:manage`, unmapped ERP finished goods only). The edit paths — `enqueueProductPushOnUpdate`, `enqueueProductPushOnImageChange` and the selling-price writer (`packages/db/src/item-price-writer.ts`) — push ONLY items that already have a `JubelioProductMapping` — before PR #343 they also pushed any unmapped ERP finished good, and the api handler then created it, so the first edit of an item imported with the box unticked put it in Jubelio. The cost of the current rule: an ERP item whose first push failed no longer self-heals on its next edit; the manual button is the recovery. The push handler still SKIPS an item with no category or an unmapped one (`category_unmapped`), so a queued push is not a created product. "Only a deliberate act" holds for the code paths, not for direct calls: the three `enqueue*` functions are still ungated `"use server"` exports (open in `docs/FOLLOWUPS.md`). See `docs/ARCHITECTURE-NOTES.md`.
- Removing a product variant from Jubelio, or retrying a push that removed one? `DELETE /inventory/items/item-variant/` answered **200 `{"status":"ok"}` for an id that does not exist** — probed on prod 2026-09-30 with an id that never existed; a variant Jubelio already deleted is assumed to answer the same, since a retry after a half-finished removal sends exactly that. So re-sending the DELETE on a retry is safe, and that is what lets `ProductPushHandler` delete in Jubelio first and drop the mappings after, with no transaction around the untimed HTTP call. The retry's catalog POST must not name the removed variant either, which is why `buildJubelioImages` builds `variation_images` from the item's current variants only. Do not "fix" the order by wrapping both in one transaction. `GET /inventory/items/{id}` for an id that does not exist answers the generic **500 `E000001`** ("An internal server error occurred"), never a 404 — a positive-control GET on a known id is the only way to tell "absent" from "broken".
