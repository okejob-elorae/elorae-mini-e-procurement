# Finance — AR, payments landmines

The full entries behind the **Finance — AR, payments** triggers in `AGENTS.md` § Landmine index, in the same order. Each one was written after someone paid for it. Read the entry for whatever surface you are about to touch before writing code; where an entry points on to `docs/ARCHITECTURE-NOTES.md`, `docs/EPIC-STATUS.md` or `docs/FOLLOWUPS.md`, follow it. When a change makes an entry wrong, fix it here in the same session — and update its trigger in `AGENTS.md` if the trigger itself moved.

- Writing to `Receivable.paidAmount`/`outstandingAmount`? Atomic `increment`/`decrement` only, inside the payment/void transaction — never read-modify-write. Same rule as `InventoryValue.reservedQty` in `docs/landmines/stock.md`. See `docs/ARCHITECTURE-NOTES.md`.
- Reading what backs a `Receivable` or a `TaxInvoice`? Never traverse `receivable.delivery` or `taxInvoice.delivery` directly — select `RECEIVABLE_SOURCE_SELECT`/`TAX_INVOICE_SOURCE_SELECT` and go through `resolveReceivableSource`/`resolveTaxInvoiceSource` (`apps/web/lib/finance/ar/receivable-source.ts`), because either model now comes from a putus `FieldSalesDelivery` OR a `KonsiSellThrough` report and each of the two relations may be null. The resolver returns a `kind`-discriminated union (`DELIVERY` | `SELL_THROUGH`) and throws `ReceivableSourceMissingError` for a row carrying neither — which is what a dangling id now produces, since an OPTIONAL relation with no FK behind it reads back as `null` instead of throwing Prisma's `Inconsistent query result`. Two halves the compiler does not cover. A `where` on the relation — `delivery: { … }` in a salesman or search filter — compiles and silently drops every sell-through row, so give it a `sellThrough` arm; `whereFor` (`lib/finance/ar/queries.ts`) nests each such `OR` in its own `AND` element because two sibling `where.OR` assignments overwrite each other. And a `deliveryId` scalar filter still compiles, which is right only on a path that is delivery-specific by nature — the delivery date correction, the nota-print CAS, `suggestOffsetAllocations`' walk from a retur's priced delivery lines. A SELL_THROUGH faktur reads `invoiceDate`/`dueDate`/`total` off its report, which approval stamps; the resolver keeps them nullable only because the row type cannot prove a faktur exists solely for an invoiced report. The faktur list sorts on `createdAt desc, id desc`, which is issue order for both sources — never put it back on `delivery.invoiceDate`, which a sell-through faktur has no value for. The piutang detail's journal retry stays delivery-only on purpose: a sell-through receivable's journals are retried from the report's page. See `docs/ARCHITECTURE-NOTES.md`.
- Creating a `Receivable` or `TaxInvoice` row, fixtures included? Exactly ONE of `deliveryId`/`sellThroughId` must be set, and only the database knows it: the migration hand-writes `Receivable_one_source_check` and `TaxInvoice_one_source_check` (`(deliveryId IS NULL) <> (sellThroughId IS NULL)`), which Prisma cannot express and does not see — both columns are plain optional fields in the generated types, so a create with neither or with both type-checks and then dies at insert on a CHECK violation. Never drop the constraint to get a write through: it is the only thing guaranteeing the resolver's two arms are exclusive. The widening kept both `deliveryId` unique indexes (`MODIFY … NULL` leaves them in place), so a delivery still backs at most one receivable and one faktur, and `sellThroughId` is `@unique` the same way. See `docs/ARCHITECTURE-NOTES.md`.
- Voiding a payment? It keeps its `PaymentAllocation` rows and its original `PAYMENT_RECEIPT` journal — a void adds a reversing `PAYMENT_VOID` journal under a distinct `sourceType`, never deletes either. Reading only the receipt journal after a void makes cash look overstated. See `docs/ARCHITECTURE-NOTES.md`.
- Wondering whether an AR journal can be retried? The gate is a `JOURNAL_PENDING` notification existing, never a missing `Journal` row — every backfilled pre-existing delivery has no journal by construction, and offering a retry off that absence would post revenue/COGS with nothing to balance against. The konsi sell-through kinds are the one exception, gated on the missing journal for the reason in the sell-through approve entry (`docs/landmines/konsi-sell-through.md`). See `docs/ARCHITECTURE-NOTES.md`.
- Correcting a delivery's dates? `updateDeliveryDatesAction` moves THREE rows (delivery, `Receivable`, both posted journals) in one transaction, and REFUSES the correction outright once the receivable has `paidAmount > 0` — void the payment first. That refusal is only total because the `paidAmount` read sits BEFORE the delivery CAS `updateMany`: `runSerializable` is a plain `prisma.$transaction`, which COMMITS on a normal return and rolls back only on a throw, so a `return { kind: "HAS_PAYMENTS" }` placed after any write commits that write while reporting a refusal. Reordering the guards, or adding a new early-return arm below a write, silently reintroduces a three-way split (delivery re-dated, receivable and both journals not) that nothing ever reconverges. Every early return in that callback must be write-free — throw, don't return, if you need to abort after a write. The journal posters hold the other side of that serialisation: `postFieldDeliveryRevenueJournal`/`postFieldDeliveryCogsJournal` (`apps/web/lib/finance/ar/delivery-journal.ts`) lock the delivery row `FOR UPDATE` as the FIRST statement of their own `runSerializable`, then read `invoiceDate` and post inside that same transaction, which is what keeps a journal retry from dating its journal on a stale `invoiceDate` while the correction re-dates the delivery and the receivable. Never drop that lock, and never read the delivery ahead of it. See `docs/ARCHITECTURE-NOTES.md`.
- Checking whether a receivable is `PAID`? `FieldSalesDelivery.total` carries sen (unlike `VanSale`/`SpgSale` totals), so `PAID` requires `outstandingAmount === 0` exactly — a cash-settled receivable can sit at `PARTIAL` with a sub-rupiah residue forever. No write-off path ships in this slice. See `docs/FOLLOWUPS.md` and `docs/ARCHITECTURE-NOTES.md`.
- Touching `lib/finance/ar/aging.ts`? `daysOverdue` floors on WIB calendar days via a hardcoded `+7h` shift, not the raw UTC epoch — `getDate()`/`getFullYear()` read the HOST machine's timezone and are NOT the fix (would pass on a WIB laptop, silently fail on prod's UTC server). See `docs/ARCHITECTURE-NOTES.md`.
- Calling an AR journal builder directly — the four delivery/payment ones, the four sell-through ones (revenue, COGS, shrinkage, surplus) in `lib/konsi-sell-through/journal.ts`, which share their shape, or that file's reversal poster `postSellThroughVoidJournal`? Don't — they MAY THROW (a negative-amount line raises `BAD_LINE`, uncaught by `generateAutoJournal`; the reversal poster calls `postJournal` directly and rethrows everything but `UNBALANCED`, `NON_POSTABLE_ACCOUNT` included). Only ever call them through `postArJournalSafely`, which turns a throw into a `JOURNAL_PENDING` flag instead of a crash on a live delivery, payment, sell-through approval or sell-through void. See `docs/ARCHITECTURE-NOTES.md`.
- Voiding a payment against a `WRITTEN_OFF` or `VOIDED` receivable? Refused with `ALREADY_SETTLED`, symmetric with `recordPayment` — without the guard a void would resurrect a written-off balance with nothing reversing the write-off in the GL, or revive a receivable whose sell-through report was voided. `VOIDED` is terminal in every AR writer: `recordPayment`, `voidPayment`, `assignCollector` and `submitCollection` refuse it `ALREADY_SETTLED`, and `submitSettlement` refuses it `NOT_OUTSTANDING` through its `OUTSTANDING`/`PARTIAL` allow-list — while a void itself refuses `SETTLEMENT_PENDING`, so settlement approval never meets one. Only `voidSellThrough` sets it, always with `outstandingAmount` 0, so the overdue sweep, credit exposure and the amplop (which filter on `OUTSTANDING`/`PARTIAL`) never see it and the aging totals fold nothing from it. A receivable status check written as a deny-list must name `VOIDED` beside `WRITTEN_OFF`, or it lets a voided receivable through. See `docs/ARCHITECTURE-NOTES.md`.
- Touching credit-limit enforcement (`Store.creditLimit`, `computeStoreCreditExposure`, `approveFieldSalesOrder`'s credit gate)? The create-time flag is advisory, the approve-time live check is authoritative — they disagree in both directions by design; never read the stored flag as the reason for an override. See `docs/ARCHITECTURE-NOTES.md`.
- Editing `approveFieldSalesOrder`'s PUTUS tail? The credit-limit refusal is a thrown `CreditLimitExceededError`, never a `return` — `runSerializable` commits on normal return, and the finalPrices per-line writes were deliberately moved to run AFTER the gate. See `docs/ARCHITECTURE-NOTES.md`.
- Reading `computeStoreCreditExposure`'s output? Exposure = outstanding receivables + approved-undelivered residual, floored per order — a receivables-only reading looks correct and silently lets every undelivered order through. See `docs/ARCHITECTURE-NOTES.md`.
- Wondering why konsi orders never trip the credit limit? Exempt by construction — a konsi order has zero value at create and never raises a `Receivable` of its own. Konsi AR does exist now, but only at sell-through invoicing, and a sell-through receivable counts toward its store's exposure like any other. Whether konsi ORDERS should now be gated on that exposure is an open decision logged in `docs/FOLLOWUPS.md`, not a missing guard — take it before adding a check. See `docs/ARCHITECTURE-NOTES.md`.
- Adding a new `AdminNotification` category anywhere? It is delivered to nobody until added to `admin-fanout.ts`'s `CATEGORY_PERMISSION` map — silent, no thrown error. See `docs/ARCHITECTURE-NOTES.md`.
- Touching a `CollectionSubmission`? It moves no money — `outstandingAmount` stays untouched until `verifyCollection` runs, and credit exposure deliberately ignores pending submissions. See `docs/ARCHITECTURE-NOTES.md`.
- Writing `submitCollection`? The over-collection guard must net BOTH kinds of `PENDING` claim inside the transaction — other collection submissions AND pending settlements' invoice claims, summed by `sumPendingClaimsOnReceivable` (`apps/web/lib/finance/ar/pending-claims.ts`) with the transaction client — not just read `outstandingAmount`. A stale read lets two submissions together over-collect an invoice, and a sum of one kind only lets a collector and a salesman each claim the same balance. See `docs/ARCHITECTURE-NOTES.md`.
- Editing `verifyCollection`? It posts the payment BEFORE flipping the submission, with a deterministic `collection-<submissionId>` idempotency key — reordering or randomising the key strands a `VERIFIED` submission with no payment. See `docs/ARCHITECTURE-NOTES.md`.
- Adding a collection-adjacent `AdminNotification` category? Same trap as the new-category entry above — missing from `CATEGORY_PERMISSION` means delivered to nobody, silently. See `docs/ARCHITECTURE-NOTES.md`.
- Wondering why `Receivable.collectorId` stays stamped after an invoice settles through another channel? It's a workflow column, not an entity — the collection queue filters on `status`, so nothing clears it and nothing should. See `docs/ARCHITECTURE-NOTES.md`.
- Adding an overdue-adjacent `AdminNotification` category? `AR_OVERDUE` is present in `CATEGORY_PERMISSION` (mapped to `collections:manage`), and so are `KONSI_COUNT_OVERDUE` and its four konsi siblings (mapped to `stores:manage`, `docs/landmines/konsi-count-schedule.md`) — a new sibling category still needs its own entry or it's delivered to nobody, silently. See `docs/ARCHITECTURE-NOTES.md`.
- Touching `runOverdueSweep`, `runKonsiCountSweep` or `runFulfillmentPushDivergenceSweep` (`apps/web/lib/fulfillment/push-divergence-sweep.ts`)? All three cron sweeps `await` `fanOutAdminNotification` on purpose, as exceptions to `void` — a cron has no waiting user and unawaited fan-outs would stampede Firebase. `reportStuckDeliveryCompletionAction` awaits too, but it is no precedent: the PWA's offline completion queue calls it from background sync and from the pending screen's Retry, where a salesman is waiting. Never copy the `await` into an interactive path. See `docs/ARCHITECTURE-NOTES.md`.
- Touching the overdue dedup query? It reads EVERY `AR_OVERDUE` `AdminNotification` row with no `take` and no `createdAt` floor, on purpose — adding either bound re-announces old crossings forever. See `docs/ARCHITECTURE-NOTES.md`.
- Wondering why an already-45-days-overdue receivable gets one alert, not three? Only the highest crossed threshold fires per sweep pass — lower thresholds already skipped past are never revisited by design. See `docs/ARCHITECTURE-NOTES.md`.
- Touching `ar.overdueThresholdDays` parsing? `parseOverdueThresholds` fails OPEN to the defaults on malformed input, the opposite of `readGlCutover`'s fail-closed — silence is the failure this feature removes. See `docs/ARCHITECTURE-NOTES.md`.
- Calling `sendNotificationToUsers` from a new site, or asserting in a spec on what it writes? It carries its own `VITEST` guard as its first statement, the same check in the same position as `fanOutAdminNotification`'s, so under vitest it writes no `NotificationQueue` row and sends no push, whichever caller reached it — a spec expecting a queue row through it sees none. Never weaken or remove that guard: vitest runs on the shared `:3308` bed and loads `apps/web/.env`'s `FIREBASE_ADMIN_*` credentials, so an unguarded run writes rows that are never pruned and can push to real phones. The only way past it is the helper's own spec, `lib/notifications/recipients.test.ts`, which clears the flag per case with `vi.stubEnv("VITEST", "")` while `@elorae/db` and `@/lib/firebase/admin` are mocked — never clear it in a spec that touches the real database. A spec that needs a caller's notify to throw, or wants to observe it, mocks `@/lib/notifications/recipients` with a pass-through `vi.fn` of the real helper and leaves the flag set, as `lib/finance/ar/overdue-sweep.test.ts` does. A new caller needs no guard of its own. The konsi count sweep's `notifySpgsOfCount`, the settlement reject writer's `notifySalesmanOfRejection` and the item import's `notifyItemsImported` still guard themselves first, as defence in depth; the overdue sweep's `notifyCollectorOfOverdue` deliberately does not, because a caller-side guard returns before that module stub is ever called. See `docs/ARCHITECTURE-NOTES.md`.
- Editing `runOverdueSweep`'s per-receivable body, or catching an error inside `sendNotificationToUsers`? The `AR_OVERDUE` row is the sweep's only record that a crossing fired (the dedup entry above), so it is written LAST: the collector push runs first, then the row, then the awaited fan-out, all inside one try/catch that logs the receivable, counts it in `failed` and moves on to the next. A throw before the row leaves no marker, so the next run retries that crossing; a crossing whose row landed is never re-announced. Two ways to break it, both silent: moving the row back ahead of the collector push marks the crossing announced before the collector is told, so a failed push is never retried; and catching the `NotificationQueue` insert inside `sendNotificationToUsers`, which today catches only the FCM send, hands the loop a success for a push that never happened, with the same result. The collector push has one recipient and that insert is the helper's only uncaught write, so a throw means nothing reached the collector and the retry does not double-notify. The one duplicate this order can cost is a push that landed followed by a failed row insert, which pushes the collector again on the next run. Same marker-last shape as the konsi count sweep's `KONSI_COUNT_DUE` row (`docs/landmines/konsi-count-schedule.md`). See `docs/ARCHITECTURE-NOTES.md`.
- Writing a `NotificationQueue` row, or an `AdminNotification.title`? Those columns are bare `String`s, i.e. `VARCHAR(191)`, and an overlong value throws on insert, so the notification reaches nobody — the fan-out sends `AdminNotification.message` (`@db.Text`, uncapped) as the push body, and most real `KONSI_REPORT_BLOCKED` messages once overflowed it. `sendNotificationToUsers` caps `title` and `body` through `capNotificationText` (`apps/web/lib/notifications/text.ts`, by code point, ending in `…`) before the queue insert and the push, which covers every caller that goes through it. A new `NotificationQueue` writer outside that sink, and every `AdminNotification.create` `title`, must cap too. See `docs/ARCHITECTURE-NOTES.md`.
- Touching `TaxInvoice.buyerNpwp`/`taxableAmount`/`ppnAmount`? They're snapshots taken once at `markTaxInvoiceCreated`, never live lookups against `Store.npwp` or `PPN_RATE_PERCENT` — editing either afterward must not retroactively change an already-filed faktur. See `docs/ARCHITECTURE-NOTES.md`.
- Calling `markTaxInvoiceSentToStore` or `revertTaxInvoiceToCreated`? Each one's `data` is `{ reason }` only — copying `markTaxInvoiceCreated`'s full data block into either would silently reassign authorship and the amounts of every faktur it touches, and copying `revertTaxInvoiceToPending`'s nulling block into the step back from `SENT_TO_STORE` would wipe the four filed values it exists to keep. See `docs/ARCHITECTURE-NOTES.md`.
- Wondering where the faktur NPWP requirement is enforced? In `markTaxInvoiceCreated` (the writer), not the dialog — every `"use server"` export is independently callable. See `docs/ARCHITECTURE-NOTES.md`.
- Adding a `TaxInvoiceStatus` member? It touches `writer.ts`'s hand-written `Status`/`from`/`to` unions, `FakturPajakPageClient`'s hand-written `totalCount` sum and hand-listed status tabs, AND `page.tsx`'s `STATUS_VALUES` array — none of them is a `Record`, so a miss fails silently, not at compile time. `status-display.ts`'s own `TaxInvoiceStatusValue` union is one more hand-written spot (next entry); widening it makes its two `Record`s fail to compile until they carry the member. The label needs copy in BOTH locales under TWO namespaces — `fakturPajak` for the queue, and `fakturPajakStatus`, which `DeliveriesCard.tsx` and `AmplopList.tsx` read through `STATUS_LABEL_KEY` — and `TaxInvoice.status` is a MySQL `ENUM` column, so the migration needs its own `ALTER TABLE … MODIFY status ENUM(...)`. `CANCELLED` is the latest member and paid all of it; it is terminal (no transition's `from` names it) and only `voidSellThrough` sets it. See `docs/ARCHITECTURE-NOTES.md`.
- Touching `lib/tax-invoices/status-display.ts`? Deliberately import-free — it declares its own `TaxInvoiceStatusValue` union instead of importing `TaxInvoiceStatusFilter` from `queries.ts`, to keep Prisma out of the client bundle. Keep both in sync by hand. Its consumers now include `FakturPajakPageClient.tsx`, `DeliveriesCard.tsx`, and (branch `amplop-digital`) `AmplopList.tsx`. See `docs/ARCHITECTURE-NOTES.md`.
- Wondering which column means "the delivering salesman" — on the amplop, or in `submitSettlement`'s ownership check? It is the resolver's `salesmanId` (`resolveReceivableSource`), and that means a different column per source. For a DELIVERY-backed receivable it is the ORDER's salesman — `delivery.order.salesmanId`, never `delivery.deliveredById`, which since the delivery-shipment work is a backoffice admin on every expedition completion; keying on `deliveredById` files the store into that admin's amplop and silently drops it from the salesman's, and a spec pins the distinction. For a SELL_THROUGH-backed one it is the report's own `KonsiSellThrough.salesmanId`, which approval stamps: required whenever the report bills anything (`SALESMAN_REQUIRED`), checked against `SALESMAN_CANDIDATE_WHERE` whenever given (`SALESMAN_INVALID`), and left null only where no receivable is created. A null report salesman owns NOTHING: the amplop's membership `OR` never matches it, and `submitSettlement` refuses that receivable `NOT_ASSIGNED` to everyone but its assigned collector. Never borrow another column to give it an owner. Any new "whose receivable is this" filter needs both arms, or it silently loses the sell-through rows. See `docs/ARCHITECTURE-NOTES.md`.
- Relying on `collections:amplop` in a test? No `Permission` row exists until `packages/db/prisma/seed-amplop-permission.sql` is hand-run — no migration applies it, nothing on the deploy path seeds, and the failure is a silently absent screen, not an error. A spec must self-seed the row with `connectOrCreate`, never assert it exists. See `docs/ARCHITECTURE-NOTES.md` and `docs/FOLLOWUPS.md`.
- An ADMIN account can't see `/pwa/pelunasan` even with the permission seeded, so don't use one to verify the seed. `pwaAccessGuard` redirects any wildcard holder to `/backoffice` BEFORE the permission check ever runs (`isSystem` → `['*']`), so ADMIN is **blocked**, not passing on the wildcard — the ADMIN grant in the seed SQL is convention-mirroring only (`seed.ts` assigns ADMIN every `Permission` row) and buys nothing functionally here. Post-seed verification on production must be done on a SALESMAN or COLLECTOR account. See `docs/ARCHITECTURE-NOTES.md`.
- Adding a store's retur credit to a multi-store screen? Use `getStoreAvailableCreditMap`, not `getStoreAvailableCredit` in a loop — it is the batched sibling sharing the same private `offsettableReturnWhere` so "available" is defined once, and it pre-seeds every requested id to `0` so absent means no credit, not not-asked. See `docs/ARCHITECTURE-NOTES.md`.
- Merging `/pwa/pelunasan` into `/pwa/collections` because they overlap? Don't — the collection queue is an actionable work queue scoped strictly to `Receivable.collectorId`; the amplop is a read-only route package with a WIDER store set and documents the queue never shows. Two home CTAs listing the same receivable is the accepted cost, so their labels must keep saying different things. See `docs/ARCHITECTURE-NOTES.md`.
- Grepping for "settlement" in `apps/web`? TWO unrelated features answer to that word — `lib/finance/settlement/` + `/backoffice/finance/settlements` is the MARKETPLACE (Shopee/TikTok) module, while the store settlement document is `lib/finance/ar-settlement/` + `app/actions/store-settlements.ts` + `/pwa/pelunasan`. The names were kept apart deliberately and the marketplace module was left unrenamed; do not consolidate them or add to the wrong one.
- Calling the MARKETPLACE `matchSettlement` (`apps/web/lib/finance/settlement/match.ts`) from a cron, a hook, an upload step or any other path no operator is watching — or touching `postSettlementJournal` (`journal.ts`)? `matchSettlement` rewrites every line's `matchStatus`, `matchedSalesOrderId`, `cogsSnapshot` and `profit` from the `SalesOrder` rows and item `cogs` as they stand today, so it must never run against a `RECONCILED` settlement, and it now refuses one itself. It runs in one interactive transaction (its own, with a 120 s timeout and 10 s `maxWait`, or the caller's) whose FIRST statement is `lockSettlementRow` (`lock.ts`), a `SELECT status … FOR UPDATE` on the `Settlement` row; on `RECONCILED` it returns `{ matched: 0, unmatched: 0, profitPending: 0, refused: "RECONCILED" }` and writes nothing. `postSettlementJournal` takes the same lock as the first statement of its own transaction, with the same 120 s budget. A match and a journal post therefore serialise: a match never rewrites the lines of a settlement whose journal has posted, and a journal never posts mid-match. Three things keep that true. Decide on the status the lock returns, never on one read before it — a locking read sees the latest committed row, a plain read sees the transaction's snapshot. Take the lock before any other read in the transaction: a caller passing its own transaction client must not have read in it first (ER_CHECKREAD under `innodb_snapshot_isolation` on newer MariaDB). `postSettlementJournal` reads its totals before opening its transaction, on purpose; given a caller's transaction client, those reads run inside it ahead of the lock, so such a caller must not depend on that snapshot (no caller passes one today). And keep the lock on BOTH sides, `Settlement` first — dropping it from either reopens the window in which a journal posted mid-match leaves `RECONCILED` lines rewritten, and taking another lock ahead of it lets the pair deadlock on lock order. The lock also blocks every other `Settlement` writer (`startSettlementResync`'s update, the sweep's stamp CAS) for as long as a match runs; they wait, bounded by the server's `innodb_lock_wait_timeout` (50 s default, not overridden here), and so does a journal post (logged in `docs/FOLLOWUPS.md`). The final status write stays guarded — an `updateMany` on `status: { not: "RECONCILED" }` — as the backstop: never "simplify" it back to a plain `update`, which would reopen the settlement as "Matched" beside a journal nothing reverses. The journal's own lines are built from the settlement totals and the fee sums, never from `cogsSnapshot`/`profit`, so a line rewrite was always damage to the profit view, not to the GL. Every caller handles the refusal: `matchSettlementAction` returns `reason: "RECONCILED"` (the page toasts and refreshes), and the detail page hides Match, Fetch from Jubelio and "Rematch now" on a `RECONCILED` settlement. `runSettlementRematchSweep` (`apps/web/lib/finance/settlement/rematch-sweep.ts`) is the pattern to copy, and each of its steps is load-bearing: it re-reads the status with `findUnique` AFTER deciding the batch is finished and stamps-and-skips a `RECONCILED` row (a cheap pre-check — the lock is the guarantee); anything else is matched FIRST and stamped LAST with a CAS on `{ id, resyncBatchId, resyncRematchedAt: null }`, so a throw or a restart leaves it unstamped for the next tick and a replaced batch claims nothing; and a match the lock refused is stamped too and counted as `skippedReconciled` (skipping without the stamp would retry it every minute forever). Do not reintroduce claim-first plus an un-stamp on failure — that shape stranded a settlement stamped-but-unmatched whenever the process died between the two. The cron job runs with `noOverlap`; keep it. See `docs/ARCHITECTURE-NOTES.md`.
- Writing or reviewing `submitSettlement`? BOTH over-claim guards — the retur headroom AND `INVOICE_OVERCLAIMED` — must net every other `PENDING` claim with the TRANSACTION client inside `runSerializable`: the retur half nets OTHER `PENDING` settlements' draws on that retur, and the invoice half nets other `PENDING` settlements AND pending collection submissions through `sumPendingClaimsOnReceivable` (`apps/web/lib/finance/ar/pending-claims.ts`), the same helper `submitCollection` calls. A read taken before the transaction lets two salesmen collect the same money and refuses the loser only at approval, after it changed hands. Same shape as `submitCollection`'s guard, and the invoice half was missing from the design until review. See `docs/ARCHITECTURE-NOTES.md`. **The SCREEN must show the same netted headroom the writer enforces, not raw `outstandingAmount` or a bare `totalValue − appliedValue`** — a form that offers credit the writer will refuse fails at the counter with the store owner watching, which is the same defect one step earlier. Both figures now come netted from `page.tsx` — an invoice's headroom on screen is `outstanding − pending collections − pending settlement claims`, the writer's own bound — and the copy beside them has to name the real bound rather than "the outstanding balance".
- Building on the settlement APPROVAL writer? It carries THREE obligations from the derived-claim design, and two are already discharged by construction — do not undo them. Approval decrements `Receivable.outstandingAmount` only through `recordPayment`'s atomic decrement (an APPROVED settlement stops counting in the netting aggregate, so the claim becomes re-claimable the instant the status leaves `PENDING`), and the status flip is the LAST write, after every component, because flipping ahead of a retur draw overstates that retur's headroom by exactly the approved amount for the width of the window. The third is still LIVE and still yours: any edit or resubmit path added later must give BOTH claim aggregates an explicit `settlementId: { not: … }` or the document refuses itself against its own rows. See `docs/ARCHITECTURE-NOTES.md`.
- Touching the settlement `draftId`? It is the document's identity before the row exists — the R2 evidence key prefix AND the submit idempotency key — so it must be caller-stable (`useState(() => crypto.randomUUID())`, never `useMemo`) and UUID-shaped, or a retry both strands the uploaded evidence under a stale prefix and duplicates the document. A collision from a different salesman or store is `DRAFT_ID_CONFLICT`, never a handed-back replay. See `docs/ARCHITECTURE-NOTES.md`.
- Changing the settlement admin fee, or the settlement preview? The fee is charged on the NETTED base (`invoices − retur − program`), never the gross, and `lib/finance/ar-settlement/calc.ts` imports nothing from `@elorae/db` but `roundCents` (via the `@elorae/db/pricing` subpath, never the barrel) because the `"use client"` form imports it directly for the live preview — a screen that recomputes its own total recreates the preview-vs-writer mismatch `docs/landmines/field-sales.md` already names twice. See `docs/ARCHITECTURE-NOTES.md`.
- Gating anything settlement-shaped? TWO permissions, and they are not interchangeable. **Filing** — the PWA screen `/pwa/pelunasan/[storeId]`, `submitStoreSettlementAction`, the proof-upload route, and the amplop's Settle button that leads to them — runs on `settlements:submit` (SALESMAN + COLLECTOR + ADMIN-by-convention), NOT `collections:collect`; a control gated on anything but what the next screen enforces renders for a role that screen refuses. **Approving** — `/backoffice/finance/pelunasan` list and detail, `approveSettlementAction`, `rejectSettlementAction`, the nav entry — runs on `collections:manage`, reused deliberately rather than minting a `settlements:approve`, which is why this needed no new seed and is ADMIN-only. Both are seeded on prod as of 2026-09-06 (`packages/db/prisma/seed-settlements-permission.sql` for the first; `collections:manage` predates it), so neither is a live-prod trap any more — a fresh environment or test bed still has to seed the first by hand. **One deliberate exception, and it is a READ surface, not a control:** `/pwa/bkm/[settlementId]` admits EITHER permission, narrowing a `settlements:submit`-only holder to settlements whose `salesmanId` is their own — see the BKM entry below. See `docs/ARCHITECTURE-NOTES.md`.
- Turning the settlement approval queue on in a fresh environment, or on prod for the first time? No RBAC seed is needed (it reuses `collections:manage`), but the two posting roles `TRADE_PROGRAM_EXPENSE` and `ADMIN_FEE_EXPENSE` have NO `JournalAccountMapping` row and nothing on the deploy path creates one — the role column is a plain `String`, so there is no migration and no seed file to run; finance maps both to a `BEBAN` account in Settings → Account Mapping. Skip it and the first approval carrying an admin fee (essentially every settlement) has `resolveAccount` throw `UnmappedRoleError`, degrading that payment's journal to `JOURNAL_PENDING` and needing a hand-mapping plus a retry — the settlement's own approval screen names the unmapped role and links to the mapping page, so that is the fastest route back. AR and the payments are unaffected; only the GL leg waits. See `docs/EPIC-STATUS.md` and `docs/FOLLOWUPS.md`.
- Adding a `SettlementErrorCode`? Nothing breaks, on purpose — there is deliberately no exhaustive `Record` anywhere on this path, so an operator-fixable code with no `REASON_KEY` entry in `SettlementForm` and no `en.json`/`id.json` key just shows the salesman a generic failure. There are THREE surfaces to add it to now, not one: `REASON_KEY` on the salesman's form, `financeStoreSettlements.err.<CODE>` in BOTH locales for the finance queue (whose `errorMessage()` falls back to `err.UNEXPECTED` via `t.has`), and — if it is a check the queue previews — the `SettlementCheckReason` `Extract<>` union in `lib/finance/ar-settlement/checks.ts`. See `docs/ARCHITECTURE-NOTES.md`.
- Reading a `StoreSettlement` as money moved? Read its STATUS first — the two answers are opposite. A `PENDING` settlement posts no journal and touches no `Receivable`; its retur claims reserve against other settlements, and its invoice claims against other settlements and pending collection submissions. An `APPROVED` one has already posted one `Payment` per retur deduction row PLUS up to three more — trade-program, admin fee, cash — and decremented AR through each of them; `RETUR_OFFSET` is one of the four component KINDS, not a fourth singleton standing beside the draws. It has NOT necessarily had a `PAYMENT_RECEIPT` journal posted per payment, and TWO different failures look identical from the `Journal` table: a crash between the status flip and the action's loop leaves payments with no journal AND no `JOURNAL_PENDING` flag (so the payment detail page offers no retry either), while a REFUSED post leaves no journal but DOES write a flag, because `postArJournalSafely` degrades a failing builder rather than throwing. The approval screen detects the missing journal either way and offers a re-post, but the re-post only repairs the crash case — against a refusal it hits the same refusal and `alreadyFlagged` dedups the notification, so the screen names the flagged reason and role and links to Settings → Account Mapping instead of implying the button is the fix. Do not "simplify" the alert back to the crash-window reading: an unmapped posting role is the documented day-one state, not the rare one. A settlement stranded `PENDING` may ALSO have real payments behind it — approval is a resumable sequence, not a transaction, so a crash mid-run leaves committed components under a still-`PENDING` document. A pending `CollectionSubmission` and a pending settlement can both stand against one invoice, but together never for more than its balance: each writer now nets the other kind through `sumPendingClaimsOnReceivable`. See `docs/ARCHITECTURE-NOTES.md` and `docs/FOLLOWUPS.md`.
- Approving a settlement, or building any new caller of `approveSettlement`? It is a RESUMABLE SEQUENCE, not a transaction — `recordPayment` and `applyReturnOffset` self-transact, so nesting them is unsafe, and what makes a crash safe is that every component's idempotency key is deterministic (`settlement-<id>-<PAYMENT_METHOD>`, and `returoffset-<returnId>-<deductionRowId>` for a draw, which reproduces the key `applyReturnOffset` mints itself). The status flip is LAST and is a CAS `updateMany` on `status: "PENDING"`; the writer posts NO journals, so a caller must loop `postArJournalSafely` over EVERY id in `paymentIds`, never just the first. It throws TWO error classes with overlapping code strings — `SettlementError` and `recordPayment`'s `PaymentError` — so discriminate on `instanceof`, never on the code string. See `docs/ARCHITECTURE-NOTES.md`.
- Rejecting a settlement, or adding a path that retires a `PENDING` one? `rejectSettlement` refuses `COMPONENTS_POSTED` while any component payment is `POSTED`, read with the transaction client before any write; the remedy is resuming the approval or voiding each posted component, and a `VOIDED` component does not block. The keys it counts come from `simpleComponentKey`/`returComponentKey` (with `DEDUCTION_TYPE_TO_PAYMENT_METHOD` for the program and fee kinds), the builders `approveSettlement` writes with — a re-spelled key matches nothing and the guard silently never fires. Keep the refusal a THROW ahead of the status CAS: `runSerializable` commits on a normal return, so a refusal returned after the flip would commit the rejection while reporting a refusal. The approval screen disables Reject on the same condition, which is a mirror, not the enforcement. The guard closes the crashed or abandoned approval, and a running one once its first component has committed (the SERIALIZABLE count then sees a POSTED key). One window is open in `docs/FOLLOWUPS.md`: a reject that reads before the FIRST component commits — that insert waits on the reject's range lock, posts behind `REJECTED`, and the rest of the run follows. See `docs/ARCHITECTURE-NOTES.md`.
- Resuming a half-posted approval, or "optimising" its component loop? A retur component must RE-ENTER `applyReturnOffset` even when its payment already exists — that writer's replay branch is what re-runs `projectReturnOffset`, and skipping it leaves the retur drawn with `appliedValue` stale at 0 and `offsetStatus` still `AVAILABLE`, permanently, which then overstates that retur's headroom at SUBMIT time for every later settlement. It takes no process kill to reach: a P2034 after `withRetry` exhausts is enough. The skip is correct ONLY for the cash/program/fee components, because `recordPayment` projects nothing onto any other row. See `docs/ARCHITECTURE-NOTES.md`.
- Adding or tightening a re-validation in `approveSettlement`? Scope it to what THIS settlement still owes, or you make a resume impossible. Checking "every selected receivable is still open" literally — the obvious reading, and the one the design called for — refuses the retry the moment one of this document's own posted components has paid a receivable off: money moved, document `PENDING` forever, no path out but hand SQL. Collectibility is exempted on TWO terms — a receivable this settlement has already allocated against (`settlementAllocated > 0`) OR one whose agreed share is spent (`agreedRemaining <= 0`) — and `agreedRemaining` ALONE is not enough: when `StoreSettlementInvoice.amount` exceeds the live balance, one component closes the receivable with the agreed share still partly unspent and the resume throws `NOT_OUTSTANDING` forever. Never collapse the pair into "skip when the effective headroom is 0", which also skips a receivable some OTHER channel closed and re-diagnoses it as `COMPONENT_EXCEEDS_HEADROOM`. It must also run BEFORE the `totalOwed > totalHeadroom` comparison (a receivable closed elsewhere also leaves zero headroom, so the other order misdiagnoses it as an allocation shortfall); existence and store ownership stay unconditional. Both pre-flights count only components that have not already posted. See `docs/ARCHITECTURE-NOTES.md`.
- Mapping a `SettlementDeductionType` to a `PaymentMethod`? Use `DEDUCTION_TYPE_TO_PAYMENT_METHOD` in `approve-writer.ts`, never a cast — two of the three spellings coincide and `PROGRAM` → `PROGRAM_DEDUCTION` does not, so `deduction.type as PaymentMethod` compiles, passes review, and then dies at the MariaDB `ENUM` column mid-approval with earlier components already posted. See `docs/ARCHITECTURE-NOTES.md`.
- Hitting `OVER_TENDER`, or offering an override to clear it? You cannot — it is one-directional by design. A store handing over MORE than expected can never allocate (components sum past the invoices' headroom and there is no unapplied-credit concept), so the check runs AHEAD of the override gate on purpose and the remedy is reject-and-refile. Never widen the override path to cover it, and never let the copy suggest one. An under-tender is the opposite: legitimate, and exactly what the tolerance and the override reason are for. See `docs/ARCHITECTURE-NOTES.md`.
- Touching the settlement variance tolerance? The `SystemSetting` key is `settlement.varianceToleranceRupiah`, parsed by the import-free `lib/finance/ar-settlement/variance-tolerance.ts`, and its "fail-open" is STRICTER, not looser — the default is 0, so malformed config demands an override reason more often, never less. The `Number.isFinite` check after the regex is load-bearing (`"9".repeat(400)` matches `\d+` and would parse to `Infinity`, disabling the gate). It is edited on Settings → Piutang (`collections:manage`); nothing seeds it. See `docs/ARCHITECTURE-NOTES.md`.
- Writing an audit row for a settlement decision? It goes INSIDE the writer's own transaction, never in the action — the action-layer placement makes the gap UNRECOVERABLE, because an approve retry lands on the write-free `alreadyApproved` branch and a reject retry throws `NOT_PENDING` over an already-successful rejection. `SETTLEMENT_VARIANCE_OVERRIDE` is a separate third row written only when an override was needed, and it is the ONLY record of why a flagged settlement was approved — `StoreSettlement` has no `overrideReason` column, so any screen showing the reason must read that row. Cap every reason at 191: `AuditLog.reason` is a bare `String?`, i.e. `VARCHAR(191)`. See `docs/ARCHITECTURE-NOTES.md`.
- Rendering a settlement's expected or variance figure — on screen or on the PRINTED BKM? Derive it through `computeSettlementTotals`, never read `StoreSettlement.expectedAmount`/`varianceAmount` — the writer never reads or reconciles those stored columns, so a screen trusting them renders a document as balanced and then watches approval refuse it, and a RECEIPT trusting them is worse still because the store keeps the paper. Same rule for the checklist's arithmetic and idempotency keys: call `approve-writer.ts`'s FIVE shared exports rather than a second copy, and do not strip those `export`s in a tidy-up. `queries.ts` consumes `computeComponentHeadroom`, `returComponentKey`, `simpleComponentKey` and the type `InvoiceRow`; `reject-writer.ts` consumes the two key builders plus `DEDUCTION_TYPE_TO_PAYMENT_METHOD` to find a settlement's posted components. Its other two `export`s, `SettlementPaymentMethod` and `HeadroomRow`, are imported by NOTHING and are not a seam: `checks.ts` restates `HeadroomRow`'s shape structurally (`{ receivableId; agreedRemaining; settlementAllocated }`) to stay import-free of the writer, so nothing type-checks the two declarations against each other and a field renamed on one side leaves the other compiling against its own copy while the screen previews different arithmetic. Same fork shape as `EPSILON` below — change one, change the other in the same commit. `EPSILON` is NOT one of them and never was: it lives in `lib/finance/ar-settlement/calc.ts`, and all four consumers (both writers, `queries.ts`, `checks.ts`) import it from there. The way it forks is a tidy-up in `calc.ts` — moving it "closer to its user" or inlining `1e-6` at one call site — because nothing type-checks two separately declared constants against each other, and the symptom is a screen and a writer disagreeing about a sub-cent margin. `calc.test.ts` pins the value for exactly that reason. See `docs/ARCHITECTURE-NOTES.md`.
- Removing the Print BKM button from `/backoffice/finance/pelunasan/[id]` because the PWA route already prints one? Don't — that button is finance's ONLY path to a BKM. `pwaAccessGuard` redirects any wildcard holder to `/backoffice` before the permission check runs, so an ADMIN can never open `/pwa/bkm/[settlementId]` however it is seeded (same fact that makes an admin account useless for verifying the amplop seed). It renders on a REJECTED settlement too, deliberately: that BKM was still handed over at a counter. `getSettlementForPrint` is a lean sibling of `getSettlementForApproval`, not a reuse — the approval query's checklist block previews what `approveSettlement` would refuse and a receipt renders none of it. See `docs/ARCHITECTURE-NOTES.md`.
