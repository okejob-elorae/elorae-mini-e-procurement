# Production landmines

The full entries behind the **Production — BOM & variants** triggers in `AGENTS.md` § Landmine index, in the same order. Each one was written after someone paid for it. Read the entry for whatever surface you are about to touch before writing code; where an entry points on to `docs/ARCHITECTURE-NOTES.md` or `docs/FOLLOWUPS.md`, follow it. When a change makes an entry wrong, fix it in the same change.

- Reading a finished-good variant's colour or size? Use `resolveVariantAxes` / `canonicalAxisKey` from `@elorae/db/variant-axes` (also re-exported from `@elorae/db` for apps/api). Variants have exactly two axes stored under `Warna` and `Ukuran`; the Jubelio catalog ingest (`mapVariationValues`) and `pnpm variants:colors` fold `color`/`Colour`/`Size`/`size` onto them, but rows written before either ran, and other item types, can still carry the old spellings, so never read `v.size` or `v.color` directly — `load-candidates.ts` did, and every smart-request pack expansion on prod missed its size because prod variants say `Ukuran` (#437). A variant's colour text is never rewritten to the master's name: it resolves to a `VariantColor` by name or alias under `colorMatchKey` (case, spaces and punctuation ignored), so it keeps matching what Jubelio shows. A spelling belongs to one colour only — `saveVariantColor` refuses a name or alias another colour already answers to. → `docs/ARCHITECTURE-NOTES.md`
- Working out how much material a work order needs? Go through `generateMaterialPlan` (`apps/web/lib/production/planning.ts`) with the WO's `skuBreakdown`, never `rule.qtyRequired × plannedQty`. A `ConsumptionRule` scoped to a colour and/or size counts only the pieces of the variants it covers (`planMaterialQuantities`, `lib/production/scoped-bom.ts`), so a scoped BOM cannot be planned without a variant mix: a GENERIC WO on one is refused (`ScopedBomNeedsVariantsError`), and a variant whose colour or size does not resolve is refused rather than silently left out. Only production planning, which has no ratio, uses an even split (`fallbackToEqualSplit`). Anything that needs a WO's per-piece quantity afterwards — HPP (`calculateHPP`) and the additional-materials preview/issue — reads the WO's own `consumptionPlan` snapshot, whose `qtyRequired` is the average per piece over that WO's mix, not the current BOM. → `docs/ARCHITECTURE-NOTES.md`
- Writing `ConsumptionRule` rows? `(finishedGoodId, materialId)` is no longer unique: one material may carry one rule per scope (Black uses fabric X, Grey fabric Y; `LABEL SIZE S` on S only). Two rules of one material must never both match one variant — they would add up and issue the material twice — so every writer has to refuse overlapping scopes the way `saveConsumptionRules` does (`findOverlappingRules`). A lookup by `findUnique({ finishedGoodId_materialId })` no longer compiles; read the rules and plan them instead.
