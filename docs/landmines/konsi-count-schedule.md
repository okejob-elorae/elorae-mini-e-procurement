# Konsi count schedule landmines

The full entries behind the **Konsi count schedule** triggers in `AGENTS.md` § Landmine index, in the same order. Each one was written after someone paid for it. Read the entry for whatever surface you are about to touch before writing code; where an entry points on to `docs/ARCHITECTURE-NOTES.md`, `docs/EPIC-STATUS.md` or `docs/FOLLOWUPS.md`, follow it. When a change makes an entry wrong, fix it here in the same session — and update its trigger in `AGENTS.md` if the trigger itself moved.

- Computing whether a store has counted this month, or showing it anywhere? Go through `countStatusFor` (`apps/web/lib/konsi-count-schedule/schedule.ts`), fed by `getStoreCountState` — the store detail page, the SPG home and the daily sweep all do, and a reader that re-derives the rule will disagree with them. Every month boundary is WIB from a hardcoded +7h offset, never `getMonth()`, which reads the host timezone and is wrong on prod's UTC server. Each month owns a SLOT from its window's `openFrom` to the next month's `openFrom`, and the TARGET month is the one whose slot holds `now` — the current month once its window has opened, the previous month before that — so a missed month stays owed only until the next window opens, one hop and no further. The target is counted when the latest APPROVED `isFullCount` stocktake's count moment, `countFinishedAt ?? approvedAt` (`countMomentOf`), is at or after the target's `openFrom`: a September count finished on 2 October credits September and October still opens on time, a count finished BEFORE the target's window opened credits the previous slot on purpose — which is why the sweep never announces an open count whose `countFinishedAt` is already before the target's `openFrom` (the next entry) — and a partial count satisfies nothing. Never credit by `countedAt`: it is the instant the count was OPENED, and `createAction` takes it from the caller. A store owes the target only if `Store.createdAt`, which stands in for eligibility, is strictly before the target's `openFrom`; otherwise it is `NOT_YET` for the next window to open. The due day and lead days are two global `SystemSetting` rows (`konsi.countDueDay`, `konsi.countLeadDays`) that fail open to their defaults per field and that nothing seeds. See `docs/ARCHITECTURE-NOTES.md`.
- Calling `runKonsiCountSweep` from a spec? Pass `storeIds` — omitted, it sweeps every active KONSI store with a method on the shared `:3308` bed and opens real counts, while an EMPTY array sweeps nothing on purpose, so never collapse `[]` into `undefined` on the way in (the optional-array filter-arm entry in `docs/landmines/stock.md`). Inject `schedule` (and `now`) instead of writing the setting rows, which other specs and the dev data share. Its SPG push goes through the sweep's own `notifySpgsOfCount`, `VITEST`-guarded as its first statement, as defence in depth on top of the guard `sendNotificationToUsers` carries itself. The sweep opens a count at most ONCE per (store, target month), keyed on the `KONSI_COUNT_DUE` rows it has written, read in full with no `take` and no date floor: with that month's DUE row present it opens nothing even when no count is open, so a cancelled sweep-opened count, or a partial count approved for the month, is NOT reopened and an admin opens the next one by hand; with no DUE row and a count already open (a manual open, or the `ALREADY_OPEN` race) it announces that count instead of creating one — unless that count's `countFinishedAt` is set and before the target month's `openFrom`, in which case it credits the previous slot once approved, so the sweep neither announces it nor writes the DUE row, and the first sweep after it closes opens a fresh count (a null `countFinishedAt` is still announced). The DUE row is the marker, so it is written LAST, after the open and the SPG push — a failure before it re-announces the next morning instead of losing the alert. The cost is a duplicate push, or, when the count the sweep opened is cancelled before the next run, a second count for the same month, since no DUE row then stops the reopen, so the no-reopen rule holds only once the DUE row is written. See `docs/ARCHITECTURE-NOTES.md`.
- Adding a stocktake approve path, or touching `approveAction`? The auto-report (`autoCreateSellThroughAfterCount`, `apps/web/lib/konsi-count-schedule/auto-report.ts`) runs AFTER `approveStoreStocktake` commits, outside its transaction, and is best-effort: it never throws — its own try/catch plus a second around the call in `approveAction` — and a report problem must never fail or roll back the approval, so the action returns `{ ok: true }` whatever the report did. Never move the call into `approveStoreStocktake`, whose serializable transaction it would then run inside (`createSellThrough` opens its own), and make any NEW approve path call it after its own commit, or counts approved there silently stop producing reports. READY, HELD and BLOCKED are announced; SKIPPED and FAILED are not. SKIPPED also covers a report someone created by hand first (`ALREADY_USED`, or `DRAFT_EXISTS` while a live report closes the same count). BLOCKED's message is a short pointer — the stocktake's docNo, the refusal code, and a prompt to open the stocktake, whose page renders the reason — and never reuses the screen's reason copy. A FAILED outcome usually means no report exists and it is created by hand from the stocktake page as before, but a FAILED carrying a `sellThroughId` means the report WAS created and not announced; `approveAction` revalidates the report routes whenever an outcome carries one. `STALE` is not announced, by decision. See `docs/ARCHITECTURE-NOTES.md`.
- Adding a konsi count or report notification? The five categories live in `apps/web/lib/konsi-count-schedule/categories.ts`, and a new one needs BOTH an entry in `admin-fanout.ts`'s `CATEGORY_PERMISSION` (all five map to `stores:manage`; a missing entry reaches nobody, silently) AND a case in `getNotificationHref` (`lib/notifications/navigation.ts`; a missing case is a bell item that goes nowhere, through its `null` fallback). Keep its metadata values flat — `toFcmData` passes strings, numbers and booleans to the push payload and drops everything else. See `docs/ARCHITECTURE-NOTES.md`.
- Reading `StoreStocktake.createdById`? It may hold `system:konsi-count` (`KONSI_COUNT_SYSTEM_ACTOR`), the sweep's creator at a store with no assigned SPG or several, which is no user. The column is a bare scalar: never add a required `User` relation on it or resolve it with `findUniqueOrThrow`, and render a creator through `createdByIsSystem` (`getStoreStocktakeById`) — today only the stocktake detail page does, as "System". See `docs/ARCHITECTURE-NOTES.md`.
