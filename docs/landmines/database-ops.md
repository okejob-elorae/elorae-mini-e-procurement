# Database, migrations, prod ops landmines

The full entries behind the **Database, migrations, prod ops** triggers in `AGENTS.md` § Landmine index, in the same order. Each one was written after someone paid for it. Read the entry for whatever surface you are about to touch before writing code; where an entry points on to `docs/ARCHITECTURE-NOTES.md`, `docs/EPIC-STATUS.md` or `docs/FOLLOWUPS.md`, follow it. When a change makes an entry wrong, fix it here in the same session — and update its trigger in `AGENTS.md` if the trigger itself moved.

- Running a migration or any destructive query locally? It lands on the **3308 dev test bed**, not on the client's data — that is safe by default, and the danger is the inverse: an ambient `DATABASE_URL` pointed at the 3307 prod tunnel makes the same command destructive with no other signal. Check what `DATABASE_URL` resolves to before any write. Either way it is `pnpm -F @elorae/db migrate:deploy` only — never `migrate dev`, which needs a CREATE DATABASE grant the shadow DB does not have and dies with P3014.
- Shipping a migration alongside app code? The deploy `migrate` job is gated on both image builds, and its `always()` is load-bearing — a legitimately SKIPPED build must not cascade-skip the migration.
- Assuming a green deploy workflow means your code is running? Check the `Deploy api`/`Deploy web` jobs specifically, and the container's image tag. Both misbehaved on 2026-09-02 — one SKIPPED with every condition satisfied and no error, one failed on an SSH dial timeout — and a skipped deploy leaves prod on the previous image while the overall run still reads success. See `docs/FOLLOWUPS.md` § Ops / infra.
- Expecting the deploy to seed RBAC rows? It migrates but NEVER seeds — permission rows are hand-run surgical SQL, post-merge.
- Running `mariadb` / `mariadb-dump` against prod? Needs SSL off — but the FLAG depends on which client is installed, and getting it wrong looks like a connection failure rather than a flag error: MariaDB's client takes `--skip-ssl`, while the MySQL 8 client (`mysql` on this machine, `mysql Ver 8.0.46`) rejects that outright and wants `--ssl-mode=DISABLED`. Check `mysql --version` before assuming. The failure is SILENT inside a `| gzip` pipe (a valid 123-byte empty archive) — verify size plus the `Dump completed on` trailer. Aggregates over `SalesOrder` need `SET SESSION max_statement_time`.
- Writing migration SQL that puts `COLLATE utf8mb4_*` on a string literal? The prod `migrate` job does not go through Prisma: it pipes each `migration.sql` into `docker exec -i elorae-db mariadb …` (`.github/workflows/deploy.yml`), and that CLI connects with `character_set_connection = utf8mb3`. Every string literal without an introducer is therefore utf8mb3, and `LIKE 'TT-%' COLLATE utf8mb4_bin` is rejected at parse time with `ERROR 1253 (42000): COLLATION 'utf8mb4_bin' is not valid for CHARACTER SET 'utf8mb3'`. The job fails, `Deploy api`/`Deploy web` are skipped, and every later deploy fails on the same file until it is fixed. The CLI stops at the first error, so statements above the failing one have already run while the file is never recorded in `_prisma_migrations` — which is also why editing a file prod has not applied yet is the fix, and why a migration should be safe to re-run. Put the binary compare on the column instead (`WHERE BINARY col LIKE 'TT-%'`, independent of the connection charset), or give the literal an introducer (`_utf8mb4'TT-%' COLLATE utf8mb4_bin`). A local `pnpm -F @elorae/db migrate:deploy` will NOT reproduce it: it connects through the Prisma driver as utf8mb4, where the same statement is valid. CI's `db-specs` job (`.github/workflows/ci.yml`) does reproduce it: it applies every migration to a fresh database through the same `mariadb` client with `--skip-ssl`, so the PR goes red — but CI is not a required check, so read the run. Test such SQL through the client the deploy uses, against the 3308 bed — `docker exec -i elorae-dev-db sh -c 'mariadb -uroot -p"$MARIADB_ROOT_PASSWORD" --skip-ssl "$MARIADB_DATABASE"' < file.sql`, which reads the password from the container's own env instead of your shell, in a read-only `SELECT COUNT(*) … WHERE …` form if you do not want the writes applied. Caught in review on the prefix channel backfill (`20260927200000_backfill_marketplace_channel_from_prefix`) before it reached prod, and reproduced on the 3308 bed through the same client.
- Writing raw SQL in code apps/web can reach — directly or through a `@elorae/db` helper? Never interpolate a Prisma SQL fragment (`Prisma.sql`, `Prisma.join`, `Prisma.empty`, `Prisma.raw`) into a tagged `$queryRaw`/`$executeRaw`. The web build bundles the Prisma runtime into several server chunks that share one `globalThis` client, and the client resolves a nested fragment with `instanceof` against its own copy's `Sql` class: a fragment built by another copy is bound as a plain string, and the `WHERE` silently matches nothing, with no error. That is how every reconciliation Match refused `NO_INVENTORY_ROW` on prod until `lockMainInventoryValueRow` became two complete queries (PR #377). Keep interpolations scalar, or build the whole query with one module's `Prisma.sql` and pass it as a single argument — `lib/finance/sales/sweep.ts` does that, and it is safe because its fragments are resolved inside its own module. No test reproduces the failure: vitest, jest and apps/api each load one runtime. The same mismatch can defeat `instanceof Prisma.PrismaClientKnownRequestError` in web, `isRetryableTxError` behind `runSerializable` above all; the root fix — loading the runtime once — is logged in `docs/FOLLOWUPS.md` (Ops / infra). See `docs/ARCHITECTURE-NOTES.md`.
