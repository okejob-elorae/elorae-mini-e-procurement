# Data ownership + auth landmines

The full entries behind the **Data ownership + auth** triggers in `AGENTS.md` § Landmine index, in the same order. Each one was written after someone paid for it. Read the entry for whatever surface you are about to touch before writing code; where an entry points on to `docs/ARCHITECTURE-NOTES.md`, `docs/EPIC-STATUS.md` or `docs/FOLLOWUPS.md`, follow it. When a change makes an entry wrong, fix it here in the same session — and update its trigger in `AGENTS.md` if the trigger itself moved.

- Writing `Item` or `StockAdjustment` from apps/api? Both are dual-owner — go through the `@elorae/db` writer helpers, never a direct Prisma write. See also `docs/BOUNDARY.md §3`.
- Adding a relation under `relationMode = "prisma"`? Do NOT conclude from the mode that there is no database FK. The mode suppresses the FKs Prisma GENERATES; it does not stop this repo hand-authoring `ALTER TABLE … ADD CONSTRAINT` in a migration, which it does routinely. Only grepping the migrations for that specific table settles it, and skipping that grep produced two separate wrong statements about one table in a single day. `Item` alone is the child end of SEVEN live hand-authored FKs carrying THREE different delete behaviours, so an item delete is refused outright by two tables, SILENTLY CASCADE-DELETES rows for two, and erases the link on three — enumerated, together with which of them `deleteItem` counts and which it does not, in `docs/FOLLOWUPS.md`. Whatever the grep says: if the Prisma relation is REQUIRED, verify the id exists inside the writer's transaction — a dangling id throws `Inconsistent query result` forever with no UI repair path — and make every `delete<Parent>` count the new child, because that count is what turns the failure into an operator-readable refusal instead of a raw FK error, a silent cascade or a dangling row. Adding a real FK to an EXISTING relation has two further costs. The migration fails on any row already dangling, so it needs a self-aborting pre-flight before its DDL and a read-only orphan check against prod before the deploy that carries it — `20261021100000_field_sales_foreign_keys` and `scripts/audit-field-sales-orphans.sql` are the worked pair. And it changes what a spec may write: Prisma never checks that a parent exists on insert, so a fixture that wrote a made-up id into the column passed before and now dies with ERROR 1452. Every relation `FieldSalesOrder` and `FieldSalesOrderLine` hold as the child (their own id columns) carries a real FK since that migration, the four relation-less actor columns (`approvedById`, `rejectedById`, `closedById`, `creditOverrideById`) included, so deleting a `User` they name now fails instead of silently orphaning the attribution, and a teardown deletes the orders before any user they name. The relations pointing AT those tables are not covered: `DeliveryShipment.orderId` and `KonsiTransfer.orderId` are still FK-less.
- Adding a permission and assuming ADMIN is gated by it? The admin wildcard is granted in CODE (`isSystem` → `['*']`), not by a DB row — a seed does not unblock admin, it makes the permission grantable to NON-admin roles.
- Adding an approval or a manager decision (approve, reject, lock, decide who bears a loss, mark pay as paid), or gating one? Give it its OWN permission code and flag it `persetujuan: true` in `ISIAN` (`apps/web/lib/rbac/penjelasan-izin.ts`; listed by `IZIN_PERSETUJUAN`); never ride it on a broad `:manage` code. The owner's rule (2026-10-29, decision 8 of 2026-11-01) is that a manager decision is admin-only by default and grantable to other roles in Settings → Peran & izin, so it must exist as its own code to be grantable at all. Before the split, approving a store count rode on `stores:manage`, an SPG transfer on `field_sales_orders:approve`, locking konsi figures on `consignment:manage` and verifying a BKM on `journals:manage`, so giving someone the everyday job handed them the decision too. Today's split: verifying a BKM, a giro, a collector deposit or a store settlement = `payments:verify` (`bolehMemverifikasi`; NOT flagged `persetujuan` — the one check the owner also gave finance, and KEUANGAN holds it); who bears a return shortfall or lost goods, including cancelling an already-decided loss = `receivables:decide_bearer` (`bolehMemutuskanBeban`); approving, rejecting, redirecting or cancelling someone else's store transfer, and the Settings → SPG transfer rules = `store_transfers:approve`, its shortfall = `store_transfers:decide_shortfall`; approving a store count, and cancelling one awaiting approval = `store_stocktakes:approve`; locking/unlocking konsi figures, and approving or voiding a konsi sell-through report = `consignment:lock`; marking SPG pay paid (konsi or putus, which also applies that SPG's commission corrections) = `spg_commission:pay`; approving or rejecting an SPG shopper-return report = `spg_returns:approve` (owner 2026-11-02; the list opens with `spg_sales:view`, the decision and the Beranda row need the approval code, and nobody decides a report they made, `PELAPOR_SAMA`); confirming, reverting or cancelling the request of a Jubelio price = `jubelio_prices:confirm` (owner 2026-11-02; admin-only by default; `/backoffice/jubelio/harga` opens with the same code, so it sits in `ROUTE_PERMISSIONS`). The konsi note and tax numbers got their own codes too (`consignment:note_number`, `consignment:tax_number`), but those are office work held by ADMIN_PENJUALAN / ADMIN_PAJAK, not approvals. Nobody verifies a payment they reported, recorded or handed in, admin included (`PEMERIKSA_SAMA`, `SELF_VERIFICATION`). What comes with a new approval code: (1) the three office roles (KEUANGAN, ADMIN_PENJUALAN, ADMIN_PAJAK) hold none by default EXCEPT the owner's list in `PERSETUJUAN_BAWAAN_PERAN_KANTOR` (`apps/web/lib/rbac/penjelasan-izin.ts`; today ADMIN_PENJUALAN → `spg_returns:approve`, owner 2026-11-02) — `apps/web/lib/rbac/peran-kantor.test.ts` requires each role's approvals in `seed.ts` and `seed-office-roles-permissions.sql` to equal that list exactly, so adding to it is an owner decision, never a convenience; (2) it needs a `Permission` row in `seed.ts` AND a hand-run SQL file for prod (prod is seeded by hand, and a code without a row cannot be granted — until it exists on a database, `getUsersWithPermission` resolves only system admins). A NEW code goes in its own run-once-safe file with NOT EXISTS-guarded inserts and a Postgres twin — `seed-owner-2026-11-02-permissions.sql` holds `spg_returns:approve` and `jubelio_prices:confirm` — never appended to `seed-max-features-permissions.sql`, which is run once: re-running it re-grants derived links the owner may have removed in Peran & izin. Also `izinPeran.izin.<code>` label and keterangan in both locales, and a `butuh` naming the view code that opens its page; (3) FOUR surfaces name the SAME code — the button, the server action, `CATEGORY_PERMISSION` in `lib/notifications/admin-fanout.ts` (else the bell tells people who then get FORBIDDEN) and the Beranda row (`lib/dashboard/antrean-kantor.ts`, `action-items.ts`) — and a cancel that discards someone else's submission is the reject half of the approval and takes the approval code; (4) when the right code depends on the document's state (an open vs a decided loss, a draft vs a submitted count), the action's pre-read only picks the readable refusal: pass the caller's flags into the writer and re-check them against the status it reads inside its `runSerializable` callback (`batalkanBarangHilang` → `TANPA_IZIN`, `cancelStoreStocktake` → `FORBIDDEN`), or a decision landing in between slips through on the broad code; (5) a page opened by two codes cannot sit in `ROUTE_PERMISSIONS`, which holds one code per route and is enforced by `proxy.ts` before the page runs — leave it unmapped and gate the page itself, and the menu entry lists the same codes as the page gate (`apps/web/app/backoffice/menu-*.spec.ts`). Seed order on prod: `seed-max-features-permissions.sql` (once), then `seed-owner-2026-11-02-permissions.sql`, then `seed-office-roles-permissions.sql`, which preflights every code it links and aborts with ERROR 1242 before writing anything if one is missing (`AGENTS.md` § Max's features).
- Calling apps/api from apps/web with `apiFetch`, or adding an api route web will call? Put every input in the PATH (or a POST body), never a query string. `apiFetch` (`apps/web/lib/internal-api.ts`) signs the full path it requests, query included, while `InternalSignGuard` (`apps/api/src/auth/internal-sign.guard.ts`) recomputes the signature from `req.path`, which Express strips of the query — so a query string 401s every time, however correct the rest of the call is. It shipped once: the manual reconciliation resolve fetched `/jubelio/inventory/snapshot?jubelioItemGroupIds=N` and could never succeed; it now calls `/jubelio/inventory/snapshot/group/:groupId`. `apiFetch` now throws on any path containing `?`, so the mistake is loud; do not "fix" that throw by stripping the query or by signing `req.originalUrl` on one side only — both sides must sign the same string.
- Building an R2 object key from anything a request carried? Every key with a caller-supplied fragment is built by `buildR2Key` (`apps/web/lib/r2-key.ts`): closed prefix union, `[A-Za-z0-9_-]{1,64}` per segment, `[a-z0-9]{2,5}` extension, `InvalidR2KeyError` on anything else. The route rejects a bad fragment with a 400 via `isSafeR2KeySegment` BEFORE doing work; the throw is the backstop. A hand-templated `` `prefix/${formValue}/…` `` lets `../`, `/` or an unbounded value escape its prefix or land on another record's objects — six routes did exactly that until the builder existed (`item-image` and `settlement-proof` already validated their fragments; all of them build through it now). The segment rule is a FLOOR, not a replacement for a stricter route check: `settlement-proof` keeps `DRAFT_ID_PATTERN` because a guessable `draftId` would let a caller overwrite another salesman's evidence, and that route's own comment says so. What must never happen is tightening an id minted by `newLocalId()` (the offline queues) to UUID-only — its `local-<ts>-<base36>` fallback is not a UUID, so the check would refuse a legitimately queued upload and strand its evidence. Checking a key someone ELSE built (a stored URL, a caller-supplied key) is the same problem from the other side: use `isR2KeyInFolder` for the exact `<folder>/<file>.<ext>` shape, never `startsWith` plus a literal `..` test — `%2e%2e` and `\` survive that as raw text and a URL parser resolves them to another object. Item images are the case that bit: `replaceItemImagesAction` accepted any URL on our R2 host, so an `items:manage` holder could adopt a delivery or settlement proof as a product image (pushing it to Jubelio) and then delete it; it now accepts only `items/<itemId>/…` or `items/_pending/…` in the exact shape, and cleanup never deletes outside a single `items/<id>/` folder. Shape is not authorization — a route that writes under a record's prefix still has to check the record exists and that the caller may act on it (the POD proof route does; see `docs/landmines/delivery-shipments.md`). See `docs/ARCHITECTURE-NOTES.md`.
- Gating a function inside a `lib/` module? Never value-import `@/lib/auth` there (an `import type` is erased and harmless). next-auth 5 beta cannot load under vitest: it imports `next/server` without a file extension, vitest leaves `node_modules` to Node's own ESM resolver, and that resolver refuses the bare path with `ERR_MODULE_NOT_FOUND`. That is why every spec that exercises a gate mocks `@/lib/auth` — and it is exactly what hides the failure: the spec written for the new gate mocks auth and stays green, while every DB-backed spec that reaches the module directly or through an import chain, and so has no reason to mock auth, dies at import before a single test runs. Production is unaffected, because Next bundles next-auth, so nothing but the test run shows it. It shipped once: an `inventory:view` gate added inside `lib/inventory/costing.ts`, which sits on the stock movers' import chain, broke 18 DB-backed specs across canvassing, delivery, field sales, konsi sell-through, konsi count schedule and inventory. Put the gate in the `app/actions/*` `"use server"` wrapper instead, with the query either in the action itself or in a plain `lib/` function the action calls — `getInventorySnapshot` and `getInventoryValue` in `app/actions/inventory.ts` are the worked example. Keep `lib/` modules free of `'use server'` for the companion reason: the directive makes every export a network-callable endpoint, so a `lib/` module carrying it must either gate every export — which needs the import this entry forbids — or expose its helpers ungated, as `costing.ts` exposed its stock-moving helpers until it dropped the directive. The `lib/` modules that still carry `'use server'` (`lib/items/images/mutations.ts`, which also value-imports auth, and `lib/production/consumption.ts`, `planning.ts` and `reconciliation.ts`) predate this entry; they are not precedent, so do not copy their shape. Before adding any import to a `lib/` module, check whether a `*.test.ts` or `*.spec.ts` reaches it without `vi.mock("@/lib/auth")` — if one does, an auth import there breaks it. See `docs/ARCHITECTURE-NOTES.md`.
- Passing `timeoutMs` to `apiFetch`, or giving it a default? The timeout is opt-in on purpose. With none, a call is bounded only by undici's roughly 300 s headers and body defaults. Two awaited callers do long synchronous work behind that: the catalog sync (`POST /jubelio/catalog/sync`) writes for as long as the catalog takes, and the reconciliation snapshot (`GET /jubelio/inventory/snapshot`) pages every item group from Jubelio, with 429 backoff, before it answers. Neither duration is measured. A short timeout does not stop the api: a timed-out catalog sync reports failure while it keeps writing, so a retry runs a second copy alongside the first, and a timed-out snapshot fails the reconciliation run. Set `timeoutMs` only on a call whose endpoint does bounded work (the settlement resync seed passes 15 s). A timeout resolves `{ ok: false, status: 504 }` rather than throwing. Never pass `Infinity`: `AbortSignal.timeout(Infinity)` throws.
- Writing a `"use server"` export that takes the acting user's id as a parameter (`userId` and its kin)? Every `"use server"` export is independently callable with any arguments, so that id is caller-supplied until proven otherwise. Call `assertActor(session.user.id, userId)` (`apps/web/lib/auth/assert-actor.ts`) right after the permission check and before the id is used for anything; it throws `ActorMismatchError` on a mismatch or an empty id. Every UI caller passing `session.user.id` is not the guarantee — that was already true before the assertion existed, and it protected nothing. Without it the id is stamped onto the document row AND onto `StockLedgerEntry.createdById`, since each writer passes its own actor parameter through, so a crafted call puts someone else's name on a real stock movement. A role check has the same rule from the other side: run it on the SESSION user, never on a user row looked up by a caller-supplied id. `approveGRNByOwner`/`declineGRNByOwner` checked `ADMIN` on `prisma.user.findUnique({ where: { id: userId } })` before the assertion went in, so any `inventory:manage` holder who passed an admin's id passed the owner gate; the lookup is safe now only because `assertActor` runs first and pins `userId` to the session. An export with no session check at all is the same hole one step further: `processReturn`/`completeReturn` in `vendor-returns.ts` had none, and now require `vendor_returns:manage`. The exports in `grn.ts`, `production.ts`, `vendor-returns.ts` and `purchase-orders.ts` that use an actor id all assert it now; one that derives its actor from the session itself (`createStockAdjustment`'s `effectiveUserId`, the supplier approve/reject actions) needs no assertion, and that is the better shape for a new action. A self-service action, one that acts on the caller's own account (setting or verifying a PIN, reading PIN history, changing a password), takes the id from the session and never as a parameter: a parameter that must equal the session id can only be misused. `pin-auth.ts` and `change-password.ts` once took one and read no session at all, so a crafted call could spend another user's PIN attempts and lock their PIN, or read their PIN history; their exports now take no user id; with no session `setupPin` and `changePassword` return `security.unauthorized` and the PIN-history reads return an empty list. `adminForcePinReset(targetUserId)` keeps its parameter because it is ADMIN-gated and the id names the target, not the actor. A PIN check that gates a write runs inside the SAME action as the write, never as a separate call from the browser. Supplier delete once verified the PIN with a separate PIN-check action (since removed) and then called `deleteSupplierAction(id)`, which a direct call reached with no PIN at all; the PIN is now an argument of `deleteSupplierAction` and is checked there before anything is deleted, and the PIN-free `DELETE /api/suppliers/[id]` that reached the same writer was removed. Server code verifies a PIN through `verifyPin(userId, pin, action, opts)` in `apps/web/lib/security/pin.ts`, passing the session id: a plain module with no `"use server"`, so it is not itself a callable action, and like every `lib/` gate it must not value-import `@/lib/auth` (entry above). It is the only PIN check, `setupPin`'s current-PIN check included: an unthrottled boolean `verifyPin` in `lib/auth.ts` once sat beside it and guarded `POST /api/suppliers/[id]`, with no attempt window and no lockout, and was removed — never add a PIN compare outside this module. A server-side caller holding its own session (`planning.ts` calling `createWorkOrder`) passes `session.user.id` and passes the assertion, but a SYSTEM actor (a cron, a `system:` id) can never pass it and needs a writer path that is not an asserting action. Other exports still take an unchecked actor id — they are open in `docs/FOLLOWUPS.md`, so check there before assuming a sibling is covered. See `docs/ARCHITECTURE-NOTES.md`.
- Reading `session.user.role` or the `User.role` column, gating on "is admin", picking the acting user for an unattended job, or writing `User.roleId`? `User.role` (ADMIN / PURCHASER / WAREHOUSE / PRODUCTION / USER) is a LEGACY MIRROR of the role definition, never chosen by anyone. It is written only by Settings → Pengguna (`simpanPenggunaAction`, `apps/web/app/actions/settings/users.ts`) and `assignUserRole` (`apps/web/app/actions/rbac.ts`), both through `peranLamaDari` (`apps/web/lib/users/peran-lama.ts`: a system role → ADMIN; a role named exactly PURCHASER/WAREHOUSE/PRODUCTION → that name; anything else and no role → USER), in the same transaction as `roleId`, with `legacyRole` in the `USER_UPDATED` audit row when it changes. Any NEW writer of `User.roleId` must write `role` the same way, or the column drifts again. Before 2026-11-01 Pengguna did not write it, so admins promoted there stayed USER in the column and demoted ones stayed ADMIN; the data-only migration `20261102130000_residual_fixes` (Postgres `52_perbaikan_sisa`) heals that drift once. The SESSION value is not the column: the `session` callback in `apps/web/lib/auth.ts` derives `session.user.role` from the role definition (`peranLamaSesi`: `*` in `permissions` → ADMIN), while `token.role` deliberately keeps the column value so the `jwt` probe can compare it with the database. Never gate on the column. For "is admin", new code uses `(session.user.permissions ?? []).includes("*")`, the house convention (`session.user.role === "ADMIN"` is equivalent today only because it is derived from that wildcard). An unattended job (cron, script) that needs an actor takes `adminSistemTertua` (`apps/web/lib/users/admin-sistem.ts`: the oldest user whose `RoleDefinition.isSystem` is true, ordered `createdAt` then `id`), never `findFirst({ where: { role: "ADMIN" } })`. The journal sweep, recurring journals, asset depreciation, the sales-journal sweep fallback and the UMKM opening-stock script all did that, and with a stale column they posted under a demoted ex-admin or, when no account read ADMIN in the column, posted nothing and said nothing (`TANPA_PENGGUNA`, `null`, a skipped order).
- Using a permission code, an `AdminNotification` category or a phone notice kind added by the 2026-11-02 round-4 answers? The Izin package's registry is the only spelling: `lib/rbac.ts` + `packages/db/prisma/seed-owner-2026-11-02b-permissions.sql` (and its postgres copy) — `deliveries:cancel_nota` (not `deliveries:cancel`), `spg_attendance:record`/`spg_attendance:verify` (not `spg_schedules:enter_checkin`/`verify_checkin`), `store_returns:decide_shortfall`, `receivables:overdue_reminder`, `vendor_bills:decide_price`, `goods_receipts:confirm_no_po`, `spg_schedules:approve`, `spg_commission:manage`; `stock_losses:decide_bearer` does not exist. No per-feature seed file. Prod order: after `seed-owner-2026-11-02-permissions.sql`, after the web image carrying the codes is live, and BEFORE `seed-office-roles-permissions.sql`, which preflights its codes and aborts with ERROR 1242 if one is missing. `PERSETUJUAN_BAWAAN_PERAN_KANTOR` now also gives KEUANGAN `spg_commission:pay` (Q9/P28), linked ONCE — by `seed-owner-2026-11-02b-permissions.sql` when KEUANGAN already exists at the run that creates `spg_schedules:approve`, otherwise by `seed-office-roles-permissions.sql` on the run that creates KEUANGAN; re-running either file never restores a removed link. The office-roles seed writes each role's default links ONLY on the run that creates that role (owner decision 2026-11-01 (8)), so a new default code for an EXISTING office role must be linked in the dated seed that creates the code, never only added to the office-roles lists. Its preflight checks 29 codes.
- Linking a bell, a Beranda row or a button to a page? It must lead only to a page its permission's DEFAULT holders can open. KEUANGAN opens only Komisi SPG among the SPG pages (P28 "Keuangan hanya halaman Komisi SPG"): the three nota bells (`DELIVERY_NOTA_VOIDED`, `DELIVERY_NOTA_CORRECTED`, `TAX_INVOICE_NOTA_CHANGED`) open `/backoffice/finance/faktur-pajak?q=<docNo>`, never the order page; Komisi SPG and Catatan check-in toko guard themselves with functions (`bolehMembukaKomisiSpg` + the `payments:verify` #utang view, `bolehMembukaCatatanHadir`) and are not in `ROUTE_PERMISSIONS`, so the menu child lists the same codes; the Beranda carrier-claim row uses the barang-hilang page guard. `peran-kantor.test.ts` pins this.
