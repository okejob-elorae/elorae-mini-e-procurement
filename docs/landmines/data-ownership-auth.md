# Data ownership + auth landmines

The full entries behind the **Data ownership + auth** triggers in `AGENTS.md` § Landmine index, in the same order. Each one was written after someone paid for it. Read the entry for whatever surface you are about to touch before writing code; where an entry points on to `docs/ARCHITECTURE-NOTES.md`, `docs/EPIC-STATUS.md` or `docs/FOLLOWUPS.md`, follow it. When a change makes an entry wrong, fix it here in the same session — and update its trigger in `AGENTS.md` if the trigger itself moved.

- Writing `Item` or `StockAdjustment` from apps/api? Both are dual-owner — go through the `@elorae/db` writer helpers, never a direct Prisma write. See also `docs/BOUNDARY.md §3`.
- Adding a relation under `relationMode = "prisma"`? Do NOT conclude from the mode that there is no database FK. The mode suppresses the FKs Prisma GENERATES; it does not stop this repo hand-authoring `ALTER TABLE … ADD CONSTRAINT` in a migration, which it does routinely. Only grepping the migrations for that specific table settles it, and skipping that grep produced two separate wrong statements about one table in a single day. `Item` alone is the child end of SIX live hand-authored FKs carrying THREE different delete behaviours, so an item delete is refused outright by one table, SILENTLY CASCADE-DELETES rows for two, and erases the link on three — enumerated, together with which of them `deleteItem` counts and which it does not, in `docs/FOLLOWUPS.md`. Whatever the grep says: if the Prisma relation is REQUIRED, verify the id exists inside the writer's transaction — a dangling id throws `Inconsistent query result` forever with no UI repair path — and make every `delete<Parent>` count the new child, because that count is what turns the failure into an operator-readable refusal instead of a raw FK error, a silent cascade or a dangling row.
- Adding a permission and assuming ADMIN is gated by it? The admin wildcard is granted in CODE (`isSystem` → `['*']`), not by a DB row — a seed does not unblock admin, it makes the permission grantable to NON-admin roles.
- Calling apps/api from apps/web with `apiFetch`, or adding an api route web will call? Put every input in the PATH (or a POST body), never a query string. `apiFetch` (`apps/web/lib/internal-api.ts`) signs the full path it requests, query included, while `InternalSignGuard` (`apps/api/src/auth/internal-sign.guard.ts`) recomputes the signature from `req.path`, which Express strips of the query — so a query string 401s every time, however correct the rest of the call is. It shipped once: the manual reconciliation resolve fetched `/jubelio/inventory/snapshot?jubelioItemGroupIds=N` and could never succeed; it now calls `/jubelio/inventory/snapshot/group/:groupId`. `apiFetch` now throws on any path containing `?`, so the mistake is loud; do not "fix" that throw by stripping the query or by signing `req.originalUrl` on one side only — both sides must sign the same string.
- Building an R2 object key from anything a request carried? Every key with a caller-supplied fragment is built by `buildR2Key` (`apps/web/lib/r2-key.ts`): closed prefix union, `[A-Za-z0-9_-]{1,64}` per segment, `[a-z0-9]{2,5}` extension, `InvalidR2KeyError` on anything else. The route rejects a bad fragment with a 400 via `isSafeR2KeySegment` BEFORE doing work; the throw is the backstop. A hand-templated `` `prefix/${formValue}/…` `` lets `../`, `/` or an unbounded value escape its prefix or land on another record's objects — six routes did exactly that until the builder existed (`item-image` and `settlement-proof` already validated their fragments; all of them build through it now). The segment rule is a FLOOR, not a replacement for a stricter route check: `settlement-proof` keeps `DRAFT_ID_PATTERN` because a guessable `draftId` would let a caller overwrite another salesman's evidence, and that route's own comment says so. What must never happen is tightening an id minted by `newLocalId()` (the offline queues) to UUID-only — its `local-<ts>-<base36>` fallback is not a UUID, so the check would refuse a legitimately queued upload and strand its evidence. Checking a key someone ELSE built (a stored URL, a caller-supplied key) is the same problem from the other side: use `isR2KeyInFolder` for the exact `<folder>/<file>.<ext>` shape, never `startsWith` plus a literal `..` test — `%2e%2e` and `\` survive that as raw text and a URL parser resolves them to another object. Item images are the case that bit: `replaceItemImagesAction` accepted any URL on our R2 host, so an `items:manage` holder could adopt a delivery or settlement proof as a product image (pushing it to Jubelio) and then delete it; it now accepts only `items/<itemId>/…` or `items/_pending/…` in the exact shape, and cleanup never deletes outside a single `items/<id>/` folder. Shape is not authorization — a route that writes under a record's prefix still has to check the record exists and that the caller may act on it (the POD proof route does; see `docs/landmines/delivery-shipments.md`). See `docs/ARCHITECTURE-NOTES.md`.
- Gating a function inside a `lib/` module? Never value-import `@/lib/auth` there (an `import type` is erased and harmless). next-auth 5 beta cannot load under vitest: it imports `next/server` without a file extension, vitest leaves `node_modules` to Node's own ESM resolver, and that resolver refuses the bare path with `ERR_MODULE_NOT_FOUND`. That is why every spec that exercises a gate mocks `@/lib/auth` — and it is exactly what hides the failure: the spec written for the new gate mocks auth and stays green, while every DB-backed spec that reaches the module directly or through an import chain, and so has no reason to mock auth, dies at import before a single test runs. Production is unaffected, because Next bundles next-auth, so nothing but the test run shows it. It shipped once: an `inventory:view` gate added inside `lib/inventory/costing.ts`, which sits on the stock movers' import chain, broke 18 DB-backed specs across canvassing, delivery, field sales, konsi sell-through, konsi count schedule and inventory. Put the gate in the `app/actions/*` `"use server"` wrapper instead, with the query either in the action itself or in a plain `lib/` function the action calls — `getInventorySnapshot` and `getInventoryValue` in `app/actions/inventory.ts` are the worked example. Keep `lib/` modules free of `'use server'` for the companion reason: the directive makes every export a network-callable endpoint, so a `lib/` module carrying it must either gate every export — which needs the import this entry forbids — or expose its helpers ungated, as `costing.ts` exposed its stock-moving helpers until it dropped the directive. The `lib/` modules that still carry `'use server'` (`lib/items/images/mutations.ts`, which also value-imports auth, and `lib/production/consumption.ts`, `planning.ts` and `reconciliation.ts`) predate this entry; they are not precedent, so do not copy their shape. Before adding any import to a `lib/` module, check whether a `*.test.ts` or `*.spec.ts` reaches it without `vi.mock("@/lib/auth")` — if one does, an auth import there breaks it. See `docs/ARCHITECTURE-NOTES.md`.
- Passing `timeoutMs` to `apiFetch`, or giving it a default? The timeout is opt-in on purpose. With none, a call is bounded only by undici's roughly 300 s headers and body defaults. Two awaited callers do long synchronous work behind that: the catalog sync (`POST /jubelio/catalog/sync`) writes for as long as the catalog takes, and the reconciliation snapshot (`GET /jubelio/inventory/snapshot`) pages every item group from Jubelio, with 429 backoff, before it answers. Neither duration is measured. A short timeout does not stop the api: a timed-out catalog sync reports failure while it keeps writing, so a retry runs a second copy alongside the first, and a timed-out snapshot fails the reconciliation run. Set `timeoutMs` only on a call whose endpoint does bounded work (the settlement resync seed passes 15 s). A timeout resolves `{ ok: false, status: 504 }` rather than throwing. Never pass `Infinity`: `AbortSignal.timeout(Infinity)` throws.
- Writing a `"use server"` export that takes the acting user's id as a parameter (`userId` and its kin)? Every `"use server"` export is independently callable with any arguments, so that id is caller-supplied until proven otherwise. Call `assertActor(session.user.id, userId)` (`apps/web/lib/auth/assert-actor.ts`) right after the permission check and before the id is used for anything; it throws `ActorMismatchError` on a mismatch or an empty id. Every UI caller passing `session.user.id` is not the guarantee — that was already true before the assertion existed, and it protected nothing. Without it the id is stamped onto the document row AND onto `StockLedgerEntry.createdById`, since each writer passes its own actor parameter through, so a crafted call puts someone else's name on a real stock movement. A role check has the same rule from the other side: run it on the SESSION user, never on a user row looked up by a caller-supplied id. `approveGRNByOwner`/`declineGRNByOwner` checked `ADMIN` on `prisma.user.findUnique({ where: { id: userId } })` before the assertion went in, so any `inventory:manage` holder who passed an admin's id passed the owner gate; the lookup is safe now only because `assertActor` runs first and pins `userId` to the session. An export with no session check at all is the same hole one step further: `processReturn`/`completeReturn` in `vendor-returns.ts` had none, and now require `vendor_returns:manage`. The exports in `grn.ts`, `production.ts` and `vendor-returns.ts` that use an actor id all assert it now; one that derives its actor from the session itself (`createStockAdjustment`'s `effectiveUserId`, the supplier approve/reject actions) needs no assertion, and that is the better shape for a new action. A server-side caller holding its own session (`planning.ts` calling `createWorkOrder`) passes `session.user.id` and passes the assertion, but a SYSTEM actor (a cron, a `system:` id) can never pass it and needs a writer path that is not an asserting action. Other exports still take an unchecked actor id — they are open in `docs/FOLLOWUPS.md`, so check there before assuming a sibling is covered. See `docs/ARCHITECTURE-NOTES.md`.
