# Delivery shipments landmines

The full entries behind the **Delivery shipments** triggers in `AGENTS.md` § Landmine index, in the same order. Each one was written after someone paid for it. Read the entry for whatever surface you are about to touch before writing code; where an entry points on to `docs/ARCHITECTURE-NOTES.md`, `docs/EPIC-STATUS.md` or `docs/FOLLOWUPS.md`, follow it. When a change makes an entry wrong, fix it here in the same session — and update its trigger in `AGENTS.md` if the trigger itself moved.

- Touching anything called a "delivery"? TWO tables mean it — `DeliveryShipment` is the logistics event (`PACKED → IN_TRANSIT → DELIVERED`), `FieldSalesDelivery` stays the accounting event, and a PUTUS completion calls the latter with the DELIVERED, never the planned, quantities — that substitution IS the partial-refuse mechanism. A KONSI completion writes no `FieldSalesDelivery` at all; it issues a `KonsiTransfer` for the delivered qty instead. Both also draw `docNo` from the same `DELIVERY` counter. See `docs/ARCHITECTURE-NOTES.md`.
- Completing a KONSI shipment? It MOVES STOCK — `completeDeliveryShipment`'s konsi branch is ONE `runSerializable`: the `IN_TRANSIT` status CAS first, then `DeliveryShipmentLine.deliveredQty`, `issueKonsiTransfer` for the lines with `deliveredQty > 0` (an all-zero completion writes no transfer), the order lines' `deliveredQty` increment and the order's `deliveryStatus`. Unlike the putus two-transaction tail it is atomic, so every failure inside it must THROW. It writes no `FieldSalesDelivery`, no `Receivable`, no `TaxInvoice` and no journal, returns `deliveryId: ""`, and takes no invoice/due dates on either method (`MISSING_DATES` is PUTUS-only, at ship and at completion). Every refusal `issueKonsiTransfer` raises is mapped by `instanceof` inside that transaction — `KonsiTransferReservationMismatchError` → `KONSI_NOT_RESERVED`, `MainStockNegativeError` → `DeliveryError` `INSUFFICIENT_STOCK`, `InventoryValueMissingError` → `NO_INVENTORY_ROW` — and all are terminal in the offline completion classifier; a new refusal the transfer can raise needs the same mapping, or it leaks as `UNEXPECTED` and the offline queue retries it to its ceiling. See `docs/ARCHITECTURE-NOTES.md`.
- Copying the POD gate's shape onto another proof check? `completeDeliveryShipment`'s `MISSING_PROOF` is this codebase's FIRST hard-blocking proof gate — every sibling (`StoreVisit.checkinOutOfRadius`) warns and never blocks, so don't harmonise the two in either direction. See `docs/ARCHITECTURE-NOTES.md`.
- Building a new caller on `completeDeliveryShipment`? It posts NO journals (`completeShipmentAction` does, after it returns, guarded on a non-empty `deliveryId` — and for `replay.deliveryId` when it refuses `REPLAY_MISMATCH`, which a new caller must copy too; see the compare-and-refuse entry below) and it throws TWO error classes — `DeliveryShipmentError` plus `DeliveryError`, which comes from `recordFieldSalesDelivery` on the putus path and from the konsi branch's own mapping of `MainStockNegativeError` to `INSUFFICIENT_STOCK` — overlapping code strings, different `instanceof`. See `docs/ARCHITECTURE-NOTES.md`.
- Editing `completeDeliveryShipment`'s PUTUS two-transaction tail? The deterministic `shipment-<id>` idempotency key and the `status: "IN_TRANSIT"` CAS `updateMany` are what make a crash between the AR write and the status write retryable — never regress either to a random key or a plain `update`. Retryable means a retry asking for the recorded values completes; one asking for different ones — quantities, or on an `EXPEDITION` shipment dates too — is refused (next entry). The KONSI branch is a single transaction with no such gap (see the KONSI completion entry above). See `docs/ARCHITECTURE-NOTES.md`.
- Retrying a field-sales delivery that may already be recorded, or changing how a caller retries one? A replayed `idempotencyKey` is COMPARE-AND-REFUSE, never replay-whatever-was-asked: `recordFieldSalesDelivery` returns the recorded delivery only when the retry asks for the same thing, and otherwise throws `REPLAY_MISMATCH` with the recorded values on `DeliveryError.replay`, before any write. Never rotate the key to get a changed retry through — after a lost-response success a fresh key ships the order twice — and never loosen the compare back to key-only, which reports success while discarding the operator's change and, on the shipment path, stamps the shipment with quantities its delivery does not record. What is compared depends on who owns the dates. A hand-entered delivery (`recordDeliveryAction`) compares the invoice/due dates AND the per-`orderLineId` quantities: its operator typed the dates, so a changed date is a correction. A `shipment-<id>` key follows the shipment's `method`, chosen in `completeDeliveryShipment`. An `EXPEDITION` shipment compares dates AND quantities, exactly like a hand-entered delivery: the backoffice operator types the dates into `CompleteShipmentDialog`, which resets them on every open, so a lines-only compare would accept a lost-response retry with re-typed dates, keep the original ones and report success. A `SALESMAN_CARRY` shipment compares quantities ONLY (`replayCompare: "linesOnly"`): its retry always carries the frozen shipment row's dates, and Edit nota dates may have corrected the recorded delivery's since, so a dates compare there refuses every retry forever — the recorded delivery's dates are the accounting truth and change only through Edit nota dates. Never collapse the two methods onto one compare in either direction. An all-zero shipment completion never calls the writer, so `completeDeliveryShipment` looks the key up itself (`findRecordedDelivery`, inside the CAS transaction) and refuses the same way — skip it and the shipment is stamped as delivering nothing, with no `deliveryId`, over a delivery whose stock and receivable already moved. A refused replay STILL posts the recorded delivery's journals: `recordDeliveryAction`, `completeShipmentAction` and `completePodAction` each call their `postDeliveryJournals` helper for `replay.deliveryId` before returning the refusal, because the crash window can leave that delivery with no journal, and a refusal that skips the post leaves no journal, no `JOURNAL_PENDING` flag and no retry path. The two shipment completion forms show the recorded values and prefill them — `CompleteShipmentDialog` its dates too — so one more submit completes consistently, per shipment line through `recordedQtyByShipmentLine`, which never asks for an order line two shipment lines share twice. The hand-entered `DeliveryFormDialog` does not prefill: the delivery exists, so it toasts the recorded number and dates, rotates its key and closes, leaving the dates to Edit nota dates. The shared `deliveryShipments.err.REPLAY_MISMATCH` copy says "dates or quantities" for the expedition dialog; the PWA sheet renders its own quantities-only `pwa.deliveries.replayMismatch` instead, because a salesman-carry refusal is never about dates. The offline pending screen resends a fixed payload, so it says to delete the queued item and complete from the delivery's page, and links there, instead of offering Retry. See `docs/ARCHITECTURE-NOTES.md`.
- Changing carrier/resi handling? `updateShipmentTracking` is decoupled from `shipDeliveryShipment` on purpose (correctable while still `PACKED`, frozen once `IN_TRANSIT`), and the ship CAS deliberately does not re-check `resiNumber` — a known, accepted race. See `docs/ARCHITECTURE-NOTES.md`.
- Gating a shipment control in the UI? `deliveries:ship` (create/pack/track/ship/cancel) and `deliveries:pod` (completing against proof) are two permissions — check the SAME one that action enforces, never the sibling next to it; that exact mismatch already shipped twice on this branch. The READ surfaces (`/backoffice/deliveries`'s route gate, the `/backoffice/deliveries/[id]` detail page and every link to it, `listShipmentsAction`, `getShipmentAction`) deliberately admit EITHER, because a POD-only actor reaches the Complete button through that list; every WRITE keeps its own single permission. See `docs/ARCHITECTURE-NOTES.md`.
- Calling `completeDeliveryShipment`? The payload must name EVERY shipment line EXACTLY once or it is refused with `LINE_MISMATCH` — a duplicate gets consumed/invoiced as the SUM by `recordFieldSalesDelivery`, an omission marks the shipment terminally `DELIVERED` with that line's `deliveredQty` null forever. See `docs/ARCHITECTURE-NOTES.md`.
- Computing what is left to ship on an order line? It is `qty − deliveredQty − cancelledQty − plannedQty already on other PACKED/IN_TRANSIT shipments` — `deliveredQty` only moves at COMPLETION, so the three-term version lets two shipments claim the same units and the second one dies on `OVER_DELIVER` after the goods left. `CreateShipmentDialog`'s prefill uses the three-term figure on purpose; the writer is the enforcement. See `docs/ARCHITECTURE-NOTES.md`.
- Closing an order's remainder, or packing a shipment? `closeFieldSalesOrderRemainder` refuses `SHIPMENT_IN_FLIGHT` while the order has any shipment `PACKED` or `IN_TRANSIT`, putus and konsi alike — its release flips each line's WHOLE reservation, so the in-flight shipment would then complete against nothing (`KONSI_NOT_RESERVED` / `OVER_DELIVER`) with its goods already travelling; never net the planned qty out instead, which still closes units on a truck. `createDeliveryShipment` refuses any order not `APPROVED` (`INVALID_STATE`). Both checks run inside the writer's transaction before any write, and the konsi shipments card disables Close remainder with the reason. See `docs/ARCHITECTURE-NOTES.md`.
- Adding a `DeliveryShipmentErrorCode` or `DeliveryErrorCode` member? Both feed `ShipmentActionResult`'s reason union, which the dialogs render as `t(\`err.${reason}\` as any)` — no exhaustive `Record` and no compile error, so a missing `err.*` key in `en.json`/`id.json` just shows the operator the raw key. Add it to BOTH locales. See `docs/ARCHITECTURE-NOTES.md`.
- Reading `completeDeliveryShipment`'s `invoiceDate`/`dueDate`? TWO sources now, branched on `method` — caller input for `EXPEDITION`, the shipment row for `SALESMAN_CARRY`, which IGNORES whatever the caller sends because the salesman carries a printed nota bearing the dates an admin committed at pack/ship time. Both params are optional in the type and still mandatory at runtime (`MISSING_DATES`) for a PUTUS order; a KONSI order raises no invoice and takes neither, on either method, and `completeShipmentAction` forwards the dates only when present, refusing a present-but-malformed one with `INVALID_REQUEST`. A third method needs its own explicit branch, since neither existing source is the default. See `docs/ARCHITECTURE-NOTES.md`.
- Trusting a declared `number` on anything reachable from a `"use server"` export? The salesman-carry GPS gate shipped BYPASSABLE: unvalidated `{ lat: null, lng: null }` coerced to `distanceMeters: 0` inside the haversine and passed both the `=== null` and the `> radius` check, completing the delivery with a fabricated "0 metres from the store" audit row. Validate with `Number.isFinite` plus a lat/lng range check — never the global `isFinite`, which coerces (`isFinite(null)` is `true`, making the guard a no-op). See `docs/ARCHITECTURE-NOTES.md`.
- Changing the delivery POD radius? There is no delivery-specific setting — the gate deliberately reuses `checkin.radiusMeters` (`SystemSetting`) and the per-store `Store.checkinRadiusMeters` override, so widening either one widens store check-in with it. See `docs/ARCHITECTURE-NOTES.md`.
- Reading `evaluateCheckinRadius`'s `distanceMeters: null`? It means OPPOSITE things at its two call sites — check-in treats it as a pass (that flow only ever warns), the POD gate refuses with `STORE_NOT_GEOCODED`. The interpretation lives in each caller and the shared helper was deliberately left untouched, so never express this gate as `if (outOfRadius)` alone. See `docs/ARCHITECTURE-NOTES.md`.
- Hitting a shipment whose `Store` row is missing? That is `NOT_FOUND`, not `STORE_NOT_GEOCODED` — `relationMode = "prisma"` means no FK behind `FieldSalesOrder.storeId`, so a dangling id is genuinely reachable, and conflating the two tells ops to geocode a store that does not exist. See `docs/ARCHITECTURE-NOTES.md`.
- Adding a `DeliveryShipmentErrorCode`/`DeliveryErrorCode` member (again)? `mapError` now exists TWICE — the original in `app/actions/delivery-shipments.ts` and a private duplicate in `app/pwa/deliveries/actions.ts`, because a `"use server"` module may only export async functions and `mapError` is synchronous. Update both or the two error-mapping surfaces silently diverge, on top of the two locale keys the entry above demands. See `docs/ARCHITECTURE-NOTES.md`.
- Setting `carriedById`? The writer does NOT verify it exists, unlike `packedById` — tolerable only because the relation is optional (so no `Inconsistent query result`) and the sole path that writes it is an admin-facing `SearchableCombobox` fed by `listCarrierCandidates()`, not raw input. A bogus id costs a shipment sitting in nobody's PWA queue with the carry unattributable; add the check the moment anything else can set it. See `docs/ARCHITECTURE-NOTES.md`.
- Reassigning who carries a shipment after it ships? Not possible — `updateShipmentTracking` is `PACKED`-gated, so `carriedById` freezes at `IN_TRANSIT` along with the resi, and cancel-and-recreate is the only escape hatch. See `docs/FOLLOWUPS.md`.
- Touching the `SALESMAN_CARRY` completion branch, or adding a new caller of `completeDeliveryShipment`? `carriedById` must EQUAL `deliveredById` there (`NOT_CARRIER`) — that identity check IS the feature's anti-fraud property, and it shipped missing: `shipDeliveryShipment` only checks the column is SET and `listMyDeliveries` only scopes the PWA queue, so for a while any `deliveries:pod` holder could open another salesman's shipment URL and close it, consuming stock, raising a receivable, posting the AR journals and stamping their own id. The GPS gate is not a substitute — it checks LOCATION, is trivially spoofed from a browser, and passes for anyone standing at the right store. The PWA page's `notFound()` on a non-matching `carriedById` is the fail-fast half only; never treat it as the enforcement. See `docs/ARCHITECTURE-NOTES.md`.
- Gating a backoffice control on `canPod` + `IN_TRANSIT` alone? Also check `method` — a `SALESMAN_CARRY` shipment can only be completed from the PWA, because `completeShipmentAction` sends no `gps` payload and the writer's `SALESMAN_CARRY` branch hard-requires one. That button rendered for salesman-carry rows and returned `MISSING_GPS` every time, in the same feature area that already carries a "gate on what the action enforces" entry. See `docs/ARCHITECTURE-NOTES.md`.
- Adding a method-conditional guard to a shared handler? Check its NEIGHBOURS — `ShipmentTrackingDialog`'s `handleShip` already held an unconditional `if (!resiNumber)`, so the new `SALESMAN_CARRY` pre-check passing still blocked EVERY salesman-carry ship attempt through the UI until that older check was scoped to `method === "EXPEDITION"`. A new branch does not make its siblings conditional. See `docs/ARCHITECTURE-NOTES.md`.
- Relying on `deliveries:pod`/`deliveries:ship` in a test? Neither `Permission` row exists in a fresh/local database until `packages/db/prisma/seed-deliveries-permissions.sql` is hand-run — no migration applies it, and nothing on the deploy path seeds. **Run on prod 2026-09-04** (`deliveries:pod`→ADMIN+SALESMAN, `deliveries:ship`→ADMIN; SALESMAN's `permissionsVersion` bumped so already-logged-in users pick it up), so this is a fresh-environment/test-bed trap now, not a live-prod one. A spec must still self-seed the rows with `connectOrCreate` rather than assert they exist — asserting is exactly what made `carrier-queries.test.ts` die in its own setup and report two passing tests over zero real coverage. See `docs/FOLLOWUPS.md`.
- Reaching for `signatureUrl`/`signatureR2Key`/`signedByName` expecting a drawn signature? They hold a photo of the signed physical nota (for a konsi order, the signed Surat Keluar) plus the receiver's typed name instead — a deliberate substitution for the card's literal "digital signature capture" wording, decided after the columns already shipped unused anticipating a canvas pad. Building an actual signature pad on top of these three columns means they are already load-bearing for something else. See `docs/ARCHITECTURE-NOTES.md`.
- Adding a second required photo (or any second upload) to this feature? Both proof keys are bound to the shipment ID and to being distinct from each other (`signatureR2Key !== proofPhotoR2Key`) — without both checks one uploaded photo can satisfy every proof requirement at once. The prefix follows the method: a `SALESMAN_CARRY` shipment's goods and nota keys must be exactly `delivery-pod-proofs/<shipmentId>/<file>.<ext>`, an `EXPEDITION` shipment's goods key exactly `delivery-proofs/<shipmentId>/<file>.<ext>` (the backoffice route's folder) — one file segment, checked by `isR2KeyInFolder`, never a prefix match, so a second photo cannot live in a sub-folder; both refuse as `MISSING_PROOF`/`MISSING_NOTA_PHOTO`, and both binds run AFTER the same-actor replay guard, never before it. Salesman-carry keys are DETERMINISTIC (`clientId` literal `"goods"`/`"nota"`, no per-attempt uniqueness) so a retried upload while the shipment is `IN_TRANSIT` overwrites the same object rather than orphaning one. Once the shipment is delivered the upload route does NOT overwrite: a same-carrier replay gets the STORED url/key back with no R2 write, so a replay never overwrites the evidence while the lost-response replay still reaches the writer's `{ ok: true }`. The one accepted exception is an upload that passed the `IN_TRANSIT` read and lands after the same carrier's completion commits, replacing the photo with that carrier's own newer one. The route's replay branch and the writer's replay guard are one contract, so both call the same predicate, `isSameActorReplay` in `lib/delivery/pod-completion-guard.ts` — change the rule there, never inline a copy in either caller. The route's 404/409 map to `NOT_FOUND`/`INVALID_STATE` through `lib/pwa/offline/pod-upload-refusal.ts` in both the sheet and the offline sync; a bare throw there would retry to the ceiling and lose the diagnosis. See `docs/ARCHITECTURE-NOTES.md`.
- Writing a client-side mirror of the GPS/radius gate? Import `evaluateCheckinRadius` (confirmed pure, safe for a client bundle) — do not hand-roll the haversine formula again. A hand-rolled version already shipped once missing the server's `Math.round(...)` step, creating a real false-negative band that could strand a salesman standing close enough. See `docs/ARCHITECTURE-NOTES.md`.
- Touching `completeDeliveryShipment`'s check ordering? The shipment fetch + the same-actor idempotent-replay guard run FIRST now, ahead of the cheap `NO_LINES`/`MISSING_PROOF`/`INVALID_QTY` payload-shape checks — a malformed payload against a nonexistent or non-`IN_TRANSIT` shipment now returns `NOT_FOUND`/`INVALID_STATE` instead of the old codes. Deliberate, regression-tested, needed so a same-actor retry after a lost response can reach the replay guard at all. See `docs/ARCHITECTURE-NOTES.md`.
- Retrying a delivery completion whose response was lost? `completeDeliveryShipment` now returns `{ok:true}` on a SAME-actor replay against an already-`DELIVERED`/`PARTIALLY_DELIVERED` shipment — but a DIFFERENT actor against the same shipment still throws `INVALID_STATE`. Never widen this to "any actor" without reopening the `NOT_CARRIER` anti-fraud entry above. This guard covers a shipment that already flipped; a shipment still `IN_TRANSIT` over an already-recorded delivery (the crash between the two transactions) never reaches it and is the compare-and-refuse entry above instead. See `docs/ARCHITECTURE-NOTES.md`.
- Building a new offline queue, or touching the completion one? Its classifier treats `FORBIDDEN`/`UNEXPECTED` as `"retry"` — the OPPOSITE of every other queue's classifier in this codebase (`classify.ts`, `photo-classify.ts` both treat those as terminal, since a human is watching those flows). An unattended queue must wait for re-login, not discard evidence on an auth failure — but needs its own ceiling (`MAX_RETRY_ATTEMPTS`) for a PERMANENTLY revoked permission, which looks identical to an expired session. See `docs/ARCHITECTURE-NOTES.md`.
- Rendering a shipment's proof photo on any screen? Never render the stored `proofPhotoUrl`/`signatureUrl` — they are caller-supplied at completion and nothing validates them. Read `goodsPhoto`/`notaPhoto` from `getDeliveryShipmentDetail`, or call the exported `deriveProofPhoto` beside it in `lib/delivery/shipment-queries.ts`, which accepts only the exact `<folder>/<file>.<ext>` shape the writer binds (`isR2KeyInFolder`, goods folder by method) and flags anything else, including a legacy URL with no key, as "cannot display" instead of dropping it silently. See `docs/ARCHITECTURE-NOTES.md`.
