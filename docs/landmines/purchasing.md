# Purchasing landmines

The full entries behind the **Purchasing** triggers in `AGENTS.md` § Landmine index, in the same order. Each one was written after someone paid for it. Read the entry for whatever surface you are about to touch before writing code; where an entry points on to `docs/ARCHITECTURE-NOTES.md` or `docs/FOLLOWUPS.md`, follow it. When a change makes an entry wrong, fix it here in the same session — and update its trigger in `AGENTS.md` if the trigger itself moved.

- Writing a PO's payment terms or its GRNs — a new receipt, a decline, a void, a receipt-date edit? While `PurchaseOrder.paymentTermsDays` is set, `PurchaseOrder.paymentDueDate` is DERIVED: the WIB calendar day of the PO's earliest GRN with `ownerDeclinedAt: null` (ordered `grnDate asc, id asc`; a pending over-receive GRN counts, since the goods are in) plus the terms, stored as WIB midnight of that date (`computePaymentDueDate` in `apps/web/lib/purchase-orders/payment-terms.ts`) — the repo's date-only shape (`parseDateOnly`), the same instant a hand-picked due date is stored as, so a day-level comparison reads both in WIB (`formatDateOnlyJakarta`), never by UTC date. With no surviving receipt it is `null`. Every writer that changes a PO's terms or its set of counting receipts calls `recomputePaymentDueDate(tx, poId)` (`apps/web/lib/purchase-orders/payment-due.ts`) inside its OWN transaction; it is idempotent, so call it unconditionally. Today that is `createGRN` and `declineGRNByOwner` (`app/actions/grn.ts`, decline calling it after stamping `ownerDeclinedAt`), `createPurchaseOrder` (`lib/purchase-orders/mutations.ts`), `updatePO` (`app/actions/purchase-orders.ts`) and `setPurchaseOrderPaymentTerms` (`lib/purchase-orders/set-payment-terms.ts`); `approveGRNByOwner` changes no receipt date and does not call it. A new GRN reversal or void path, or anything that edits `grnDate`, must call it too — skip it and nothing fails: the date silently keeps pointing at a receipt that no longer counts, and finance pays on the wrong day. Four more ways to break it: (1) never write `paymentDueDate` from client input while terms are set — both PO writers ignore a client-sent date then, and a new writer must too; the manual date belongs only to a PO with `null` terms, which `recomputePaymentDueDate` leaves untouched (so setting terms back to `null` keeps the last derived date, now editable). (2) Terms are a PO SNAPSHOT: `createPurchaseOrder` defaults them from `Supplier.paymentTermsDays` only when the payload omits the field (explicit `null` means no terms; the offline sync path relies on the default), and nothing afterwards reads the supplier's value — never compute an existing PO's date from `Supplier.paymentTermsDays`, or a supplier edit rewrites every open PO's due date. (3) `updatePO` refuses CLOSED and CANCELLED POs, and a single-delivery PO goes straight to CLOSED on its first GRN, so a terms correction goes through `setPurchaseOrderPaymentTerms` (action `setPOPaymentTerms`, `purchase_orders:edit`, PIN past DRAFT), which allows every status but CANCELLED and refuses a paid PO — never loosen `updatePO`'s CLOSED guard to do it. (4) The value rule is an integer 0–365 or `null`, enforced in the writers through `paymentTermsDaysField`/`parsePaymentTermsDays`; `0` is legal (pay on receipt) and a cleared input is `null`, never `0`. See `docs/ARCHITECTURE-NOTES.md`; the gaps left open are in `docs/FOLLOWUPS.md` § Purchasing.
