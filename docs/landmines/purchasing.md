# Purchasing landmines

The full entries behind the **Purchasing** triggers in `AGENTS.md` § Landmine index, in the same order. Unlike most landmine files, these entries are preventive: they were written with the feature, before anything broke, to mark how its design can be broken. Read the entry for whatever surface you are about to touch before writing code; where an entry points on to `docs/ARCHITECTURE-NOTES.md` or `docs/FOLLOWUPS.md`, follow it. When a change makes an entry wrong, fix it here in the same session — and update its trigger in `AGENTS.md` if the trigger itself moved.

- Writing a PO's payment terms or its GRNs — a new receipt, a decline, a void, a receipt-date edit? While `PurchaseOrder.paymentTermsDays` is set, `PurchaseOrder.paymentDueDate` is DERIVED: the WIB calendar day of the PO's earliest GRN with `ownerDeclinedAt: null` (ordered `grnDate asc, id asc`; a pending over-receive GRN counts, since the goods are in) plus the terms, stored as WIB midnight of that date (`computePaymentDueDate` in `apps/web/lib/purchase-orders/payment-terms.ts`) — the repo's date-only shape (`parseDateOnly`), the same instant a hand-picked due date is stored as, so a day-level comparison reads both in WIB (`formatDateOnlyJakarta`, or `daysOverdue` in the payment reminder sweep), never by UTC date. With no surviving receipt it is `null`. Every writer that changes a PO's terms or its set of counting receipts calls `recomputePaymentDueDate(tx, poId)` (`apps/web/lib/purchase-orders/payment-due.ts`) inside its OWN transaction; it is idempotent, so call it unconditionally. Today that is `createGRN` and `declineGRNByOwner` (`app/actions/grn.ts`, decline calling it after stamping `ownerDeclinedAt`), `createPurchaseOrder` (`lib/purchase-orders/mutations.ts`), `updatePO` (`app/actions/purchase-orders.ts`) and `setPurchaseOrderPaymentTerms` (`lib/purchase-orders/set-payment-terms.ts`); `approveGRNByOwner` changes no receipt date and does not call it. A new GRN reversal or void path, or anything that edits `grnDate`, must call it too — skip it and nothing fails: the date silently keeps pointing at a receipt that no longer counts, and finance pays on the wrong day. Four more ways to break it: (1) never write `paymentDueDate` from client input while terms are set — both PO writers ignore a client-sent date then, and a new writer must too; the manual date belongs only to a PO with `null` terms, which `recomputePaymentDueDate` leaves untouched (so setting terms back to `null` keeps the last derived date, now editable). (2) Terms are a PO SNAPSHOT: `createPurchaseOrder` defaults them from `Supplier.paymentTermsDays` only when the payload omits the field (explicit `null` means no terms; the default covers payloads that omit the field, such as offline POs queued before terms existed — an offline PO queued now carries the form's value, pre-filled from the IndexedDB supplier cache, and a cache filled before terms existed holds none until the next reference-data sync), and nothing afterwards reads the supplier's value — never compute an existing PO's date from `Supplier.paymentTermsDays`, or a supplier edit rewrites every open PO's due date. (3) `updatePO` refuses CLOSED and CANCELLED POs, and a single-delivery PO goes straight to CLOSED on its first GRN, so a terms correction goes through `setPurchaseOrderPaymentTerms` (action `setPOPaymentTerms`, `purchase_orders:edit`, PIN past DRAFT), which allows every status but CANCELLED and refuses a paid PO — never loosen `updatePO`'s CLOSED guard to do it. `updatePO` refuses a paid PO too, but only when the submitted terms differ from the stored ones, so the rest of a paid PO stays editable. The writer opens with a `SELECT … FOR UPDATE` on the PO row instead of a plain read: a locking read waits out a GRN writer holding that row and opens no REPEATABLE READ snapshot, so its recompute sees every receipt committed before it — keep the lock first if you edit it. (4) The value rule is an integer 0–365 or `null`, enforced through `paymentTermsDaysField`/`parsePaymentTermsDays` on every path that writes either column: `supplierSchema`/`supplierUpdateSchema` (`lib/suppliers/mutations.ts`), `poSchema` (`lib/validations/index.ts`, which the online and offline PO creates both parse), `updatePO`, `setPurchaseOrderPaymentTerms`, `PUT /api/suppliers/[id]` (which parses `supplierUpdateSchema` and writes through `updateSupplier`), and the `/api/sync` `SUPPLIER_CREATE` and `SUPPLIER_UPDATE` handlers (the update validates the key only when the payload carries it; the rest of that handler is unvalidated mass assignment, logged in `docs/FOLLOWUPS.md`). A new path that writes terms parses through the same helper; `0` is legal (pay on receipt) and a cleared input is `null`, never `0`. See `docs/ARCHITECTURE-NOTES.md`; the gaps left open are in `docs/FOLLOWUPS.md` § Purchasing.
- Touching the PO payment reminder sweep (`runPaymentReminderSweep` in `apps/web/lib/purchase-orders/payment-reminder-sweep.ts`, cron 08:30 Asia/Jakarta)? It is modelled on the AR overdue sweep and inherits that sweep's rules — read the `runOverdueSweep` entries in `docs/landmines/finance-ar.md` (dedup query, highest crossed threshold, fail-open parsing, cron-only `await`) before editing it. Here they mean: the dedup read takes EVERY `PO_PAYMENT_DUE` `AdminNotification` row with no `take` and no `createdAt` floor, because those rows are the only record that a crossing fired; the row is the marker, written inside the per-PO try/catch BEFORE the fan-out (there is no per-person push ahead of it, unlike the AR collector push), so a throw before it leaves the crossing for the next run; and `await fanOutAdminNotification` is there only because this is a cron — never copy it into an interactive path. The dedup groups rows by `metadata.poId` + `metadata.dueDate` (the due date's ISO string) and keeps the highest `metadata.thresholdDays` announced; a PO fires only when its highest crossed threshold exceeds that, one notification per PO per run. The due date is in the key on purpose: a moved due date (terms corrected, the counting receipt declined, a hand-entered date edited) re-arms its reminders. Drop `dueDate` from the key or the metadata and every reminder after a terms correction is silenced; drop `thresholdDays` from the metadata and the read skips the row, so the crossing re-announces every run. Thresholds are signed WIB days relative to the due date (negative = before, computed by `daysOverdue`), read from the `po.paymentReminderDays` `SystemSetting` through `parsePaymentReminderDays`, which fails OPEN to `[-7, -1, 0, 7]`; the settings action (`setPaymentReminderDays`, `purchase_orders:edit`) stores only what `validatePaymentReminderDays` accepts (whole numbers within ±365), so the page can never save a value the sweep would discard. The 200-per-run cap is applied AFTER every crossing is computed and sorted — upcoming and due-today reminders (highest crossed threshold `<= 0`) first, then overdue, earliest due first within each — so an overdue backlog drains behind the live reminders; apply the cap in plain due-date order and a backlog of old overdue POs starves a PO due next week of its pre-due reminders for good, since only the highest crossed threshold fires once its turn comes. A spec calling `runPaymentReminderSweep` must pass `poIds` and `asOf` — omitted, it sweeps every unpaid PO on the shared `:3308` bed — and must snapshot and restore the shared `po.paymentReminderDays` row, never delete it unconditionally. Bell copy formats the due date in Asia/Jakarta (`buildPaymentReminderCopy`, `apps/web/lib/purchase-orders/payment-reminder-copy.ts`); never `toLocaleDateString` without a time zone, since prod runs in UTC and a WIB-midnight due date would print as the day before. See `docs/ARCHITECTURE-NOTES.md`; open items are in `docs/FOLLOWUPS.md` § Purchasing.
