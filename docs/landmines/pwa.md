# PWA landmines

The full entries behind the **PWA** triggers in `AGENTS.md` § Landmine index, in the same order. Each one was written after someone paid for it. Read the entry for whatever surface you are about to touch before writing code; where an entry points on to `docs/ARCHITECTURE-NOTES.md`, `docs/EPIC-STATUS.md` or `docs/FOLLOWUPS.md`, follow it. When a change makes an entry wrong, fix it here in the same session — and update its trigger in `AGENTS.md` if the trigger itself moved.

- Editing `apps/web/proxy.ts`? It IS the Next 16 middleware (renamed from `middleware.ts`), runs on every request, and gates `/pwa/*` — it is NOT dead code.
- Testing PWA offline behaviour, or chasing a 404 from the service worker? The Serwist SW only exists in a production build, and a committed `public/**/sw.js` / `workbox-*.js` poisons the precache manifest and kills SW install — never commit generated SW files.
- Touching PWA push — token registration, the SW's `push`/`notificationclick` handlers, or a new notification type meant to reach a phone? PWA pushes arrive at the existing Serwist SW (`apps/web/app/pwa/sw.ts`), never at a Firebase messaging SW: two service workers cannot share the `/pwa/` scope. So a PWA token MUST be minted against the `/pwa/` registration — `registerFcmToken({ serviceWorkerScope: "/pwa/" })` (`apps/web/components/notifications/fcm-client.ts`), as `PwaPushRegistrar` (silent refresh on load, only once permission is granted) and `EnablePushCard` (the one explicit prompt, on `/pwa/notifications` — iOS grants permission only from a gesture) do. Called with no scope, as the backoffice `FcmRegistration` does, `getToken` falls back to Firebase's default worker, which does not exist in this repo, so a PWA token minted that way never lands on a worker that shows anything. Every `push` event MUST end in `showNotification`, an unreadable payload included (Chrome's `userVisibleOnly` contract), which is why `parsePushPayload` never throws and falls back to a generic title and `/pwa/notifications`. `apps/web/lib/pwa/push-payload.ts` is bundled into the SW, so it keeps RELATIVE imports only, of import-free modules (`../notifications/navigation`) — the worker bundle may not resolve the `@/` alias, and whatever a module imports ships inside the worker. A tap lands on `getNotificationHref(type, data, "pwa")`, so a new type that should open a PWA screen needs its `pwa` case there. A push lands only on whichever surface registered last: `User.fcmToken` is ONE column, so a user on both backoffice and PWA keeps only the latest device. The SW handlers are covered by no type-check (`app/pwa/sw.ts` is excluded from `tsconfig.json`) and run only in a production build; device delivery is verifiable only on prod.
