# PWA landmines

The full entries behind the **PWA** triggers in `AGENTS.md` § Landmine index, in the same order. Each one was written after someone paid for it. Read the entry for whatever surface you are about to touch before writing code; where an entry points on to `docs/ARCHITECTURE-NOTES.md`, `docs/EPIC-STATUS.md` or `docs/FOLLOWUPS.md`, follow it. When a change makes an entry wrong, fix it here in the same session — and update its trigger in `AGENTS.md` if the trigger itself moved.

- Editing `apps/web/proxy.ts`? It IS the Next 16 middleware (renamed from `middleware.ts`), runs on every request, and gates `/pwa/*` — it is NOT dead code. An unauthenticated request under `/pwa/api/` gets a JSON 401 (`{ error: "UNAUTHENTICATED" }`), never the `/login` redirect PWA pages get: a `fetch` follows a 307, re-POSTs the body to `/login`, and an offline queue classifying whatever that answers could evict evidence it never uploaded (a 200 reads as success). Keep API paths on the 401, and keep the visit-photo sync's `redirect: "manual"` (a redirect reads as status 0, a retry) as the backstop (PR #480).
- Testing PWA offline behaviour, or chasing a 404 from the service worker? The Serwist SW only exists in a production build, and a committed `public/**/sw.js` / `workbox-*.js` poisons the precache manifest and kills SW install — never commit generated SW files.
- Touching PWA push — token registration, the SW's `push`/`notificationclick` handlers, or a new notification type meant to reach a phone? PWA pushes arrive at the existing Serwist SW (`apps/web/app/pwa/sw.ts`), never at a Firebase messaging SW: two service workers cannot share the `/pwa/` scope. So a PWA token MUST be minted against the `/pwa/` registration — `registerFcmToken({ serviceWorkerScope: "/pwa/" })` (`apps/web/components/notifications/fcm-client.ts`), or `daftarkanPush` (`apps/web/lib/pwa/push.ts`, which hands `navigator.serviceWorker.getRegistration("/pwa/")` to `getToken`), as `PwaPushRegistrar` and `SegarkanPush` (silent refreshes on load, only once permission is granted) and Kabar's `PushHp` (`apps/web/app/pwa/kabar/PushHp.tsx`, the one explicit prompt, on `/pwa/kabar` — iOS grants permission only from a gesture) do. `/pwa/notifications` only redirects to Kabar since owner decision 7 (2026-11-01). Called with no scope, as the backoffice `FcmRegistration` does, `getToken` falls back to Firebase's default worker, which does not exist in this repo, so a PWA token minted that way never lands on a worker that shows anything. Every `push` event MUST end in `showNotification`, an unreadable payload included (Chrome's `userVisibleOnly` contract), which is why `parsePushPayload` never throws and falls back to a generic title and `/pwa/kabar`. `apps/web/lib/pwa/push-payload.ts` is bundled into the SW, so it keeps RELATIVE imports only, of import-free modules (`../notifications/navigation`) — the worker bundle may not resolve the `@/` alias, and whatever a module imports ships inside the worker. A tap — the push, a Kabar row (`app/pwa/kabar/baris.ts`) and the "kabar baru" island chip (`PemantauKabarHp`) alike — resolves through `getNotificationHref(type, data, "pwa")`, which tries Max's `tautanKabar` (`JENIS_KABAR`) first, then `TUJUAN_HP` (`tujuanDiHp`), and only ever returns a `/pwa…` path other than Kabar itself, or `null` — never a `/backoffice` path; `null` means the tap only marks it read. So a new type first needs an entry in `NOTIFICATION_TYPES` (`lib/notifications/navigation.ts`), then BOTH its office `case` in the exhaustive switch (a `never` check) AND an entry in `TUJUAN_HP` (a `Record<NotificationType, …>`; `DI_KANTOR` when it has no phone screen). Missing either is a type error, but a type that is never ADDED to the tuple fails the `isNotificationType` guard and routes nowhere, silently. A type with no screen still goes in the tuple with an explicit `return null` case (PR #476). A push lands only on whichever surface registered last: `User.fcmToken` is ONE column, so a user on both backoffice and PWA keeps only the latest device. The SW handlers are covered by no type-check (`app/pwa/sw.ts` is excluded from `tsconfig.json`) and run only in a production build; device delivery is verifiable only on prod.
