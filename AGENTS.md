# Agent context — Elorae

Quick orientation for any new coding-agent session in this repo. Read this first, then `docs/BOUNDARY.md` for the architectural contract.

This file is the single source of truth for repo context. The root `CLAUDE.md` is a **symlink to it**, not a copy — edit `AGENTS.md` and never replace that symlink with a real file. Claude Code discovers both names but a real `CLAUDE.md` WINS and suppresses `AGENTS.md` entirely (measured on 2.1.259), so a pointer stub there would silently stop this file from loading; the symlink resolves to this content and loads it exactly once. On Windows, git needs `core.symlinks=true` or the checkout becomes a text file holding the string `AGENTS.md`.

## What this is

pnpm + Turborepo monorepo for an ERP + Jubelio marketplace integration.

```
apps/web/        Next.js 16 App Router — the ERP UI + NextAuth + node-cron (VPS)
apps/api/        NestJS 11 — Jubelio integration service (token, webhooks, queue)
packages/db/     Prisma 7 schema + generated client + MariaDB adapter (shared)
docs/BOUNDARY.md Service-boundary contract — source of truth for who-writes-what
AGENTS.md        This file — repo context + landmine index. `CLAUDE.md` is a symlink to it.
reference/       Local-only planning artifacts (gitignored). EPIC todos now live on the GitHub board (epic issues).
```

Database: **MariaDB 11.4** self-hosted in the docker-compose stack on the Hostinger VPS. Migrated off TiDB Cloud Serverless 2026-06-28 after the free tier exhausted its monthly quota.

**Local dev does NOT point at prod.** The default `DATABASE_URL` in `apps/web/.env` is `127.0.0.1:3308` — the local `elorae-dev-db` container from `docker-compose.dev.yml`, an isolated test bed. Prod is reached only through a deliberate SSH tunnel on **3307**, and `DATABASE_URL_PROD` (which no code reads) is an inert bookmark for it. Migrations, seeds, backfills and the test suite all run against 3308 by default and are safe there. See `docs/local-db-testbed.md`.

## Code conventions

- **Double quotes** for string literals in all TS/JS source (whole monorepo, including `apps/web`). No ESLint quote rule enforces single — safe.
- **No comments on Prisma schema models.** Field-level `//` comments forbidden; rationale lives in `docs/`. Migration SQL `--` comments are fine.
- **Adding a `DocType` enum member requires updating TWO `Record<DocType, …>` maps, not one — and TWO `ALTER TABLE … MODIFY docType ENUM(...)` statements on top of them (see the landmine index entry, which carries the migration half).** `apps/web/lib/docNumber.ts` (the generator) AND `apps/web/app/actions/settings/doc-numbers.ts` (the Settings → Document Numbers seeder) each hold their own `DEFAULT_CONFIGS` with identical shape. Missing either is a **build-breaking** type error that `apps/web` type-check would catch — but that check never runs locally here, so it surfaces only in the Docker build inside the deploy workflow. It happened on the delivery branch (PR #229 → deploy `31293514640`), where the schema advanced and prod was left serving the old image against it. **That specific outcome is no longer reachable**: `604a877` (2026-08-13) gated the `migrate` job on the image builds, so a web type error now blocks the migration instead of racing it — nothing ships and no schema moves. The error still costs a failed deploy. A third map, `DOC_TYPE_LABELS` in `apps/web/app/backoffice/settings/documents/page.tsx`, is keyed on the **local 8-member** `DocType` from `@/lib/constants/enums`, not Prisma's — leave it alone unless you deliberately widen that union too.
- **Four TypeScript shapes have shipped as build-breaking errors here — they are inference bugs, and reviewers cannot settle inference from source; only `tsc` can.** They surface solely in `pnpm -F @elorae/web type-check`, which is the owner's to run — **vitest transpiles without type-checking, so a green test run proves nothing about them**. Left undetected they fail the web image build during deploy, which blocks the gated `migrate` job: nothing ships and no schema moves until someone fixes it.
  1. **Truthiness never eliminates a `string` member of a union.** `if (input.storeId)` does NOT narrow the `else` branch to the sibling member, because `string` includes `""`, which is falsy. Adding `storeId?: undefined` to the sibling is necessary but not sufficient — it fixes the TRUE branch only. Discriminate on `!== undefined`, or add a real runtime guard (`if (!input.stocktakeId) return …`) that narrows honestly instead of asserting the state away with a cast.
  2. **Spreading a value whose parameter carries an index signature contributes no concrete fields.** `serializeListItemForClient` in `apps/web/lib/items/queries.ts` takes `{ …; [k: string]: unknown }`, so `{ ...rest }` carries that index signature into the return type and `item.id` loses its concrete type (it resolves to `unknown`, not to a missing property) — a direct `as Array<{ id: string; … }>` is then rejected as insufficiently overlapping. Go through `unknown` (`as unknown as X`), which is the compiler's own suggestion; live examples at `apps/web/app/pwa/spg/stocktake/SpgStocktakeAddItemSheet.tsx` and `apps/web/app/backoffice/store-stocktakes/[id]/StocktakeDetailClient.tsx`.
  3. **Constructing a library class in a test needs its FULL required-param set.** `new Prisma.PrismaClientKnownRequestError(msg, { code })` is missing `clientVersion`; every other construction in the repo passes `clientVersion: "test"`. Grep for an existing one before writing a new one.
  4. **Narrowing a PROPERTY does not survive into a nested closure; narrowing a `const` variable does.** A correctly discriminated union still fails: under `{row.proof.status === "error" && <Button onClick={() => upload(row.proof.file)} />}`, `row.proof.file` inside the handler resolves to the whole union's `File | null`, not the `error` arm's `File`, because the compiler cannot prove `row.proof` is unchanged by the time the click fires. The JSX guard reads like it narrows and does not. Hoist it first — `const proof = row.proof;` at the top of the `.map` body, then guard and use `proof` — which is why `SettlementForm.tsx` declares one in each of its two deduction-row maps. This one is invisible to review: the union is right, the guard is right, and only `tsc` sees it.
- **Branch names + commit messages + PR titles + spec docs are shared artifacts** — no EPIC-XX or L1-L9 labels in them. Use feature names. EPIC-XX labels live only on the GitHub board (epic issue titles) — never in shared code artifacts.
- **One-liner commit messages.** No body. No `Co-Authored-By` trailer. Conventional Commits format (`feat(api): ...`, `fix(db): ...`, etc.).
- **Subpath exports for `@elorae/db` pure helpers.** Client-component imports must use `@elorae/db/color` or `@elorae/db/pantone` (NOT the main barrel) to avoid dragging Prisma/mariadb into the client bundle.

## Workflow conventions

- **Match existing UI patterns before inventing new ones.** Before writing any new page/form/list, open a sibling module and copy the shape. Backoffice CRUD list reference = `apps/web/app/backoffice/purchase-orders/PurchaseOrdersPageClient.tsx` (header row + inline filter row + Card-wrapped table with CardHeader icon+title, empty state inside CardContent, no `p-6` on the server page — layout handles padding). Backoffice form reference = `apps/web/app/backoffice/suppliers/`. PWA reference = `apps/web/app/pwa/HomeShell.tsx` + `apps/web/app/pwa/stores/StoreList.tsx` (icon-prefixed rows, `bg-primary text-primary-foreground` icon circles for contrast on dark theme, `Card`/`Badge`/`Button` from `@/components/ui/*` — never native `<button>`/`<input>`/`<table>`). Grep + read one existing example before drafting.
- **Before opening a PR, run a CONSISTENCY SWEEP over what the change made stale — the review fleet does not do this for you.** Reviewers read the DIFF, so they are strong on whether new code is correct and blind to text that describes it from outside the diff. Every CI-bot finding across five consecutive PRs was audited and they fell into four classes, listed below. Not one was caught by a dedicated code reviewer, and every one of them was greppable. (Resist restating that audit as a tally — the first version of this rule carried counts that did not add up, which is its own small demonstration of why a number in a rule rots faster than a class does.) Sweep these four, by name:
  1. **Describing text for behaviour you changed.** Grep the changed identifiers and error codes across `apps/web/lib/i18n/messages/*.json`, `docs/`, `AGENTS.md` and nearby code comments. A locale string that still explains the old rule renders confidently wrong copy to an operator; a rule elsewhere in the SAME file that contradicts the one you just edited is worse, because the file reads as authoritative. Both have shipped here.
  2. **The sibling you did not touch.** When a fix names N sites, grep for the N+1th before calling it done — a stale-closure read was fixed in one add-row handler while TWO siblings beside it carried the identical bug, and on another branch four sites describing a permission mechanism were corrected while a fifth, in a different file, was not. A length guard was added inside a loop that `continue`s past one enum member, while the column it protected was written for every member. Also check the PR body itself: a test plan claiming behaviour the code does not have is a finding.
  3. **Every numeric bound against the column it protects.** A `String?` with no `@db.Text` is MySQL `VARCHAR(191)`; a validator capping at 300 lets a value pass and then die at insert as an untyped error. Check the DERIVED value too — a key capped at 191 still overflows once something prepends a URL prefix to it.
  4. **Paginated helpers called with defaults.** `listOffsettableReturns` and its kin take `page`/size and silently return the first page; a caller that means "all of them" gets 25 and no signal. If the caller means "all of them", it needs an unpaged variant — do not paper over it with a runtime `rows.length === total` assertion, which throws on the perfectly normal case of more than one page. Pin the completeness in a test instead.
  When you dispatch the whole-branch review fleet, give ONE reviewer this as its explicit lens — "for every behaviour this branch changed, find the text that describes it and say what is now false" — rather than assuming a correctness reviewer will wander into it. They reliably do not.
- **Plan before implementing** any non-trivial feature. Brainstorming → spec doc (`docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`) → plan doc (`docs/superpowers/plans/YYYY-MM-DD-<topic>-plan.md`) → implement → PR. The `superpowers:*` skills enforce this when invoked. `docs/superpowers/` is local-only (gitignored) — specs/plans never ship in PRs.
- **On merge, update the docs the change invalidates** — in the same session, not later. Tick the slice's row in `docs/EPIC-STATUS.md` (status → ✅, append PR # + merge date); flip any shipped item in `docs/FOLLOWUPS.md` to `- [x]` **and append the PR #** (that number is what makes a ticked item traceable later), and move every new follow-up there (never leave one in a PR body — they die on merge); and if the change created a new trap, add its entry to `docs/ARCHITECTURE-NOTES.md` plus a one-liner in the landmine index below. Also tick the matching story on the GitHub board.
- **TDD for non-trivial logic.** Pure functions, handlers, routers, processors get failing tests first. Module-wiring and infra-glue files are exempt.
- **Never force-push master.** Past divergence with a teammate's monolith branch was resolved by *recreating* their content in the monorepo, not by force-merging. See `project_master_divergence` memory.
- **`git check-ignore -v` before staging any dotfile** to confirm it's actually ignored.
- **Never commit secrets.** Even when staging looks clean, double-check `git diff --cached` for `.env`-shaped content.

## Landmine index

One line per known trap: **the situation you are in — what bites — where the detail lives.** Every one of them was written after someone paid for it. If a line matches what you are about to do, open the matching entry in `docs/ARCHITECTURE-NOTES.md` BEFORE writing code — and follow its onward pointers into `docs/EPIC-STATUS.md` / `docs/FOLLOWUPS.md` where it names them.

**Stock, inventory, reservations**

- Looking up an `InventoryValue` row? The variant key may legitimately be `null` OR `""` — variantless rows key on `null`, while simple-item carts and `VanStock` deliberately key `""`. Always use the OR-tolerant lookup (`OR: [{ variantSku: null }, { variantSku: "" }]`); a lookup strict on either spelling misses rows and forks a phantom row. Never "fix" one spelling into the other.
- Writing to `InventoryValue` / `reservedQty`? Atomic Prisma `increment`/`decrement` only, never read-modify-write — the webhook worker is concurrent and races the ERP ship path across processes. That rule still governs `reservedQty` and the DELTA movers; the SET movers (`setMainStock`/`setStoreStock`) are the documented exception, because a physical count is authoritative and they legitimately read the previous quantity before writing an absolute — reasoning in `docs/ARCHITECTURE-NOTES.md`. And a `qtyOnHand` write is no longer yours to make as a direct Prisma call, with ONE exception: `reservation-writer.ts` still moves it through a plain `tx.inventoryValue.update` twice and through a raw guarded `UPDATE` once, for the reasons in the `Writing reservedQty?` entry three below.
- Moving stock anywhere? Go through the movers in `packages/db/src/stock-balance.ts` — `moveMainStock`/`moveStoreStock`/`moveVanStock` for a signed delta, `setMainStock`/`setStoreStock` for an absolute count — and never write a quantity onto `InventoryValue`/`StoreStock`/`VanStock` directly. Each mover moves the balance and appends a `StockLedgerEntry` in the SAME transaction, and `apps/web/lib/inventory/stock-balance-guard.test.ts` fails on a new direct write. The predecessor is the reason: `StockMovement` drifted precisely because a writer could move `InventoryValue` without appending to it, and konsi, van, retur and consume all did — so its stored running balance disagrees with `InventoryValue.qtyOnHand` on any item those paths ever touched. `StockMovement` has NO production writer left — the movers are the only way stock moves now, and the predecessor table is a FROZEN ARCHIVE of pre-retirement history that nothing appends to. Never add a write to it to "keep the two in step": there is nothing to keep in step, and the new row would be the only one of its kind. The table and the model are KEPT rather than dropped because its rows are still READ, by two surfaces needing coverage the ledger structurally cannot have — `deleteItem`'s guard and the stock card's variant picker, each its own entry below. Its historical running-balance drift against `InventoryValue.qtyOnHand` was never measured and never repaired, and stopping the writes FROZE that drift rather than fixing it, so treat an archived balance as indicative and never as a figure to reconcile against. See `docs/ARCHITECTURE-NOTES.md`.
- Reading or writing `StockLedgerEntry.totalCost`/`balanceValue`? NULL means UNRECONSTRUCTIBLE, never zero — and a real `0` is the opposite claim, also legitimate, so neither may stand in for the other. The columns were added with no backfill: every row the ledger already held carries null, and the moving average at that instant is recorded nowhere else, which makes this a SECOND cutover inside the first (quantity history begins at the ledger's own cutover, value history begins later). A reader must therefore render a placeholder rather than `Rp 0` — the main stock card does, behind a standing note saying exactly that, and its CSV export writes an empty cell rather than a zero. A stamped `0`, by contrast, says the movement was genuinely worthless, which is true of an item that has never been costed; that is why the fabric-aggregate opname path lands a real `0` instead of leaving the columns undefined — both by passing an unguarded `delta * avgCost` that already evaluates to zero, and by a literal `0` on the row-provisioning append beside it — since stamping null there would make every opname on an uncosted item refuse to post. That refusal is the mechanism, not a side effect: `opnameNetDelta` (`apps/web/lib/inventory/opname-journal.ts`) sums the ledger's `totalCost` over one opname's rows and THROWS on a null rather than folding it in as zero, because a silent zero posts an inventory-variance journal short by exactly that row's value with nothing on screen to flag it. Never soften that throw into a `?? 0`, and never omit the value columns from a writer whose rows an opname will sum. The movers FORWARD both values and compute neither — the caller owns the cost basis, so pass the same expression you already computed for your own balance write, never a re-derivation, or the ledger and the balance table end up disagreeing about one movement. See `docs/ARCHITECTURE-NOTES.md`.
- Deleting an `Item`, or tidying `deleteItem`'s blocker list? It counts BOTH `StockMovement` and `StockLedgerEntry`, and the two counts refuse two DIFFERENT failures — so dropping either is wrong for a different reason, and each deletion looks individually safe. The archive half: `StockMovement` has no writers left, but `StockMovement.item` is still a REQUIRED Prisma relation with no database FK behind it, so an archived row left pointing at a deleted item throws `Inconsistent query result` on every read that joins it, forever; stopping the writes froze that archive, it did not empty it, and this count is the only thing standing in front of it. The ledger half: `StockLedgerEntry` declares no relation to `Item` at all, deliberately, so ledger history outlives the item it describes and an orphaned row can never crash a read — which is precisely why it is useless as a crash guard, and why its count is there for the other reason, refusing to silently strand live stock history behind a deleted item. "The archive is dead, drop its count" and "the ledger cannot crash anything, drop its count" are both individually plausible and both wrong. See `docs/ARCHITECTURE-NOTES.md`.
- "Simplifying" `getItemVariantOptions` (`apps/web/app/actions/stock-card.ts`) back onto one table? It unions THREE sources on purpose — `Item.variants`, `StockLedgerEntry` and `StockMovement` — because the two movement tables have complementary blind spots and neither alone is a superset. The ledger misses any variant that sat at ZERO at cutover, since the backfill wrote an `OPENING` row only for non-zero balances; `StockMovement` misses every variant that only ever moved through a field-sales path, which never wrote it; and only the catalog can offer a variant that has never moved at all. Dropping any one of them silently makes a real variant unselectable in the stock card, the movement view and both adjustment forms. Their two variantless exclusions are also NOT interchangeable: the ledger's `variantSku` is `NOT NULL` defaulting to `""` so it takes `{ not: "" }`, `StockMovement`'s is nullable so it takes `{ not: null }`, and only one of the two wrong substitutions is a compile error. `StockMovement` stopped being written entirely when the retirement finished, so its half of this union is a FROZEN pre-retirement archive — it can only fall further behind, and it still cannot be dropped, because the ledger's zero-at-cutover blind spot is equally permanent and nothing will ever fill it. See `docs/FOLLOWUPS.md`.
- Reading an `InventoryValue` row before writing it? OR-tolerance on the READ is not enough — pass the row's id to the mover as `inventoryValueId` so the write provably lands on the row you read, instead of the mover re-resolving the same null/`""` bucket independently. Rows created through the ERP are spelled `null` (`apps/web/lib/items/mutations.ts`), so a strict `findUnique` on a normalised `""` key misses them, and pairing that strict read with an OR-tolerant write is what destroyed the moving average on every receipt of a variantless item: the read found nothing, `previousAvgCost` fell back to 0, and the write then SET `avgCost`/`totalValue` on the real `null` row from that zeroed base — 100 @ 10 then 100 @ 20 ends at 20, not 15. Worst defect on the ledger branch; four fix rounds. `findExistingInventoryValueRow` in `apps/web/lib/inventory/costing.ts` is the ONE spelling of that lookup **inside `apps/web`**, tie-break included — reuse it there, never write a second; the sole straggler is `lib/field-sales/writer.ts`'s `hasInventoryRow`, an existence check that pins no id, and it is a known exception rather than a precedent. `packages/db` cannot import the helper (it sits above `apps/web`), so it carries its OWN copies, and there are more than two — four of them must all match the helper's shape, tie-break included, and move together with it: `stock-balance.ts`'s `moveMainStock` AND `setMainStock`, `sales-return-writer.ts`'s return-accept restore, and `stock-writer.ts`'s `applyJubelioStockAdjustment`. Two further `packages/db` lookups are deliberately NOT that shape and must not be "harmonised" into it — `reservation-writer.ts`'s `findFieldSalesInventory` prefers an EXACT `""` row and only then falls back to `null`, because a bare OR can decrement the sibling row and orphan `reservedQty` on an item carrying both spellings; and `item-price-writer.ts` reads `avgCost` only, item-level with no variant input at all, so it pins no row and needs no tie-break. A missing `orderBy: { id: "asc" }` is the half that reads as cosmetic and is not — four spellings shipped on this branch without it, and because each pins its resolved id into the mover, two paths over one dual bucket can pin DIFFERENT rows and interleave two independent balances under a single ledger key. `moveMainStock`'s `createIfMissing` opens a variantless row spelled `null`, matching `items/mutations.ts` and every other writer that opens one — two specs pin it by name. Spelling it `""` was tried and reverted: it would buy `@@unique([itemId, variantSku])` as a fork guard, since MySQL enforces that constraint for `""` and treats NULLs as distinct, but the price is a second spelling for the same logical row — the phantom-`""` problem these OR-tolerant lookups exist to survive. The concurrent double-create it would have guarded is narrow (the branch only fires when NO row exists under either spelling) and is logged in `docs/FOLLOWUPS.md` instead. See `docs/ARCHITECTURE-NOTES.md`.
- Writing `reservedQty`? A reservation is NOT a stock movement — only `qtyOnHand` is, and a write touching `reservedQty` alone gets no ledger entry, ever. `packages/db/src/reservation-writer.ts` is the single documented exception to the movers, for two reinforcing reasons. Its raw guarded `UPDATE`s are cross-process race guards — `WHERE qtyOnHand >= n` on the field-sales consume, `WHERE (qtyOnHand - reservedQty) >= n` on the konsi reserve — which cannot be expressed as Prisma calls at all. And every `qtyOnHand` write in that file, the one raw statement and the two plain `tx.inventoryValue.update`s alike, decrements `reservedQty` in the SAME statement; splitting that pair to route the quantity half through a mover strands stock reserved against nothing, permanently. It calls `appendStockLedger` by hand instead, once per `qtyOnHand` movement and never for a reservation. Nothing asserts that second half; it is pinned by review only. See `docs/ARCHITECTURE-NOTES.md`.
- Wondering why a no-op wrote a ledger row? NO delta mover has a zero-delta short-circuit — `moveStoreStock` and `moveVanStock` no more than `moveMainStock` — while `setMainStock`/`setStoreStock` both do, and the asymmetry is deliberate: a DELTA mover may still legitimately need to write `avgCost`/`totalValue` when the quantity does not move, whereas a SET that changes nothing has nothing to record. So a no-op Jubelio stock webhook writes a `qty: 0` ADJUSTMENT entry on MAIN, and an unchanged stocktake line writes none. On the STORE side the missing short-circuit is currently not observable: both konsi-retur writers skip a zero line at the CALL SITE before reaching a mover, so the all-zero "lost sack" receive (valid on every line) produces no entry at all — the guard is the caller's, not the mover's, so never state it as a mover behaviour and never claim a store-side zero row exists. Those rows now reach a screen: the store detail card and the movement view both RENDER them rather than filtering them, because a processed document that moved nothing is a real event an operator is entitled to see. Do not harmonise the movers in either direction, and do not add a `qty !== 0` filter to a read surface to tidy them away. See `docs/ARCHITECTURE-NOTES.md`.
- Trusting the balance-write guard to have caught you? It greps for Prisma MODEL calls only and is blind to raw SQL — `reservation-writer.ts`'s own raw guarded `UPDATE`s are invisible to it, matched or not — there are three, of which TWO touch `InventoryValue` (one moves `qtyOnHand` and appends a ledger entry by hand, one moves only `reservedQty` and appends nothing) while the third updates `StockReservation`, which is not a balance table. A new `$executeRaw`/`$queryRaw` that touches `InventoryValue`/`StoreStock`/`VanStock` passes the suite whether or not it appends to the ledger, so it must append by hand at the call site AND be added to the guard's `ALLOWED` list deliberately, with its reasoning written down like every other entry there. Do not widen the regex to chase SQL text — that was considered and rejected as brittle and false-positive-prone.
- Creating a balance row at quantity 0 (a new ERP item, a synced catalog variant, a bootstrap before a lookup)? That is row PROVISIONING, not a movement: it writes no ledger entry, because an opening entry of zero carries no information. The guard exempts it BY PATH, not by shape — so a file that provisions rows has to join `ALLOWED`, and, once there, any real quantity change later added to that same file escapes the guard silently. Keep the provisioning create and the quantity move in different files where you can.
- Supplying `balanceQty` to `appendStockLedger`? Do not copy that read-back into a path whose write already returns the row.
- Decrementing main stock? `moveMainStock` REFUSES a delta that would take `qtyOnHand` below zero and throws `MainStockNegativeError` — the floor is a condition in the UPDATE's own `where`, not an advisory pre-check, because every caller's own guard is computed from a pre-read that the atomic decrement then races. Do not clamp it, do not catch-and-continue, and do not copy the guard onto `moveStoreStock`/`moveVanStock`: a STORE balance goes negative on purpose with a stocktake as the correction path, and main has no such correction. See `docs/ARCHITECTURE-NOTES.md`.

- Building on the store-to-store transfer (`apps/web/lib/stores/transfer/writer.ts`)? Stock moves at APPROVE and only at approve, so a PENDING transfer has moved nothing and cancelling one is a pure status flip with no ledger entry and nothing to reverse — never add a compensating move to the cancel path. See `docs/ARCHITECTURE-NOTES.md`.

Two `Record<DocType, …>` maps must both get it — `apps/web/lib/docNumber.ts` and `apps/web/app/actions/settings/doc-numbers.ts` — missing either only breaks in the Docker build during deploy, which fails the deploy and, through the gated `migrate` job, blocks the migration with it. The Prisma enum widening alone is not enough either: `DocNumberConfig.docType` and `DocumentNumber.docType` are MySQL `ENUM` columns, so the migration also needs TWO `ALTER TABLE … MODIFY docType ENUM(...)` statements widening them — skip those and `generateDocNumber` dies with a data-truncation error the moment the new member is first used. `DocType.SELLTHRU` (the konsi sell-through report, prefix `SLT/`) is the newest instance and paid all four; `DocType.STORETRF` (the store-to-store transfer) was the one before it, and `DocType.BKM` (the store settlement document, prefix `BKM/`) the one before that.

**Konsi sell-through report**

- Touching how a sell-through report picks its ledger window (`apps/web/lib/konsi-sell-through/window.ts`)? Every `STORE` ledger row of the store must fall in EXACTLY ONE report: the window is `(previous boundary, boundary]`, store-scoped, lower edge exclusive and pinned by a test. The boundary is the MAX `createdAt` of the closing stocktake's OWN `StoreStocktake` ledger rows, so it is defined by the rows it must contain and cannot split one approval's rows across two reports — never swap in the stocktake's `approvedAt`, a separate timestamp whose order against those rows depends on write order inside the stocktake writer's transaction. `approvedAt` is only the fallback for a count that changed nothing and so wrote no rows (`setStoreStock` short-circuits). Neither is a commit time: a row's `createdAt` is fixed when its insert runs — Prisma 7 even builds `@default(now())` in the client, one `new Date()` per query — so a transaction still open when a boundary is read can later commit a row stamped at or before it (the race logged in `docs/FOLLOWUPS.md`). A database-side default would not close that gap. The race is closed ONE level deep by carry-forward: `computeLateMovements` (`apps/web/lib/konsi-sell-through/late.ts`) re-derives the PREVIOUS report's window from that report's own inputs and compares the result against that report's stored figures MINUS its stored `late*Qty` columns — what it had itself carried from ITS predecessor. The non-zero per-key differences feed the current derivation as `lateMovements`, each line that received one is flagged `hasLateMovements`, and such a line is kept even when its totals net to zero, since dropping it would lose the late figures and the next report would carry them again. Never compare against the bare totals: every report would then re-bill, negated, whatever its predecessor carried. The previous report's lines and invoice are never modified. A row that commits after TWO reports are approved is caught by neither (logged). A closing count whose boundary precedes the store's earliest `STORE` ledger row is refused `BEFORE_LEDGER_CUTOVER`: its window has no history behind it. Openings are the previous APPROVED report's line `closingQty`, never a scan for the last `balanceQty`, so each report opens exactly where the last one closed. See `docs/ARCHITECTURE-NOTES.md`.
- Cancelling a sell-through report, or adding any path that retires one? `stocktakeKey` (the closing stocktake's id) and `chainKey` (`${storeId}:${previousId ?? "root"}`) are the LIVE uniqueness keys, non-null only while the report is not cancelled — one live report per count and one live successor per report, which is what makes one-DRAFT-per-store structural under concurrent creates rather than a pre-check. `cancelSellThrough` nulls BOTH in the same CAS; a retire path that nulls only one strands either the stocktake or the store's chain slot for good, with no screen that can free it. `closingStocktakeId` and `previousId` stay behind as history, and neither is a relation — plain ids (only `closingStocktakeId` is indexed), so there is no 1:1 delete emulation to order a teardown around. See `docs/ARCHITECTURE-NOTES.md`.
- Adding a store-side `StoreStock` writer, or giving one a new `refType`? `deriveSellThroughLines` (`apps/web/lib/konsi-sell-through/derive.ts`) classifies every `STORE` ledger row in the window through an explicit `refType` switch and REFUSES anything it does not name, surfacing as `UNKNOWN_REF_TYPE` — deliberately, since the registry is exhaustive over the union and not over the column, and a skipped movement would misstate a billed quantity. Nothing compiles against that switch, so the new writer ships green and then every sell-through report at a store it touched refuses to create or approve. Decide whether the movement is in, out, sold or gap and add its case in the same change. See `docs/ARCHITECTURE-NOTES.md`.
- Setting `Store.sellThroughMethod`? KONSI-only, refused at the write boundary (`assertValidSellThroughMethod` in `apps/web/lib/stores/queries.ts`) — including a KONSI → PUTUS edit still carrying one: the writer refuses and never clears it silently, and the store form normalises it on submit the way it does `priceDiscountPercent`. A report snapshots the method at creation into `KonsiSellThrough.method`, and the hold, the resolution rules and approve all read THAT, never the store's current setting — re-reading the store would let an edit made while a report is DRAFT flip its held lines billable. `updateStore` also refuses KONSI → PUTUS while the store has a DRAFT report (`StoreHasDraftSellThroughError`), and approve re-checks the store is still KONSI (`NOT_KONSI`) — keep both, since a PUTUS store's DRAFT could otherwise never be approved. See `docs/ARCHITECTURE-NOTES.md`.
- Approving a sell-through report, or building a screen that predicts one? Approve RE-DERIVES every line inside its own transaction and refuses `STALE` on any difference from the stored figures; the remedy is cancel and recreate, never an in-place refresh, so an approved report always shows what the admin reviewed. It re-checks `NOT_KONSI`, `RETUR_IN_FLIGHT` and `TRANSFER_IN_FLIGHT` before that and `HELD` only after it, and its re-derivation includes the carry-forward, whose late figures are part of the `STALE` comparison — never move the hold ahead of the re-derivation, or an admin resolves lines on a report that must be cancelled anyway. It moves NO stock (the stocktakes already SET the balance) — do not add a mover to it. It DOES move money: approving IS invoicing, and it is the only invoice path for a konsi store — never add a second one. `INVOICE` mode prices every line, stamps the invoice date, the due date (invoice date + `Store.paymentTempo` days), the total and the salesman on the report and `unitPrice`/`lineTotal` on each line, and creates the `Receivable` and `TaxInvoice` only when the total is above zero; `BASELINE` mode is for a store's FIRST report only (`previousId` null, else `BASELINE_NOT_FIRST`), needs a reason and bills nothing — no receivable, faktur or journal. That is true of the MODE and not of the `baseline` column: the migration marked every report already `APPROVED` before invoicing existed as a baseline, first or not, and their billed units were not necessarily billed by hand — so never read `baseline: true` as "first report" or as "invoiced outside the ERP". The revenue, COGS and shrinkage journals (`KONSI_SELLTHRU_REVENUE`/`_COGS`/`_SHRINKAGE`, all dated on the invoice date) are posted by `approveSellThroughAction` AFTER the writer commits, each through `postArJournalSafely`, and one still owed is retried from the report's own page, never the piutang detail. The retry and the page's pending banner are gated on the owed journal being MISSING (`sellThroughJournalGaps`, `journal.ts`), not on a `JOURNAL_PENDING` flag — a flag never clears, so the banner would outlive a successful retry, and a crash between the commit and the posts writes none, so no retry would ever appear. That gate is safe here only because every report approved before invoicing existed is a baseline and owes nothing; never copy it onto the delivery retry, whose backfilled receivables have no journal by construction. Its rules have one spelling each: the create preconditions are `checkSellThroughPreconditions` (`writer.ts`), run by both `createSellThrough` and the read-only `getSellThroughEligibility`; the gap-sign → resolution arms and the needs-a-reason rule are `resolutionArmsFor`/`resolutionNeedsReason` (`derive.ts`), read by the writer and the detail screen; the price is `priceSellThroughLines` (`pricing.ts`), run by approve and by the DRAFT preview; and who may own the receivable is `SALESMAN_CANDIDATE_WHERE` (`salesman-candidates.ts`), read by the dialog's list and the writer's check. Never restate any of them beside a caller. See `docs/ARCHITECTURE-NOTES.md`.
- Adding a `SellThroughErrorCode`? The code is passed to the screen as-is with no exhaustive `Record`, so nothing fails to compile — a missing string renders the raw key. A code the CREATE path can raise needs copy in BOTH locales under TWO namespaces: `konsiSellThrough.err.<CODE>` for the report's own screens, and `storeStocktakes.detail.sellThrough.reason.<CODE>` for the create button on the stocktake detail page, which renders precondition refusals and create failures alike. The second is the one that gets missed — it already was once, caught in review.
- Adding a sell-through approve refusal? It needs `konsiSellThrough.err.<CODE>` in BOTH locales. The invoicing codes (`UNPRICED`, `INVALID_INVOICE_DATE`, `SALESMAN_REQUIRED`, `SALESMAN_INVALID`, `BASELINE_NOT_FIRST`, `BASELINE_REASON_REQUIRED`) have NO key under `storeStocktakes…` on purpose — the stocktake page creates reports and never approves one, and only approve raises them; do not add one to complete a pair. That does not extend to every code approve can raise: `HELD` and `STALE` do carry keys there. A code whose `detail` carries data rather than copy also needs its own branch in `errorMessage` (`SellThroughDetailClient.tsx`), whose generic arm interpolates `detail` raw: `UNPRICED`'s detail is the refused lines' comma-joined `itemId::variantSku` keys, named back as products through `productNamesForKeys`.
- Pricing a sell-through line? The invoice bills the item's CATALOG selling price. `priceSellThroughLines` (`apps/web/lib/konsi-sell-through/pricing.ts`) does not call `computeStorePrice` and never reads `Store.markupPercent`: the markup prices what the store's own customer pays at the SPG POS, and the store keeps the markup, so it never reaches the invoice — and a KONSI store with no markup still invoices. A line is UNPRICED only when its item has no usable selling price; approve refuses `UNPRICED` naming every billed line it could not price, and the remedy is setting the selling price and approving again — approve and the DRAFT preview both reprice live, so unlike `STALE` no cancel is needed. Never route the invoice back through `computeStorePrice`'s KONSI branch: it would bill the store its customer's marked-up price. See `docs/ARCHITECTURE-NOTES.md`.
- Creating a sell-through report, or changing how returns settle at a KONSI store? A retur takes its goods off the shelf when raised but `StoreStock` drops only later — at approve for a FIELD retur, at receipt (plus an approve-time delta) for an ADMIN one — so `RETUR_IN_FLIGHT` refuses a closing count when any retur of the store (either origin) was raised on or before the count moment (`countFinishedAt ?? approvedAt`) and is still pending OR was approved only after that moment. Never narrow it to the pending statuses: approving the retur later does not clean a count that missed those units. The remedy is a later count, whose rows net the contaminated one out. `TRANSFER_IN_FLIGHT` (`assertNoTransferInFlight`, beside it, run from the same two places) refuses while a PENDING store transfer touching the store — from it or to it — and moving an item::variant the closing count COUNTED has `movedAt` ≤ the count moment. It deliberately has NO approved-later arm: an approved transfer's ledger rows sit inside the window and the stocktake exclusion kept `StoreStock` right, so the report derives the move as in/out with no gap. Never copy the retur's `approvedAt > countMoment` arm across. Its remedy differs from the retur's too: such a transfer can no longer be approved (`COUNTED_SINCE_MOVE`), so it is cancelled, the move stands in the count as variance, and it is raised again for any keys the count did not count, or with the real move time if the goods moved after the count. Its copy lives in both namespaces, like every create-path `SellThroughErrorCode`. See `docs/ARCHITECTURE-NOTES.md`.

**Field sales — retur, konsi, nota, faktur**

- Adding a `FieldReturnStatus` member? FOUR separate `Record<FieldReturnStatus, …>` maps exist across the backoffice clients, and a missing one only breaks in the Docker build, failing the deploy. (Same shape as the two `DocType` maps in § Code conventions — including the fact that since `604a877` the gated `migrate` job means a broken build blocks the migration rather than trailing it.)
- Adding a `FieldReturnErrorCode`? `ERROR_CODE_MAP` in `apps/web/app/actions/field-returns.ts` is a `Record<FieldReturnErrorCode, …>` that must stay exhaustive too — a code added to `errors.ts` without a matching entry here only breaks in the Docker build, failing the deploy. Third instance of this exact shape (the two `DocType` maps, the four `FieldReturnStatus` maps above, now this) — treat it as a pattern, not a coincidence, whenever you touch an enum anywhere near field returns.
- Raising an ADMIN-origin field retur? The nullable `notaPhotoUrl`/`notaPhotoR2Key`/`transport` columns are a widened COLUMN, not a relaxed rule — `createFieldReturn` still requires all three for a FIELD-origin return, enforced in the writer per `origin`, because every `"use server"` export is independently callable and a form omission is not a database guarantee.

- Resolving a retur mismatch? Variance direction is enforced in the WRITER, not the UI — every `"use server"` export is an independently callable endpoint, so the UI withholding a control is not a guarantee.
- Rendering a retur value? `unitPrice` is a rounded 2dp REFERENCE figure and does not multiply back — `lineValue`/`totalValue` are the only authoritative figures; a partly PRICED `totalValue` is `null`, never a partial sum (unrelated to a partly DRAWN retur, which has a real `totalValue` and a non-zero `appliedValue` — see the draw-down entries below).
- Editing `lib/field-sales/retur/variance.ts`? Deliberately import-free because a `"use client"` component imports it — one import drags the `@elorae/db` barrel (Prisma + the mariadb driver) into the browser bundle. `pricing-rules.ts` beside it is import-free for a DIFFERENT reason: no client component imports it today, and the rule is kept as cheap insurance against one ever doing so.
- Adding a doc-number sequence for a new register? Take your own `DocType` — field retur takes `FIELDRET`, NOT the vendor-return `RET`; sharing a counter interleaves two registers and lets a Settings prefix edit renumber the other one.
- Touching `recordFieldSalesDelivery`? It creates exactly one `TaxInvoice` per nota tagihan inside its own serializable transaction — the finance queue is keyed on the nota being ISSUED, not printed, so a delivery written without that row is invisible to finance and fails closed and silent.
- Changing the konsi approve path? An already-APPROVED order must REFUSE a payload carrying admin-added lines rather than returning its idempotent `ok` — returning `ok` reports a success that created nothing.
- Wondering why a store stops getting konsi suggestions for an item it used to carry? `listKonsiSuggestions`'s never-sent exclusion (`sentItemIds`) is PERMANENT once the item has appeared on any non-rejected konsi order line that is not fully cancelled, even after that store's `StoreStock` drops to zero — that silence is why `StoreAssortmentLine` exists: an assortment gap catches exactly the case never-sent can't, and it gates nothing (advisory only, no push transfer of its own). See `docs/ARCHITECTURE-NOTES.md`.
- Reading or writing an assortment-gap test? On-hand is physical `StoreStock` PLUS the store's open (approved, not yet delivered) konsi qty (`qty − deliveredQty − cancelledQty` over its `APPROVED` konsi lines, packed or not) from `openKonsiQtyByKey` (`apps/web/lib/field-sales/konsi-open-qty.ts`) — konsi stock reaches `StoreStock` only at shipment completion, so a `StoreStock`-only test calls goods on a truck a gap and invites sending them twice. BOTH gap tests — `listAssortmentGaps` and the approve-time `currentAssortmentGapKeys` behind the `ALREADY_SENT` exemption — go through that one helper so they cannot disagree; a third must too. Keep the two figures apart: `AssortmentGapRow.onHandQty` stays PHYSICAL and the open qty rides separately as `inTransitQty`, summed only inside the gap test and rendered as a muted "+N on order, not yet delivered" hint — never fold it into `onHandQty`, which is the figure a store keeper checks against the shelf. See `docs/ARCHITECTURE-NOTES.md`.
- Touching `Store.priceDiscountPercent`, `Store.markupPercent`, or an SPG/van sale price? The two sale writers price differently. `apps/web/lib/spg/sale-writer.ts` prices with the store's REAL `termsType` through `spgUnitPrice` (`apps/web/lib/spg/pricing.ts`): a KONSI store charges `sellingPrice × (1 + markupPercent/100)`, a PUTUS store its list price less its discount, and a KONSI store with a missing or invalid markup refuses `NO_PRICE` rather than selling at the catalog price. The SPG catalog preview (`getSellableCatalogForSpg`) prices through the same helper over the same `SPG_STORE_PRICING_SELECT` — never change one without the other; the preview is what the SPG collects cash against. `apps/web/lib/canvassing/sale-writer.ts` (van) still hardcodes `termsType: "PUTUS"`, discount included, even at a consignment store — so a KONSI store holding a discount would silently discount its van sales, which is why the write boundary refuses a non-null discount on a KONSI store rather than trusting `termsType` alone. Validating a markup? `isValidMarkupPercent` in `@elorae/db/pricing` is the one spelling of the rule — the KONSI pricing branch, the SPG POS's `isSpgStoreMarkupMissing`, the store write boundary (`InvalidMarkupPercentError`) and the konsi order screen all call it — and `MARKUP_PERCENT_MAX` beside it is the one spelling of the ceiling, which the store form's input also reads; never restate either. `Store.markupPercent` is still physically the column `marginPercent` behind `@map`, so raw SQL must say `marginPercent`. Adding another `computeStorePrice` call site? Both percent params are required on purpose, but a `select` that omits a column still compiles and hands over `undefined`: a missing `markupPercent` comes back flagged at the catalog price, so any caller that charges it must refuse on `flagged` (the SPG path does; konsi approve's informational line value deliberately does not), while a missing `priceDiscountPercent` still makes the PUTUS branch return NaN (`roundCents(sellingPrice * (1 - NaN))`), dying at the Decimal write rather than pricing at full list. See `docs/ARCHITECTURE-NOTES.md`.
- Touching `VanSale`/`SpgSale` `total` or `subtotal`? They mean different things on purpose — `subtotal` is the exact 2dp line sum, `total` is that sum rounded half-up to WHOLE rupiah via `roundToWholeRupiah` (`packages/db/src/pricing.ts`), because sen do not exist as physical cash. Payment (`amountPaid`/`cashReceived`) is compared against `total`, never `subtotal`. `VanSellShell`/`SpgSaleShell` derive their own preview total from the SAME helper — a shell that recomputes its own rounding recreates the preview-vs-writer mismatch this file's discount landmine already names twice. This is a behaviour change on a shipped path wherever `Item.sellingPrice` itself is fractional (`Decimal(14,2)` permits it) independent of any discount. See `docs/ARCHITECTURE-NOTES.md`.
- Widening `PaymentMethod`? It costs FOUR edits beyond the enum, and it has now been widened twice. TWO `ALTER TABLE … MODIFY` statements, because `Payment.method` and `CollectionSubmission.method` are separate MySQL `ENUM` columns over the one Prisma enum and widening either alone truncates the other on write — and the collector's submission path must independently refuse the new member in its OWN writer, not only at the action boundary, or a collector could submit a claim that posts a revenue reversal with no retur behind it. `debitRole` in `payment-journal.ts` is the single journal seam (widen it there and the void reversal is correct for free; never mint a second `sourceType`), each new role also needing a `POSTING_ROLES` + `POSTING_ROLE_ACCOUNT_TYPES` entry and `role.*`/`desc.*` copy in both locales. `RecordPaymentInput["method"]` in `payment-writer.ts` is a HAND-WRITTEN union the Prisma widening does not touch — a compile error, so the cheap one. And the payments list absorbs a new member SILENTLY, in TWO places. Every label site spanning the FULL union goes through `lib/finance/ar/payment-method-display.ts`, whose exhaustive `Record` turns a new member into a compile error rather than a wrong-but-plausible label, plus a locale key in each of the `payments` and `piutang` namespaces in both files — but a map over a NARROWER closed set is a deliberate exception, not a miss to fix: `COMPONENT_METHOD_LABEL_KEY` in `SettlementApprovalClient.tsx` is exhaustive over only the four methods a settlement component can post as and reads its copy from the `financeStoreSettlements` namespace, so folding it in would both widen it past what that document can produce and point it at the wrong strings. The FILTER control is the half that stays silent even with the label map in place: derive its `<SelectItem>`s from `PAYMENT_METHOD_VALUES`, as `PaymentsPageClient.tsx` now does — a hand-listed set labels and parses a new member correctly and leaves it unfilterable, with nothing type-checking the list. See `docs/ARCHITECTURE-NOTES.md`.
- Touching `voidPayment`? It RE-PROJECTS the retur a `RETUR_OFFSET` payment drew from — `projectReturnOffset(fieldReturnId, tx)` inside its own transaction, and `tx` is load-bearing because that helper opens its OWN `runSerializable` when handed no client; zero effect the normal (cash) case. It deliberately does NOT null `Payment.fieldReturnId` — the link is history, like the allocations and the receipt journal. Every early return added to that callback must stay write-free. See `docs/ARCHITECTURE-NOTES.md`.
- A `FieldReturn` that approved with `valuationStatus: PENDING` can never be offset — post-approval repricing is refused (`ALREADY_APPROVED`), so this is terminal, not "not yet". See `docs/ARCHITECTURE-NOTES.md`.
- Adding a retur-offset-adjacent error code? It belongs on `PaymentErrorCode`/`PaymentActionReason`, never on `FieldReturnErrorCode` — `ERROR_CODE_MAP` in `app/actions/field-returns.ts` is deliberately unaffected by this feature. See `docs/ARCHITECTURE-NOTES.md`.
- Wondering why an available retur credit doesn't reduce `computeStoreCreditExposure`? By design — no `Receivable` has changed and no journal exists yet, the same reasoning that already excludes a pending `CollectionSubmission`. See `docs/ARCHITECTURE-NOTES.md`.
- Reading a retur's spendable credit? It is `totalValue − appliedValue`, never `totalValue` — a retur is drawn down in PARTS now and stays `AVAILABLE` with `appliedValue > 0` between draws, so `offsetStatus` alone no longer tells you how much is left. All SEVEN read surfaces already carry the subtraction (`listOffsettableReturns`, `listAllOffsettableReturns` (the unpaged store-scoped sibling the settlement screen uses — `listOffsettableReturns` caps at 25 and silently drops the rest), `getStoreAvailableCredit`, `getStoreAvailableCreditMap`, `suggestOffsetAllocations`, `listFieldReturns`, `getFieldReturnById`); a NINTH left on `totalValue` overstates the store's credit and invites a draw the writer refuses. **One documented EXCEPTION, and only one:** `SettlementReturDetail.remaining` (the settlement approval preview, `lib/finance/ar-settlement/queries.ts`) is the eighth surface and deliberately computes `totalValue − Σ(POSTED payments carrying the retur)` instead — it mirrors the approval writer's own `RETUR_OVERCLAIMED` ceiling, which reads the payments, and survives the projection lag between a draw committing and `projectReturnOffset` landing. Do not "fix" that one back onto `appliedValue`; do not copy its formula onto any other surface. See `docs/ARCHITECTURE-NOTES.md`.
- Never hand-increment or hand-decrement `FieldReturn.appliedValue`. It is a PROJECTION of the POSTED payments carrying that `fieldReturnId`, written by `projectReturnOffset` as a plain SET — which is exactly what makes it idempotent across replays, crashes and voids. Treating it as a reservation (CAS it, then post the payment) was designed and REJECTED as unfixable, not merely skipped. See `docs/ARCHITECTURE-NOTES.md`.
- Calling `applyReturnOffset`? The `eventId` is the CALLER's to keep stable across retries of ONE logical draw — the key is `returoffset-<returnId>-<eventId>`, and both failure directions are silent: a fresh id per attempt DRAWS THE RETUR AGAIN instead of replaying, a reused id hands back the earlier payment and draws nothing while reporting success. Backoffice sheet mints a `useState` UUID reseeded per open (never `useMemo`); a settlement caller passes the deduction row's id. See `docs/ARCHITECTURE-NOTES.md`.
- Posting a `RETUR_OFFSET` payment from a NEW caller? Pass `fieldReturnId` into `recordPayment` — the over-draw ceiling (`EXCEEDS_REMAINING`, plus the retur's own `WRONG_STORE`/`NOT_VALUED` guards) lives INSIDE that serializable transaction and is skipped entirely when the field is absent, so a caller that stamps the link afterward instead can over-draw a retur with nothing refusing it. See `docs/ARCHITECTURE-NOTES.md`.
- Gating a retur-offset control on a prior VOIDED draw? Don't — `hasVoidedOffsetAttempt` is gone and re-application after a void WORKS now (new event, new key, fresh payment). The old gate's premise is false, and reinstating it permanently bricks any retur that ever had a draw voided. `PAYMENT_VOIDED` survives only for a replay of the SAME `eventId`. See `docs/ARCHITECTURE-NOTES.md`.

**Delivery shipments**

- Touching anything called a "delivery"? TWO tables mean it — `DeliveryShipment` is the logistics event (`PACKED → IN_TRANSIT → DELIVERED`), `FieldSalesDelivery` stays the accounting event, and a PUTUS completion calls the latter with the DELIVERED, never the planned, quantities — that substitution IS the partial-refuse mechanism. A KONSI completion writes no `FieldSalesDelivery` at all; it issues a `KonsiTransfer` for the delivered qty instead. Both also draw `docNo` from the same `DELIVERY` counter. See `docs/ARCHITECTURE-NOTES.md`.
- Completing a KONSI shipment? It MOVES STOCK — `completeDeliveryShipment`'s konsi branch is ONE `runSerializable`: the `IN_TRANSIT` status CAS first, then `DeliveryShipmentLine.deliveredQty`, `issueKonsiTransfer` for the lines with `deliveredQty > 0` (an all-zero completion writes no transfer), the order lines' `deliveredQty` increment and the order's `deliveryStatus`. Unlike the putus two-transaction tail it is atomic, so every failure inside it must THROW. It writes no `FieldSalesDelivery`, no `Receivable`, no `TaxInvoice` and no journal, returns `deliveryId: ""`, and takes no invoice/due dates on either method (`MISSING_DATES` is PUTUS-only, at ship and at completion). Every refusal `issueKonsiTransfer` raises is mapped by `instanceof` inside that transaction — `KonsiTransferReservationMismatchError` → `KONSI_NOT_RESERVED`, `MainStockNegativeError` → `DeliveryError` `INSUFFICIENT_STOCK`, `InventoryValueMissingError` → `NO_INVENTORY_ROW` — and all are terminal in the offline completion classifier; a new refusal the transfer can raise needs the same mapping, or it leaks as `UNEXPECTED` and the offline queue retries it to its ceiling. See `docs/ARCHITECTURE-NOTES.md`.
- Copying the POD gate's shape onto another proof check? `completeDeliveryShipment`'s `MISSING_PROOF` is this codebase's FIRST hard-blocking proof gate — every sibling (`StoreVisit.checkinOutOfRadius`) warns and never blocks, so don't harmonise the two in either direction. See `docs/ARCHITECTURE-NOTES.md`.
- Building a new caller on `completeDeliveryShipment`? It posts NO journals (`completeShipmentAction` does, after it returns, guarded on a non-empty `deliveryId`) and it throws TWO error classes — `DeliveryShipmentError` plus `DeliveryError`, which comes from `recordFieldSalesDelivery` on the putus path and from the konsi branch's own mapping of `MainStockNegativeError` to `INSUFFICIENT_STOCK` — overlapping code strings, different `instanceof`. See `docs/ARCHITECTURE-NOTES.md`.
- Editing `completeDeliveryShipment`'s PUTUS two-transaction tail? - Writing to `Receivable.paidAmount`/`outstandingAmount`? Atomic `increment`/`decrement` only, inside the payment/void transaction — never read-modify-write. Same rule as `InventoryValue.reservedQty` above. See `docs/ARCHITECTURE-NOTES.md`.
- Reading what backs a `Receivable` or a `TaxInvoice`? Never traverse `receivable.delivery` or `taxInvoice.delivery` directly — select `RECEIVABLE_SOURCE_SELECT`/`TAX_INVOICE_SOURCE_SELECT` and go through `resolveReceivableSource`/`resolveTaxInvoiceSource` (`apps/web/lib/finance/ar/receivable-source.ts`), because either model now comes from a putus `FieldSalesDelivery` OR a `KonsiSellThrough` report and each of the two relations may be null. Two halves the compiler does not cover. And a `deliveryId` scalar filter still compiles, which is right only on a path that is delivery-specific by nature — the delivery date correction, the nota-print CAS, `suggestOffsetAllocations`' walk from a retur's priced delivery lines. The faktur list sorts on `createdAt desc, id desc`, which is issue order for both sources — never put it back on `delivery.invoiceDate`, which a sell-through faktur has no value for. The third is still LIVE and still yours: any edit or resubmit path added later must give BOTH claim aggregates an explicit `settlementId: { not: … }` or the document refuses itself against its own rows. See `docs/ARCHITECTURE-NOTES.md`.
- Touching the settlement `draftId`? It is the document's identity before the row exists — the R2 evidence key prefix AND the submit idempotency key — so it must be caller-stable (`useState(() => crypto.randomUUID())`, never `useMemo`) and UUID-shaped, or a retry both strands the uploaded evidence under a stale prefix and duplicates the document. A collision from a different salesman or store is `DRAFT_ID_CONFLICT`, never a handed-back replay. See `docs/ARCHITECTURE-NOTES.md`.
- Changing the settlement admin fee, or the settlement preview? The fee is charged on the NETTED base (`invoices − retur − program`), never the gross, and `lib/finance/ar-settlement/calc.ts` imports nothing from `@elorae/db` but `roundCents` (via the `@elorae/db/pricing` subpath, never the barrel) because the `"use client"` form imports it directly for the live preview — a screen that recomputes its own total recreates the preview-vs-writer mismatch this index already names twice. See `docs/ARCHITECTURE-NOTES.md`.
- Gating anything settlement-shaped? TWO permissions, and they are not interchangeable. **Filing** — the PWA screen `/pwa/pelunasan/[storeId]`, `submitStoreSettlementAction`, the proof-upload route, and the amplop's Settle button that leads to them — runs on `settlements:submit` (SALESMAN + COLLECTOR + ADMIN-by-convention), NOT `collections:collect`; a control gated on anything but what the next screen enforces renders for a role that screen refuses. **Approving** — `/backoffice/finance/pelunasan` list and detail, `approveSettlementAction`, `rejectSettlementAction`, the nav entry — runs on `collections:manage`, reused deliberately rather than minting a `settlements:approve`, which is why this needed no new seed and is ADMIN-only. Both are seeded on prod as of 2026-09-06 (`packages/db/prisma/seed-settlements-permission.sql` for the first; `collections:manage` predates it), so neither is a live-prod trap any more — a fresh environment or test bed still has to seed the first by hand. **One deliberate exception, and it is a READ surface, not a control:** `/pwa/bkm/[settlementId]` admits EITHER permission, narrowing a `settlements:submit`-only holder to settlements whose `salesmanId` is their own — see the BKM entry below. See `docs/ARCHITECTURE-NOTES.md`.
- Turning the settlement approval queue on in a fresh environment, or on prod for the first time? No RBAC seed is needed (it reuses `collections:manage`), but the two posting roles `TRADE_PROGRAM_EXPENSE` and `ADMIN_FEE_EXPENSE` have NO `JournalAccountMapping` row and nothing on the deploy path creates one — the role column is a plain `String`, so there is no migration and no seed file to run; finance maps both to a `BEBAN` account in Settings → Account Mapping. Skip it and the first approval carrying an admin fee (essentially every settlement) has `resolveAccount` throw `UnmappedRoleError`, degrading that payment's journal to `JOURNAL_PENDING` and needing a hand-mapping plus a retry — the settlement's own approval screen names the unmapped role and links to the mapping page, so that is the fastest route back. AR and the payments are unaffected; only the GL leg waits. See `docs/EPIC-STATUS.md` and `docs/FOLLOWUPS.md`.
- Adding a `SettlementErrorCode`? Nothing breaks, on purpose — there is deliberately no exhaustive `Record` anywhere on this path, so an operator-fixable code with no `REASON_KEY` entry in `SettlementForm` and no `en.json`/`id.json` key just shows the salesman a generic failure. There are THREE surfaces to add it to now, not one: `REASON_KEY` on the salesman's form, `financeStoreSettlements.err.<CODE>` in BOTH locales for the finance queue (whose `errorMessage()` falls back to `err.UNEXPECTED` via `t.has`), and — if it is a check the queue previews — the `SettlementCheckReason` `Extract<>` union in `lib/finance/ar-settlement/checks.ts`. See `docs/ARCHITECTURE-NOTES.md`.
- Reading a `StoreSettlement` as money moved? Read its STATUS first — the two answers are opposite. A `PENDING` settlement posts no journal and touches no `Receivable`; its retur/invoice claims reserve only against other settlements. An `APPROVED` one has already posted one `Payment` per retur deduction row PLUS up to three more — trade-program, admin fee, cash — and decremented AR through each of them; `RETUR_OFFSET` is one of the four component KINDS, not a fourth singleton standing beside the draws. It has NOT necessarily had a `PAYMENT_RECEIPT` journal posted per payment, and TWO different failures look identical from the `Journal` table: a crash between the status flip and the action's loop leaves payments with no journal AND no `JOURNAL_PENDING` flag (so the payment detail page offers no retry either), while a REFUSED post leaves no journal but DOES write a flag, because `postArJournalSafely` degrades a failing builder rather than throwing. The approval screen detects the missing journal either way and offers a re-post, but the re-post only repairs the crash case — against a refusal it hits the same refusal and `alreadyFlagged` dedups the notification, so the screen names the flagged reason and role and links to Settings → Account Mapping instead of implying the button is the fix. Do not "simplify" the alert back to the crash-window reading: an unmapped posting role is the documented day-one state, not the rare one. A settlement stranded `PENDING` may ALSO have real payments behind it — approval is a resumable sequence, not a transaction, so a crash mid-run leaves committed components under a still-`PENDING` document. A pending `CollectionSubmission` and a pending settlement can also both stand against one invoice: the two writers do not net each other. See `docs/ARCHITECTURE-NOTES.md` and `docs/FOLLOWUPS.md`.
- Approving a settlement, or building any new caller of `approveSettlement`? It is a RESUMABLE SEQUENCE, not a transaction — `recordPayment` and `applyReturnOffset` self-transact, so nesting them is unsafe, and what makes a crash safe is that every component's idempotency key is deterministic (`settlement-<id>-<PAYMENT_METHOD>`, and `returoffset-<returnId>-<deductionRowId>` for a draw, which reproduces the key `applyReturnOffset` mints itself). The status flip is LAST and is a CAS `updateMany` on `status: "PENDING"`; the writer posts NO journals, so a caller must loop `postArJournalSafely` over EVERY id in `paymentIds`, never just the first. It throws TWO error classes with overlapping code strings — `SettlementError` and `recordPayment`'s `PaymentError` — so discriminate on `instanceof`, never on the code string. See `docs/ARCHITECTURE-NOTES.md`.
- Resuming a half-posted approval, or "optimising" its component loop? A retur component must RE-ENTER `applyReturnOffset` even when its payment already exists — that writer's replay branch is what re-runs `projectReturnOffset`, and skipping it leaves the retur drawn with `appliedValue` stale at 0 and `offsetStatus` still `AVAILABLE`, permanently, which then overstates that retur's headroom at SUBMIT time for every later settlement. It takes no process kill to reach: a P2034 after `withRetry` exhausts is enough. The skip is correct ONLY for the cash/program/fee components, because `recordPayment` projects nothing onto any other row. See `docs/ARCHITECTURE-NOTES.md`.
- Adding or tightening a re-validation in `approveSettlement`? Scope it to what THIS settlement still owes, or you make a resume impossible. Checking "every selected receivable is still open" literally — the obvious reading, and the one the design called for — refuses the retry the moment one of this document's own posted components has paid a receivable off: money moved, document `PENDING` forever, no path out but hand SQL. Collectibility is exempted on TWO terms — a receivable this settlement has already allocated against (`settlementAllocated > 0`) OR one whose agreed share is spent (`agreedRemaining <= 0`) — and `agreedRemaining` ALONE is not enough: when `StoreSettlementInvoice.amount` exceeds the live balance, one component closes the receivable with the agreed share still partly unspent and the resume throws `NOT_OUTSTANDING` forever. Never collapse the pair into "skip when the effective headroom is 0", which also skips a receivable some OTHER channel closed and re-diagnoses it as `COMPONENT_EXCEEDS_HEADROOM`. It must also run BEFORE the `totalOwed > totalHeadroom` comparison (a receivable closed elsewhere also leaves zero headroom, so the other order misdiagnoses it as an allocation shortfall); existence and store ownership stay unconditional. Both pre-flights count only components that have not already posted. See `docs/ARCHITECTURE-NOTES.md`.
- Mapping a `SettlementDeductionType` to a `PaymentMethod`? Use `DEDUCTION_TYPE_TO_PAYMENT_METHOD` in `approve-writer.ts`, never a cast — two of the three spellings coincide and `PROGRAM` → `PROGRAM_DEDUCTION` does not, so `deduction.type as PaymentMethod` compiles, passes review, and then dies at the MariaDB `ENUM` column mid-approval with earlier components already posted. See `docs/ARCHITECTURE-NOTES.md`.
- Hitting `OVER_TENDER`, or offering an override to clear it? You cannot — it is one-directional by design. A store handing over MORE than expected can never allocate (components sum past the invoices' headroom and there is no unapplied-credit concept), so the check runs AHEAD of the override gate on purpose and the remedy is reject-and-refile. Never widen the override path to cover it, and never let the copy suggest one. An under-tender is the opposite: legitimate, and exactly what the tolerance and the override reason are for. See `docs/ARCHITECTURE-NOTES.md`.
- Touching the settlement variance tolerance? The `SystemSetting` key is `settlement.varianceToleranceRupiah`, parsed by the import-free `lib/finance/ar-settlement/variance-tolerance.ts`, and its "fail-open" is STRICTER, not looser — the default is 0, so malformed config demands an override reason more often, never less. The `Number.isFinite` check after the regex is load-bearing (`"9".repeat(400)` matches `\d+` and would parse to `Infinity`, disabling the gate). Nothing seeds the row and there is no settings screen for it. See `docs/ARCHITECTURE-NOTES.md`.
- Writing an audit row for a settlement decision? It goes INSIDE the writer's own transaction, never in the action — the action-layer placement makes the gap UNRECOVERABLE, because an approve retry lands on the write-free `alreadyApproved` branch and a reject retry throws `NOT_PENDING` over an already-successful rejection. `SETTLEMENT_VARIANCE_OVERRIDE` is a separate third row written only when an override was needed, and it is the ONLY record of why a flagged settlement was approved — `StoreSettlement` has no `overrideReason` column, so any screen showing the reason must read that row. Cap every reason at 191: `AuditLog.reason` is a bare `String?`, i.e. `VARCHAR(191)`. See `docs/ARCHITECTURE-NOTES.md`.
- Rendering a settlement's expected or variance figure — on screen or on the PRINTED BKM? Derive it through `computeSettlementTotals`, never read `StoreSettlement.expectedAmount`/`varianceAmount` — the writer never reads or reconciles those stored columns, so a screen trusting them renders a document as balanced and then watches approval refuse it, and a RECEIPT trusting them is worse still because the store keeps the paper. Same rule for the checklist's arithmetic and idempotency keys: call `approve-writer.ts`'s FOUR shared exports — `computeComponentHeadroom`, `returComponentKey`, `simpleComponentKey` and the type `InvoiceRow` — rather than a second copy, and do not strip those `export`s in a tidy-up. Its other two `export`s, `SettlementPaymentMethod` and `HeadroomRow`, are imported by NOTHING and are not a seam: `checks.ts` restates `HeadroomRow`'s shape structurally (`{ receivableId; agreedRemaining; settlementAllocated }`) to stay import-free of the writer, so nothing type-checks the two declarations against each other and a field renamed on one side leaves the other compiling against its own copy while the screen previews different arithmetic. Same fork shape as `EPSILON` below — change one, change the other in the same commit. `EPSILON` is NOT one of them and never was: it lives in `lib/finance/ar-settlement/calc.ts`, and all four consumers (both writers, `queries.ts`, `checks.ts`) import it from there. The way it forks is a tidy-up in `calc.ts` — moving it "closer to its user" or inlining `1e-6` at one call site — because nothing type-checks two separately declared constants against each other, and the symptom is a screen and a writer disagreeing about a sub-cent margin. `calc.test.ts` pins the value for exactly that reason. See `docs/ARCHITECTURE-NOTES.md`.
- Removing the Print BKM button from `/backoffice/finance/pelunasan/[id]` because the PWA route already prints one? Don't — that button is finance's ONLY path to a BKM. `pwaAccessGuard` redirects any wildcard holder to `/backoffice` before the permission check runs, so an ADMIN can never open `/pwa/bkm/[settlementId]` however it is seeded (same fact that makes an admin account useless for verifying the amplop seed). It renders on a REJECTED settlement too, deliberately: that BKM was still handed over at a counter. `getSettlementForPrint` is a lean sibling of `getSettlementForApproval`, not a reuse — the approval query's checklist block previews what `approveSettlement` would refuse and a receipt renders none of it. See `docs/ARCHITECTURE-NOTES.md`.
- Putting a bottom-anchored control on ANY backoffice route? `QuickActionFAB` is `fixed bottom-6 right-6 z-50`, `h-14 w-14`, rendered unconditionally and permission-free by `BackofficeShell` — so it owns a 24-80px box bottom-right plus ~12px of shadow, and a `fixed inset-x-0 bottom-0` bar collides with it below `lg` (`sm:justify-end` makes it worse, not better). The settlement approval bar clears it with `pr-28`; it is the first such bar in `app/backoffice` and will not be the last. See `docs/FOLLOWUPS.md`.

**Data ownership + auth**

- Writing `Item` or `StockAdjustment` from apps/api? Both are dual-owner — go through the `@elorae/db` writer helpers, never a direct Prisma write. See also `docs/BOUNDARY.md §3`.
- Adding a relation under `relationMode = "prisma"`? Do NOT conclude from the mode that there is no database FK. The mode suppresses the FKs Prisma GENERATES; it does not stop this repo hand-authoring `ALTER TABLE … ADD CONSTRAINT` in a migration, which it does routinely. Only grepping the migrations for that specific table settles it, and skipping that grep produced two separate wrong statements about one table in a single day. `Item` alone is the child end of SIX live hand-authored FKs carrying THREE different delete behaviours, so an item delete is refused outright by one table, SILENTLY CASCADE-DELETES rows for two, and erases the link on three — enumerated, together with which of them `deleteItem` counts and which it does not, in `docs/FOLLOWUPS.md`. Whatever the grep says: if the Prisma relation is REQUIRED, verify the id exists inside the writer's transaction — a dangling id throws `Inconsistent query result` forever with no UI repair path — and make every `delete<Parent>` count the new child, because that count is what turns the failure into an operator-readable refusal instead of a raw FK error, a silent cascade or a dangling row.
- Adding a permission and assuming ADMIN is gated by it? The admin wildcard is granted in CODE (`isSystem` → `['*']`), not by a DB row — a seed does not unblock admin, it makes the permission grantable to NON-admin roles.

**Database, migrations, prod ops**

- Running a migration or any destructive query locally? It lands on the **3308 dev test bed**, not on the client's data — that is safe by default, and the danger is the inverse: an ambient `DATABASE_URL` pointed at the 3307 prod tunnel makes the same command destructive with no other signal. Check what `DATABASE_URL` resolves to before any write. Either way it is `pnpm -F @elorae/db migrate:deploy` only — never `migrate dev`, which needs a CREATE DATABASE grant the shadow DB does not have and dies with P3014.
- Shipping a migration alongside app code? The deploy `migrate` job is gated on both image builds, and its `always()` is load-bearing — a legitimately SKIPPED build must not cascade-skip the migration.
- Assuming a green deploy workflow means your code is running? Check the `Deploy api`/`Deploy web` jobs specifically, and the container's image tag. Both misbehaved on 2026-09-02 — one SKIPPED with every condition satisfied and no error, one failed on an SSH dial timeout — and a skipped deploy leaves prod on the previous image while the overall run still reads success. See `docs/FOLLOWUPS.md` § Ops / infra.
- Expecting the deploy to seed RBAC rows? It migrates but NEVER seeds — permission rows are hand-run surgical SQL, post-merge.
- Running `mariadb` / `mariadb-dump` against prod? Needs SSL off — but the FLAG depends on which client is installed, and getting it wrong looks like a connection failure rather than a flag error: MariaDB's client takes `--skip-ssl`, while the MySQL 8 client (`mysql` on this machine, `mysql Ver 8.0.46`) rejects that outright and wants `--ssl-mode=DISABLED`. Check `mysql --version` before assuming. The failure is SILENT inside a `| gzip` pipe (a valid 123-byte empty archive) — verify size plus the `Dump completed on` trailer. Aggregates over `SalesOrder` need `SET SESSION max_statement_time`.

**Jubelio integration**

- Verifying a Jubelio webhook signature? HMAC-SHA256 in header `Sign` — their docs *text* is wrong, their code example is right.
- Reaching for any Jubelio endpoint? Grep `reference/jubelio-openAPI.yaml` FIRST, then confirm the shape LIVE — the spec both lags and misdescribes (the purpose-built order-by-no lookup returns 200-with-empty-body for settled orders).
- Adding an outbound push to Jubelio? It goes through the `JubelioOutbox` table, not a direct call — handler file + payload builder + spec + router case.
- Debugging a stuck inbound event? `JubelioWebhookEvent.status` is authoritative (`RECEIVED → PROCESSING → PROCESSED / SKIPPED / DEAD`); a sweeper rescues stuck rows every 10 min.
- Touching `outbox-poller.service.ts` or the processor's catch block? Two independent mechanisms kept a failed OUTBOUND row `PENDING` at `attempts: 1` forever instead of reaching `DEAD` — a retained BullMQ job holding the deterministic `jobId` (making `q.add` a silent no-op) and a failure that left the row `PROCESSING` (making every retry LOSE the status-guarded claim and take the guard's early-return arm, which completes the job successfully). Prod ran that way for months with zero DEAD rows and zero admin notifications. Reintroducing EITHER one restores the wedge; `lastEnqueuedAt` will keep advancing and hide it. The same `jobId` trap applies to the INBOUND webhook queue — both now go through `queue/finished-jobs.ts`'s `clearFinishedJob`, so a new queue that hand-rolls its own `add()` reintroduces it. See `docs/ARCHITECTURE-NOTES.md`.
- Detecting an "already in that state" reply from Jubelio? It is an HTTP 500 whose real reason is free-text Indonesian at `err.cause.code`, never a machine-readable code and never `err.code` — the invented `"ALREADY_IN_STATE"` marker the handlers used to test for was never set by anything. Use the shared `outbox/handlers/already-in-state.ts`; add observed phrasings to its marker list rather than loosening the match. See `docs/ARCHITECTURE-NOTES.md`.
- Building a WMS pick push? `POST /wms/sales/picklists/` takes the create-and-autocomplete body (`picklist_id: 0`, `picklist_no: "[auto]"`, `picker_id`, per-line `salesorder_detail_id` + `item_id`) — a bare `{ids}` is rejected with a `picklist_no` validation error, which is how every pick push silently failed on prod. Its neighbour `POST /wms/sales/packlist/mark-as-complete/` genuinely does take `{ids}`; the two are not symmetric. See `docs/ARCHITECTURE-NOTES.md`.
- Adding a Jubelio call whose response carries contact data (addresses, phones, emails)? Shaping it out of your service's return value does NOT stop it being retained — `JubelioHttpService` logs the RAW body into `JubelioApiCall.responseBody` before any mapping runs, and nothing prunes that table. Pass `redactResponseBody: true` on the request init — and note the catch block has TWO sinks, the DB row AND a `logger.error` to stdout, so a fix that covers only one still leaks to the container logs. See `docs/ARCHITECTURE-NOTES.md`.
- Sending a `location_id` to any Jubelio WMS endpoint? It is **`-1`** — the literal id of the only location, "Warehouse Elorae", confirmed live via `GET /jubelio/locations` 2026-09-02. A real id, not a typo: pick and ship both shipped hardcoding `1`, which does not exist here — pick pushes first failed Joi on the payload shape, then, once that was fixed, died on `location_picklist_header` FK violations (`code: "23503"`). Pack sends no `location_id` at all. Re-check the endpoint before changing it; do not "correct" the negative number. See `docs/ARCHITECTURE-NOTES.md`.
- Extending `ALREADY_IN_STATE_MARKERS` because a skip did not fire? Jubelio's body `code` is NOT a stable type — the same call returned free-text Indonesian one day and the bare SQLSTATE `"23505"` the next. Adding SQLSTATEs to the marker list would swallow real defects; the condition to detect is a repeated identical DB-constraint error, not a reason string. See `docs/FOLLOWUPS.md`.
- Reading `SalesOrder.fulfillmentStatus`/`pickedAt`/`packedAt` as proof Jubelio agrees? It is not — the local stamp and the outbox row are written in one transaction, but a push that later skips or dies never rolls them back, and nothing reconciles the two. See `docs/ARCHITECTURE-NOTES.md`.

**Print documents**

- Injecting a `lib/print/*-html.ts` builder's output with `dangerouslySetInnerHTML`? Only TWO of them may be injected — `spg-sale-nota-html.ts` and `van-sale-nota-html.ts` return class-scoped `<div>` fragments; EVERY other builder returns a full `<!DOCTYPE html>` document, and its embedded `printCssBase` is unlayered, so fragment parsing drops the `<html>`/`<body>` wrapper, attaches the `<style>` anyway, and the whole app takes the print sheet's padding, white background, font size and `--border` for as long as the route stays mounted. Both families return a bare `string` and nothing distinguishes them at compile time — only the NAME does: a document is `build<Thing>Html(opts)` (fourteen, all taking one options object), a fragment is `<thing>NotaHtml(sale)` (`spgSaleNotaHtml`, `vanSaleNotaHtml`, both taking the domain entity). Full-document builders go in an iframe: a visible `<iframe srcDoc>` for a preview screen, `printHtmlInIframe` for print-only. Shipped as a live defect on the BKM view, caught in review. See `docs/ARCHITECTURE-NOTES.md`.
- Building a new printable document and reaching for `PrintLayout` + `print.css`? Wrong family — `app/print/**` + `components/print/PrintLayout.tsx` is the analytical REPORT pattern (balance sheet, cash flow, income statement, trial balance, WO reconciliation). A transaction document is a pure `lib/print/<doc>-html.ts` builder over `print-theme.ts` with a locale-agnostic `labels` object. The settlement BKM's own epic card asked for the wrong one — so the scope text you are handed is not authority here. See `docs/ARCHITECTURE-NOTES.md` and `docs/EPIC-STATUS.md`.
- Auto-sizing an iframe to its own content? Measure `contentDocument.body`, NEVER `documentElement` — the root element's box fills the initial containing block, so its `scrollHeight` is floored at the viewport height and the frame can only ever grow: a short document keeps its placeholder dead space forever and a rotation to a wider viewport can never shrink it back. A `ResizeObserver` on top of the wrong element fixes one direction only. Poll `readyState` rather than trusting a one-shot `srcDoc` `load`, and cap the poll. See `docs/ARCHITECTURE-NOTES.md`.
- "Harmonising" the BKM's money formatting onto the whole-rupiah `idr` its neighbours use? Don't — `settlement-bkm-html.ts` renders 2dp on purpose, matching the settlement screens it is the paper artifact of, because every figure behind it carries sen (`Decimal(15,2)` receivables, a documented sub-rupiah `PARTIAL` residue). Rounding makes the invoice column visibly not add up on a page the store signs, and prints a −0,40 variance as −Rp 0 on the copy the store keeps. Whole rupiah is the minority spelling anyway: three builders still hold their own `Math.round` formatter and every other one goes through `print-theme.ts`'s `money()`, already 2dp. Change all of a document's money or none. `field-sales-nota-tagihan-html.ts` plausibly has the same defect and is logged, not fixed. See `docs/FOLLOWUPS.md`.
- Adding a backoffice print trigger? Call `lib/print/print-html-in-iframe.ts`, do not hand-roll one. It was extracted from two copies that had ALREADY drifted apart silently — one removed the iframe on an unconditional 1s timeout with no error path, the other returned early with a toast — and further hand-rolled copies still sit across `app/backoffice`. See `docs/FOLLOWUPS.md`.

**PWA**

- Editing `apps/web/proxy.ts`? It IS the Next 16 middleware (renamed from `middleware.ts`), runs on every request, and gates `/pwa/*` — it is NOT dead code.

## What NOT to do

- Don't put EPIC-XX refs in commits, PRs, branch names, or shared specs.
- Don't bundle multiple sub-projects into one PR. Each sub-project is its own slice.
- Don't write to web-owned tables from apps/api (and vice versa) without going through a `@elorae/db` helper — see `docs/BOUNDARY.md §3`.
- Don't add Prisma model comments. Don't add `Co-Authored-By` trailers to commits.
- Don't run `prisma migrate dev` — not against the 3308 test bed, not against the VPS MariaDB. It creates throwaway migrations, resets state, and needs a CREATE DATABASE grant for its shadow database that neither host gives it (P3014). Hand-author the migration SQL and use `migrate:deploy` only.
- Don't deploy apps/api or apps/web to Vercel. Both need persistent processes; Vercel functions don't fit (node-cron, BullMQ workers). Production target is the Hostinger VPS.
- **Don't run the whole test suite** (no filter, or repo-wide). It's slow + wasteful. Scope to the specs you changed. **api (jest):** `pnpm -F @elorae/api test -- <pattern> [<pattern>...]` (jest treats each positional arg as a testPathPattern, OR-ed). **web (vitest):** `pnpm -F @elorae/web exec vitest run <pattern> [<pattern>...]` — positional args are file-path filters. **DO NOT use `pnpm -F @elorae/web test -- <pattern>`** — the `--` pattern is NOT forwarded to vitest, so it silently runs the FULL ~450-test suite against `:3308` (confirmed 2026-07-26; the jest-style `test --` form only works for api). Only widen if a change plausibly affects unrelated specs. **api jest is capped at `maxWorkers: "50%"` and transpiles without type-checking** (`isolatedModules` in `apps/api/tsconfig.json`) — before that it built one TypeScript language service per worker, and jest's default of `cores - 1` workers (15 on a 16-vCPU box) saturated a WSL box with 7.6GB into swap. Pass `--maxWorkers=4` on top if the machine is already loaded, and keep patterns narrow: three directory-shaped patterns matched 16 spec files where 7 were wanted.
- **`pnpm -F @elorae/api type-check` runs against `tsconfig.spec.json`, not the build tsconfig — do NOT "simplify" it back to `tsc --noEmit`.** The build config excludes `src/**/*.spec.ts` (so specs stay out of `dist`), which means bare `tsc --noEmit` never checked a single api spec file; ts-jest's per-file language service was the only thing doing it, and turning that off would have left api specs unchecked by anything. `tsconfig.spec.json` extends the build config and re-includes specs, so one tsc run now covers what 15 jest workers used to. It also widens `rootDir` to the repo root, which is load-bearing: six specs under `src/db-shared/` and `src/web-shared/` import across package boundaries by relative path (`packages/db/src/*`, `apps/web/lib/redis/*`) to test the SOURCE rather than the built `@elorae/db` barrel, and the inherited `rootDir: ./src` made every one a TS6059 "not under rootDir" error. Nothing is emitted, so `rootDir` is decorative there — do not "tidy" it back. Note `isolatedModules` sits in the BUILD tsconfig because that is the only file ts-jest reads (it resolves the literal name `tsconfig.json` upward from jest's rootDir), so it constrains `nest build` too — clean today (no enums, no `export =`, no re-exports anywhere in `apps/api/src`), but its TS1272 rule for types referenced in a decorated signature is dormant only because `module` is `commonjs`; flipping that to an ES target arms it across every Nest constructor.
- **Never write an id filter as identifier shorthand in a spec teardown.** `deleteMany({ where: { itemId } })` collapses to `deleteMany({})` — deleting the WHOLE TABLE on the shared `:3308` bed — whenever the fixture hook threw before assigning that id, because **Prisma drops an `undefined` filter term** (measured: `item.count({ where: { id: undefined } })` returns every row). Declare fixture ids `= ""`, reset them at the top of the hook, and pass every one through `seededId()` from `@elorae/db`'s `src/spec-teardown.ts` so the filter is explicit. Prefer `delete` over `deleteMany` for a single row where you can — `delete` REJECTS an undefined id instead of widening, which is fail-closed. Same rule for `in: [...]` lists (`?? []`). Never filter a teardown on a prefix, a category or a date range alone: those over-match real rows without any variable being undefined.
- **In a teardown, delete the child of a 1:1 relation BEFORE its parents — `KonsiTransfer` before `DeliveryShipment`, and a `Receivable`/`TaxInvoice` before the `KonsiSellThrough` or `FieldSalesDelivery` it hangs off.** Under `relationMode = "prisma"` Prisma emulates the optional 1:1's delete behaviour, and a parent `deleteMany` that matches several parents each holding a child dies with `Expected zero or one element, got 2` — the emulation expects at most one child across the whole batch. It passes with one parent, so it only surfaces once a spec builds a second shipment with a transfer, and the aborted teardown then leaks every later row (the next `beforeEach` collides on its own fixture's unique codes). The receivable/faktur pair joined this rule when both of their source relations became optional 1:1s; `lib/konsi-sell-through/test-fixtures.ts` deletes every report of its store in one `deleteMany`, so it has to delete their receivables and fakturs first the moment a spec on it creates one. For the receivable/faktur pair it does not even take a second parent: the emulated default for an optional relation is `SetNull`, so deleting a report or delivery that still has one tries to null the child's source column, and the one-source CHECK refuses it. No production path deletes shipments, deliveries or sell-through reports; this bites specs.
- **A test-bed spec that calls a DB-WIDE function must scope it to the spec's own seeded rows.** The tests share `:3308` with real dev data. A function that sweeps/batches over ALL matching rows (e.g. `postPendingSalesJournals`, any future reconcile/backfill sweep) will mutate REAL rows when a spec invokes it — e.g. the sales-journal sweep test journaled real orders to the test's chart accounts, then teardown FK-failed and leaked. Give such functions an optional scope param (`orderIds`/filter) and pass it from the spec; a single-seeded-row test masks the global reach in review. Learned 2026-07-26 (EPIC-13-03).
- **Don't type-check the whole repo** (turbo/all-package). Scope to the one package you changed: `pnpm -F @elorae/api type-check` only. (`@elorae/web` type-check stays the user's — it saturates disk; never run it.) tsc can't do single-file, so package-scope is the finest partial available.
